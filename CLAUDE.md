# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

`postit` is a marketing tool for non-technical users on a small budget, self-hosted by a team or run as one hosted deployment: a Rust (edition 2024) REST API + background worker with a React web client (`web/`) and a Flutter mobile client (`mobile/`, Android and iOS only). Users sign in through a generic OIDC provider (Zitadel in dev), connect their own accounts (email sending method, Telegram, Slack, Discord, Bluesky, Mastodon, TikTok, X, YouTube, LinkedIn, Facebook, Instagram, Threads), write or AI-draft posts, publish them now, scheduled, or recurring, send email campaigns to consented contacts, reply to comments, and see analytics, in English. Owners can delegate scoped access to other users. It is **not** a CLI. Product guidelines (real accounts only, official APIs only, AI drafts and people approve) are in plan 03.

The repository is a multi-crate Rust workspace under `backend/` (crates `config`, `core`, `i18n`, `http`, `data`, `jobs`, `mail`, `identity`, `oauth`, `agent-kit`, `agents/mock`, `agents/email`, `agents/telegram`, `media`, `contacts`, `notify`, `publishing`, `drafter`, `api`, `server`, plus `xtask`, and `vault`) implementing plan 02 phases through P10 (API and server, `backend/openapi.json` and `web/src/api/schema.d.ts` generated by `cargo xtask openapi`; the React web app in `web/`; the admin job console: `JobConsole` over the `jobs`/`job_attempts` ledger, the `/admin/jobs*` API, and the web Jobs screens; P9: production startup requirements in `postit-config`, the doctor/backup/restore commands (now `doctor`, `db backup`, `db restore`), the `web`, `contract` and `docker` CI jobs, `docs/deployment.md` and `docs/configuration.md`; P10 hardening: token `aud`/client checks, security headers and the web CSP sent by the server, refresh-token renewal with no iframes, a shared no-secret-leak test harness, a production dependency audit in CI, and the threat model in `docs/security.md`). P11 is built: `mobile/` is a Flutter app (Android verified, iOS scaffolded) with separate web, Android, and iOS OIDC clients, the emulator scripts `mobile/tool/android-dev.ps1`/`.sh`, and the `app` CI job. B3 is built: `postit-oauth` (platform catalog, credential store, `AccountService`) connects accounts from pasted credentials with a check-then-confirm step, lists, renames, checks, and disconnects them, and imports them from CSV, behind the `/api/v1/accounts*` routes; B4 is built: `postit-media` (content sniffing, generated storage keys, `FsMediaStore`, probing and thumbnails with `ffprobe` behind a feature, HMAC-signed URLs, `MediaService`, the `media_gc` job) behind the `/api/v1/media*` routes (single-request and resumable uploads, ranges, view URLs) and the signed `/public/media/*` routes, with a per-user quota reserved atomically; B5 is built: `postit-agent-kit` (shared agent plumbing, test kit, conformance suite) and `postit-agent-mock` (scripted broadcast and direct agents `mock`/`mock_direct`, credential-based; its `mock_oauth` variant is test-only). B6 is built: delegation. Owners grant another active user `view`/`edit`/`publish` access to all accounts or a limited set, optionally expiring, behind `/api/v1/delegations*`, `/me/workspaces` and `/users/lookup`; `Scope` resolves `X-Postit-Act-As` on every request (403 `delegation_invalid` when no live grant applies, 403 `owner_only` on self, admin and unauthenticated routes), the `delegation_expiry` job ends due grants. B7 is built: the OAuth connection engine in `postit-oauth` (start, a bearer-free callback that stores a pending result, an authenticated confirm, token refresh, revoke, and platform deauthorization events, behind `/api/v1/accounts/connect/*` and `/api/v1/platforms/{id}/oauth/callback`) is proven against the mock OAuth provider. D1 is built: `postit-publishing` runs the publishing jobs on the mock agents (`publishing` queue, leases fenced by `dispatch_gen`, pre-send checks, quotas, parking, backoff retries, processing polls, reconcile of unknown outcomes, the due sweep, account preflight, direct deliveries, cancellation at safe checkpoints, graceful shutdown) and offers the `PublishingService` the D3 routes will wrap; `postit-notify` records in-app notifications in the producer's transaction (deliveries, reconnects, delegation changes, pending users) and sends a coalesced critical email, a daily comment digest, and Web Push (VAPID, RFC 8291 in `notify/src/ece.rs`) behind `/api/v1/notifications*`, `/api/v1/push/vapid-public-key`, `/api/v1/me/push-endpoints*`, and the widened `/me/preferences`; the web profile page has the push and notification settings (service worker `web/public/sw.js`); unknown job types are re-queued for `jobs.unknown_type_max_age`. Open D1 items: `docs/plans/2026-10-29-d1-publishing-engine-notifications-verification.md` (human checks). C1 is built: `postit-contacts` (`ContactService`: consented contacts and lists under the per-owner `contacts_cap`, suppressions with precedence `manual` < `bounced` < `unsubscribed` = `complained`, a streamed CSV import staged in `contact_import_rows` and applied by the `contact_import` job on the `contacts` queue, a streamed CSV export, and the `email_event_apply` job) behind `/api/v1/contacts*`, `/api/v1/contact-lists*`, and `/api/v1/suppressions*`. C2 is built: `postit-agent-email` (platform `email`, a direct agent: SMTP through `lettre` over the address policy, `mrml` rendering with merge tags and an English footer, stage-aware bounce classification, the sender-level pause, DNS checks through `hickory-resolver`); `postit-api` has the signed public unsubscribe, click, and open routes (`/public/u/*`, `/public/t/*`; a `GET` never unsubscribes), the real `LinkSigner`, `POST /api/v1/accounts/{id}/test-email`, and `GET /api/v1/accounts/{id}/dns-check`. No screens yet (D4, D6); campaigns are proven through `PublishingService` and, since D3, `POST /api/v1/posts/{id}/publish`, against an in-process SMTP sink (`postit-agent-email`'s `testkit` feature). Open C1/C2 items: `docs/plans/2026-10-30-c1-c2-contacts-email-agent-deferred.md` (agent work) and `-verification.md` (human checks). C3 is built: `postit-agent-telegram` (platform `telegram`, a broadcast credentials agent over the Bot API: text, photo, GIF, video, document, and albums streamed from the media store, discovery by a read-only peek at `my_chat_member` updates plus chats named by hand, `reconcile` `Unsupported`, every call `Sensitivity::Opaque` because the bot token sits in the URL path). ## Layout

`backend/` is the Rust workspace (API, worker, internal mail listener, `xtask`), `web/` the React client, `mobile/` the Flutter client, `docker/` the stack, and `backend/openapi.json` the generated API contract.

## Commands

Quality gates required by every phase (plan 02 P1 exit criteria) — keep them passing:

```sh
cargo fmt --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo check --workspace --all-targets
cargo test --workspace
```

```sh
cargo xtask openapi             # regenerate backend/openapi.json and web/src/api/schema.d.ts (--check to verify; needs Node and `pnpm install` in web/)
```

Web client commands live in `web/CLAUDE.md`.

App commands, from `mobile/` (Flutter 3.47.6; Windows: run through PowerShell):

```sh
flutter pub get
dart format --output=none --set-exit-if-changed lib/main.dart lib/data lib/state lib/ui test integration_test
flutter analyze && flutter test
flutter run --flavor development --dart-define-from-file=config/development.json
./tool/android-dev.ps1 help     # emulator setup (Google APIs image)
```

`cargo xtask openapi` also regenerates `mobile/lib/api/` (needs Flutter and `flutter pub get` in `mobile/`); `--skip-dart` skips that on a machine without Flutter, but `--check` and CI never skip it. Dart's `HttpClient` ignores Android's `network_security_config`, so development builds trust the dev CA through the `assets/dev/` flavor asset and `devTrust`.

Docker lives under `docker/`. Never type the compose `-f` chain by hand. The operator scripts
at the repo root, each a `.sh`/`.ps1` twin with one job (the VigilixMambo convention), are
`compose` (the stack), `db` (`psql`, `backup`, `restore`, `drop`, and `prepare`, which refreshes
the sqlx offline caches on a scratch database), `vault` (`unpack`, `pack`, `check`), `doctor`
(machine and vault checks, read-only), `cert`, and `js` (the web client's pnpm packages and gate); `docs/scripts.md` indexes them and the
`scripts` skill has the commands, naming, and hostnames. Their shared code is
`scripts/lib/common.{sh,ps1}`; `bash tests/scripts/run.sh` tests both halves of every script.

**Vault.** Per-environment secrets are packed into committed `!ref/vault.7z`; extract with
`./vault.sh unpack` (password out of band) to get `!ref/vault/<environment>/`.
`!ref/vault/` itself is git-ignored except for `.gitkeep` — never commit the extracted
files in the clear. Layout: one folder per environment, **one `KEY=value` file per project**
(`postgres.env`, `postit.env`, and `zitadel.env` in development only), holding **secrets
only** — usernames, passwords, keys, client secrets. URLs and all other settings are config
and stay with the project (`backend/config/<environment>.toml`, the compose files);
`database.url` must not carry credentials. The one exception is `DATABASE_URL` in each `postgres.env`, which
sqlx tooling and the DB-backed tests read (qa and production hold a host placeholder until the
host exists). Every environment, development included, uses the
default `postgres` superuser with a random password from the vault. Containers read the files
with `env_file:`; a native `cargo run` reads `postit.env` through `POSTIT_SECRETS_FILE`
(default set in `backend/.cargo/config.toml`). The maintainer re-packs `vault.7z` after a
vault change (`./vault.sh pack`); Claude edits the extracted files only and never re-packs the
archive, and never runs `vault pack` against the real vault.

## Target architecture (plan 01)

Multi-crate workspace under `backend/crates/`, on Rust stable with a `rust-version = "1.98"` floor, package names prefixed `postit-`. Plan 02 crates: `config`, `http`, `data`, `jobs` (only crate depending on apalis), `mail`, `identity` (OIDC verification, claims transformation, users, delegation resolution), `api` (axum + utoipa), `server` (bin `postit`, composition root, builds the `AgentRegistry` with each platform agent behind a Cargo feature), plus a `core` skeleton (ID newtypes, `Clock`, `IdGenerator`) created in P1. Plan 03's crate map (`vault`, `oauth`, `media`, `agent-kit`, `agents/*`, `contacts`, `drafter`, `publishing`, `inbox`, `analytics`, `notify`) is in plan 01's repository layout.

Cross-cutting rules:

- `http` (plan 02, extended in B1) is the only place that builds `reqwest` clients: retry classification, backoff+jitter, governor rate limiting, redaction, streaming bodies.
- **Auth is OIDC only.** No passwords or postit-issued tokens. API verifies bearer JWTs (iss, aud, exp, signature via cached JWKS); users keyed on `(issuer, sub)`, never email. Role (`admin`/`member`) and status (`pending`/`active`/`disabled`) live in Postgres; IdP role claims are ignored. First sign-in is `pending` until an admin approves; first admin comes from `auth.bootstrap`.
- **Private per user, with delegation.** Every owned table has `owner_id` plus `created_by`/`updated_by` (the actor). `OwnerScope { actor, owner, access }` is the only access check: repositories in `postit-data` filter by owner and delegation account limit; services call `scope.require(capability)`. Delegates act via `X-Postit-Act-As` at levels `view`/`edit`/`publish`; no re-delegation. Admins manage users and deployment settings, never user content or secrets.
- Platform developer apps are deployment-level config (`[platforms.<id>]`); `platforms` table uses the agent's platform ID as a text primary key, upserted at startup. Credential platforms (Telegram, Slack, Discord, Bluesky, Mastodon, email) need no deployment config.
- Each platform is an **agent** (never "plugin"); AI drafting is the **drafter**. Shared code consumes the agent contract and core models only; platform API types never leak out of agent crates. Adding a platform = new crate + feature + one registration line.
- DRY: one owner per concern (plan 01 "Engineering standards"); workspace-level dependencies and `[workspace.lints]`.
- Secrets use `secrecy` types and are stored only vault-sealed; never log tokens, auth codes, API keys, or signed URLs; redaction is tested.
- Live publishing is on in every environment but every live publish is explicitly confirmed; a runtime kill switch and per-platform `enabled` flags stop it; dry-run works everywhere. CI never publishes live.
- Platform tests use wiremock plus the conformance suite; live smoke tests are opt-in (`POSTIT_LIVE_TESTS=1`).
- Large media is streamed/chunked, never fully buffered.
- Partial success is preserved per delivery; non-idempotent failures become `OutcomeUnknown` and are reconciled, never blindly retried.
- essentialMix-rs crates from crates.io with `"0"` specs: `emixdb` (pagination), `emixcrypto` (SHA-256, `default-features = false`). Not `emixai`/`emixnet`/`emixlog` — reasons in plan 01.
