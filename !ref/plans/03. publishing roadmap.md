# Publishing Roadmap

> Plan 03 (2026-09-25). Phases A1–G3. Read [01. Vision and architecture](01.%20vision%20and%20architecture.md) first: the decisions, engineering standards, crate map, identity and delegation model, and data model live there and are not repeated here. Every phase builds on [02. Foundation](02.%20foundation.md) (P1–P10).

## Objective

Turn the foundation into the publishing product: the platform plugin contract, stored-secret encryption, social OAuth, media, delegation, five platform plugins, the publishing engine, LLM drafting, notifications, and the Flutter publishing UI.

## Delivery model

- **Foundation first.** Group A starts as soon as its plan 02 prerequisites land.
- **Parallel tracks.** Group B infrastructure runs in parallel after Group A. Platform tracks (C, E, F) run in parallel once the platform kit (B5) exists.
- **Mock-first.** The `mock` plugin (B5) lets the publishing engine, the REST surface, the Flutter UI, and orchestration be built and tested before any real platform is complete.
- **Release safety.** Every live publish is explicitly confirmed by the acting user. Dry-run works everywhere. The kill switch and per-platform `enabled` flags stop live publishing without a redeploy, except native-scheduled uploads already on the platform, which the switch dialog and doctor report for individual cancellation (plan 01, "Kill switch limit"). CI never publishes live.
- **Access in every test.** Every phase that adds owned data or endpoints adds isolation tests for four callers: the owner, a delegate at each level, a delegate limited to other accounts, and an unrelated user.

## REST surface

All routes are under `/api/v1`, return problem+json errors, and paginate with the `emixdb::ResultSet` shape. `utoipa` generates the contract and the Dart client is regenerated from it.

Unless marked otherwise, a route acts in the caller's own workspace, or in the owner's workspace when `X-Postly-Act-As` names a valid delegation. The **Access** column gives the minimum delegation level; `owner` means the route rejects act-as with 403 `owner_only`. "Whole post in limit" and "whole job in limit" apply the plan 01 [whole-object rule](01.%20vision%20and%20architecture.md#delegation) for limited delegates.

## Key flows

### Connecting a social account

1. Flutter calls `POST /social-accounts/connect/{platform}` with `return_to`: the web app origin, or the native scheme for the flavor (`postly-dev://oauth-done`, `postly-qa://oauth-done`, `postly://oauth-done`). `return_to` is checked against an allowlist from config.
2. The API creates an `oauth_states` row: a random 32-byte state stored as a hash, the PKCE verifier sealed, a 10-minute expiry. It returns the provider's `authorize_url`.
3. Flutter opens it: a new tab or popup on web, the system browser on native (`flutter_web_auth_2` or `url_launcher`).
4. The provider redirects to `/api/v1/platforms/{id}/oauth/callback?code&state`.
5. The server consumes the state row (single use, deleted in the same transaction), exchanges the code, runs the plugin's post-exchange hook (for example, Meta's long-lived token exchange and Page token derivation), discovers the accounts (YouTube channels, Facebook Pages, Instagram professional accounts), upserts `social_accounts`, seals the tokens, and redirects to `return_to?result=ok`. Accounts already connected by another owner are skipped (plan 01, `social_accounts`), and the redirect adds `code=account_connected_elsewhere` with the number skipped.
6. Flutter refreshes the account list.

Expired or reused state, provider denial, and missing scopes redirect with `result=error&code=…` and create no rows.

### Token refresh

- A `refresh_social_token` cron job runs every 5 minutes and refreshes tokens that expire within 15 minutes. Plugins also refresh on demand after a 401.
- Both paths take `pg_advisory_xact_lock` keyed on the account ID, re-read the token, and skip the refresh if another process already did it. The rotated token is written in the same transaction. This makes X's refresh-token rotation safe across the API and worker processes.
- `invalid_grant` or a revoked token sets the account to `needs_reconnect`, sends a critical notification to the owner, and parks pending deliveries for that account with the reason `account_needs_reconnect`. Reconnecting resumes them.

### Publishing

1. `POST /posts/{id}/publish` checks access (level and account limit), then runs full validation: common rules, then capability rules through the plugin's `TextMeasure` and limits, then the plugin's `validate`. Any violation returns 422 with every violation. A live publish without `confirm: true` returns 400 `confirmation_required`.
2. In one transaction, the API creates the job and one delivery per target account, recording the actor in `created_by`, then enqueues `publish_delivery` for each with `run_at` set to the schedule time or now.
3. The worker claims the delivery with `UPDATE deliveries SET state = 'claimed' … WHERE id = $1 AND state = 'pending' AND job not cancelled AND scheduled_at matches RETURNING …`. That row update is the lock; a duplicate or stale apalis job finds nothing to claim and exits.
4. The worker checks that the owner is `active`, then `app_settings.publishing.live` and `platforms.enabled`. A disabled owner parks the delivery with `owner_disabled` (plan 01, [Roles and statuses](01.%20vision%20and%20architecture.md#roles-and-statuses)). If the kill switch or the platform flag blocks a live delivery, the delivery is parked with `live_publish_disabled` or `platform_disabled` and a notification is sent. It never silently degrades to a dry-run.
5. The worker calls `plugin.publish(resolved_post, mode)`:
   - Success: `Published`, or `Processing` followed by `poll_delivery_status` jobs.
   - Retryable failure: backoff with full jitter from `postly-http`, a new `run_at`, and a retry budget (5 attempts by default), ending in `DeadLetter`.
   - Ambiguous failure of a non-idempotent call: `OutcomeUnknown`, then `reconcile_delivery`. If the plugin returns `Unsupported`, the delivery is parked for the user to retry or resolve. It is never blindly retried.
6. Multi-step plugins (Instagram containers, TikTok `publish_id`, YouTube resumable sessions) persist `container_ref` before each next step, so a retry resumes rather than duplicating.
7. The job status is derived from its deliveries (`published`, `partial`, or `failed`). The post status mirrors the job while the job's `post_version` is the post's current version, and becomes `draft` once the post is edited (plan 01, `posts`). Notifications go out on `DeadLetter`, `OutcomeUnknown`, `needs_reconnect`, and a `partial` job, to the owner and to the delegate who created the job while their grant is active.

**Native scheduling.** When the plugin declares `supports_native_schedule` (YouTube `publishAt`, Facebook scheduled posts) and the user chooses it, the worker uploads immediately with the remote publish time and the delivery moves to `Processing` until the platform confirms.

**Due sweep.** The deliveries table is the source of truth, not the apalis queue. A cron job every minute re-enqueues any due `pending` delivery with no live job, so a lost queue entry delays a post by at most a minute.

**Dry-run.** A dry-run job validates, resolves overrides, and records the planned remote actions in `delivery_attempts` without calling any mutating endpoint.

### Rescheduling and cancelling

- `PATCH /publish-jobs/{id}` with a new time is allowed only while every delivery is `pending`. It updates `scheduled_at` and enqueues a new `publish_delivery`. The old apalis job wakes, sees that `scheduled_at` moved, and exits without claiming.
- A native-scheduled delivery that is already uploaded is rescheduled or deleted through the plugin where supported; otherwise the API returns 409 `not_reschedulable`.
- Cancelling sets pending deliveries to `Cancelled`. An in-flight delivery is cancelled at its next safe checkpoint.

### Media

- `POST /media` streams to `{storage_root}/{owner_id}/{yyyy}/{mm}/{uuid}`, computing SHA-256 while streaming. Size limits are enforced during the stream. The MIME type is sniffed from content, not trusted from the client.
- `MediaProbe` reads dimensions and duration without decoding (pure-Rust container parsing; an optional `ffprobe` implementation behind a feature).
- `MediaHost::public_url(asset, ttl)` signs `id|exp` with HMAC-SHA256 using `media.signing_key` (a `_FILE` secret). The default TTL is 1 hour. The public route verifies in constant time.
- The storage root is the only place media is read from. Paths are generated, never user-supplied, and are canonicalized and checked against the root.
- `media_gc` (daily cron) deletes assets that are unreferenced and older than 24 hours, and `failed` uploads.

### Acting through a delegation

1. The Flutter client reads `GET /me/workspaces` and lets the user switch workspace. The chosen owner ID goes into `X-Postly-Act-As` on every request.
2. The `Scope` extractor in `postly-api` asks `postly-identity` to resolve the header. A missing, revoked, or expired grant, or an inactive owner or delegate, returns 403 `delegation_invalid`.
3. Services call `scope.require(capability)`. Repositories filter by the owner and the account limit, so rows outside the limit behave as not found.
4. The client hides actions the level does not allow, but the server is the only enforcement.

## Group A — Domain foundation

### Phase A1 — Core domain models and the plugin contract

Needs P1. Extend the `postly-core` skeleton from P1 (ID newtypes, `Clock`, `IdGenerator`) with:

- **Open platform identity.**
  - `PlatformId` is a validated lowercase string newtype such as `"x"` or `"youtube"`. There is no closed enum.
  - `PlatformDescriptor` holds the ID, display name, `Capabilities`, an optional `OAuthProviderSpec`, the plugin config schema version, and `supports_native_schedule`.
- **Accounts.** `AccountRef { platform: PlatformId, account: SocialAccountId }`. Publish targets are `AccountRef`s, not platforms.
- **Post models.** `Post` (text, media, link, tags, `disclose_ai_generated`), `PostOverrides` (per-`AccountRef` patch), and `PostVersion`.
- **Media.**
  - `MediaAsset`: kind, MIME type, byte size, optional duration and dimensions, content hash, and a `MediaSource`.
  - `MediaSource` is `Stored(MediaId)`, `PublicUrl(Url)`, or `RemoteRef`. There are no local paths.
  - Traits: `MediaStore` (open a stream by `MediaId`), `MediaProbe`, and `MediaHost` (public URL for a stored asset). Implementations live in `postly-media`.
- **Contracts.**
  - `PlatformPlugin`: `descriptor()`, `config_schema()`, `create_client(ctx) -> Box<dyn PlatformClient>`. The context carries the resolved plugin config, an HTTP handle, a token accessor, a media accessor, and the clock.
  - `PlatformClient`: `account_info` / health, `discover_accounts` (after OAuth), `validate`, `publish(resolved_post, mode)` with `DryRun` or `Live`, `status(receipt)`, `delete(receipt)`, `reschedule(receipt, at)` (optional), and `reconcile(delivery)` returning `Unsupported` where the platform cannot look posts up.
  - `PluginRegistry` maps `PlatformId` to `Arc<dyn PlatformPlugin>`, rejects duplicates, and is built explicitly by the composition root.
- **Receipts and statuses.** `PublishReceipt` (`Submitted`, `Processing`, `Published`, remote ID and URL), `AccountStatus`, and `DeliveryState`: `Pending → Claimed → InFlight → {Processing → Published | Failed(retryable) | OutcomeUnknown | DeadLetter | Cancelled | Parked(reason)}`.
- **Validation engine.** Common rules, then capability rules, then platform `validate`. Returns all violations.
- **Structured errors.** `PlatformError` covers authentication, authorization/scope, validation, rate limit (with retry-after), quota, transport, unsupported capability, remote API error, and outcome unknown, each with a retry classification.
- **Test seams.** `Clock` and `IdGenerator` (from the P1 skeleton) are passed into the plugin context.

Tests: serialization round trips, validation matrices, override resolution, registry duplicate rejection, and the trait-object compile test.

**Exit criteria:** all shared types are documented and tested. Core has no platform-specific, HTTP, or database code.

### Phase A2 — Vault, platforms table, and platform configuration

Needs A1 and P4.

- **`postly-vault`:**
  - Envelope encryption with XChaCha20-Poly1305. Key-encryption keys come from `vault.keys` (a list of versioned keys, `_FILE` secrets, at least 32 bytes each); the newest version seals, every listed version opens.
  - A `Sealed<T>` type for columns, with the key version and nonce stored alongside the ciphertext and the row ID bound as associated data so ciphertext cannot be moved between rows.
  - Development and QA may use a generated dev key with a startup warning. Production refuses to start without one.
  - `POST /admin/vault/rotate` enqueues a job that re-seals every sealed column under the newest key.
- **`platforms` table** and the startup upsert from the registry.
- **`[platforms.<id>]` configuration.** Each table is opaque to core and deserialized by the owning plugin (client ID, client secret as a `_FILE` secret, API version, …). Unknown platform tables and tables for plugins not compiled in are reported at startup. The redirect URI is derived from `server.public_url` and shown to admins.
- **`[publishing]`**: `live` default (`true` in every environment), retry budget, and sweep interval. **`[media]`**: storage root, size limits per kind, signing key, public URL TTL.

**Exit criteria:** sealed values round trip, rotation re-seals every row, a row's ciphertext cannot be opened under another row's ID, secrets never appear in `Debug`, errors, or logs, and platform config validation reports actionable errors.

## Group B — Shared infrastructure

B1 and B2 run in parallel after Group A. B3, B4, and B6 follow; B5 needs B1 and B3.

### Phase B1 — HTTP resilience and observability

Needs A1 and P2. Extends the foundation `postly-http`:

- Retry classification: transient errors retry; rate-limited responses honor `Retry-After` and plugin-supplied reset headers; non-idempotent mutations are never retried once the body may have been received and surface as an outcome-unknown error.
- Exponential backoff with full jitter (seeded in tests) and a retry budget.
- `governor` rate limiters keyed by plugin-defined buckets (per app, per account, per endpoint). Limits are per process; plugins that need a cross-process limit (for example, a daily quota) use `platform_quota_usage` instead.
- Streaming request bodies from `MediaStore` streams.
- Redaction of configured sensitive URL patterns, including signed media URLs.
- Deterministic time and jitter in test helpers.

**Exit criteria:** retry, timeout, rate-limit, redaction, and error mapping are verified without real API calls. No crate other than `postly-http` constructs a `reqwest::Client`.

### Phase B2 — Domain schema and scoped repositories

Needs A1, A2, and P4.

- Migrations for every owned-content table in plan 01, [Owned content](01.%20vision%20and%20architecture.md#owned-content-plan-03), plus `platforms` and `app_settings`.
- `Access::Delegated { level, accounts }` added to `OwnerScope`, with the capability table from plan 01. Every owned-content repository filters by owner and, where rows are account-bound (social accounts, overrides, deliveries, quota usage), by the account limit.
- Admin repositories for users, platforms, and settings stay separate types and cannot read owned content.
- Atomic claim queries for deliveries, the due-sweep query, and `FOR UPDATE SKIP LOCKED` where batch processing needs it.
- The idempotency constraint on deliveries (`sha256(job_id, account_id)`), the partial unique index allowing one non-terminal publish job per post, and the deployment-wide unique key on (`platform_id`, `remote_account_id`).
- The `post_locked` check in the post and override repositories.
- The `delete_user` job extended to cancel jobs, delete native-scheduled remote posts where supported, revoke tokens, and delete owned content and stored media (plan 01, [User deletion](01.%20vision%20and%20architecture.md#user-deletion)).
- The `oauth_state_purge` cron job.
- List methods return `emixdb::ResultSet<T>` with `emixdb::Pagination`.

Tests: the four-caller isolation matrix for every repository (using constructed scopes; the delegations table arrives in B6), concurrent claim tests, the idempotency constraint, a second job republishing the same version, the one-live-job index, `post_locked`, the sealed-column plaintext check, and migrations from empty and from each prior version.

**Exit criteria:** repositories can create posts, enqueue jobs, claim due deliveries safely under concurrency, record attempts, and reconcile success, failure, and unknown outcomes, with isolation and account limits proven by tests.

### Phase B3 — Social OAuth and token storage

Needs A2, B1, B2, P4, and P5. Create `postly-oauth`:

- OAuth 2.0 authorization-code flow with PKCE, driven by the plugin-provided `OAuthProviderSpec`: endpoints, scopes, PKCE support, client-auth method, extra parameters, token-response quirks, and an optional post-exchange hook. **No provider-specific configuration lives in this crate.**
- The server-side callback flow from [Connecting a social account](#connecting-a-social-account), including `oauth_states` and the `return_to` allowlist.
- A `TokenStore` trait with `PgTokenStore` (vault-sealed `social_tokens`) and an in-memory store for tests.
- Cross-process serialized refresh with advisory locks, the `refresh_social_token` cron, and the `needs_reconnect` transition.
- Revocation where the provider supports it, otherwise local deletion.
- Clear errors for missing platform config, denied authorization, invalid or expired state, expired or revoked refresh tokens, and missing scopes.
- **Phase-start check:** confirm each provider's redirect URI rules for development. Google web clients require a public top-level domain, and Meta and TikTok may reject `postly.local`. The documented fallback is a dev tunnel hostname (cloudflared or ngrok) configured as `server.public_url` for OAuth callbacks.

Tests: PKCE and state validation, single-use state, the `return_to` allowlist, an account already connected by another owner being skipped without revealing the owner, refresh behavior, concurrent refresh across two pools, persistence round trips, redacted diagnostics, and mocked authorization endpoints.

**Exit criteria:** any plugin-provided spec can connect, refresh, retrieve, and revoke credentials through the server-side callback without depending on platform code or exposing secrets.

### Phase B4 — Media

Needs B2 and P4. Create `postly-media`:

- `FsMediaStore` over the configured storage root (a Docker volume in compose).
- Streamed intake with per-kind size limits, content sniffing, SHA-256 while streaming, and probing.
- `SignedUrlMediaHost` and the public route with range support.
- `media_gc` cron job.
- The media endpoints from [REST surface](#rest-surface).

Tests: streaming without full buffering (bounded memory test), limit enforcement mid-stream, MIME spoofing rejected, signature and expiry checks, range requests, GC behavior, and the isolation matrix.

**Exit criteria:** large uploads never buffer the whole file, signed URLs work for anonymous fetchers and fail closed, and no user-supplied path reaches the filesystem.

### Phase B5 — Platform kit and mock plugin

Needs B1 and B3. Create `postly-platform-kit`:

- `OAuthProviderSpec` builder and wiring into `postly-oauth`.
- A resumable/chunked upload driver: chunk size, resume-offset query, progress callback. Reused by YouTube, TikTok, X, and Meta.
- `poll_until` for remote processing status, with backoff and cancellation.
- Error-classification helpers from `HttpError`, HTTP status, and platform error codes to `PlatformError`.
- Capability-declaration helpers and common `TextMeasure` implementations (grapheme count, X-weighted count).
- `testkit` feature: `run_conformance::<P: PlatformPlugin>(fixture)` plus shared wiremock fixtures.

Create `postly-platform-mock`: fully featured, scriptable failures (including `OutcomeUnknown` and `needs_reconnect`), a mock OAuth provider served by the testkit, and documented as the template for new platforms.

**Exit criteria:** the mock plugin passes the conformance suite. A new plugin needs only its protocol code, its capability declaration, and one registration line in `postly-server`.

### Phase B6 — Delegation

Needs B2 and P6.

- Migrations for `delegations` and `delegation_accounts` (plan 01, [Identity](01.%20vision%20and%20architecture.md#identity-plan-02-except-delegations-in-plan-03)).
- `postly-identity`: the delegation service (grant, change level and account limit, revoke, leave, expiry) and act-as resolution. Owner and delegate must both be `active`. No re-delegation: a delegated scope can never reach the delegation service.
- `postly-api`: the `Scope` extractor reads `X-Postly-Act-As`; the workspace, delegation, and lookup endpoints from [REST surface](#rest-surface); `owner_only` enforcement on owner-only routes.
- Disabling or deleting either user makes their delegations inactive or removes them. Removing a social account removes it from every account limit. A limited grant left with no accounts stays valid (posts and media only) and both parties are notified (plan 01, "Empty account limit").
- Tests: composite `(owner_id, …)` FKs reject cross-owner `post_media`, overrides, deliveries, and `delegation_accounts`; concurrent owner and delegate edits produce 412 `version_conflict` for the loser.
- Audit events for every delegation change. In-app notifications to the other party are added in D1 once `postly-notify` exists.

Tests: act-as with valid, revoked, expired, and self grants; inactive owner or delegate; re-delegation attempts; level changes and revocation taking effect on the next request; the lookup endpoint's exact-match, duplicate-email, and rate-limit behavior; account-limit changes; the whole-object rule for limited delegates on post edits, cancel, and reschedule.

**Exit criteria:** a delegate can act in the owner's workspace with exactly the granted level and account limit, and nothing else, proven at the service and HTTP layers.

## Group C — Initial platform clients

C1 and C2 run in parallel after B5. All tests use mocks; CI never needs live credentials.

### Phase C1 — X plugin

- OAuth 2.0 PKCE with scopes `tweet.read`, `tweet.write`, `users.read`, `offline.access`, and `media.write`. Refresh-token rotation is handled by B3.
- X API v2 post creation and deletion.
- Media upload through the v2 chunked endpoints (INIT, APPEND, FINALIZE, STATUS) using the kit driver.
- Capabilities: X-weighted text length (URLs count as a fixed length), image, GIF, and video limits, media count.
- Mapping of X errors, rate-limit headers, and access-tier errors to clear `PlatformError`s.
- Dry-run executes everything except the final create and upload calls.
- `reconcile` looks up recent posts by the account to find one created by an unknown-outcome attempt.

**Exit criteria:** a connected X account can validate, publish, delete, and report health, all with deterministic mocked tests.

### Phase C2 — YouTube plugin

- Google OAuth spec: offline access with a consent prompt for a refresh token, and the `youtube.upload` and `youtube.readonly` scopes.
- Channel discovery; each channel is a social account.
- Resumable upload through the kit driver: streaming from `MediaStore`, chunk alignment, resume by querying the offset, progress. The upload session URL is persisted as `container_ref`.
- Title, description, tags, category, privacy, `publishAt` native scheduling (with `reschedule`), made-for-kids, and the altered or synthetic content disclosure.
- Optional thumbnail upload. Processing status is polled.
- **Quota awareness.** Per-call quota cost is declared and daily usage is tracked in `platform_quota_usage`. A publish is refused preflight with `quota_exceeded` if the remaining quota is insufficient.

**Exit criteria:** large uploads never buffer the whole file, interrupted uploads resume, and receipts distinguish upload completion from processing completion.

## Group D — Application

### Phase D1 — Publishing engine and notifications

Needs B2, B4, B5, B6, and P5. Create `postly-publishing` and `postly-notify`:

- Job and delivery creation, the state machine, and the job types `publish_delivery`, `poll_delivery_status`, and `reconcile_delivery`, registered through `postly-jobs` with ID-only `JobSummary`s so they appear in the admin Jobs console.
- The claim, kill-switch check, retry budget, dead-letter, reconcile, and parking behavior from [Publishing](#publishing).
- Native scheduling, rescheduling, and cancellation.
- The due-sweep cron.
- Dry-run recording.
- `postly-notify`: records notifications for the recipients defined in plan 01 (owner, plus the delegate actor while their grant is active), and sends critical kinds through `postly-mail` when the recipient's `email_notifications` is on. It registers a mail context loader for its kinds, so email jobs carry only notification IDs (plan 02, `postly-mail`). Adds delegation notifications from B6. Templates use `askama`.

Tests: due-delivery selection, concurrent workers, stale and duplicate apalis jobs, a console retry of every job type causing no duplicate post or email, retries, cancellation, rescheduling, partial multi-account success, restart recovery, kill switch, `needs_reconnect` parking and resumption, `owner_disabled` parking and resumption (with overdue deliveries staying parked), `delete_user` with pending, in-flight, and native-scheduled deliveries, unknown-outcome reconciliation, notification fan-out to owner and delegate, and jobs surviving delegation revocation.

**Exit criteria:** queued work is durable, safely claimed, observable, retryable, and idempotent, and a crash after a remote success cannot cause a duplicate post.

### Phase D2 — Content generation (LLM layer)

Needs B1 and B2. Create `postly-content` (behind the `ai` feature in `postly-server`, enabled by default):

- **Provider-neutral trait.** `LlmProvider` with `chat(request)` and optional `chat_stream`. Messages, system prompt, temperature, max tokens, JSON-schema structured output where supported, and token usage are modeled provider-neutrally. `ImageProvider` is a separate optional trait.
- **Two wire-protocol adapters** built on `postly-http`:
  - `openai-compatible`: Chat Completions with configurable base URL, headers, and query parameters. Serves OpenAI, Abacus AI RouteLLM (`https://routellm.abacus.ai/v1`), Gemini's OpenAI endpoint (`https://generativelanguage.googleapis.com/v1beta/openai/`), OpenRouter, Groq, DeepSeek, Mistral, xAI, Together, Ollama, LM Studio, vLLM, and other compatible servers. Tolerates provider extensions and missing `usage`.
  - `anthropic`: the native Messages API.
- **Per-user, opencode-shaped providers.** Each `ai_providers` row stores the same shape as an opencode `provider` entry, so users can paste an entry field for field. The API key is stored separately and sealed. `npm` values map to protocols (`@ai-sdk/openai-compatible` and `@ai-sdk/openai` to `openai-compatible`, `@ai-sdk/anthropic` to `anthropic`, `@ai-sdk/google` to `openai-compatible` with the Gemini base URL); an explicit `protocol` overrides. Presets for `openai`, `anthropic`, `gemini`, `abacus`, `openrouter`, and `ollama` need only a key; preset base URLs are verified at phase start. postly never reads opencode's files.
- **Delegates** with `edit` can generate with the owner's providers. They see provider names and models, never keys or config.
- **Outbound URL policy.** Custom base URLs are user-supplied, so requests to private and loopback address ranges are refused unless the admin enables `ai.allow_private_endpoints` (needed for a self-hosted Ollama).
- **Generation pipeline.** A prompt template plus platform capability data for each target (length, hashtag conventions, media constraints), structured output parsing, core validation, and one repair attempt. The result is a draft with `disclose_ai_generated = true` and an `ai_generations` record.
- No provider keys appear in logs, drafts, or generation records. Prompts are stored only when the owner enables `store_ai_prompts`.

Tests: wiremock contract tests for both protocols (including Gemini-style and Abacus-style responses), a mock provider, the URL policy, and deterministic validation and repair.

**Exit criteria:** the library produces a validated, disclosure-flagged draft for any configured provider without touching publishing credentials.

**Deferred:** video generation. `VideoProvider` is reserved but not implemented.

### Phase D3 — Publishing REST surface

Needs D1, D2, B3, B4, B6, and P6.

- Every endpoint in [REST surface](#rest-surface), with thin handlers over the service crates.
- Schedule input is RFC 3339 with an offset, or a local date-time plus an IANA zone (`chrono-tz`), defaulting to the acting user's `timezone` preference. Times are stored in UTC. Schedules that fall into a DST gap or overlap are rejected with a clear violation.
- ETags on job and calendar reads.
- Rate limits on connect, upload, generate, publish, and user lookup.
- `api/openapi.json` and the Dart client regenerated; the contract CI job stays green.

Tests: HTTP-level tests for every endpoint with the mock plugin, the four-caller isolation matrix at the HTTP layer (every route against the Access column), confirmation rules, error codes, and the OAuth callback redirects.

**Exit criteria:** with the mock plugin and wiremock, an HTTP client can connect an account, upload media, create or generate a post, validate it, dry-run it, schedule it, reschedule it, watch it publish, and see history and notifications, both as the owner and as a `publish` delegate.

### Phase D4 — Flutter publishing UI

Needs D3 and P7. Builds on the plan 02 shell (Riverpod, go_router, dio, `oidc`, generated client).

- **Workspace switcher:** own workspace and received delegations from `GET /me/workspaces`. The interceptor adds `X-Postly-Act-As`. Actions the level or account limit does not allow are hidden, and a banner shows whose workspace is active.
- **Delegations:** grant (lookup by exact email, level, all accounts or chosen accounts, optional expiry), edit, revoke; a received list with leave.
- **Accounts:** accounts grouped by platform with status chips (active, needs reconnect, revoked). Connect, reconnect, disconnect, and health check (owner only). Unavailable and disabled platforms are hidden.
- **Media library:** upload with progress (file picker on desktop and web, `image_picker` or `file_picker` on mobile), thumbnail grid with metadata, delete blocked while in use.
- **Composer:** text with live per-target counters (capability-driven, with server `validate` debounced for exact counts such as X-weighted length), media picker, target accounts, per-target override tabs, an AI panel (provider and model, topic, targets) that fills the draft, and validation grouped by target.
- **Publish dialog:** now or scheduled (date and time in the user's zone, native scheduling where supported), a dry-run toggle, and for live runs a per-target summary with explicit confirmation.
- **Queue and history:** paginated lists with per-target delivery rows (state, remote link, last error, created by) and retry or resolve on `DeadLetter` and `OutcomeUnknown`.
- **Notifications:** a bell with an unread badge (polled), a list that marks read and deep-links into jobs, accounts, and delegations, and the email toggle in profile.
- **AI providers:** add or edit from presets or custom, set the key, test, list models, choose a default.
- **Preferences:** time zone, email notifications, store AI prompts.
- **Admin:** platforms (configured, compiled in, enabled toggle, redirect URI to copy into each developer portal), the global live-publishing switch, and the doctor report (G2).
- **Native OAuth return:** a custom scheme per flavor (`postly-dev`, `postly-qa`, `postly`) for social account connection. Deep-link handling is limited to this callback and the sign-in callback; universal links remain a non-goal.

Tests: widget tests against a mocked client (including each delegation level), golden tests for the composer, and an integration test against the dev compose stack with the mock plugin: connect, compose, schedule, and see the post published; then `member@postly.local` does the same as a `publish` delegate.

**Exit criteria:** the full publishing flow works from the Flutter web, desktop, and mobile builds against the mock plugin, in the user's own workspace and through a delegation.

### Phase G3 — Security and reliability hardening

- Threat model of the web-facing surface:
  - OIDC: token validation, `kid` refetch limits, principal cache staleness, bootstrap.
  - Delegation: act-as resolution, level and account-limit enforcement, no re-delegation, lookup enumeration.
  - OAuth callback: state binding, single use, PKCE, and the `return_to` allowlist.
  - CORS and rate limits, re-verified with the new routes.
  - Signed media URLs: signature scope, expiry, no enumeration, range handling.
  - Uploads: limits, content sniffing, storage-root confinement.
  - Outbound requests: the LLM base URL policy and platform endpoints.
  - The vault key lifecycle, including loss of a key version.
- Access fuzzing across every endpoint with the four callers.
- Cancellation and restart tests during uploads, container workflows, and scheduled jobs.
- CI: `cargo deny`, fmt, clippy, tests, conformance suites, the SQLx offline cache check, and the contract drift check. CI never publishes live.

**Exit criteria:** reproducible builds, no secret leakage in any tested output, proven owner isolation and delegation limits, durable queue recovery, platform-isolated failures, and documented release checks.

## Platform constraints and risks

Verify each at the start of the relevant phase, since platform policies change:

- **X:** write access and cost depend on the API access tier. Refresh tokens rotate. Media upload endpoints have moved from v1.1 to v2.
- **YouTube:** uploads from an unverified API project are locked to private until the project passes an audit. The daily quota is small, and uploads are expensive against it.
- **TikTok:** unaudited apps can only post with private visibility. `PULL_FROM_URL` needs domain verification of the API host.
- **Meta:** App Review is required for publishing permissions beyond test users. Instagram requires a professional account linked to a Page and is rate-limited per 24 hours. Most media must be at a public URL.
- **Redirect URIs in development:** Google, Meta, and TikTok may reject `https://postly.local`. The dev tunnel fallback is verified in B3 and documented in G2.
- **Public media in development:** platforms cannot fetch from `postly.local`. Instagram and TikTok `PULL_FROM_URL` need the tunnel in development, or the mock plugin.
- **Live publishing is on in development by decision.** A development worker connected to a real account posts for real. Mitigations: per-publish confirmation, the kill switch, `platforms.enabled`, the dry-run toggle, and the `test_account` label shown in the publish dialog.
- **Delegated live publishing.** A `publish` delegate can post to the owner's real accounts. Mitigations: the same confirmation, account limits, `created_by` shown in history, and owner notifications.
- **Calendar package license:** checked in D5.
- **apalis 1.0 release status:** inherited from plan 02; re-checked at the start of D1.
- **Anthropic via its OpenAI-compatible endpoint** is feature-limited, which is why a native adapter exists.
