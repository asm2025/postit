# Publishing Roadmap

> Plan 03 (2026-09-25). Phases A1–G3. Read [01. Vision and architecture](01.%20vision%20and%20architecture.md) first: the decisions, engineering standards, crate map, identity and delegation model, and data model live there and are not repeated here. Every phase builds on [02. Foundation](02.%20foundation.md) (P1–P10).

## Objective

Turn the foundation into the publishing product: the platform plugin contract, stored-secret encryption, social OAuth, media, delegation, five platform plugins, the publishing engine, LLM drafting, notifications, and the Flutter publishing UI.

## Delivery model

- **Foundation first.** Group A starts as soon as its plan 02 prerequisites land.
- **Parallel tracks.** Group B infrastructure runs in parallel after Group A. Platform tracks (C, E, F) run in parallel once the platform kit (B5) exists.
- **Mock-first.** The `mock` plugin (B5) lets the publishing engine, the REST surface, the Flutter UI, and orchestration be built and tested before any real platform is complete.
- **Release safety.** Every live publish is explicitly confirmed by the acting user. Dry-run works everywhere. The kill switch and per-platform `enabled` flags stop live publishing without a redeploy, except native-scheduled uploads already on the platform, which the switch dialog and doctor report for individual cancellation (plan 01, "Kill switch limit"). CI never publishes live.
- **Access in every test.** Every phase that adds owned data or endpoints adds isolation tests for four callers: the owner, a delegate at each level, a delegate limited to other accounts, and an unrelated user.

## REST surface

All routes are under `/api/v1`, return problem+json errors, and paginate with the `emixdb::ResultSet` shape. `utoipa` generates the contract and the Dart client is regenerated from it.

Unless marked otherwise, a route acts in the caller's own workspace, or in the owner's workspace when `X-Postly-Act-As` names a valid delegation. The **Access** column gives the minimum delegation level; `owner` means the route rejects act-as with 403 `owner_only`, and `admin` routes reject act-as the same way. "Whole post in limit" and "whole job in limit" apply the plan 01 [whole-object rule](01.%20vision%20and%20architecture.md#delegation) for limited delegates.

Which phase builds a route: B4 the media routes, B6 the workspace, delegation, and lookup routes, D3 every other route except `GET /admin/doctor` (G2).

## Key flows

### Connecting a social account

1. Flutter calls `POST /social-accounts/connect/{platform}` with `return_to`: the web app origin (`/oauth-done`), the mobile scheme for the flavor (`postly-dev://oauth-done`, `postly-qa://oauth-done`, `postly://oauth-done`), or on desktop a loopback URL `http://127.0.0.1:{port}/oauth-done` served by the app for this one connection, as the sign-in does (no custom-scheme registration on Windows or Linux). `return_to` is checked against `oauth.return_to_allowlist`; loopback is allowed with any port.
2. The API creates an `oauth_states` row: a random 32-byte state stored as a hash, the PKCE verifier sealed, a 10-minute expiry. It returns the provider's `authorize_url`.
3. Flutter opens it: a new tab or popup on web, the system browser on native (`flutter_web_auth_2` or `url_launcher`).
4. The provider redirects to `/api/v1/platforms/{id}/oauth/callback?code&state`.
5. The server consumes the state (single use), exchanges the code, runs the plugin's post-exchange hook (for example, Meta's long-lived token exchange and Page token derivation), and discovers the accounts (YouTube channels, Facebook Pages, Instagram professional accounts). It stores the sealed tokens and the discovered accounts on the state row as a **pending result** with a new random `connect_id` (stored as a hash, same 10-minute expiry), creates no grant or account yet, and redirects to `return_to?result=ok&connect_id=…`.
6. Flutter calls `POST /social-accounts/connect/{connect_id}/confirm` with its bearer token. The server accepts it only when the caller is the user who started the connection, and then, in one transaction: deletes the state row, creates the `social_grants` row, upserts `social_accounts` (reconnecting an existing account moves it to the new grant), and deletes any previous grant left with no accounts. Accounts already connected by another owner are skipped (plan 01, `social_accounts`); the response lists them as `account_connected_elsewhere` with the number skipped. A confirm by any other user returns 404 and deletes the pending result.
7. Flutter refreshes the account list.

**Why the confirm step.** The callback has no bearer token and postly sets no cookies, so without it an attacker could start a connection, send the `authorize_url` to a victim, and have the victim's social account attached to the attacker's postly user. The `connect_id` reaches only the browser that completed the authorization, and only its signed-in user can confirm it.

Expired or reused state, provider denial, and missing scopes redirect with `result=error&code=…` and create no rows. An unconfirmed result expires with its state row.

### Token refresh

- A `refresh_social_token` cron job runs every 5 minutes and refreshes tokens that expire within 15 minutes. Plugins also refresh on demand after a 401.
- Both paths take `pg_advisory_xact_lock` keyed on the **grant** ID (accounts that share a grant share its tokens), re-read the token, and skip the refresh if another process already did it. The rotated token is written in the same transaction. This makes X's refresh-token rotation safe across the API and worker processes.
- `invalid_grant` or a revoked token sets the grant and its accounts to `needs_reconnect` and sends a critical notification to the owner. Deliveries for those accounts are not touched here: the worker parks them with `account_needs_reconnect` when they come due (step 4 of [Publishing](#publishing)), and the due sweep resumes them after a reconnect under the [parking rule](#delivery-states). The delivery state machine stays in `postly-publishing`.
- **Credentials that cannot be refreshed.** Some grants end on a fixed date whatever postly does: Meta long-lived user tokens and data-access expiry, and refresh tokens of Google projects in "testing" publishing status (7 days). The plugin reports a `reconnect_by` time from the token response or its metadata, stored on the grant. The `refresh_social_token` cron sends the owner a notification 7 days and 1 day before it, and a critical one once it has passed; `social_grants.reconnect_warned` makes each reminder go out once.
- **Platform-initiated deauthorization.** When a platform calls `POST /platforms/{id}/events/deauthorize` or `data_deletion` (Meta requires both for App Review), the plugin verifies the request and names the remote user. postly sets the matching grants and accounts to `revoked`, deletes their tokens, notifies the owners, and records `social_account_revoked_by_platform`. A data-deletion request answers in the format the platform expects, with a confirmation code and a status URL.
- **Account preflight.** An `account_preflight` cron job (every 10 minutes) calls `account_info` for each account that has a delivery due within the next hour and was not checked in the last hour. An authentication failure takes the `needs_reconnect` path above, so the owner hears about a platform-side revocation before the post is due, not after it fails.

### Publishing

1. `POST /posts/{id}/publish` checks access (level and account limit), takes `SELECT … FOR UPDATE` on the post, and checks `If-Match` against `posts.version` (412 `version_conflict` if someone edited the post after the user reviewed it). It then runs full validation: common rules, then capability rules through the plugin's `TextMeasure` and limits, then the options schema, then the plugin's `validate`. Any violation returns 422 with every violation. A live publish without `confirm: true` returns 400 `confirmation_required`.

   A schedule time up to 1 minute in the past is treated as "now"; an earlier time is a violation. `native_schedule` applies to the targets whose plugin declares `supports_native_schedule`; the other targets use postly scheduling, and the publish dialog shows which is which. For native targets, the time must also fall inside the plugin's declared `native_schedule_window` (for example, Facebook's minimum lead and maximum horizon). Quota and daily-limit checks here are advisory; the worker enforces them.
2. In the same transaction, the API resolves the per-target content into the job's `content_snapshot`, creates the job and one delivery per target account (`next_attempt_at` = the schedule time or now, `dispatch_gen` = 0), recording the actor in `created_by`, and enqueues `publish_delivery { delivery_id, dispatch_gen }` for each with `enqueue_in` and `run_at` = `next_attempt_at`. A live publish records a `publish_confirmed` audit event with the actor and target account IDs.
3. The worker claims the delivery with `UPDATE deliveries SET state = 'claimed', lease_expires_at = now() + lease … WHERE id = $1 AND dispatch_gen = $2 AND state = 'pending' AND next_attempt_at <= now() AND job not cancelled RETURNING …`. That row update is the lock. Every change that re-enqueues a delivery (retry backoff, reschedule, unpark, user retry, sweep) increments `dispatch_gen` in the same statement, so a duplicate or stale apalis job finds nothing to claim and exits. The worker renews the lease (`publishing.lease`, default 5 minutes) every third of its length while it works.

   **Fenced writes.** Every worker write after the claim is conditioned on the `dispatch_gen` it claimed and the state it expects (`… WHERE id = $1 AND dispatch_gen = $2 AND state = 'in_flight'`), and also bumps `publish_jobs.version`. A worker that stalled past its lease finds its write rejected. If it holds a success receipt, it records it through the reconcile path instead: an `OutcomeUnknown` delivery with a matching receipt becomes `Published`, so a late success is never lost and never duplicated.
4. Before any remote call, the worker checks, in order, and parks the delivery with the matching reason if one fails: the owner is `active` (`owner_disabled`, plan 01, [Roles and statuses](01.%20vision%20and%20architecture.md#roles-and-statuses)); the account is `active` (`account_needs_reconnect`); the plugin is compiled in (`platform_unavailable`) and enabled (`platform_disabled`); for live deliveries, `app_settings.publishing.live` (`live_publish_disabled`); and the quota reservation described in [Quotas](#quotas) (`quota_exceeded`). A parked live delivery sends a notification and never silently degrades to a dry-run. The worker then re-runs validation against the current capabilities and options schema, because they may have changed since scheduling; violations end the delivery in `Failed` with `validation_failed`.
5. The worker moves the delivery to `InFlight` and calls `plugin.publish(resolved_post, mode)`, where `resolved_post` comes from the job's `content_snapshot`, never from the current post:
   - Success: `Published`, or `Processing` followed by `poll_delivery_status` jobs.
   - Retryable failure: back to `Pending` with `next_attempt_at` from backoff with full jitter (`postly-http`), `dispatch_gen` incremented, and `enqueue_at` for the new time. The retry budget (5 attempts by default) ends in `DeadLetter`.
   - Permanent failure (validation rejected by the platform, missing permission, content refused): `Failed` with the classified error.
   - Ambiguous failure of a non-idempotent call: `OutcomeUnknown`, then `reconcile_delivery`. If the plugin returns `Unsupported`, the delivery is parked with `outcome_unresolvable` for the user to retry or resolve. It is never blindly retried.
6. Multi-step plugins (Instagram containers, TikTok `publish_id`, YouTube resumable sessions) persist `container_ref` before each next step, so a retry resumes rather than duplicating.
7. The job status is derived from its deliveries (see [Delivery states](#delivery-states)). The post status mirrors the latest **live** job while that job's `post_version` is the post's current version, and becomes `draft` once the post is edited (plan 01, `posts`). Notifications go out on `DeadLetter`, `Failed`, `OutcomeUnknown`, a parked delivery, `needs_reconnect`, and a `partial` job, to the owner and to the delegate who created the job while their grant is active.

**Processing.** `poll_delivery_status` polls with backoff from 15 seconds up to 15 minutes between polls. A delivery still `Processing` after `publishing.processing_timeout` (default 24 hours) moves to `OutcomeUnknown` and is reconciled. For a native-scheduled upload, the timeout counts from its `remote_publish_at`, not from the upload.

**Native scheduling.** When the plugin declares `supports_native_schedule` (YouTube `publishAt`, Facebook scheduled posts) and the user chooses it, the worker uploads immediately with the remote publish time, stored in `remote_publish_at`. The delivery stays `Processing`: it is polled until the platform accepts the upload, then not again until the remote publish time, and then as above until the platform reports it live.

**Graceful shutdown.** On shutdown, an `InFlight` delivery stops at its next safe checkpoint and returns to `Pending` with an incremented `dispatch_gen`, instead of waiting for its lease to expire and being treated as an unknown outcome. A delivery past its final create or publish call finishes first, within `server.shutdown_timeout`.

**Due sweep.** The deliveries table is the source of truth, not the apalis queue. The `delivery_due_sweep` cron job (every minute) needs nothing from apalis:
- A `pending` delivery whose `next_attempt_at` is more than `publishing.sweep_grace` (default 2 minutes) past gets its `dispatch_gen` incremented and a new `publish_delivery`. The old queue entry, if any, is now stale and exits.
- A `claimed` delivery with an expired lease made no remote call yet, so it returns to `pending` and is re-enqueued the same way.
- An `in_flight` delivery with an expired lease (the worker crashed mid-call) moves to `OutcomeUnknown` and is reconciled. Multi-step plugins resume from `container_ref`.
- A `parked` delivery whose cause has cleared is unparked under the [parking rule](#delivery-states). The sweep checks each reason against current state: the owner is `active`, the account is `active`, the plugin is compiled in and enabled, `publishing.live` is on, and the quota period has rolled over. The sweep is the only place that unparks, so re-enabling a user, reconnecting an account, or flipping a switch needs no call into `postly-publishing` and takes effect within a minute.

So a lost queue entry or a crashed worker delays a post by at most a few minutes and never duplicates it.

**Dry-run.** A dry-run job runs immediately (no `at`, no native scheduling). It validates, resolves overrides, and records the planned remote actions in `delivery_attempts` without calling any mutating endpoint. Its deliveries end in `Simulated` or `Failed`. Dry-run jobs are not covered by the one-non-terminal-job index and never change `posts.status`, so a dry-run neither blocks nor fakes a real publish.

### Delivery states

| State | Meaning | Terminal |
|---|---|---|
| `Pending` | Waiting for `next_attempt_at`. | no |
| `Claimed` | A worker holds the lease; no remote call yet. | no |
| `InFlight` | Remote calls in progress. | no |
| `Processing` | Accepted by the platform; waiting for processing or the native publish time. | no |
| `OutcomeUnknown` | A non-idempotent call may or may not have succeeded; reconcile is running. | no |
| `Parked(reason)` | Waiting for the cause to clear or for the user. | no |
| `Published`, `Failed`, `DeadLetter`, `Cancelled`, `Simulated` | Final results. | yes |

Transitions:

- `Pending` → `Claimed` (claim), `Cancelled`.
- `Claimed` → `InFlight`, `Parked` (step 4), `Failed` (revalidation), `Pending` (expired lease).
- `InFlight` → `Published`, `Processing`, `Pending` (retryable, or graceful shutdown at a safe checkpoint), `DeadLetter`, `Failed`, `OutcomeUnknown` (ambiguous failure or expired lease), `Cancelled` (safe checkpoint), `Simulated` (dry-run).
- `Processing` → `Published`, `Failed`, `OutcomeUnknown` (processing timeout), `Cancelled` (native-scheduled upload deleted on the platform).
- `OutcomeUnknown` → `Published` (reconcile found the post, or a late worker reported its receipt), `Pending` (reconcile proved no post exists), `Parked(outcome_unresolvable)`.
- `Parked` → `Pending` (the due sweep found the cause cleared, or user retry), `Cancelled`.
- `DeadLetter`, `Failed` → `Pending` by user retry. `OutcomeUnknown`, `Parked(outcome_unresolvable)`, and `DeadLetter` → `Published` or `Failed` by user resolve.

**Parking reasons:** `owner_disabled`, `account_needs_reconnect`, `platform_unavailable`, `platform_disabled`, `live_publish_disabled`, `quota_exceeded`, and `outcome_unresolvable`.

**Parking rule.** When the due sweep finds the cause cleared (the owner is re-enabled, the account reconnected, the platform compiled back in or enabled, the kill switch turned on, the quota period rolled over), a parked delivery returns to `Pending` automatically only if its due time is at most `publishing.park_grace` (default 15 minutes) in the past. Otherwise it stays parked and the owner is notified, because a stale post may no longer be wanted: the owner or a `publish` delegate retries or cancels it. `outcome_unresolvable` never clears on its own. Plan 01's `owner_disabled` rule is this rule.

**Job status** is derived from its deliveries: `scheduled` while every non-terminal delivery is either `Pending` with a future time or a native-scheduled upload waiting for its `remote_publish_at`; `publishing` while any delivery is non-terminal otherwise; once all are terminal, `published` (all `Published` or `Simulated`), `cancelled` (all `Cancelled`), `failed` (none `Published`), or `partial`. A job with a parked or unknown-outcome delivery is non-terminal, so its post stays locked (`post_locked`) until the user retries, resolves, or cancels that delivery.

### Rescheduling, cancelling, and retrying

- `PATCH /publish-jobs/{id}` with a new time is allowed while every non-terminal delivery is either `Pending` or an uploaded native-scheduled delivery whose plugin supports `reschedule`; otherwise it returns 409 `not_reschedulable` and changes nothing. `Pending` deliveries get the new `scheduled_at` and `next_attempt_at`, an incremented `dispatch_gen`, and a new `publish_delivery`. Native-scheduled deliveries are rescheduled through the plugin one at a time; if one fails, the response lists it and the ones already moved keep their new time.
- `POST /publish-jobs/{id}/cancel` cancels every cancellable delivery of the job; `POST /deliveries/{id}/cancel` cancels one. `Pending` and `Parked` deliveries become `Cancelled`. An `InFlight` delivery gets `cancel_requested_at` set, and the worker, which checks it at each safe checkpoint, cancels it there: before the first mutating call or between upload chunks, never after the final create or publish call. A delivery past its last checkpoint finishes, and the response lists it. An uploaded native-scheduled delivery is deleted through the plugin and becomes `Cancelled`; where the plugin cannot delete it, it stays `Processing` and the response lists it as `not_cancellable`, because it will still go live. An `OutcomeUnknown` delivery cannot be cancelled; it is resolved.
- `POST /deliveries/{id}/retry` applies to `DeadLetter`, `Failed`, `Parked`, and `OutcomeUnknown` deliveries. It is a new live publish of the job's `content_snapshot`, even if the post was edited since: it needs `confirm: true`, revalidates the snapshot (a deleted media asset is a 422 violation), passes the same step-4 checks, and resets `attempt_count`. The retry dialog shows the snapshot content, not the current post. For `OutcomeUnknown` and `Parked(outcome_unresolvable)` it also needs `acknowledge_outcome_unknown: true` (400 `acknowledgement_required` otherwise), because the earlier attempt may already have posted. A retry that would make a terminal job non-terminal again is refused with 409 `job_active` while the post has another non-terminal live job.

### Quotas

- Plugins declare quota buckets in their descriptor: the scope (`app` for deployment-wide limits such as YouTube's per-project daily quota or an X app's monthly post cap, `account` for per-account limits), the period (`day` or `month`, calendar-aligned in the reset time zone), the cost of each operation, the default limit, and the reset time zone. `[platforms.<id>]` can override the limits to match the developer app's actual allocation.
- **Rolling windows** (Instagram's limit on API-published posts per moving 24 hours) are not buckets. The plugin checks them against the platform's own usage endpoint before publishing (`content_publishing_limit` for Instagram) and returns a quota error with a `retry_after`. The delivery is parked with `quota_exceeded` until then (stored in `next_attempt_at`), and the sweep treats that time passing as the cause clearing.
- Usage lives in `platform_app_quota_usage` (deployment table) and `platform_quota_usage` (owned, per account), keyed by `period_start`. The worker reserves units atomically at claim time (`UPDATE … SET units_used = units_used + $cost WHERE units_used + $cost <= $limit`) and releases them when no remote call was made. An exhausted bucket parks the delivery with `quota_exceeded`.
- `GET /admin/doctor` shows app-bucket usage per platform. It never shows which user consumed it.

### Disconnecting a social account

`DELETE /social-accounts/{id}` (owner only):

1. `Pending` and `Parked` deliveries for the account are cancelled. In-flight deliveries finish first.
2. Uploaded native-scheduled deliveries are deleted on the platform where the plugin supports it. The rest are listed in the response, because they will still go live.
3. The account leaves its grant and its `social_account_tokens` row is deleted. When the grant has no other accounts left, it is revoked at the provider where supported and deleted; otherwise it stays, because sibling accounts still use it.
4. The account's overrides are deleted, and it is removed from every delegation account limit (plan 01, "Empty account limit").
5. The row is kept with status `disconnected`, so delivery history keeps its account. Disconnected accounts are hidden from account lists and targets. Reconnecting the same remote account by the same owner reactivates the row; another owner may connect it, because the deployment-wide unique key excludes `disconnected` rows.

### Media

- `POST /media` creates the `media_assets` row in `uploading` first, then streams to `{storage_root}/{owner_id}/{yyyy}/{mm}/{uuid}`, computing SHA-256 while streaming. Size limits are enforced during the stream. It suits small files; the client uses upload sessions above `media.single_request_max` (default 20 MB).
- **Route limits.** Upload routes, the chunk route, and the public media route declare their own body limits and timeouts (plan 02, `postly-api`): chunks up to `media.chunk_max` (default 16 MB), no overall timeout on streamed downloads, and an idle timeout instead.
- **Resumable upload sessions** for large files and flaky mobile networks. `POST /media/uploads` declares the filename and total size, checks them against the per-kind limit and the owner's storage quota up front (counting the declared bytes of the owner's other open sessions), and creates a `media_assets` row in `uploading`. `PUT /media/uploads/{id}` appends one chunk with `Content-Range`; a range that does not start at the stored offset returns 409 `upload_offset_mismatch`, and `HEAD` returns the current offset so the client can resume after a dropped connection or an app restart. `complete` streams the file once to compute SHA-256, sniffs, probes, and marks the asset `ready`. Sessions expire after `media.upload_session_ttl` (default 24 hours).
- **Accepted types.** The MIME type is sniffed from content, not trusted from the client, and must be on an allowlist: JPEG, PNG, GIF, WebP, MP4, and QuickTime. Anything else, including SVG, HTML, and HEIC, returns 415 `unsupported_media_type`. HEIC is excluded because none of the initial platforms reliably accepts it and it cannot be decoded in pure Rust; the mobile pickers request JPEG. postly does not transcode or resize; a platform that rejects a format or aspect ratio reports it as a validation violation.
- `MediaProbe` reads dimensions and duration without decoding (pure-Rust container parsing; an optional `ffprobe` implementation behind a feature).
- **Thumbnails.** Image thumbnails are generated at completion with the pure-Rust `image` crate under a pixel-count limit. Video thumbnails need the `ffprobe` feature (ffmpeg); without it the client shows a placeholder. The published Docker image installs Debian's `ffmpeg` and enables the feature. `GET /media/{id}/thumbnail` serves them.
- **Viewing in the client.** `GET /media/{id}/view-url` returns signed URLs for the content and thumbnail (TTL `media.view_url_ttl`, default 10 minutes), served by the public route, because web image and video elements cannot send a bearer header. Native clients may use the bearer routes directly.
- **Storage quota.** `media.user_quota_bytes` (default 20 GiB, 0 for unlimited) caps each owner's total stored bytes; exceeding it returns 413 `storage_quota_exceeded`.
- `MediaHost::public_url(asset, ttl)` signs `id|exp` with HMAC-SHA256 using `media.signing_key` (a `_FILE` secret). The default TTL is 1 hour, and a fresh URL is issued for each attempt. The public route verifies in constant time.
- **Public reachability.** Signed URLs are built on `media.public_base_url` (default `server.public_url`). Platforms that pull media (Instagram, TikTok `PULL_FROM_URL`, Facebook photos by URL) fetch from the internet, so that host must be publicly reachable in QA and production; the rest of the API may stay private behind it. `GET /admin/doctor` warns when it resolves to a private address.
- `MediaSource::PublicUrl` is produced only by `MediaHost` for platforms that pull media. Users cannot create media from a URL, so postly never fetches user-supplied URLs.
- Media responses (`content`, `thumbnail`, and the public route) send the stored MIME type with `X-Content-Type-Options: nosniff` and `Content-Security-Policy: sandbox`.
- The storage root is the only place media is read from. Paths are generated, never user-supplied, and are canonicalized and checked against the root.
- Assets in the media library are kept until the owner deletes them. `DELETE /media/{id}` returns 409 `media_in_use` while a post or the snapshot of a non-terminal job references the asset.
- `media_gc` (daily cron) deletes `failed` uploads, expired upload sessions with their partial files, and files under the storage root that have no row and are older than `media.upload_session_ttl`, so a file whose upload is still streaming is never removed.

### Acting through a delegation

1. The Flutter client reads `GET /me/workspaces` and lets the user switch workspace. The chosen owner ID goes into `X-Postly-Act-As` on every request.
2. The `Scope` extractor in `postly-api` asks `postly-identity` to resolve the header. A missing, revoked, or expired grant, or an inactive owner or delegate, returns 403 `delegation_invalid`.
3. Services call `scope.require(capability)`. Repositories filter by the owner and the account limit, so rows outside the limit behave as not found.
4. The client hides actions the level does not allow, but the server is the only enforcement.

## Group A — Domain foundation

### Phase A1 — Core domain models and the plugin contract

Needs P1. Extend the `postly-core` skeleton from P1 (ID newtypes, `Clock`, `IdGenerator`) with:

- **Open platform identity.**
  - `PlatformId` is a validated lowercase string newtype such as `"x"` or `"youtube"`. There is no closed enum.
  - `PlatformDescriptor` holds the ID, display name, an icon (PNG bytes embedded in the plugin crate, served by `GET /platforms/{id}/icon`) and a brand color, `Capabilities`, an optional `OAuthProviderSpec`, the plugin config schema version, `supports_native_schedule` with its `native_schedule_window` (minimum lead and maximum horizon), the quota buckets with their periods (see [Quotas](#quotas)), and the `publish_options_schema`. The icon and color let the Flutter client show a new platform without code changes.
  - `OAuthProviderSpec` and the token accessor trait (`TokenStore`: read the current token for an account, refresh after a 401) are core types. `postly-oauth` implements them and `postly-platform-kit` builds on them; neither depends on the other.
- **Per-target publish options.** Platform-specific fields (YouTube title, category, privacy, made-for-kids; TikTok privacy, interaction toggles, and commercial-content disclosure; Instagram post type) are not core `Post` fields. Each plugin declares them as a JSON Schema restricted to a small set that the Flutter client renders generically: string, multi-line text, enum (dropdown or radio), boolean, integer, and date-time, plus `x-postly-*` hints (`no_default` forces an explicit choice, `consent_text` shows text the user must see before publishing, `depends_on` hides a field). The subset is part of the contract, so a new platform needs no Flutter code. The chosen values live in the override's `options` and are validated by the core engine against the schema. `PlatformClient::publish_options(account)` merges live account data into the schema, such as the privacy levels and maximum duration from TikTok's creator info.
- **Accounts.** `AccountRef { platform: PlatformId, account: SocialAccountId }`. Publish targets are `AccountRef`s, not platforms.
- **Post models.** `Post` (text, media with per-item alt text, link, tags, `disclose_ai_generated`), `PostOverrides` (per-`AccountRef` patch of `text`, `link`, `tags`, and `media`, plus `options`), `PostVersion`, and `PublishSnapshot` (the resolved per-target content stored on a job and published by the worker).
- **Media.**
  - `MediaAsset`: kind, MIME type, byte size, optional duration and dimensions, content hash, and a `MediaSource`.
  - `MediaSource` is `Stored(MediaId)`, `PublicUrl(Url)`, or `RemoteRef`. There are no local paths.
  - Traits: `MediaStore` (open a stream by `MediaId`), `MediaProbe`, and `MediaHost` (public URL for a stored asset). Implementations live in `postly-media`.
- **Contracts.**
  - `PlatformPlugin`: `descriptor()`, `config_schema()`, `create_client(ctx) -> Box<dyn PlatformClient>`, and optional `handle_event(kind, request)` for platform-initiated `deauthorize` and `data_deletion` callbacks: it verifies the request (for example, Meta's signed request) and returns the remote user it concerns plus the response body the platform expects. The context carries the resolved plugin config, an HTTP handle, a token accessor, a media accessor, and the clock.
  - `PlatformClient`: `account_info` / health, `discover_accounts` (after OAuth), `publish_options(account)`, `validate`, `publish(resolved_post, mode)` with `DryRun` or `Live`, `status(receipt)`, `delete(receipt)` (used only to cancel native-scheduled uploads and in user deletion; deleting live posts is a non-goal), `reschedule(receipt, at)` (optional), `reconcile(delivery)` returning `Unsupported` where the platform cannot look posts up, and `revoke()` (optional; revokes the grant the client's token belongs to).
  - `PluginRegistry` maps `PlatformId` to `Arc<dyn PlatformPlugin>`, rejects duplicates, and is built explicitly by the composition root.
- **Receipts and statuses.** `PublishReceipt` (`Processing` or `Published`, remote ID and URL), `AccountStatus`, and `DeliveryState` with the states, transitions, and parking reasons from [Delivery states](#delivery-states), implemented as a transition function that rejects every other move.
- **Validation engine.** Common rules (including schedule time and native schedule window), then capability rules, then the options schema, then platform `validate`. Returns all violations.
- **Structured errors.** `PlatformError` covers authentication, authorization/scope, validation, rate limit (with retry-after), quota, transport, unsupported capability, remote API error, and outcome unknown, each with a retry classification.
- **Test seams.** `Clock` and `IdGenerator` (from the P1 skeleton) are passed into the plugin context.

Tests: serialization round trips, validation matrices, options-schema validation (including rejection of schema features outside the subset), override resolution, every allowed and forbidden state transition, registry duplicate rejection, and the trait-object compile test.

**Exit criteria:** all shared types are documented and tested. Core has no platform-specific, HTTP, or database code.

### Phase A2 — Vault, platforms table, and platform configuration

Needs A1 and P4.

- **`postly-vault`:**
  - Envelope encryption with XChaCha20-Poly1305. Key-encryption keys come from `vault.keys` (a list of versioned keys, `_FILE` secrets, at least 32 bytes each); the newest version seals, every listed version opens.
  - A `Sealed<T>` type for columns, with the key version and nonce stored alongside the ciphertext and the table, column, and row ID bound as associated data, so ciphertext cannot be moved between rows or swapped between columns of one row (an access token for a refresh token).
  - `development.toml` ships a fixed vault key, clearly marked insecure and dev-only (like `audit.pseudonym_key`), so sealed values survive restarts. QA and production refuse to start without `vault.keys`, and likewise without `media.signing_key`.
  - A re-seal routine in `postly-data` re-seals every sealed column under the newest key, in batches, resumable after a crash. `vault` sits below `jobs`, so `postly-server` registers the `vault_rotate` job that runs it (like `data_retention`), and D3 adds `POST /admin/vault/rotate`.
- **`platforms` table** and the startup upsert from the registry. This is the only phase that migrates it.
- **`[platforms.<id>]` configuration.** Each table is opaque to core and deserialized by the owning plugin (client ID, client secret as a `_FILE` secret, API version, …). Unknown platform tables and tables for plugins not compiled in are reported at startup. The redirect URI is derived from `server.public_url` and shown to admins.
- **`[publishing]`**: `live` default (`true` in every environment), retry budget, `lease`, `sweep_grace`, `park_grace`, and `processing_timeout`. **`[media]`**: storage root, size limits per kind, `single_request_max`, `chunk_max`, `upload_session_ttl`, `user_quota_bytes`, signing key, `public_base_url`, public URL TTL, `view_url_ttl`. **`[oauth]`**: `return_to_allowlist` (web origins and native schemes; loopback is always allowed for desktop). **`[ai]`**: `request_timeout` and `allow_private_endpoints` (deployment config, not a runtime setting, because it widens what the server may reach). **`[vault]`**: `keys`. **`[platforms.<id>]`** may override quota bucket limits.

**Exit criteria:** sealed values round trip, rotation re-seals every row, a row's ciphertext cannot be opened under another row's ID, secrets never appear in `Debug`, errors, or logs, and platform config validation reports actionable errors.

## Group B — Shared infrastructure

### Phase B1 — HTTP resilience and observability

Needs A1 and P2. Extends the foundation `postly-http`:

- Retry classification: transient errors retry; rate-limited responses honor `Retry-After` and plugin-supplied reset headers; non-idempotent mutations are never retried once the body may have been received and surface as an outcome-unknown error.

**Exit criteria:** queued work is durable, safely claimed, observable, retryable, and idempotent, and a crash after a remote success cannot cause a duplicate post.

### Phase D2 — Content generation (LLM layer)

Needs B1 and B2. Create `postly-content` (behind the `ai` feature in `postly-server`, enabled by default):

- **Provider-neutral trait.** `LlmProvider` with `chat(request)`. Messages, system prompt, temperature, max tokens, JSON-schema structured output where supported, and token usage are modeled provider-neutrally. Streaming has no consumer (the client polls, and SSE is a non-goal), so it is not part of the trait.
- **Two wire-protocol adapters** built on `postly-http`:
  - `openai-compatible`: Chat Completions with configurable base URL, headers, and query parameters. Serves OpenAI, Abacus AI RouteLLM (`https://routellm.abacus.ai/v1`), Gemini's OpenAI endpoint (`https://generativelanguage.googleapis.com/v1beta/openai/`), OpenRouter, Groq, DeepSeek, Mistral, xAI, Together, Ollama, LM Studio, vLLM, and other compatible servers. Tolerates provider extensions and missing `usage`.
  - `anthropic`: the native Messages API.
- **Per-user, opencode-shaped providers.** Each `ai_providers` row stores the same shape as an opencode `provider` entry, so users can paste an entry field for field. The API key is stored separately and sealed. `npm` values map to protocols (`@ai-sdk/openai-compatible` and `@ai-sdk/openai` to `openai-compatible`, `@ai-sdk/anthropic` to `anthropic`, `@ai-sdk/google` to `openai-compatible` with the Gemini base URL); an explicit `protocol` overrides. Presets for `openai`, `anthropic`, `gemini`, `abacus`, `openrouter`, and `ollama` need only a key; preset base URLs are verified at phase start. postly never reads opencode's files.
- **Delegates** with `edit` can generate with the owner's providers. They see provider names and models, never keys or config.
- **Outbound URL policy.** Custom base URLs are user-supplied, so every provider request goes through the B1 address-policy client: private, loopback, and link-local addresses are refused at connect time, and redirects are not followed, unless the operator sets `ai.allow_private_endpoints` in config (needed for a self-hosted Ollama).
- **Targets in limit.** A limited delegate can generate only for targets in their account limit.
- **Generation pipeline.** A prompt template plus platform capability data for each target (length, hashtag conventions, media constraints), structured output parsing, core validation, and one repair attempt. The result is draft content with `disclose_ai_generated = true` plus an `ai_generations` record, returned to the client; no post is created. When the client saves it with `POST /posts` and the `generation_id`, the record's `post_id` is set.
- **Timeouts.** Generation calls use `ai.request_timeout` (default 120 seconds), and the generate route is exempt from the global request timeout up to that value.
- **Spend visibility.** Delegates with `edit` spend the owner's provider credit. There is no spending cap; `GET /ai/generations` shows the owner every generation with its actor, model, and token usage.
- No provider keys appear in logs, drafts, or generation records. Prompts are stored only when the owner enables `store_ai_prompts`.

Tests: wiremock contract tests for both protocols (including Gemini-style and Abacus-style responses), a mock provider, the URL policy (including a hostname that resolves to a private address and a redirect to one), and deterministic validation and repair.

**Exit criteria:** the library produces a validated, disclosure-flagged draft for any configured provider without touching publishing credentials.

**Deferred:** image and video generation. `ImageProvider` and `VideoProvider` are reserved names, not implemented.

## Group F — TikTok

### Phase F1 — TikTok Content Posting API plugin

Needs B5 and B4.

- **Direct Post only.** Posts go live on the account (private until the app passes TikTok's audit). Sending to the user's TikTok inbox as a draft (`video.upload`) is not supported.
- TikTok OAuth spec with checks for the required scopes (`user.info.basic`, `video.publish`).
- Creator info query (nickname, allowed privacy levels, interaction toggles, maximum duration), required before posting and exposed through `publish_options`.

## Platform constraints and risks

Verify each at the start of the relevant phase, since platform policies change:

- **X:** write access and cost depend on the API access tier, and post caps apply per app, across every user of the deployment. Refresh tokens rotate. Media upload endpoints have moved from v1.1 to v2.
- **YouTube:** uploads from an unverified API project are locked to private until the project passes an audit. The daily quota is small, is shared by every user of the deployment, and uploads are expensive against it. Refresh tokens of a project in "testing" status expire after 7 days.
- **TikTok:** unaudited apps can only post with private visibility. The audit checks the posting UX (creator info, no default privacy, disclosures, consent text). `PULL_FROM_URL` needs domain verification of the API host.
- **Meta:** App Review is required for publishing permissions beyond test users. Instagram needs a professional account, linked to a Page when using Facebook Login (the login path is decided at E2 start), and is rate-limited per 24 hours. Most media must be at a public URL. Long-lived tokens and data access expire on fixed dates and need a reconnect.
- **Redirect URIs in development:** Google, Meta, and TikTok may reject `https://postly.local`. The dev tunnel fallback is verified in B3 and documented in G2.
- **Public media in development:** platforms cannot fetch from `postly.local`. Instagram and TikTok `PULL_FROM_URL` need the tunnel in development, or the mock plugin.
- **Live publishing is on in development by decision.** A development worker connected to a real account posts for real. Mitigations: per-publish confirmation, the kill switch, `platforms.enabled`, the dry-run toggle, and the `test_account` label shown in the publish dialog.
- **Delegated live publishing.** A `publish` delegate can post to the owner's real accounts. Mitigations: the same confirmation, account limits, `created_by` shown in history, and owner notifications.
- **Calendar package license:** checked in D5.
- **apalis 1.0 release status:** inherited from plan 02; re-checked at the start of D1.
- **Anthropic via its OpenAI-compatible endpoint** is feature-limited, which is why a native adapter exists.
