## Objective

Turn the foundation into a marketing tool that people with little technical experience and a small budget can run on their own: one place to publish to their own social accounts and to email their own contact lists, with AI help writing the text, comment replies, recurring posts, campaigns, and analytics. It ships in the user's language (English or Arabic first), on the web and on Android.

## Product guidelines

These are product rules, not phase details. Every phase follows them, and a feature that needs to break one comes back to the plan first.

- **Real accounts only.** Users connect accounts they own or manage. postit never creates accounts on a platform, never generates identities, and never runs several accounts as different "people" to make one voice look like many. No captcha solving, proxy rotation, user-agent rotation, or other bot-detection evasion.
- **Official APIs only.** Agents use each platform's published API, through OAuth or a scoped, revocable token the platform issues for that purpose (bot token, webhook URL, app password, personal access token). postit never stores a platform password and never drives a platform's website with browser automation.
- **AI drafts, people approve.** The drafter writes text only, never images, video, or audio; media always comes from the user. Every live post, every comment, and every reply is confirmed by a person before it goes out. The one exception is a recurring post with "rewrite each time" on: confirming the recurrence confirms its future rewritten occurrences, and the dialog says so.
- **Email only to people who agreed.** Contacts are imported with a recorded consent source, every campaign carries a one-click unsubscribe and the sender's postal address, unsubscribes and bounces are suppressed permanently, and the operator can cap each user's sending.
- **Simple first.** A feature reaches non-technical users only with plain-language messages, a guided setup, and safe defaults. A validation message says what is wrong and what the platform wants, not an error code.
- **Persona means writing style.** A brand profile and a per-account writing style shape the drafter's tone. They describe the user's own business and voice, never a fictional person.

## Delivery model

- **Releases.** The plan ships in three releases. Each one leaves the product usable.
    - **R1, first usable release** (household use: the operator and their family testing on a real phone): A1–A2, B1–B7, C1–C5, D0–D6, G0–G2. Web plus Android, with Email, Telegram, Slack, Discord, Bluesky, and Mastodon. B7 (OAuth) is in R1 although no R1 agent uses it, because the clients' connection screens are built once in D4 and D6 and are tested against the mock OAuth provider; TikTok then needs no client work.
    - **R2, TikTok and engagement:** E1–E4, F1, C6. Recurring posts, inbox and replies, analytics, media fitting, TikTok, and the HTTP email services.
    - **R3, remaining platforms and hardening** (required before renting the service to anyone else): F2–F7, G3–G5.
- **Parallel tracks.** Group B runs in parallel after Group A. Agent tracks (C, F) run in parallel once the agent kit (B5) exists. D0 needs nothing from this plan and can start at once.
- **Mock-first.** The `mock` agent (B5) lets the engine, the REST surface, the client UIs, and orchestration be built and tested before any real agent is complete.
- **Release safety.** Every live publish is explicitly confirmed by the acting user. Dry-run works everywhere. The kill switch and per-platform `enabled` flags stop live publishing without a redeploy, except native-scheduled uploads already on the platform (plan 01, "Kill switch limit"). CI never publishes live and never sends real email.
- **Access in every test.** Every phase that adds owned data or endpoints adds isolation tests for four callers: the owner, a delegate at each level, a delegate limited to other accounts, and an unrelated user.
- **One migration until the first production deployment.** Until G1 goes live, schema changes edit the single `server/crates/data/migrations/0001_init.sql` in place, and the dev database is reset; "schema for X" in this plan means "add X to that file". From the G1 deployment on, every schema change is a new migration file, so production data survives upgrades. G1's exit checklist includes freezing `0001_init.sql`.
- **Two hosting modes, one image.** A self-hosted deployment for one team and a hosted deployment the operator runs for many independent users are the same image and the same config keys. Nothing in this plan branches on the mode; per-user limits (plan 01, `user_limits`) are how the hosted mode is kept safe.

## Concepts

### Agents

An **agent** is the compile-time implementation of one platform: a crate under `server/crates/agents/<id>/` implementing the `Agent` contract from `postit-core`. The word "plugin" from the archived plan is retired everywhere: code, docs, and UI. AI drafting is the **drafter**, never an agent.

Each agent declares, as data:

- **Kind.** `broadcast` (publish once to an account; its followers see it) or `direct` (send to each recipient of a contact list from a sending identity).
- **Connect method.** `oauth(OAuthProviderSpec)` or `credentials(schema)`. A credentials schema uses the same JSON Schema subset as publish options, with `x-postit-secret` marking fields that are sealed (bot token, app password, webhook URL, SMTP password). Clients render both generically.
- **Formats.** The shapes of content the agent accepts. See [Formats and validation](#formats-and-validation).
- **Capabilities.** Optional abilities, each backed by an extension trait the agent's client exposes: `Commenter` (reply to a comment, comment on a post), `InboxReader` (fetch new comments), `MetricsReader` (post and account metrics), `DirectSender` (direct agents), `NativeScheduler` (reschedule and delete native-scheduled uploads). A client exposes them through `fn commenter(&self) -> Option<&dyn Commenter>` and the like; the conformance suite checks that declared capabilities and exposed traits agree.
- **Publish options schema** (per-target fields such as a YouTube title or TikTok privacy, rendered generically by the clients), quota buckets, the native schedule window, an icon, and a brand color, so the clients show a new platform without code changes.

### Accounts and targets

- A **connected account** is something the user publishes to or sends from: a TikTok profile, a Facebook Page, a Telegram channel, a Slack channel's webhook, an email sending identity. Table `connected_accounts`, ID `AccountId` (already in `postit-core`).
- A **grant** holds the credential: an OAuth authorization (which may yield several accounts, such as all Pages a person manages) or a pasted credential (a Telegram bot token may reach several channels). Table `account_grants`.
- A **target** is always a connected account. For a direct agent, the target's options also name the audience (contact lists, optional tag filter).
- **Target groups** are saved sets of accounts ("All bakery accounts") the composer can pick in one click.

### Posts, variants, and kinds

- A **post** is one piece of content: text, optional media, link, and tags. It publishes to many targets.
- A **variant** is the per-target view: the post plus that target's **override** (text, link, tags, media subset, options). The drafter writes one variant per target in random mode. An email target's override holds the email document (subject, preheader, blocks).
- A post's **kind** is `post` or `comment`. A comment post has exactly one target and a `reply_to` (the remote post, and the remote comment when it is a reply). Replies and comments therefore get versioning, confirmation, history, AI linkage, and the delivery engine's duplicate protection for free.
- **Controlled mode:** the user writes the post. **Random mode:** the user gives a prompt and optional media, and the drafter writes the variants. Both end in the same draft the user reviews.

### Brand profile and writing style

- **Brand profile**, one per owner: business description, audience, products and services, words to avoid, default language, and up to five example posts the user likes.
- **Writing style**, one per connected account: tone, emoji use, hashtag habits, language override, and free-form notes.
- The drafter receives both, the target's formats and limits, and the user's prompt. Neither is a persona of a fictional person.

### Campaigns

A **campaign** is a named group with a date range and a color. Posts (including email sends) may belong to one. Campaigns filter the queue, history, and calendar and drive the campaign comparison chart.

### Recurring posts

A post may carry one **recurrence**: a repeat rule (daily, weekly on chosen days, monthly on a day; ending on a date, after N occurrences, or never) in a time zone, plus an optional "rewrite each time" flag. Each occurrence becomes its own publish job. See [Recurring posts](#recurring-posts-1).

### Inbox

For accounts whose agent implements `InboxReader`, postit fetches new comments on the account's posts into an **inbox**. Each item can be read, dismissed, or replied to. The drafter can propose a reply; the user edits and confirms it.

## Formats and validation

A **format** is a shape of content an agent accepts. Agents declare a list of `FormatSpec`s:

- `id`: one of `text`, `link`, `image`, `carousel`, `video`, `short_video`, `story`, `reel`, `html_email`. The set is closed in core; an agent may declare `text` with images allowed, for example.
- Text rules: a `TextMeasure` (graphemes, X-weighted, UTF-16 units, bytes), a maximum, and whether text is required.
- Media rules: count range, allowed kinds and MIME types, byte size, pixel dimensions, aspect-ratio ranges, duration range, and **safe zones** (rectangles, as fractions of the frame, where the platform's own UI covers the media, such as TikTok's caption and button rail).
- Which publish option selects it, when the platform needs an explicit choice (Instagram's post type).

The validation engine, in `postit-core`, runs for each target: common rules (schedule time, native schedule window), then picks the format (from the options, or inferred from the media: no media is `text`, one vertical video under the limit is `short_video`), then format rules, then the options schema, then the agent's own `validate`. It returns every violation at once. A violation has a stable `code`, parameters, and an optional **suggested fix** (`fit { aspect: "9:16" }`, `trim { max_ms }`, `remove_media`, `shorten_text { max }`), so the clients can show "Fit for TikTok" instead of an error. Violation messages are rendered by the clients in the user's language from the code and parameters ([Localization](#localization)).

Formats are data, not a type hierarchy, because platforms span categories: Facebook does text, image, video, reels, and stories; X does text with images or video. The UI can still group targets ("needs a video") from the declared formats.

## Key flows

### Connecting an account with credentials

1. The client renders the platform's credentials schema (bot token; webhook URL; handle and app password; instance URL and token; or the email sending method) with a step-by-step "where to find this" guide per platform, translated.
2. `POST /accounts/credentials/{platform}` validates the fields against the schema, then calls the agent's `verify_credentials`, which checks them against the platform (Telegram `getMe`, a Bluesky session, a Mastodon `verify_credentials`, an SMTP `EHLO` and `AUTH`) and discovers accounts (for Telegram, the channels and groups whose `my_chat_member` updates show the bot as an admin; for webhooks, the one channel the URL names). Any user-supplied host (Mastodon instance, SMTP host, Bluesky PDS) goes through the [outbound address policy](#phase-b1--http-resilience-and-outbound-address-policy).
3. The result is stored as a **pending connection** (sealed credential plus discovered accounts, 10-minute expiry) and returned with a `connect_id`. Bad credentials return 422 `credentials_invalid` with the agent's plain-language reason.
4. The client shows the discovered accounts as a checklist; `POST /accounts/connect/{connect_id}/confirm` creates the grant and the chosen accounts in one transaction, under the same rules as OAuth (an account already connected by another owner is skipped and reported as `account_connected_elsewhere`).

**CSV import.** `POST /accounts/import/{platform}` takes a CSV whose columns are the credentials schema's fields (plus `display_name`). Each row runs steps 2 and 4 with every discovered account chosen. `commit=false` returns the per-row report (ok, invalid credentials, already connected, discovery found nothing) without creating anything; `commit=true` creates the valid rows and reports the rest. The uploaded file is streamed and never stored; secrets are sealed per row. OAuth platforms cannot be imported, because each account needs its owner's consent on the platform's own page.

**Email has one sending method per owner.** The email agent allows one non-disconnected email account per owner (`sending_method_exists` otherwise). Switching methods edits that account's credentials, so history keeps its account.

### Connecting an account with OAuth

1. The client calls `POST /accounts/connect/{platform}` with `return_to`: the web app origin (`/oauth-done`) or the mobile scheme for the flavor (`postit-dev://oauth-done`, `postit-qa://oauth-done`, `postit://oauth-done`). `return_to` is checked against `oauth.return_to_allowlist`.
2. The API creates an `oauth_states` row: a random 32-byte state stored as a hash, the PKCE verifier sealed, a 10-minute expiry. It returns the provider's `authorize_url`. For platforms with one account per login (X, TikTok), the URL asks the provider to show its login or account picker (`prompt=login`, `force_login`, or the platform's equivalent, verified per agent), so connecting a second account does not silently reuse the browser's current session.
3. The client opens it: a new tab or popup in the web app, the system browser in the mobile app.
4. The provider redirects to `/api/v1/platforms/{id}/oauth/callback?code&state`.
5. The server consumes the state (single use), exchanges the code, runs the agent's post-exchange hook (for example, Meta's long-lived token exchange and Page token derivation), and discovers every account the consent reaches (YouTube channels, Facebook Pages with their linked Instagram professional accounts, LinkedIn pages the member administers). It stores the sealed tokens and the discovered accounts on the state row as a **pending result** with a new random `connect_id` (stored as a hash, same 10-minute expiry), creates no grant or account yet, and redirects to `return_to?result=ok&connect_id=…`.
6. The client shows the discovered accounts as a checklist and calls `POST /accounts/connect/{connect_id}/confirm` with its bearer token and the chosen `account_ids`. The server accepts it only when the caller is the user who started the connection, and then, in one transaction: deletes the state row, creates the `account_grants` row, upserts the chosen `connected_accounts` (reconnecting an existing account moves it to the new grant), and deletes any previous grant left with no accounts. Accounts already connected by another owner are skipped; the response lists them as `account_connected_elsewhere` with the number skipped, without saying who owns them. A confirm by any other user returns 404 and deletes the pending result.

**Why the confirm step.** The callback has no bearer token and postit sets no cookies, so without it an attacker could start a connection, send the `authorize_url` to a victim, and have the victim's account attached to the attacker's postit user. The `connect_id` reaches only the browser that completed the authorization, and only its signed-in user can confirm it.

Expired or reused state, provider denial, and missing scopes redirect with `result=error&code=…` and create no rows. An unconfirmed result expires with its state row.

### Credential refresh

- A `refresh_credentials` cron job runs every 5 minutes and refreshes OAuth tokens that expire within 15 minutes. Agents also refresh on demand after a 401.
- Both paths take `pg_advisory_xact_lock` keyed on the **grant** ID (accounts that share a grant share its tokens), re-read the token, and skip the refresh if another process already did it. The rotated token is written in the same transaction, which makes X's refresh-token rotation safe across the API and worker processes.
- `invalid_grant` or a revoked token sets the grant and its accounts to `needs_reconnect` and sends a critical notification to the owner. Deliveries are not touched here: the worker parks them with `account_needs_reconnect` when they come due, and the due sweep resumes them after a reconnect under the [parking rule](#delivery-states).
- **Credentials that cannot be refreshed.** Some OAuth grants end on a fixed date (Meta long-lived tokens and data-access expiry; Google projects in "testing" status after 7 days). The agent reports a `reconnect_by` time, stored on the grant; the cron notifies the owner 7 days and 1 day before it and critically once it has passed, each once (`reconnect_warned`).
- **Pasted credentials** (bot tokens, webhook URLs, app passwords, SMTP logins) do not refresh. An authentication failure on use or in preflight moves the grant and its accounts to `needs_reconnect` the same way, and the owner re-enters the credential.
- **Platform-initiated deauthorization.** When a platform calls `POST /platforms/{id}/events/deauthorize` or `data_deletion` (Meta requires both for App Review), the agent verifies the request and names the remote user. postit sets the matching grants and accounts to `revoked`, deletes their credentials, notifies the owners, and records `account_revoked_by_platform`. A data-deletion request answers in the format the platform expects.
- **Account preflight.** An `account_preflight` cron job (every 10 minutes) calls `account_info` for each account with a delivery or recurrence occurrence due within the next hour that was not checked in the last hour, so the owner hears about a revocation before the post is due.

### Publishing

1. `POST /posts/{id}/publish` checks access (level and account limit), takes `SELECT … FOR UPDATE` on the post, and checks `If-Match` against `posts.version` (412 `version_conflict` if someone edited the post after the user reviewed it). It then runs full [validation](#formats-and-validation) for every target. Any violation returns 422 with every violation. A live publish without `confirm: true` returns 400 `confirmation_required`.

    A schedule time up to 1 minute in the past is treated as "now"; an earlier time is a violation. `native_schedule` applies to the targets whose agent declares `supports_native_schedule`; the other targets use postit scheduling, and the publish dialog shows which is which. For native targets, the time must fall inside the agent's `native_schedule_window`. Quota and daily-limit checks here are advisory; the worker enforces them.

2. In the same transaction, the API resolves every target's variant into the job's `content_snapshot`, creates the job and one delivery per target account (`next_attempt_at` = the schedule time or now, `dispatch_gen` = 0), recording the actor in `created_by`, and enqueues `publish_delivery { delivery_id, dispatch_gen }` for each with `enqueue_in` and `run_at` = `next_attempt_at`. A live publish records a `publish_confirmed` audit event with the actor, the post kind, and the target account IDs.
3. The worker claims the delivery with `UPDATE deliveries SET state = 'claimed', lease_expires_at = now() + lease … WHERE id = $1 AND dispatch_gen = $2 AND state = 'pending' AND next_attempt_at <= now() AND job not cancelled RETURNING …`. That row update is the lock. Every change that re-enqueues a delivery (retry backoff, reschedule, unpark, user retry, sweep) increments `dispatch_gen` in the same statement, so a duplicate or stale apalis job finds nothing to claim and exits. The worker renews the lease (`publishing.lease`, default 5 minutes) every third of its length while it works.

    **Fenced writes.** Every worker write after the claim is conditioned on the `dispatch_gen` it claimed and the state it expects, and bumps `publish_jobs.version`. A worker that stalled past its lease finds its write rejected; if it holds a success receipt, it records it through the reconcile path instead (an `OutcomeUnknown` delivery with a matching receipt becomes `Published`), so a late success is never lost and never duplicated.

4. Before any remote call, the worker checks, in order, and parks the delivery with the matching reason if one fails: the owner is `active` (`owner_disabled`); the account is `active` (`account_needs_reconnect`); the agent is compiled in (`platform_unavailable`) and enabled (`platform_disabled`); for live deliveries, `app_settings.publishing.live` (`live_publish_disabled`); and the quota reservation from [Quotas](#quotas) (`quota_exceeded`). A parked live delivery sends a notification and never silently degrades to a dry-run. The worker then revalidates against the current formats and options schema; violations end the delivery in `Failed` with `validation_failed`.
5. The worker moves the delivery to `InFlight` and calls the agent with the variant from the job's `content_snapshot`, never from the current post: `publish` for a `post`, `Commenter::comment` for a `comment`, and the [direct flow](#sending-an-email-campaign) for a direct agent.
    - Success: `Published`, or `Processing` followed by `poll_delivery_status` jobs.
    - Retryable failure: back to `Pending` with `next_attempt_at` from backoff with full jitter, `dispatch_gen` incremented, and `enqueue_at` for the new time. The retry budget (5 attempts by default) ends in `DeadLetter`.
    - Permanent failure (validation rejected by the platform, missing permission, content refused): `Failed` with the classified error.
    - Ambiguous failure of a non-idempotent call: `OutcomeUnknown`, then `reconcile_delivery`. If the agent returns `Unsupported`, the delivery is parked with `outcome_unresolvable` for the user to retry or resolve. It is never blindly retried.
6. Multi-step agents (Instagram containers, TikTok `publish_id`, YouTube resumable sessions) persist `container_ref` before each next step, so a retry resumes rather than duplicating.
7. The job status is derived from its deliveries. The post status mirrors the latest live job while that job's `post_version` is the post's current version, and becomes `draft` once the post is edited. Notifications go out on `DeadLetter`, `Failed`, `OutcomeUnknown`, a parked delivery, `needs_reconnect`, and a `partial` job, to the owner and to the delegate who created the job while their grant is active.

**Processing.** `poll_delivery_status` polls with backoff from 15 seconds up to 15 minutes. A delivery still `Processing` after `publishing.processing_timeout` (default 24 hours) moves to `OutcomeUnknown` and is reconciled; for a native-scheduled upload the timeout counts from `remote_publish_at`. Direct deliveries stay `Processing` while their batches run and are exempt from the timeout while batches are queued.

**Native scheduling.** When the agent declares `supports_native_schedule` (YouTube `publishAt`, Facebook scheduled posts) and the user chooses it, the worker uploads immediately with the remote publish time, stored in `remote_publish_at`. The delivery stays `Processing`: polled until the platform accepts the upload, then not again until the remote publish time, and then until the platform reports it live.

**Graceful shutdown.** On shutdown, an `InFlight` delivery stops at its next safe checkpoint and returns to `Pending` with an incremented `dispatch_gen`. A delivery past its final create or publish call finishes first, within `server.shutdown_timeout`.

**Due sweep.** The deliveries table is the source of truth, not the apalis queue. The `delivery_due_sweep` cron job (every minute):

- re-enqueues a `pending` delivery whose `next_attempt_at` is more than `publishing.sweep_grace` (default 2 minutes) past, with an incremented `dispatch_gen`;
- returns a `claimed` delivery with an expired lease to `pending` (no remote call was made) and re-enqueues it;
- moves an `in_flight` delivery with an expired lease to `OutcomeUnknown` and reconciles it (multi-step agents resume from `container_ref`);
- re-enqueues missing `direct_send_batch` jobs for direct deliveries with queued rows and no live batch;
- unparks a `parked` delivery whose cause has cleared, under the [parking rule](#delivery-states). It is the only place that unparks, so re-enabling a user, reconnecting an account, or flipping a switch takes effect within a minute without calling into `postit-publishing`.

A lost queue entry or a crashed worker delays a post by at most a few minutes and never duplicates it.

**Dry-run.** A dry-run job runs immediately. It validates, resolves overrides, and records the planned remote actions in `delivery_attempts` without calling any mutating endpoint (a direct dry-run materializes nothing and reports the audience count). Its deliveries end in `Simulated` or `Failed`. Dry-run jobs are not covered by the one-non-terminal-job index and never change `posts.status`.

**Unknown job types on a rolling deploy** (open item 2 from plan 02 P5): a worker that does not know a job type re-queues it as pending with `run_at` + 60 seconds and no attempt consumed, instead of killing it, because recurring and scheduled work makes mixed-version workers likely. D1 implements this in `postit-jobs`.

### Delivery states

| State | Meaning | Terminal |
|---|---|---|
| `Pending` | Waiting for `next_attempt_at`. | no |
| `Claimed` | A worker holds the lease; no remote call yet. | no |
| `InFlight` | Remote calls in progress. | no |
| `Processing` | Accepted by the platform; waiting for processing, the native publish time, or (direct) the remaining batches. | no |
| `OutcomeUnknown` | A non-idempotent call may or may not have succeeded; reconcile is running. | no |
| `Parked(reason)` | Waiting for the cause to clear or for the user. | no |
| `Published`, `Failed`, `DeadLetter`, `Cancelled`, `Simulated` | Final results. | yes |

Transitions:

- `Pending` → `Claimed` (claim), `Cancelled`.
- `Claimed` → `InFlight`, `Parked`, `Failed` (revalidation), `Pending` (expired lease).
- `InFlight` → `Published`, `Processing`, `Pending` (retryable, or graceful shutdown at a safe checkpoint), `DeadLetter`, `Failed`, `OutcomeUnknown` (ambiguous failure or expired lease), `Cancelled` (safe checkpoint), `Simulated` (dry-run).
- `Processing` → `Published`, `Failed`, `OutcomeUnknown` (processing timeout), `Cancelled` (native-scheduled upload deleted on the platform, or a direct delivery cancelled with its queued rows).
- `OutcomeUnknown` → `Published` (reconcile found the post, or a late worker reported its receipt), `Pending` (reconcile proved no post exists), `Parked(outcome_unresolvable)`.
- `Parked` → `Pending` (the sweep found the cause cleared, or user retry), `Cancelled`.
- `DeadLetter`, `Failed` → `Pending` by user retry. `OutcomeUnknown`, `Parked(outcome_unresolvable)`, and `DeadLetter` → `Published` or `Failed` by user resolve.

**Parking reasons:** `owner_disabled`, `account_needs_reconnect`, `platform_unavailable`, `platform_disabled`, `live_publish_disabled`, `quota_exceeded`, and `outcome_unresolvable`.

**Parking rule.** When the sweep finds the cause cleared, a parked delivery returns to `Pending` automatically only if its due time is at most `publishing.park_grace` (default 15 minutes) in the past. Otherwise it stays parked and the owner is notified, because a stale post may no longer be wanted; the owner or a `publish` delegate retries or cancels it. `outcome_unresolvable` never clears on its own.

**Job status** is derived from its deliveries: `scheduled` while every non-terminal delivery is `Pending` with a future time or a native-scheduled upload waiting for its `remote_publish_at`; `publishing` while any delivery is otherwise non-terminal; once all are terminal, `published` (all `Published` or `Simulated`), `cancelled` (all `Cancelled`), `failed` (none `Published`), or `partial`. A job with a parked or unknown-outcome delivery is non-terminal, so its post stays locked (`post_locked`) until the user retries, resolves, or cancels that delivery.

### Rescheduling, cancelling, and retrying

- `PATCH /publish-jobs/{id}` with a new time is allowed while every non-terminal delivery is `Pending` or an uploaded native-scheduled delivery whose agent implements `NativeScheduler`; otherwise it returns 409 `not_reschedulable` and changes nothing. `Pending` deliveries get the new time, an incremented `dispatch_gen`, and a new `publish_delivery`. Native-scheduled deliveries are rescheduled through the agent one at a time; if one fails, the response lists it and the ones already moved keep their new time.
- `POST /publish-jobs/{id}/cancel` cancels every cancellable delivery of the job; `POST /deliveries/{id}/cancel` cancels one. `Pending` and `Parked` deliveries become `Cancelled`. An `InFlight` delivery gets `cancel_requested_at`, and the worker cancels it at its next safe checkpoint: before the first mutating call or between upload chunks, never after the final create or publish call. A direct delivery in `Processing` cancels its queued rows; rows already sent stay sent. An uploaded native-scheduled delivery is deleted through the agent and becomes `Cancelled`; where the agent cannot delete it, it stays `Processing` and the response lists it as `not_cancellable`. An `OutcomeUnknown` delivery cannot be cancelled; it is resolved.
- `POST /deliveries/{id}/retry` applies to `DeadLetter`, `Failed`, `Parked`, and `OutcomeUnknown` deliveries. It is a new live publish of the job's `content_snapshot`: it needs `confirm: true`, revalidates the snapshot (a deleted media asset is a 422 violation), passes the same step-4 checks, and resets `attempt_count`. For `OutcomeUnknown` and `Parked(outcome_unresolvable)` it also needs `acknowledge_outcome_unknown: true` (400 `acknowledgement_required` otherwise). A retry that would make a terminal job non-terminal again is refused with 409 `job_active` while the post has another non-terminal live job.

### Quotas

- Agents declare quota buckets in their descriptor: the scope (`app` for deployment-wide limits such as YouTube's per-project daily quota or an X app's monthly post cap; `account` for per-account limits), the period (`day` or `month`, calendar-aligned in the reset time zone), the cost of each operation (publish, comment, inbox poll, metrics call), the default limit, and the reset time zone. `[platforms.<id>]` can override the limits.
- **Rolling windows** (Instagram's API-published posts per moving 24 hours) are not buckets. The agent checks them against the platform's own usage endpoint before publishing and returns a quota error with `retry_after`; the delivery is parked with `quota_exceeded` until then.
- Usage lives in `platform_app_quota_usage` (deployment) and `platform_quota_usage` (owned, per account), keyed by `period_start`. The worker reserves units atomically at claim time (`UPDATE … SET units_used = units_used + $cost WHERE units_used + $cost <= $limit`) and releases them when no remote call was made. An exhausted bucket parks the delivery with `quota_exceeded`; inbox polls and metric calls simply stop until the period rolls over.
- **The per-user email cap** is not a platform quota: it lives in `user_limits` and is reserved per recipient by the direct flow.
- `GET /admin/doctor` shows app-bucket usage per platform, never which user consumed it.

### Disconnecting an account

`DELETE /accounts/{id}` (owner only):

1. `Pending` and `Parked` deliveries for the account are cancelled, and queued direct-send rows with them. In-flight deliveries finish first.
2. Uploaded native-scheduled deliveries are deleted on the platform where the agent supports it. The rest are listed in the response, because they will still go live.
3. The account leaves its grant and its `account_tokens` row is deleted. When the grant has no other accounts left, it is revoked at the provider where supported and deleted; otherwise it stays.
4. The account's overrides and inbox items are deleted, it is removed from every target group, recurrence, and delegation account limit (plan 01, "Empty account limit"), and a recurrence left with no targets pauses.
5. The row is kept with status `disconnected`, so delivery history keeps its account. Reconnecting the same remote account by the same owner reactivates the row; another owner may connect it, because the deployment-wide unique key excludes `disconnected` rows.

### Acting through a delegation

1. The client reads `GET /me/workspaces` and lets the user switch workspace. The chosen owner ID goes into `X-Postit-Act-As` on every request.
2. The `Scope` extractor in `postit-api` asks `postit-identity` to resolve the header. A missing, revoked, or expired grant, or an inactive owner or delegate, returns 403 `delegation_invalid`.
3. Services call `scope.require(capability)`. Repositories filter by the owner and the account limit, so rows outside the limit behave as not found.
4. The client hides actions the level does not allow, but the server is the only enforcement.

### Sending an email campaign

1. The user composes a post with an email target. The override's email document holds the subject, preheader, and blocks (heading, text, image, button, divider; the footer with the sender's postal address and the unsubscribe link is added automatically and cannot be removed). The options name the contact lists and an optional tag filter, and whether open tracking is on (default off, with a one-line disclosure).
2. Publishing validates as usual: subject required, at least one list, the account's sending method verified, a postal address present, every image a stored media asset, and the rendered HTML within size limits.
3. When the delivery runs, `postit-publishing` **materializes the audience** in one statement (the query lives in `postit-data`): one `direct_sends` row per subscribed contact in the chosen lists and filter, skipping anyone on the owner's suppression list, with the count stored on the delivery. The audience is fixed at this moment; later list changes do not affect a running campaign.
4. The delivery moves to `Processing`, and `direct_send_batch` jobs (owned by `postit-publishing`) claim the rows in batches sized by the transport (`email.batch_size`, default 50). For each batch, publishing loads the recipients' fields and passes the agent's `DirectSender::send_batch` a list of `DirectRecipient { send_id, address, merge_fields, locale }` plus the snapshot variant and a `LinkSigner` (a core trait in the agent context, implemented in `postit-api`'s public-route module with `email.signing_key`) that builds unsubscribe, click, and open URLs. The email agent renders each message (merge fields, the unsubscribe URL, `List-Unsubscribe` and `List-Unsubscribe-Post` headers, rewritten links, an automatic plain-text part), sends at the transport's rate, and returns one result per recipient. The agent never touches the database or `postit-contacts`; the contract stays generic for a later WhatsApp agent.
5. **Caps.** Each send reserves one unit against the owner's daily email cap (`user_limits.email_daily_cap`, operator-set). When the cap is reached, the remaining rows wait for the next day and continue automatically; the delivery shows the progress ("1,200 of 3,000 sent; continues tomorrow"). This is not a parking state: the campaign is progressing as fast as the operator allows.
6. Per-recipient results live on `direct_sends` (`queued`, `sent`, `failed`, `suppressed`, `bounced`). The delivery becomes `Published` when every row is terminal, with counts on the delivery; a campaign where some recipients failed is still `Published`, and the failures are visible per recipient. Sending is at-least-once per recipient, like `send_email`: a crash between the transport's accept and the row update can send one message twice.
7. **Bounces and complaints.** SMTP permanent rejections (5xx) at send time mark the row `bounced` and add the address to suppressions; temporary ones (4xx) retry within the batch budget. HTTP transports (C6) also receive delivery, bounce, and complaint events through their signed webhooks.
8. **Unsubscribe.** The token is self-contained: an HMAC-signed (`email.signing_key`) payload of the owner ID, the address hash, the language, and the send ID. It needs no database row, so it keeps working after `direct_sends` are purged or the post is deleted, and it never expires. `POST /public/u/{token}` unsubscribes in one click; `GET` shows a confirmation page in the token's language. Either adds the address hash to the owner's suppressions and marks a matching contact `unsubscribed`. The public routes live in `postit-api` and call `postit-contacts`.
9. **Tracking.** Links are rewritten to `/public/t/c/{token}`, where the signed token carries the send ID and the destination URL itself, so the redirect can only go to a URL the campaign contained (no open redirect) and still works after purges; a click is recorded only while its send row exists. The open pixel exists only when the campaign enabled it.
10. **Images.** Email images use signed URLs with `email.image_url_ttl` (default 365 days). An asset referenced by a direct delivery's snapshot cannot be deleted (`media_in_use`) until that TTL has passed since the send, so images keep loading when recipients open mail late.

`POST /accounts/{id}/test-email` sends the current draft to the acting user's own address without touching any contact or the cap. `GET /accounts/{id}/dns-check` looks up the sending domain's SPF, DKIM, and DMARC records and returns plain-language guidance.

### Recurring posts

1. `PUT /posts/{id}/recurrence` stores the rule (an RFC 5545 RRULE subset: `FREQ` daily, weekly with `BYDAY`, or monthly with `BYMONTHDAY`; `INTERVAL`; `UNTIL` or `COUNT`), the time zone (default the acting user's preference), the targets, and the rewrite flag. It needs `confirm` and `If-Match`, like a live publish, and records `recurrence_confirmed` with the post version it confirmed.
2. The `recurrence_tick` cron (every minute) finds recurrences whose next occurrence is within `recurrence.lead` (default 10 minutes), creates a live publish job for it scheduled at the occurrence time, and advances `next_occurrence_at`. Occurrences are computed in the recurrence's time zone and stored in UTC, so "every Tuesday 10:00" stays at 10:00 local time across daylight-saving changes; a time that falls into a DST gap moves to the next valid minute, and an overlap uses the first instance.
3. **Rewrite each time.** With the flag on, the tick asks the drafter for a fresh variant per target from the post's text, the brand profile, and the writing style, and the occurrence publishes the rewrite. Without an AI provider, or when the rewrite fails validation after one repair attempt, the occurrence is skipped and the owner is notified; postit never silently falls back to the duplicate text, because platforms such as X reject exact duplicates.
4. **Editing pauses.** Any change that bumps the post's version pauses its recurrence; resuming needs `confirm`, so a confirmation always covers the content that will publish. The post is editable between occurrences, because an occurrence job exists only from `recurrence.lead` before its time until it finishes.
5. **One job at a time.** An occurrence is skipped, with a notification, when the post still has a non-terminal live job (for example, a parked previous occurrence). Skipped occurrences are recorded on the recurrence.
6. Pausing, deleting the recurrence, the kill switch, and per-platform switches stop future occurrences. Disconnecting an account removes it from the recurrence's targets; a recurrence left with no targets pauses.

### Inbox and replies

1. For each active account whose agent implements `InboxReader`, the `inbox_poll` cron (every minute, selecting due accounts) fetches new comments since the account's stored cursor. Accounts with a post published in the last 7 days are polled every `inbox.active_interval` (default 5 minutes); others every `inbox.idle_interval` (default 1 hour). Polls count against the agent's quota buckets. Webhooks, where a platform offers them, are a later optimization behind the same table.
2. Each comment is stored once in `inbox_items` (unique on account and remote comment ID) with its remote post, parent, author handle and display name, text, and time, linked to the delivery when the remote post was published by postit. Author avatars are not downloaded.
3. New items produce one coalesced notification per account per poll ("3 new comments on Bakery (Instagram)") as in-app, push, and, when the user enabled it, a daily email digest.
4. Opening an item shows the thread. "Draft reply" calls `POST /ai/generate` with `mode: reply` and the item; the drafter sees the comment, the original post, the brand profile, and the account's writing style, in the comment's language unless the user picks another.
5. `POST /inbox/{id}/reply` creates a comment post (`kind: comment`, `reply_to` the item) and its publish job in one transaction, which requires `confirm`. The item becomes `replied` when the delivery is `Published`.
6. **Comment on a post.** The composer's "Comment" mode creates a comment post from a pasted post URL or a post the user published through postit. The agent's `Commenter` resolves the URL to a remote post and refuses targets the platform does not allow (for example, Facebook Pages and Instagram can comment only on their own content), as a validation violation.

Inbox items are third-party personal data: they are deleted when their account is disconnected and after `retention.inbox_items` (default 180 days).

### Analytics collection

- **Post metrics.** When a delivery becomes `Published` on an agent with `MetricsReader`, `collect_post_metrics` jobs are scheduled at 1 hour, 24 hours, 7 days, and 30 days after it. Each stores a snapshot of what the platform returns (views, likes, comments, shares, saves, clicks; absent values stay null) in `post_metric_snapshots`.
- **Account metrics.** `collect_account_metrics` (daily cron) stores each account's follower count and, where available, reach in `account_metrics_daily`.
- **Email metrics** come from `direct_sends` and `email_events`: sent, delivered (HTTP transports), bounced, unsubscribed, clicked, and opened (only with open tracking).
- Metric calls count against the agent's quota buckets and stop at the first quota error; a missed snapshot is skipped, not retried later.
- **Charts** (web with `recharts`, already a dependency; mobile with a charting package chosen at E3 start): one post over time across its targets, one account's follower and engagement trend, posts compared within a campaign, and an overview of the last 30 days.

### Media

- `POST /media` creates the `media_assets` row in `uploading` first, then streams to `{storage_root}/{owner_id}/{yyyy}/{mm}/{uuid}`, computing SHA-256 while streaming. Size limits are enforced during the stream. It suits small files; the client uses upload sessions above `media.single_request_max` (default 20 MB).
- **Route limits.** Upload routes, the chunk route, and the public media route declare their own body limits and timeouts: chunks up to `media.chunk_max` (default 16 MB), no overall timeout on streamed downloads, and an idle timeout instead.
- **Resumable upload sessions** for large files and flaky mobile networks. `POST /media/uploads` declares the filename and total size, checks them against the per-kind limit and the owner's storage quota up front (counting the declared bytes of the owner's other open sessions), and creates a `media_assets` row in `uploading`. `PUT /media/uploads/{id}` appends one chunk with `Content-Range`; a range that does not start at the stored offset returns 409 `upload_offset_mismatch`, and `HEAD` returns the current offset so the client can resume after a dropped connection or an app restart. `complete` streams the file once to compute SHA-256, sniffs, probes, and marks the asset `ready`. Sessions expire after `media.upload_session_ttl` (default 24 hours).
- **Accepted types.** The MIME type is sniffed from content and must be on an allowlist: JPEG, PNG, GIF, WebP, MP4, and QuickTime. Anything else, including SVG, HTML, and HEIC, returns 415 `unsupported_media_type`. The mobile pickers request JPEG.
- `MediaProbe` reads dimensions and duration (pure-Rust container parsing; the `ffprobe` implementation behind a feature, enabled in the published image, which installs Debian's `ffmpeg`).
- **Thumbnails.** Image thumbnails come from the `image` crate under a pixel-count limit; video thumbnails need the `ffprobe` feature. `GET /media/{id}/thumbnail` serves them.
- **Viewing in the client.** `GET /media/{id}/view-url` returns signed URLs for the content and thumbnail (TTL `media.view_url_ttl`, default 10 minutes), because web image and video elements cannot send a bearer header. The mobile app may use the bearer routes directly.
- **Storage quota.** `user_limits.storage_quota_bytes` (default from `media.user_quota_bytes`, 20 GiB; 0 for unlimited) caps each owner's stored bytes, derived assets included; exceeding it returns 413 `storage_quota_exceeded`.
- `MediaHost::public_url(asset, ttl)` signs `id|exp` with HMAC-SHA256 using `media.signing_key`. The default TTL is 1 hour, and a fresh URL is issued for each attempt. The public route verifies in constant time.
- **Public reachability.** Signed URLs are built on `media.public_base_url` (default `server.public_url`). Agents that pull media (Instagram, Slack image blocks) need that host reachable from the internet. `GET /admin/doctor` warns when it resolves to a private address.
- `MediaSource::PublicUrl` is produced only by `MediaHost`. Users cannot create media from a URL, so postit never fetches user-supplied media URLs.
- Media responses send the stored MIME type with `X-Content-Type-Options: nosniff` and `Content-Security-Policy: sandbox`. The storage root is the only place media is read from; paths are generated, canonicalized, and checked against the root.
- **Fitting** (E4): see [Phase E4](#phase-e4--media-fitting). Derived assets (fitted, remuxed, cover frames) are `media_assets` rows with `derived_from` and `fit_spec`, and are deleted with their source unless a non-terminal job's snapshot references them.
- Assets in the media library are kept until the owner deletes them. `DELETE /media/{id}` returns 409 `media_in_use` while a post or the snapshot of a non-terminal job references the asset.
- `media_gc` (daily cron) deletes `failed` uploads, expired upload sessions with their partial files, and files under the storage root with no row that are older than `media.upload_session_ttl`.

### Notifications and push

- `postit-notify` records every notification in-app, emails critical kinds (per-user opt-out, as before), and pushes the kinds the user enabled for push (defaults: new comments, failed or parked deliveries, a skipped recurrence, `needs_reconnect`).
- **Android push uses UnifiedPush.** The app registers with the user's distributor app (such as ntfy) and sends the endpoint and keys to `POST /me/push-endpoints`. The server sends RFC 8291 encrypted Web Push with VAPID (RFC 8292) through `postit-http`. Endpoints are device-supplied URLs, so sending goes through the outbound address policy (`push.allow_private_endpoints` for self-hosted distributors on a LAN). Endpoint URLs and keys are sealed. A `404` or `410` from an endpoint deletes it.
- **Payload.** The notification ID plus a short title and body rendered server-side in the recipient's locale ("3 new comments on Bakery (Instagram)"). Never comment text, post text, or tokens. Tapping it opens the item; for a comment, the app opens the thread with "Draft reply" ready.
- **Polling fallback.** Without a distributor, the app schedules a periodic WorkManager task (Android's 15-minute minimum) that calls `GET /notifications/unread-count` and shows a local notification when it rises. The app explains, once, that installing ntfy makes alerts instant.
- **iOS** gets the polling fallback (background fetch) only; APNs is out of scope while there is no App Store distribution.
- No FCM: it would keep the app out of F-Droid. A Google Play build would add an FCM flavor later.

### Localization

- **Languages:** English (US, the default) and Arabic, with right-to-left layout. French and German are welcome when cheap, after R1; nothing in the design is specific to two languages.
- **The server sends codes, not sentences.** Every API error and validation violation has a stable `code` and parameters; problem+json `detail` stays English for developers. Clients translate from the code.
- **Server-rendered text** (notification emails, push titles and bodies, unsubscribe pages, legal page chrome) uses the recipient's `user_preferences.locale`, or for a contact the campaign's language. Message catalogs live in a new leaf crate, `postit-i18n` (no internal dependencies; the catalog format is chosen at D0 start, with Project Fluent as the default candidate), so `postit-mail`, `postit-notify`, and `postit-api`'s public pages all use them. Each crate keeps its own templates.
- **Locale formatting.** Dates use the Gregorian calendar; digits, number, and date formats follow the locale. Times show in the user's time zone.
- **Content language** is separate from UI language: the drafter writes in the language chosen per post or account, and post text in any script displays with the correct direction (`dir="auto"` on the web, `TextDirection` detection in Flutter).

### Phase A2 — Vault, platforms table, and configuration

Needs A1 and P4.

- **`postit-vault`:**
    - Envelope encryption with XChaCha20-Poly1305. Key-encryption keys come from `vault.keys` (a list of versioned keys, `_FILE` secrets, at least 32 bytes each); the newest version seals, every listed version opens.
    - A `Sealed<T>` type for columns, with the key version and nonce stored alongside the ciphertext and the table, column, and row ID bound as associated data, so ciphertext cannot be moved between rows or swapped between columns of one row.
    - `development.toml` ships a fixed vault key, clearly marked insecure and dev-only (like `audit.pseudonym_key`), so sealed values survive restarts.
    - A re-seal routine in `postit-data` re-seals every sealed column under the newest key, in batches, resumable after a crash. `postit-server` registers the `vault_rotate` job that runs it, and D3 adds `POST /admin/vault/rotate`.
- **`platforms` table** and the startup upsert from the registry. A row whose agent is compiled out stays, and the API reports the platform as unavailable in this build.
- **`[platforms.<id>]` configuration.** Each table is opaque to core and deserialized by the owning agent (client ID, client secret as a `_FILE` secret, API version, quota overrides). Unknown platform tables and tables for agents not compiled in are reported at startup. OAuth redirect URIs are derived from `server.public_url` and shown to admins. Credential agents (Telegram, Slack, Discord, Bluesky, Mastodon, email) need no deployment config; they are enabled by default.

Config sections:

- `[publishing]`: `live`, retry budget, `lease`, `sweep_grace`, `park_grace`, `processing_timeout`.
- `[media]`: as before, plus `fit_concurrency`, `fit_max_duration`, and `ffmpeg_path`.
- `[oauth]`: `return_to_allowlist`.
- `[ai]`: `request_timeout`, `allow_private_endpoints`.
- `[email]`: `signing_key` (`_FILE` secret; unsubscribe and tracking tokens and suppression hashes), `batch_size`, `image_url_ttl` (default 365 days), `tracking_base_url` (default `server.public_url`), `allow_private_hosts`.
- `[push]`: `vapid_private_key` (`_FILE` secret), `vapid_subject`, `allow_private_endpoints`.
- `[limits]`: defaults for new users' `user_limits` (`email_daily_cap`, `contacts_cap`, `storage_quota_bytes`).
- `[recurrence]`: `lead`. `[inbox]`: `active_interval`, `idle_interval`. `[retention]`: the new purges.
- `[legal]`: paths to the operator's privacy, terms, and data-deletion Markdown files.
- `[vault]`: `keys`.

QA and production refuse to start without `vault.keys`, `media.signing_key`, `email.signing_key`, and, when push is enabled, `push.vapid_private_key`.

**Exit criteria:** sealed values round trip, rotation re-seals every row, a row's ciphertext cannot be opened under another row's ID, secrets never appear in `Debug`, errors, or logs, and config validation reports actionable errors.

## Group B — Shared infrastructure

### Phase B1 — HTTP resilience and outbound address policy

Needs A1 and P2. Extends the foundation `postit-http`:

- Retry classification: transient errors retry; rate-limited responses honor `Retry-After` and agent-supplied reset headers; non-idempotent mutations are never retried once the body may have been received and surface as an outcome-unknown error.
- Exponential backoff with full jitter (seeded in tests) and a retry budget.
- `governor` rate limiters keyed by agent-defined buckets (per app, per account, per endpoint). Limits are per process; cross-process limits use the quota tables.
- Streaming request bodies from `MediaStore` streams.
- Redaction of configured sensitive URL patterns, including signed media URLs, webhook URLs, and push endpoints.
- Deterministic time and jitter in test helpers.

The **outbound address policy** covers every user-supplied host: AI endpoints, Mastodon instances, Bluesky PDS hosts, push endpoints, and SMTP hosts.

- HTTP: a client variant whose resolver drops private, loopback, link-local, and unique-local addresses unless the matching `allow_private_endpoints` flag is set, checked on the resolved address at connect time (no DNS rebinding), with redirects not followed.
- SMTP: `postit-http` exposes the same resolve-and-check as a function, and the email agent connects `lettre` only to an address that passed it. A self-hosted deployment that sends through a LAN relay sets `email.allow_private_hosts`.

**Exit criteria:** retry, timeout, rate-limit, redaction, error mapping, and the address policy for both HTTP and SMTP are verified without real network calls. No crate other than `postit-http` constructs a `reqwest::Client`.

### Phase D2 — Drafter (LLM layer)

Needs B1 and B2. Create `postit-drafter` (renamed from `postit-content`, behind the `ai` feature):

- **Bring your own key.** AI providers are per user only; the deployment configures none. Every drafter action without a provider returns `ai_provider_required`, and the clients show a "connect an AI provider" prompt there instead of hiding the action.
- **Provider-neutral trait.** `LlmProvider` with `chat(request)`: messages (text and image parts), system prompt, temperature, max tokens, JSON-schema structured output where supported, and token usage. No streaming (the client polls; SSE is a non-goal).
- **Protocols:** `openai-compatible` (Chat Completions with configurable base URL, headers, and query parameters; tolerant of provider extensions and missing `usage`) and native `anthropic` (the Messages API; Anthropic's OpenAI-compatible endpoint is feature-limited).
- **Presets** that need only a key, each with an in-app "get your key" guide (translated) and a Test button: Google Gemini (has a free tier), OpenAI, Anthropic, OpenRouter, Abacus AI RouteLLM, MiniMax, Moonshot (Kimi). Local presets, available only when `ai.allow_private_endpoints` is set: Ollama, llama.cpp server, vLLM, LM Studio. Plus custom OpenAI-compatible. Preset base URLs and model listing are verified at phase start. Consumer chat subscriptions (ChatGPT Plus, Claude Pro, Gemini Advanced) cannot be used by third-party apps; the guide says so plainly.
- **Modes:** `post` (one variant per target, plus an email subject and preheader for email targets), `reply` (from an inbox item), and `rewrite` (for recurrences). Each prompt includes the brand profile, the target's writing style, the target's formats and limits, the language, and the user's prompt.
- **Media as context.** In `post` mode, attached images are sent to the model when the chosen model accepts images; for a video, a few frames plus its duration are sent, obtained through a core `FrameExtractor` trait that `postit-media` implements and `postit-server` injects (the drafter does not depend on `postit-media`). When the model takes no images, the drafter proceeds on text and says so. The output is always text.
- Structured output, core validation per target, and one repair attempt; the result is draft content with `disclose_ai_generated` set and an `ai_generations` record. No post is created.
- **Opencode-shaped providers.** Each `ai_providers` row stores the shape of an opencode `provider` entry, so users can paste one field for field; the API key is stored separately and sealed. `npm` values map to protocols (`@ai-sdk/openai-compatible` and `@ai-sdk/openai` to `openai-compatible`, `@ai-sdk/anthropic` to `anthropic`, `@ai-sdk/google` to `openai-compatible` with the Gemini base URL); an explicit `protocol` overrides. postit never reads opencode's files.
- **Delegates** with `edit` generate with the owner's providers and see names and models, never keys or config. A limited delegate generates only for targets in their limit.
- **Outbound URL policy.** Every provider request goes through the B1 address-policy client, unless the operator sets `ai.allow_private_endpoints`.
- **Timeouts.** Generation calls use `ai.request_timeout` (default 120 seconds); the generate route is exempt from the global request timeout up to that value.
- **Spend visibility.** `GET /ai/generations` shows the owner every generation with its actor, mode, model, and token usage. No key appears in logs, drafts, or generation records; prompts are stored only when the owner enables `store_ai_prompts`.

Tests: wiremock contract tests for both protocols and each preset's response quirks, image and frame context, a text-only model with images attached, `ai_provider_required`, every mode's prompt assembly (snapshot), the address policy, and deterministic validation and repair.

**Exit criteria:** the drafter produces validated, disclosure-flagged variants for any configured provider in every mode, without touching publishing credentials.

### Phase G1 — First deployment

Needs P9 and G0. A public deployment the household can use day to day, and that TikTok's audit, OAuth callbacks, and unsubscribe links can reach.

- **Target:** any Linux VPS with Docker and about 4 GB of RAM or more (Postgres, the IdP, API, worker, and the reverse proxy together). Hostinger KVM and AWS Lightsail are the candidates; PaaS hosts that cannot run an always-on worker with a persistent disk (Vercel, Heroku) are out. The image stays host-neutral.
- **Reverse proxy:** Caddy with automatic HTTPS in front of the production compose stack (plan 01's "no bundled TLS proxy" non-goal is lifted for this one deployment recipe; the image still contains none).
- **IdP:** phase-start decision between running Zitadel in the production compose and a hosted Zitadel tier, by RAM and cost.
- **Terraform** in `deploy/terraform/<provider>/` for the chosen provider, written once it is chosen (Hostinger's `hostinger/hostinger` provider is the default assumption; Lightsail through `hashicorp/aws` otherwise): the server, a static IP, DNS records, SSH keys, and the firewall; cloud-init installs Docker. Terraform state contains secrets and lives outside git (a remote backend or the vault, decided in the phase).
- **Migration freeze:** `0001_init.sql` is frozen when this deployment first holds data; later phases add new migration files (see [Delivery model](#delivery-model)).
- **Operations:** `stack backup` on a schedule with an off-host copy, the restore drill (plan 01 definition of done) run once against this deployment, and upgrade steps.
- A domain name, DNS, and the mail-sending guidance for the operator's own notifications.

**Exit criteria:** the deployment serves the web app and API over HTTPS on a real domain, survives a reboot, has a tested restore, and can be rebuilt from Terraform and the vault.

### Phase G5 — Security and reliability hardening

Required before the hosted deployment accepts users outside the household.

- Threat model of the web-facing surface:
    - OIDC: token validation, `kid` refetch limits, principal cache staleness, bootstrap.
    - Delegation: act-as resolution, level and account-limit enforcement, no re-delegation, lookup enumeration.
    - Connection: OAuth state binding, single use, PKCE, the `return_to` allowlist, the confirm step against connect CSRF, credential verification, CSV import parsing limits, and the platform event routes' signature checks.
    - Public email routes: token forgery, enumeration, the click redirect limited to snapshot URLs, and webhook signature checks.
    - CORS and rate limits, re-verified with the new routes.
    - Signed media URLs: signature scope, expiry, no enumeration, range handling.
    - Uploads and fitting: limits, quotas, sessions, content sniffing, image decoding limits, ffmpeg input handling (resource limits, malformed files), serving headers, storage-root confinement.
    - Outbound requests: the address policy for every user-supplied host (AI, Mastodon, Bluesky PDS, SMTP, push), DNS rebinding, redirects.
    - Third-party personal data in inbox items and contacts: retention, deletion, export.
    - Abuse controls on the hosted deployment: sign-up approval, caps, rate limits.
    - Job console: no user content in summaries or errors for any job type.
    - The vault key lifecycle, including loss of a key version.
- Access fuzzing across every endpoint with the four callers.
- Cancellation and restart tests during uploads, container workflows, direct batches, fitting, and scheduled jobs.
- CI: `cargo deny`, fmt, clippy, tests, conformance suites, the SQLx offline cache check, catalog completeness, and the contract drift check. CI never publishes live or sends real email.
- The backup and restore drill from plan 01's definition of done, performed against QA: restore Postgres, the media volume, and the separately stored secrets into a fresh stack, then confirm sign-in, sealed credentials opening, media serving, and scheduled deliveries and recurrences resuming.

**Exit criteria:** reproducible builds, no secret leakage in any tested output, proven owner isolation and delegation limits, durable queue recovery, platform-isolated failures, every public route and user-supplied host covered by tests, a completed and documented restore drill, and documented release checks.

## Platform constraints and risks

Verify each at the start of the relevant phase:

- **Email deliverability.** Gmail and Yahoo require SPF, DKIM, and DMARC alignment and one-click unsubscribe for bulk senders. A user's mail can go to spam despite correct code; the DNS check and docs are the mitigation. Sending is at-least-once per recipient.
- **Spam from the hosted deployment.** Even with user-supplied sending methods, abuse reflects on the operator. Mitigations: sign-up approval, consent attestation, the contact and daily caps, and suppression.
- **Telegram:** Bot API upload limits; a bot cannot read a channel's comments unless it is in the linked discussion group; no message lookup, so ambiguous sends need the user to resolve them.
- **Slack and Discord webhooks:** no lookup and no inbox; a leaked webhook URL lets anyone post, so it is sealed and never displayed again after entry.
- **Bluesky and Mastodon:** app passwords and personal tokens are strong credentials; the guides tell users to create a dedicated one they can revoke. Instance rules vary.
- **TikTok:** unaudited apps post private only and to a few test users; the audit checks the posting UX; comment APIs may not be available to this app type.
- **X:** paid access tiers, app-level caps across every user, rotating refresh tokens.
- **YouTube:** unverified projects upload private; the small daily quota is shared by every user; testing-mode refresh tokens expire after 7 days.
- **Meta (Facebook, Instagram, Threads):** App Review and business verification; professional accounts only for Instagram; rolling 24-hour limits; fixed-date token expiry.
- **LinkedIn:** organization posting requires partner approval.
- **ffmpeg on a small VPS:** fitting is CPU-bound; the concurrency limit and duration cap keep the server responsive. Debian's ffmpeg is invoked as a separate process.
- **UnifiedPush adoption:** non-technical users must install a distributor for instant alerts; the polling fallback keeps them informed within about 15 minutes.
- **Third-party personal data** (contacts, comment authors): retention defaults, deletion on disconnect and user deletion, and export for contacts.
- **Live publishing is on in development by decision.** A development worker connected to a real account posts for real. Mitigations: per-publish confirmation, the kill switch, `platforms.enabled`, the dry-run toggle, and the `test_account` label shown in the publish dialog.
- **Delegated live publishing.** A `publish` delegate can post to the owner's real accounts. Mitigations: the same confirmation, account limits, `created_by` shown in history, and owner notifications.
- **Dependency names:** every library chosen at a phase start is checked against the repository's dependency-name rule.
- **Redirect URIs and public media in development:** the dev tunnel fallback (B7).
