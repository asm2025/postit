# Infrastructure and tooling

> Plan 04 (2026-09-25). Phases V1–V5. Assumes [01. Vision and architecture](01.%20vision%20and%20architecture.md) and [02. Foundation](02.%20foundation.md) (environments, Docker dev, `postit-data` migrations in P4). Adopts the vault, Docker layout, and operator-script conventions from the VigilixMambo reference repo, adapted to postit's stack (Rust/sqlx, no AWS/ECS) and its no-passwords OIDC-only model.

## Objective

When this plan is done:

- Local secrets and per-environment config overrides are packed into a single `!ref/vault/vault.7z` archive, extracted in place, matching the VigilixMambo pattern already documented informally.
- The two root-level compose files move under `docker/`, renamed to the conventional `docker-compose.yaml` / `docker-compose.dev.yaml`, alongside a `docker/.env.example`.
- `drop-db.ps1` / `drop-db.sh` give a scripted, confirmed way to drop an environment's Postgres database.
- `migrate.ps1` / `migrate.sh` wrap `sqlx-cli` (add/run/revert/info) plus `cargo sqlx prepare`, once `postit-data` has embedded migrations (plan 02 P4).
- `CLAUDE.md` and `README.md` describe all of the above, so a fresh clone follows the same setup story VigilixMambo does.

None of this changes application behavior. It is tooling and repository layout only.

## Why not a straight copy of VigilixMambo's scripts

VigilixMambo's `drop-db`/`migrate` scripts carry two things postit does not have and should not invent here:

- **ECS scaling and an SSM bastion tunnel.** postit has no Terraform, no AWS account, and no plan to add one — plan 02's [QA and production hosting](02.%20foundation.md#qa-and-production-hosting) is "the same image, promoted, run by the operator's own Compose/Kubernetes/whatever," reached directly. So `drop-db` here has nothing to scale down and nothing to tunnel through; it connects to whatever host the operator gives it.
- **EF Core.** postit's migrations are `sqlx` migrations embedded in `postit-data` (plan 02 P4, [Data layer](02.%20foundation.md#data-layer)) and applied automatically by the server at every boot under a Postgres advisory lock (plan 02, [Process roles](02.%20foundation.md#process-roles)). `migrate.ps1`/`.sh` are a thin `sqlx-cli` wrapper for authoring migrations and refreshing the offline query cache, not a `dotnet ef`-style scaffolding tool.

What does carry over unchanged: the vault-as-a-packed-archive convention, retyping the database name before an irreversible drop, `docker-compose.yaml` living under `docker/` instead of `compose.yaml` at the root, and treating "the process that auto-migrates on boot must not be running while you drop" as a hard rule — just enforced with `docker compose stop`/`start` instead of ECS desired-count juggling.

## V1: Vault packaging

- Create `!ref/vault/<environment>/` folders (`development`, `qa`, `production`) holding the files an operator or a fresh clone needs and must not commit in the clear:
  - `postit-database-url.txt`, `postit-pseudonym-key.txt`, `postit-smtp-password.txt` — the plaintext values behind the `POSTIT__…__KEY_FILE` secrets already named in `deploy/env/qa.env.example` and `deploy/env/production.env.example`.
  - `local.toml` for `development` — a ready-to-copy `server/config/local.toml` (the file `cargo xtask zitadel-bootstrap` normally writes), for anyone who wants working config without running the bootstrap step.
- `!ref/vault/` itself stays git-ignored except for a `.gitkeep`; the packed archive is what gets committed.
- Pack it exactly like VigilixMambo: `7z a !ref/vault.7z !ref/vault/*` (or `-p<password>` for an encrypted archive) run from the repo root, producing `!ref/vault.7z` next to the `plans/` folder. Document extraction the same way Mambo's README does:

  ```bash
  cd "!ref"
  7z x vault.7z
  ```

  and the Windows equivalent (extract into `!ref/`, giving `!ref/vault/...`).
- `CLAUDE.md` gets a short "Vault" note under Commands pointing at this; `README.md` gets the full "Extract configuration files (vault)" section, adapted from Mambo's.
- Re-packing is manual (`7z a` after editing files in place) — no script owns it, matching Mambo, since it changes rarely and a script would just wrap one command.

**Exit:** `!ref/vault.7z` exists and extracts to the layout above; README documents extraction; nothing under `!ref/vault/` is tracked directly.

## V2: Docker directory restructure

- Move `compose.yaml` → `docker/docker-compose.yaml` and `compose.dev.yaml` → `docker/docker-compose.dev.yaml`. Add `docker/docker-compose.qa.yaml` and `docker/docker-compose.prod.yaml` (currently referenced in plan 02 as root-level `compose.qa.yaml`/`compose.prod.yaml`, not yet created) in the same directory when they're built.
- Add `docker/.env.example` (currently there is none) documenting `DB_PASSWORD` and any other Compose-time variable, and a git-ignored `docker/.env` for the operator's local overrides — mirrors Mambo's `docker/.env` / `docker/.env.example` pair.
- Existing `docker/postgres/`, `docker/shared/`, `docker/zitadel/` subfolders and their contents are unaffected — relative paths inside the compose files (`./postgres/init`, `./shared/nginx/...`, `./zitadel/steps.yaml`) already resolve correctly once the compose files sit in `docker/`, since those paths are currently written as `./docker/...` from the repo root. **They must be edited to drop the `docker/` prefix** when the files move, since the new working directory for `docker compose -f docker/docker-compose.yaml ...` (or `cd docker && docker compose ...`) is `docker/` itself.
- Every command example changes from:

  ```sh
  docker compose -f compose.yaml -f compose.dev.yaml --profile app up
  ```

  to (run from `docker/`, matching Mambo's "run all compose commands from the `docker/` directory"):

  ```sh
  cd docker
  docker compose -f docker-compose.yaml -f docker-compose.dev.yaml --profile app up
  ```

- Update every reference to `compose.yaml` / `compose.dev.yaml` in `CLAUDE.md`, `README.md`, and plan 02 ([Docker dev](02.%20foundation.md#development-hosting), [QA and production hosting](02.%20foundation.md#qa-and-production-hosting), the CI `docker` job) to the new path and the `cd docker` convention. Plan 02 is the authoritative spec for the environments and CI, so this phase edits it in place rather than leaving two docs disagreeing — same rule as the [Project state](../../CLAUDE.md) note that the plans are one consistent set, not layered revisions.
- `cert.ps1`/`cert.sh` already write into `docker/shared/nginx/certs/`; no change needed there.

**Exit:** `docker/docker-compose.yaml` and `docker/docker-compose.dev.yaml` exist, no root-level `compose*.yaml` remains, `docker compose config` resolves cleanly from `docker/`, and every doc reference matches.

## V3: `drop-db.ps1` / `drop-db.sh`

Scoped to Postgres only — no ECS, no bastion. Behavior:

- `drop-db.ps1 <environment> [-Force] [-NoStop]` / `drop-db.sh <environment> [--force] [--no-stop]`, where `<environment>` selects `!ref/vault/<environment>/postit-database-url.txt` (or, for `development`, falls back to `server/config/local.toml` / `server/config/development.toml` defaults against `docker/docker-compose.yaml`'s published Postgres port).
- Parses the `postgres://` URL into host/port/db/user/password (equivalent to VigilixMambo's Npgsql key=value parsing, just a different connection-string shape).
- **Before dropping:** unless `--no-stop`, run `docker compose -f docker/docker-compose.yaml [-f docker/docker-compose.<environment>.yaml] --profile app stop` (or, for a non-Compose qa/production target, print the equivalent instruction and require `--no-stop` to proceed) — this is postit's equivalent of Mambo's ECS scale-to-zero: the server runs migrations on every boot, so a live container recreates the schema mid-drop otherwise. After the drop, `docker compose ... start` restores it, exactly mirroring the "scale back up and wait for stable" shape but against Compose instead of ECS (`docker compose ps` polled until `running`/healthy replaces `describe-services`).
- Connects to the `postgres` maintenance database via `psql` (same two-statement `pg_terminate_backend` + `DROP DATABASE IF EXISTS` as Mambo's script, same reasoning: `DROP DATABASE` cannot run inside the implicit transaction a single `-c` with two statements would open).
- Confirmation: retype the database name; `production` always prompts and refuses `--force`, matching Mambo exactly.
- No region flag, no AWS credential check, no SSM tunnel cleanup — none of that machinery has an equivalent here, so it's simply absent rather than stubbed.

**Exit:** running `./drop-db.sh development --force` against the dev stack drops and the server rebuilds a clean schema on the next `docker compose up`; `production` cannot be forced.

## V4: `migrate.ps1` / `migrate.sh`

Depends on plan 02 P4 (`postit-data` embeds `sqlx` migrations under `server/crates/data/migrations`). Until then this phase is blocked — note it as such rather than building against a directory that doesn't exist yet.

- `migrate.ps1 {add|run|revert|info|prepare} [Name]` / `migrate.sh {add|run|revert|info|prepare} [Name]`, a thin wrapper around `sqlx-cli` that always passes the right `--source` and `DATABASE_URL`, so it works from any directory the way Mambo's script always passes the right `--project`/`--startup-project`:
  - `add <Name>` → `sqlx migrate add -r <Name> --source server/crates/data/migrations` (reversible migrations: `.up.sql` + `.down.sql`, matching plan 01's "expand, then contract" compatibility rule).
  - `run` → `sqlx migrate run --source server/crates/data/migrations`.
  - `revert` → `sqlx migrate revert --source server/crates/data/migrations`.
  - `info` → `sqlx migrate info --source server/crates/data/migrations`.
  - `prepare` → `cargo sqlx prepare --workspace` (refreshes `.sqlx/`, the offline query cache CI checks with `cargo sqlx prepare --check --workspace`).
- `DATABASE_URL` resolution: `POSTIT_ENV` (default `development`) picks the vault file from V1, unless `DATABASE_URL` is already set in the environment (script never overrides an explicit one).
- No `clear` operation: `sqlx` migration files are content-addressed by checksum in `sqlx.migrations`, so silently deleting them the way Mambo's EF `clear` does would desync already-applied environments. If a clean slate is genuinely needed, that's a manual `drop-db` + delete-and-`add` again, done deliberately, not a one-word script command.

**Exit:** `migrate.ps1 add <name>` scaffolds a reversible migration under `server/crates/data/migrations`; `migrate.ps1 prepare` regenerates `.sqlx/` and `cargo sqlx prepare --check --workspace` passes in CI.
