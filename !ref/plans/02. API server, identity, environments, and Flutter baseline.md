# API Server, Identity, Environments, and Flutter Baseline

> Plan 02 (2026-09-25). Builds on [01. social publishing platform roadmap](01.%20social%20publishing%20platform%20roadmap.md) (revision 2) and changes its product shape: postly is no longer a CLI. It becomes a Rust API server with background jobs plus a Flutter client. This plan sets up the baseline that later plans build on. Plan 03 revises the roadmap to match.

## Objective

When this plan is done, postly is a working vertical slice:

- A Dockerized Rust API server and background worker run against PostgreSQL in three environments: `development`, `qa`, and `production`.
- A Flutter app for web, desktop, and mobile signs in as the seeded admin. It forces a password change, supports forgot/reset password by email, and gives admins a dashboard shell with user management.
- A Hangfire-style job runner, apalis behind our own seam, sends email and runs a recurring cleanup job.

No social-platform, drafting, or publishing features are in this plan. Those come in plan 03 and later.

## Decisions

| Topic | Decision |
|---|---|
| Product shape | Two parts: a Rust REST API with background jobs, and a Flutter UI (web, desktop, mobile). **No end-user CLI.** |
| Tenancy | Self-hosted, small team. One deployment per owner. Several users share the connected social accounts. No tenant isolation. |
| User auth | **Local users only, permanently.** No OIDC or external IdP. Postly issues its own tokens. |
| Database | **PostgreSQL** (18) via SQLx, with compile-checked queries and a committed offline `.sqlx` cache. |
| Background jobs | **apalis** (`apalis`, `apalis-postgres`, `apalis-cron`, optionally `apalis-board`) with an exact version pin, wrapped by our own `JobQueue` seam in one crate. |
| Repo layout | Monorepo: `server/` (Cargo workspace), `app/` (Flutter), `api/openapi.json` (generated contract), `docker/`, `deploy/`. |
| Processes | One binary `postly`, one image. `POSTLY_ROLE=all|api|worker`. |
| Environments | `POSTLY_ENV=development|qa|production`, with layered config per environment and matching Flutter flavors. |
| Dev hosting | `https://postly.local` with a self-signed cert trusted in the OS root store and a hosts-file entry. Ports in 44300–44399. |
| Default admin | `admin` / `P@$$w0rd123!`, forced to change on first login. Production requires an explicit password and email at first boot. |

## Engineering standards

The roadmap's "Engineering standards" section still applies unchanged: DRY ownership, workspace dependencies and lints, `thiserror` in libraries with `anyhow` only in the binary, typed secrets (`secrecy`), newtype IDs with UUID v7, deterministic tests, `tracing`, and the dependency hygiene rules. The emix crate policy also stands (`emixdb` for pagination, `emixcrypto` for SHA-256).

This plan adds these rules:

- **Thin handlers.** axum handlers parse input, call a service, and map the result. Business rules live in service crates so jobs and tests reuse them without HTTP.
- **One owner per new concern.**
  - Config and environments: `postly-config`.
  - Postgres access: `postly-data`.
  - Users, passwords, tokens, and mail: `postly-identity`.
  - The job runner: `postly-jobs`. It is the only crate that depends on apalis.
  - HTTP surface and OpenAPI: `postly-api`.
- **The API contract is generated, never hand-written.** `utoipa` annotations produce `api/openapi.json`, and the Dart client is generated from that file. CI fails if either is stale.
- **No secret reaches a log, an error, an API response, or the OpenAPI examples.** This covers password hashes, tokens, token hashes, and SMTP or JWT keys. Tests assert it.

## Environments

### Environment selection

- `POSTLY_ENV` is `development`, `qa`, or `production`. Any other value fails startup.
- It defaults to `development` only when it is unset *and* the binary is a debug build. A release build without `POSTLY_ENV` refuses to start.

### Configuration layering

Configuration is loaded with `figment`, and later layers override earlier ones:

1. `config/default.toml`
2. `config/{env}.toml`
3. `config/local.toml` (development only, git-ignored)
4. `POSTLY__SECTION__KEY` environment variables (`__` separates nesting levels)
5. `POSTLY__…__KEY_FILE` variants, which read the value from a file. These support Docker and Kubernetes secrets.

Secrets deserialize into `SecretString`. At startup the server logs the effective config with secrets redacted. The binary also validates config and exits non-zero with actionable messages when anything is wrong.

### Per-environment behavior

| Setting | development | qa | production |
|---|---|---|---|
| Logs | pretty, `debug` | JSON, `info` | JSON, `info` |
| Swagger UI `/docs` | on | on | off (`/api/openapi.json` stays available) |
| CORS allowed origins | `https://postly.local:44310` | configured | configured |
| JWT signing key | dev default allowed (warned) | required secret (≥ 32 bytes) | required secret (≥ 32 bytes) |
| Seed admin password | `P@$$w0rd123!` unless overridden | `P@$$w0rd123!` unless overridden | `POSTLY_ADMIN_PASSWORD` **required** at first boot |
| Seed admin email | `admin@postly.local` unless overridden | `admin@postly.local` unless overridden | `POSTLY_ADMIN_EMAIL` **required** at first boot |
| Mail transport | Mailpit (SMTP on 44325) | SMTP (use a test inbox) | SMTP |
| TLS | server or nginx terminates with the dev cert | reverse proxy | reverse proxy |
| Live social publishing (future plans) | off | off | on only with an explicit flag |

### Development hosting

- **Domain:** `postly.local` resolves to `127.0.0.1` and `::1` through `C:\Windows\System32\drivers\etc\hosts` (or `/etc/hosts`). A `localhost` request redirects to `postly.local`.
- **Certificates:** `cert.ps1` and `cert.sh` take `gen`, `trust`, `setup` (the default), and `help`, following the VigilixMambo scripts. They create a self-signed certificate with SAN `DNS:postly.local, IP:127.0.0.1, IP:::1` in `.crt`, `.key`, and `.pfx` form under `docker/shared/nginx/certs/`, and install it into the Windows Trusted Root store (`certutil -addstore Root`, which needs an elevated shell) or the Linux/macOS equivalent. Key material is git-ignored.
- **Port map.** All dev ports sit in 44300–44399. 44301–44304 are reserved as a gap after the API.

| Port | Service |
|---|---|
| 44300 | API: `/api/v1/*`, `/docs`, `/api/openapi.json`, `/health`, `/ready` |
| 44305 | Worker: `/health`, `/ready`, and `/jobs` (apalis-board, admin-only) |
| 44310 | Flutter web |
| 44320 | Mailpit web inbox |
| 44325 | Mailpit SMTP |
| 44340 | Postgres (published for SQLx tooling and `cargo sqlx prepare`) |

- **Docker dev** (`docker compose -f compose.yaml -f compose.dev.yaml up`):
  - An nginx container terminates TLS on 44300, 44305, 44310, and 44320 (Mailpit UI) and proxies to plain-HTTP containers: `server` (role `all`) and `web` (the static Flutter build).
  - Postgres and Mailpit publish their ports as shown above.
  - Containers trust the dev cert through a mounted CA file.
- **Native dev** (`cargo run` and `flutter run`):
  - Only `postgres` and `mailpit` come from compose.
  - The server terminates TLS itself with rustls (`axum-server`) when `server.tls.cert_path` and `server.tls.key_path` are set. `development.toml` points them at the generated cert.
  - In role `all`, the API binds 44300 and the worker endpoints bind 44305.
  - Flutter web runs on 44310 with the same certificate. Confirm the Flutter web-dev-server TLS options at the start of P8.
- **Cookies and CORS.** `postly.local:44300` and `postly.local:44310` are the same site but different origins. CORS allows the web origin with credentials, and the `SameSite=Strict` refresh cookie still works. QA and production need the same shape, for example `api.example.com` and `app.example.com`.
- **Mobile dev.** Emulators and devices don't read the host's hosts file or trust store.
  - The Flutter `development` flavor includes a debug-only trust configuration for the dev certificate: Android `network_security_config` in the `development` source set only, and a documented profile install for the iOS simulator.
  - The README documents name resolution: `adb reverse` or the emulator hosts file for Android, the Mac hosts file for the iOS simulator, and a LAN IP mapped to `postly.local` for physical devices.

### QA and production hosting

- The same image is promoted through dev, QA, and production. Only configuration changes.
- `compose.qa.yaml` and `compose.prod.yaml` run separate `api` and `worker` services with restart policies and Docker `secrets:`. They publish no database port and include no nginx.
- TLS is terminated by the operator's reverse proxy on 443 using configured hostnames. The 443xx convention applies to development only. The README gives a Caddy example; it isn't bundled.
- `server.trusted_proxies` (CIDRs) controls which hops may set `X-Forwarded-For`, which rate limiting and audit use.

## Server design

### Process roles

- `POSTLY_ROLE=all` (the development default) runs the API and the worker in one process. `api` runs only the HTTP API and enqueues jobs. `worker` runs only the job runner and its small HTTP surface on the worker port.
- Migrations run at startup under SQLx's Postgres advisory lock, so concurrent starts are safe. apalis keeps its tables in its own schema.
- The only flags are `postly --version` and `postly healthcheck`. The second calls the local `/health` and serves the Docker `HEALTHCHECK`.
- Shutdown is graceful on SIGTERM and Ctrl-C: stop accepting work, drain in-flight requests and jobs, then close the pool.

### `postly-config`

- Holds the typed settings tree: `server` (bind addresses, TLS paths, trusted proxies, public URLs), `database`, `auth` (JWT key, TTLs, lockout, rate limits), `mail` (transport, from address, SMTP), `jobs` (concurrency, cron schedules), `seed` (admin username, email, password), `app` (`public_url` of the web app, used in email links), and `cors`.
- Owns the environment enum, the layering, the `_FILE` secret resolution, validation, and the redacted dump.

### `postly-data`

- Owns the `PgPool` factory with its timeouts and pool size, the embedded migrations, and the repositories.
- Schema, owned by postly (UUID v7 IDs generated in Rust, `timestamptz` everywhere):
  - `users`:
    - Identity: `id`, `username citext unique`, `email citext unique`, `first_name`, `last_name`, `role`.
    - Credentials and lockout: `password_hash`, `must_change_password`, `failed_attempts`, `locked_until`, `password_changed_at`.
    - Lifecycle: `disabled_at`, `created_at`, `updated_at`.
    - `role` is checked to be `admin` or `member`.
  - `refresh_tokens`:
    - Identity and lineage: `id`, `user_id`, `family_id`.
    - Secret: `token_hash bytea unique`.
    - Lifetime: `issued_at`, `expires_at`, `absolute_expires_at`, `used_at`, `revoked_at`.
    - Client context: `user_agent`, `ip`.
  - `user_tokens`: `id`, `user_id`, `purpose` (`password_reset` or `invite`), `token_hash bytea unique`, `expires_at`, `consumed_at`, `created_at`.
  - `audit_events`: `id`, `at`, `actor_user_id`, `subject_user_id`, `kind`, `ip`, `details jsonb`. It records login success and failure, lockout, password change and reset, invites, and user admin changes. It never stores secrets.
- Repository APIs return domain types. List endpoints use `emixdb::Pagination` and `ResultSet<T>`.
- Tests use `#[sqlx::test]` with a per-test database.

### `postly-identity`

Owns users, passwords, tokens, email, and seeding. It has no HTTP types.

- **Passwords:**
  - argon2id with OWASP-recommended parameters (configurable).
  - Policy for every password, including the seed: 12–128 characters, not equal to the username, and different from the user's current password.
- **Login:**
  - Accepts a username or an email.
  - Five consecutive failures lock the account for 15 minutes (configurable).
  - Every failure returns the same generic error, including unknown user, wrong password, locked, and disabled.
  - Unknown usernames run a dummy hash so timing does not reveal whether an account exists.
- **Access token:**
  - JWT, HS256, 15-minute TTL.
  - Claims: `sub`, `role`, `sid` (the refresh family), and `mcp` (must change password), plus `iat`, `exp`, `iss`, and `aud`.
  - Verified statelessly.
- **Refresh token:**
  - 256-bit random and opaque. Only its SHA-256 hash is stored (`emixcrypto`).
  - Rotated on every use.
  - **Presenting an already-used token revokes the whole family.**
  - 14-day sliding and 30-day absolute lifetime.
- **Revocation:** a password change or reset, an admin reset, disabling a user, or changing a role revokes all of the user's refresh tokens. Access tokens that are already issued expire within their 15-minute TTL. This trade-off is accepted and documented.
- **Password reset (forgot password):**
  - Request by email. The response is always the same and takes roughly the same time.
  - Rate-limited per IP and per email.
  - For an active user, the token is 256-bit, stored hashed, valid for 30 minutes, and single use. Issuing one invalidates earlier outstanding reset tokens.
  - A disabled or unknown user gets no email, but the response is unchanged.
  - Completing the reset:
    1. Applies the password policy and sets the new password.
    2. Clears lockout and `must_change_password`.
    3. Consumes the token and revokes all refresh tokens.
    4. Sends a "password changed" notice.
- **Invites:** when an admin creates a user, the user gets a "set your password" email with an `invite` token valid for 72 hours. An admin can instead set a temporary password, which forces a change at next login.
- **Admin rules:** the last active admin cannot be disabled or demoted.
- **Mail:**
  - The `Mailer` trait has an `SmtpMailer` (`lettre`, TLS or STARTTLS, credentials as `SecretString`) and a `MemoryMailer` for tests.
  - Messages are rendered from embedded `askama` templates in plain text and HTML: invite, password reset, and password changed.
  - Email links use `app.public_url`, for example `{app.public_url}/reset-password?token=…`. Mobile users open the web page. Deep links are deferred.
  - Identity never sends mail inline. It enqueues a `send_email` job.
- **Seeding:**
  - Runs only when `users` is empty.
  - Creates `admin` with role `admin` and `must_change_password = true`, using the seed email and password from config.
  - Development and QA default to `P@$$w0rd123!` and `admin@postly.local`.
  - In production, a missing `POSTLY_ADMIN_PASSWORD` or `POSTLY_ADMIN_EMAIL` fails startup with a clear message.

### `postly-jobs`

- **The seam:** a `JobQueue` trait (`enqueue`, `enqueue_at`) plus a typed job registration API. apalis types never leave this crate.
- **The worker runner** builds the apalis monitor from config: concurrency, retry policy with exponential backoff, and Postgres storage in its own schema with LISTEN/NOTIFY fetch.
- **Jobs in this plan:**
  - `send_email`: retried with backoff. It gives up after a configured budget and records an audit event.
  - `cleanup_expired_tokens`: recurring through `apalis-cron`, hourly by default. It deletes expired or consumed `refresh_tokens` and `user_tokens`.
- **Dashboard:** `apalis-board` is mounted at `/jobs` on the worker port and restricted to admins with the same JWT verification as the API. If the board isn't compatible with the pinned apalis release, drop it and log the gap for a later Flutter "Jobs" page.
- **Version risk:** apalis 1.0 is at a release candidate (`1.0.0-rc.10` on 2026-09-15; stable is 0.7.4). Pin an exact version (`=`) and check the latest release at the start of P6. Upgrades touch only this crate.

### `postly-api`

- An axum router under `/api/v1` with tower middleware:
  - Request ID propagated as `x-request-id`.
  - Tracing spans with redaction.
  - Timeout and body size limit.
  - CORS from config.
  - `tower_governor` rate limiting on `/auth/*`, keyed by client IP after trusted-proxy resolution.
- **Errors:** RFC 9457 `application/problem+json` with a stable `code` extension (`invalid_credentials`, `password_change_required`, `validation_failed`, and so on) and the request ID. Internal errors never expose details.
- **Extractors:** `AuthUser` verifies the bearer JWT, and `RequireAdmin` checks the role. While `mcp` is set, every endpoint except `auth/change-password`, `auth/logout`, and `me` returns 403 `password_change_required`.
- **Endpoints:**

| Method and path | Auth | Purpose |
|---|---|---|
| `POST /api/v1/auth/login` | none | Username or email plus password. Returns an access token. The refresh token goes in the body for native clients, or in a cookie for web. |
| `POST /api/v1/auth/refresh` | refresh token | Rotates the refresh token and returns a new access token. The cookie variant checks `Origin` against allowed origins. |
| `POST /api/v1/auth/logout` | any | Revokes the current family and clears the cookie. |
| `POST /api/v1/auth/change-password` | user | Takes the current and new password. Clears `must_change_password` and revokes other sessions. |
| `POST /api/v1/auth/forgot-password` | none | Always returns 202. |
| `POST /api/v1/auth/reset-password` | reset or invite token | Sets the password. |
| `GET /api/v1/me` | user | Current user profile. |
| `PATCH /api/v1/me` | user | Updates first name, last name, and email. |
| `GET /api/v1/users` | admin | Paginated list with search. |
| `POST /api/v1/users` | admin | Creates a user and sends an invite, or sets a temporary password. |
| `GET /api/v1/users/{id}` | admin | Detail view. |
| `PATCH /api/v1/users/{id}` | admin | Updates names, email, role, and disabled state. |
| `POST /api/v1/users/{id}/reset-password` | admin | Sets a temporary password and forces a change. |
| `GET /health`, `GET /ready` | none | Liveness, and readiness (the database is reachable). |

- **Client transport:**
  - Web: the refresh token is an `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth` cookie, and the access token lives only in memory.
  - Native: the refresh token goes in the response body. The client signals its type with a header (`X-Postly-Client: web|native`).
- **OpenAPI:** `utoipa` generates the spec, served at `/api/openapi.json` with Swagger UI at `/docs` outside production. `cargo xtask openapi` writes `api/openapi.json`.
- Tests drive the router with `tower::ServiceExt::oneshot`, using a real Postgres (`sqlx::test`), a `MemoryMailer`, and a test job queue.

### `postly-server` (bin `postly`)

The composition root:

1. Load config and initialize tracing.
2. Build the pool and run migrations.
3. Seed the admin.
4. Build the identity service and the job queue.
5. Start the roles selected by `POSTLY_ROLE`, with optional rustls TLS.
6. Shut down gracefully.

It also owns `postly healthcheck` and `postly --version`, and it is the only crate that uses `anyhow`.

### Docker image

- `server/Dockerfile` is multi-stage: `cargo-chef` for cached dependency layers, then a `SQLX_OFFLINE=true` release build (profile `dist`), then a `debian:bookworm-slim` runtime.
- The runtime has CA certificates, runs as a non-root user, and declares `HEALTHCHECK CMD postly healthcheck`.
- `EXPOSE 8080` (API) and `8081` (worker). Containers speak plain HTTP; nginx or the operator's proxy terminates TLS.
- Tags: `postly-server:<version>` and `postly-server:<git-sha>`.

## Flutter client (`app/`)

- **Toolchain:** latest Flutter stable at the start of P8, pinned in `pubspec.yaml` (`environment.flutter`) and in CI. Targets: web, Windows, macOS, Linux, Android, and iOS.
- **Stack:** `flutter_riverpod` for state, `go_router` with auth-aware redirects for routing, and `dio` for HTTP.
  - A dio interceptor attaches the access token and performs a **single-flight refresh** on 401, so concurrent requests share one refresh.
- **Generated client:** built from `api/openapi.json` into `app/lib/api/` by `cargo xtask openapi`, which runs the Dart generator. The generator choice, `swagger_parser` or `openapi-generator` `dart-dio`, is confirmed at the start of P8 and never edited by hand.
- **Environments:**
  - `--dart-define-from-file=config/{development,qa,production}.json` supplies `API_BASE_URL` and `ENV`.
  - Android product flavors and iOS schemes named `development`, `qa`, and `production` use distinct app IDs (`io.github.asm2025.postly.dev`, `.qa`, and `io.github.asm2025.postly`), so all three can be installed side by side.
  - Desktop and web use dart-define only.
- **Token storage:**
  - Native: `flutter_secure_storage` (Keychain, Keystore, DPAPI, libsecret) holds the refresh token.
  - Web: the refresh token is the HttpOnly cookie, and `dio` sends credentials.
  - Access tokens are kept in memory only on every platform.
- **Screens:**
  - Sign in.
  - Forgot password and reset password (the web route `/reset-password?token=…` also handles invites).
  - Forced change password.
  - Dashboard shell: a responsive layout (navigation rail on wide screens, drawer on narrow) with an empty Home and a Profile page (edit names and email, change password, sign out).
  - **Users** (admin only): list with search and pagination, create (invite or temporary password), edit (names, email, role, disabled), and reset password.
- **Theme and UI:** light, dark, and system theme. Errors are mapped from the problem+json `code` to user-facing messages.
- **Tests:**
  - Unit tests for the auth state machine and refresh interceptor, using a mocked HTTP adapter.
  - Widget tests for the forms and redirects.
  - An `integration_test` smoke flow against a running dev server (opt-in, not in CI).

## Testing and CI

- **Rust:**
  - Unit tests per crate.
  - Integration tests against real Postgres (`#[sqlx::test]`). CI uses a `postgres:18` service container.
  - Redaction tests for config dumps, errors, and logs, covering password, token, JWT key, and SMTP password.
  - Security behavior tests: lockout, enumeration-safe responses, refresh reuse detection, the forced-change gate, and the production seed refusal.
- **GitHub Actions:**
  - **`server` job (Linux):**
    - `cargo fmt --check`
    - `cargo clippy --workspace --all-targets --all-features -- -D warnings`
    - `cargo test --workspace` with a Postgres service
    - `cargo sqlx prepare --check --workspace`
    - `cargo deny check`
  - **`server-windows` job:** `cargo check` and `clippy`, with no database.
  - **`contract` job:** runs `cargo xtask openapi` and fails if `api/openapi.json` or the generated Dart client differ from the committed files.
  - **`app` job:** `flutter analyze`, `flutter test`, and `flutter build web --dart-define-from-file=config/qa.json`.
  - **`docker` job:** builds the image (no push) and runs a container smoke test: start compose with Postgres, then check `/health`.
- CI never needs real SMTP, certificates, or social credentials.

## Phases

### P1: Monorepo restructure and workspace foundation

- Move the Cargo workspace into `server/`: root `Cargo.toml`, `[workspace.package]`, `[workspace.dependencies]`, `[workspace.lints]`, and the existing `release`, `dist`, and `dev.package."*"` profiles.
- Add `rust-toolchain.toml` (1.98.1, rustfmt and clippy) and `deny.toml`.
- Create empty crates `config`, `data`, `identity`, `jobs`, `api`, and `server` (bin `postly`), plus `xtask`.
- Remove starter dependencies that no crate uses: `dotenv`, `log`, the `blocking`, `cookies`, and `socks` reqwest features, `html-entities`, and `num_cpus`.
- Update `.gitignore` for certificates, `local.toml`, `.env` files, and Flutter build output.
- Add a CI skeleton with the `server` and `server-windows` jobs.

**Exit:** the quality gates pass in `server/`, `postly --version` runs, and CI is green.

### P2: Configuration and environments

- Implement `postly-config` as described: the environment enum, layered TOML, env vars, `_FILE` secrets, validation, and the redacted dump.
- Add `config/*.toml` for all three environments and `deploy/env/*.env.example`.

**Exit:** precedence tests, unknown-key and invalid-value errors, a release build refusing to start without `POSTLY_ENV`, and redaction tests all pass.

### P3: Dev infrastructure

- Add `cert.ps1` and `cert.sh`, and document the hosts entry.
- Add `compose.yaml` (postgres) and `compose.dev.yaml` (nginx with the TLS server blocks for 44300, 44305, 44310, and 44320, mailpit, and the published ports).
- Add `docker/shared/nginx/nginx.conf`, `server/Dockerfile`, and `.dockerignore`.
- Write the README quick start for Windows first, with Linux and macOS notes.

**Exit:** on a fresh Windows machine, following the README yields a trusted `https://postly.local:44300/health` (the server added in P7 answers it; until then nginx serves a placeholder) and a Mailpit inbox at `https://postly.local:44320`. nginx terminates TLS for the Mailpit UI as well; SMTP on 44325 stays plain, because it's local-only.

### P4: Data layer

- Implement `postly-data`: the pool, migrations for `users`, `refresh_tokens`, `user_tokens`, and `audit_events`, the repositories, and the committed `.sqlx` cache.

**Exit:** `#[sqlx::test]` suites cover every repository, migrations apply from empty, and `cargo sqlx prepare --check` passes.

### P5: Identity

- Implement `postly-identity`: hashing and policy, login and lockout, JWT, refresh rotation and reuse detection, reset and invite tokens, admin rules, the `Mailer` trait and templates, seeding, and audit events.

## Impact on the roadmap (input to plan 03)

These parts of roadmap revision 2 are superseded and must be rewritten in revision 3:

- **Objective and non-goals.** The "GUI or web server" and "multi-user or server deployment" non-goals are reversed. The product is an API server with a Flutter client, used by a small team within one deployment.
- **Target workspace.** Everything moves under `server/crates/`. `crates/app` (the CLI) becomes `server/crates/server` plus `api`.
- **A1 and A3.** Replaced by P1 and P2 of this plan. `postly.toml` in the user config directory and the `--config` flag are dropped. The `{env:}`, `{file:}`, and `{keyring:}` secret references are reconsidered against `_FILE` secrets.
- **B1 (social OAuth).**
  - Loopback and manual-paste callbacks are replaced by server-side redirect callbacks: `https://<api host>/api/v1/platforms/{id}/oauth/callback`, where the Flutter client opens the provider's authorize URL.
  - The OS keyring token store does not fit a headless server. It is replaced by social tokens encrypted at rest in Postgres (envelope encryption with a key from config or secrets).
  - Per-account serialized refresh stays, but it now needs to work across processes (Postgres advisory locks rather than in-process mutexes).
- **B3 (persistence).** SQLite becomes PostgreSQL. Every domain table gains ownership and audit columns (`created_by`, `updated_by`). Social accounts are shared within the deployment, with optional per-user permissions to be decided in plan 03. Leasing uses apalis plus `FOR UPDATE SKIP LOCKED` where domain queries need it.
- **D1 (scheduler).** Rebuilt on `postly-jobs` (apalis). The delivery state machine (`OutcomeUnknown`, reconcile, idempotency keys, partial success) stays domain logic in postly tables.
- **D3 (CLI).** Removed. Every user-facing capability becomes a REST endpoint plus a Flutter screen. The emix `terminal` and `emixthreading` spinner dependencies are dropped.
- **Media.** Local file paths become server-side media intake: streamed upload endpoints, a storage abstraction (filesystem volume first), and the media path policy applied to the server's storage root. `MediaHost` becomes central, because Instagram and TikTok need public URLs.
- **G2 and G3.** `postly doctor` becomes an admin API endpoint and screen. The threat model gains the web-facing surface: CORS, cookies, rate limits, uploads, and the job dashboard.

## Non-goals for this plan

- Social accounts, drafts, publishing, scheduling UI, and AI generation (plan 03 onward).
- External identity providers or OIDC (excluded permanently).
- MFA/TOTP, email-change verification, mobile deep links or universal links, push notifications, and localization (candidates for later plans).
- Multi-tenancy, horizontal-scale tuning, Kubernetes manifests, and bundled TLS or reverse proxy for QA and production.

## Risks and checks at phase start

- **apalis 1.0 is still a release candidate.** Pin an exact version and re-check releases at the start of P6. The seam contains the fallout. apalis-board compatibility decides whether `/jobs` ships in this plan.
- **Flutter web TLS dev server options** and the **Dart OpenAPI generator** choice are confirmed at the start of P8.
- **Mobile trust of the self-signed dev certificate** is the most fragile part of the dev setup. The debug-only trust configuration must never ship in `qa` or `production` builds, and a build check enforces this.
- **A public default password.** `P@$$w0rd123!` is published in the repo. The forced change on first login and the production first-boot requirement are the controls, and both are tested.
