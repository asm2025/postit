# Social Publishing Roadmap, Revision 3

> Plan 03 (2026-09-25). Revision 3 of the roadmap. It **supersedes** [01. social publishing platform roadmap](01.%20social%20publishing%20platform%20roadmap.md) (revision 2) and builds on [02. API server, identity, environments, and Flutter baseline](02.%20API%20server%2C%20identity%2C%20environments%2C%20and%20Flutter%20baseline.md). Plan 02's phases P1–P9 are the foundation that every phase here depends on. Changes from revision 2 are summarized in [Revision notes](#revision-notes) at the end.

## Objective

postly is a self-hosted service for a small team. Each user connects their own social accounts, creates posts by hand or with an LLM, publishes them immediately or on a schedule (postly-scheduled or platform-native), and tracks delivery history. The product is the plan 02 Rust API server and background worker plus the Flutter client (web, desktop, mobile).

The initial platforms are X, YouTube, Facebook, Instagram, and TikTok. They are **compile-time plugins** to a platform-agnostic core: each platform is its own crate implementing the `PlatformPlugin` contract, and new platforms (Threads, LinkedIn, Bluesky, Mastodon, …) are added without changing the core, the publishing engine, the schema, the REST API, or the Flutter client.

Platform-specific OAuth details, validation, rate limits, upload protocols, and API types stay inside each platform crate. Shared code consumes only the plugin contract and the core domain models.

## Decisions

| Topic | Decision |
|---|---|
| Ownership | **Private per user.** Social accounts, tokens, media, posts, jobs, deliveries, AI providers, and notifications belong to one user (`owner_id`). No sharing and no team permissions. |
| Admin role | Admins manage users and deployment settings: platform developer apps, the live-publishing kill switch, per-platform enablement, and diagnostics. Admins **cannot** read other users' content or secrets. |
| Platform developer apps | Deployment-level. One client ID/secret per platform in config (`[platforms.<id>]` plus `_FILE` secrets). Each user connects their own accounts through them. |
| LLM provider keys | **Per user.** Each user configures providers (opencode-shaped) with their own keys. No deployment-level AI config. |
| Stored secrets | Social tokens, PKCE verifiers, and LLM keys are sealed in Postgres with envelope encryption (`postly-vault`). |
| Social OAuth callback | Server-side: `https://<api host>/api/v1/platforms/{id}/oauth/callback`. The Flutter client only opens the authorize URL and receives the result redirect. |
| Media hosting | Filesystem storage volume. postly serves media to platforms through short-lived HMAC-signed public URLs. `MediaStore` and `MediaHost` are traits, so an S3 backend can be added later without contract changes. |
| Live publishing | **On in every environment.** Every live publish requires explicit confirmation. A runtime kill switch (`publishing.live`) and per-platform `enabled` flags can stop it. A per-publish dry-run toggle is always available. |
| Scheduling UI | Composer, queue, history, **and** a calendar (month, week, agenda) with drag-to-reschedule. |
| Platform order | X and YouTube first. Meta (Facebook, Instagram) and TikTok follow in parallel. |
| Notifications | In-app notifications plus email for critical events, with a per-user email opt-out. No mobile push. |
| Live progress | Polling with ETags. No SSE or WebSocket in this revision. |

## Engineering standards

These apply to every phase and are part of every phase's exit criteria. Plan 02's additions (thin handlers, generated API contract, no secret in any output) apply too.

### DRY and ownership

- **One owner per concern.** Each cross-cutting concern has exactly one implementation that everything else reuses:
  - Config and environments: `postly-config`.
  - Postgres access and owner scoping: `postly-data`.
  - Users, passwords, sessions, and mail: `postly-identity`.
  - The job runner: `postly-jobs`, the only crate that depends on apalis.
  - HTTP surface and OpenAPI: `postly-api`.
  - Outbound HTTP transport, retry, and redaction: `postly-http`.
  - Encryption of stored secrets: `postly-vault`.
  - Social OAuth flows and token storage: `postly-oauth`.
  - Media storage, intake, probing, and public hosting: `postly-media`.
  - Shared plugin machinery and the conformance suite: `postly-platform-kit`.
  - Meta Graph API client: `postly-platform-meta`.
  - Delivery state machine and publishing orchestration: `postly-publishing`.
  - Notifications: `postly-notify`.
- **Platforms declare, the engine executes.** Validation runs in one core engine that reads plugin-supplied capability data: limits, media rules, and a text-measure function (for example, X's weighted character count). No validation logic is duplicated per endpoint or per platform.
- **One conformance suite.** Every plugin passes the same generic suite from `postly-platform-kit` (feature `testkit`): the dry-run contract, error mapping, idempotency, cancellation, and redaction. Platform crates add only protocol-specific tests.
- **Shared wiremock fixtures** for mocked OAuth, token refresh, rate-limit responses, and malformed payloads come from the testkit.
- **Owner scoping lives in one place.** Every repository method in `postly-data` that reads or writes owned rows takes an `OwnerScope` and filters on `owner_id`. Handlers and services never write their own ownership filters.
- **Workspace-level dependencies.** Every dependency version is declared once in `[workspace.dependencies]`; crates use `dep.workspace = true` and enable only the features they need.

### Rust best practices

- `[workspace.lints]` inherited by all crates:
  - `unsafe_code = "forbid"`.
  - `clippy::all` and `clippy::pedantic` at warn. Allowances are justified in `Cargo.toml` comments.
  - `clippy::unwrap_used`, `clippy::expect_used`, and `clippy::panic` denied outside tests.
  - `missing_docs` warn on library crates.
- **Errors.** Library crates use `thiserror` enums. Only `postly-server` uses `anyhow` for top-level reporting. Errors carry structured context and never include secret values. The API maps them to RFC 9457 problem+json with a stable `code` extension.
- **Secrets are typed.** Tokens, auth codes, API keys, client secrets, and encryption keys use `secrecy::SecretString` (or newtypes over it) so `Debug` and `Display` redact by construction. Log redaction is a backstop.
- **Newtypes** for identifiers: `UserId`, `PlatformId`, `SocialAccountId`, `PostId`, `MediaId`, `PublishJobId`, `DeliveryId`, `RemotePostId`, `AiProviderId`, `ModelId`. Internal IDs are UUID v7.
- **Deterministic tests.** Injected `Clock` and `IdGenerator` traits, a seeded jitter RNG, and no real network in non-ignored tests.
- **Async trait objects.** `PlatformClient`, `PlatformPlugin`, `LlmProvider`, `TokenStore`, `MediaStore`, and `MediaHost` are used as `dyn` objects. Phase A1 adds a trait-object compile test and picks one approach: native dyn-compatible async traits if the pinned toolchain supports them, otherwise `async-trait`.
- **Tracing** with `tracing` and `tracing-subscriber` everywhere. `#[instrument(skip(...))]` on any function that receives a secret.
- **Dependency hygiene.** reqwest uses rustls, streaming, JSON, and multipart only. `cargo-deny` covers licenses, advisories, and duplicate crates.

### Reuse of essentialMix-rs (`emix*` crates)

Crates come from crates.io with a loose `"0"` spec, declared once in `[workspace.dependencies]`, with `default-features = false` where a crate enables heavy defaults. `Cargo.lock` keeps builds reproducible. Because a `0.x` minor bump is semver-breaking, run the full quality gates after each `cargo update`.

| Crate | Use in postly | Where |
|---|---|---|
| `emixdb` | `Pagination` and `ResultSet<T>` for every list endpoint | `data`, `api` |
| `emixcrypto` (`default-features = false`) | `Sha256Hash` for media content hashes and idempotency keys | `core`, `data`, `media` |
| `emixcore` | Only as a conversion source: `impl From<emixcore::Error>` where emix APIs are called | where used |

Revision 2 also used `emix` (`terminal` prompts) and `emixthreading` (spinner) for the CLI. Both are dropped with the CLI. The evaluation of crates that are **not** used stands:

- `emixai`: built on kalosm with heavy local-inference dependencies, a hard-coded OpenAI model enum, and no custom base URL. postly's `LlmProvider` layer could later be upstreamed.
- `emixnet`: `pool_max_idle_per_host(0)` disables connection reuse, a forced JSON `Content-Type` breaks multipart and binary uploads, and it enables a cookie store. Worth fixing upstream with an options struct.
- `emixlog`: log4rs/slog-based; postly standardizes on `tracing`.
- `emixseaorm`, `emixdiesel`: postly uses SQLx.
- `emixcollections`: no current need.
- `emix::datetime::parse_date_any`: interprets input as UTC and ignores the time zone. Schedule input is time-zone-aware (see D3).

## Delivery model

- **Foundation first.** Plan 02 (P1–P9) delivers the workspace, config, Postgres, identity, jobs, the API shell, Docker, CI, and the Flutter shell. Group A here starts as soon as its plan 02 prerequisites land.
- **Parallel tracks.** Group B infrastructure runs in parallel after Group A. Platform tracks (C, E, F) run in parallel once the platform kit (B5) exists.
- **Mock-first.** The `mock` plugin (B5) lets the publishing engine, the REST surface, the Flutter UI, and orchestration be built and tested before any real platform is complete.
- **Release safety.** Every live publish is explicitly confirmed by the user. Dry-run works everywhere. The kill switch and per-platform `enabled` flags stop live publishing without a redeploy. CI never publishes live.

**Dependency direction** is strictly downward:

- `core` depends on nothing internal.
- Platform crates depend on `core` and `platform-kit`. They never depend on each other, except `facebook` and `instagram` on `meta`.
- `vault` depends on `config`. `oauth`, `media`, `content`, `publishing`, and `notify` depend on `core`, `http`, `data`, and `vault` as needed.

- Only `api` and `server` see every crate. `server` registers each platform plugin behind a Cargo feature (`x`, `youtube`, `facebook`, `instagram`, `tiktok`, `mock-platform`), all enabled by default except `mock-platform`, which is enabled in development and CI builds.

## Data model

All tables are owned by postly, use UUID v7 IDs generated in Rust, and use `timestamptz`. Every owned table carries `owner_id` (FK to `users`), `created_at`, `updated_at`, `created_by`, and `updated_by`. `audit_events` from plan 02 gains `owner_id`.

- **`platforms`**: `id text PRIMARY KEY` (checked against `^[a-z][a-z0-9_-]{0,31}$`), `display_name`, `enabled bool`, `first_seen_at`.
  - `id` is the plugin identifier from `PlatformDescriptor` (`x`, `youtube`, …). It is a natural text key so adding a platform needs no migration and IDs are identical across environments. Values are short and inline; a surrogate integer would add joins or mapping without measurable gain at this scale.
  - The server upserts one row per registered plugin at startup, after migrations. Code stays the source of truth; the table gives referential integrity and the admin `enabled` switch.
  - A row whose plugin is compiled out stays, and the API reports the platform as unavailable in this build.
- **`social_accounts`**: `platform_id text REFERENCES platforms(id)`, `remote_account_id`, `display_name`, `avatar_url`, `scopes text[]`, `status` (`active`, `needs_reconnect`, `revoked`), `test_account bool` (informational label only). Unique on (`owner_id`, `platform_id`, `remote_account_id`).
- **`social_tokens`**: `account_id` (1:1), `access_token` sealed, `refresh_token` sealed, `expires_at`, `key_version`.
- **`oauth_states`**: `state_hash bytea unique`, `user_id`, `platform_id text REFERENCES platforms(id)`, `pkce_verifier` sealed, `return_to`, `expires_at` (10 minutes).
- **`media_assets`**: `storage_key`, `original_filename`, `mime`, `bytes`, `sha256`, `width`, `height`, `duration_ms`, `status` (`uploading`, `ready`, `failed`).
- **`posts`**: `text`, `link`, `tags text[]`, `disclose_ai_generated bool`, `version int`, `status` (`draft`, `scheduled`, `publishing`, `published`, `partial`, `failed`, `cancelled`).
  - **`post_media`**: `post_id`, `media_id`, `position`.
  - **`post_overrides`**: `post_id`, `account_id`, `patch jsonb`. Overrides never mutate the canonical post; the engine resolves a per-target view.
- **`publish_jobs`**: `post_id`, `post_version`, `scheduled_at` (UTC, null for "now"), `native_schedule bool`, `dry_run bool`, `status` (derived from deliveries), `cancelled_at`.
- **`deliveries`**: `job_id`, `account_id`, `state`, `idempotency_key bytea UNIQUE`, `attempt_count`, `next_attempt_at`, `remote_id`, `remote_url`, `container_ref` (Instagram container ID, TikTok `publish_id`, YouTube upload session), `last_error jsonb`, `parked_reason`.
  - `idempotency_key = sha256(post_id, post_version, account_id)` via `emixcrypto`.
- **`delivery_attempts`**: `delivery_id`, `started_at`, `finished_at`, `outcome`, classified error, redacted request summary.
- **`ai_providers`**: `provider_key`, `config jsonb` (opencode-shaped, without the key), `api_key` sealed, `is_default bool`.
- **`ai_generations`**: `provider_id`, `model`, `prompt_hash`, `prompt` (only when the user enables storing prompts), token usage, `post_id`.
- **`platform_quota_usage`**: `account_id`, `platform_id text REFERENCES platforms(id)`, `day date`, `units_used`.
- **`notifications`**: `kind`, `severity`, `payload jsonb`, `read_at`, `emailed_at`.
- **`user_preferences`**: `user_id` (1:1), `email_notifications bool`, `timezone` (IANA), `store_ai_prompts bool`.
- **`app_settings`**: deployment-level runtime settings edited by admins. Initially `publishing.live`, seeded from config.

Token and key values exist in the database only as vault-sealed ciphertext. A test asserts that no column contains a plaintext value from the test fixtures.

**User deletion.** Deleting a user revokes their social tokens at each provider where supported, deletes their owned rows and stored media, and keeps `audit_events` with the user ID replaced by a pseudonymous hash.

## REST surface

All routes are under `/api/v1`, return problem+json errors, are owner-scoped unless marked admin, and paginate with the `emixdb::ResultSet` shape. `utoipa` generates the contract and the Dart client is regenerated from it (plan 02 rules).

- **Platforms:** `GET /platforms` lists descriptors and capabilities for platforms that are configured, compiled in, and enabled.
- **Social accounts:**
  - `POST /social-accounts/connect/{platform}` with `{ return_to }` returns `{ authorize_url }`.
  - `GET /platforms/{id}/oauth/callback` completes the flow (no JWT; the state row binds it to its user) and redirects to `return_to?result=ok|error&code=…`.
  - `GET /social-accounts`, `GET /social-accounts/{id}`, `DELETE /social-accounts/{id}` (revokes the token), `POST /social-accounts/{id}/check` (health and scopes).
- **Media:**
  - `POST /media`: streamed multipart upload.
  - `GET /media`, `GET /media/{id}`, `GET /media/{id}/content` (authenticated), `DELETE /media/{id}` (409 while referenced).
  - `GET /public/media/{id}?exp=…&sig=…`: the signed public route used by platforms. Supports HTTP range requests. Invalid or expired signatures return 404.
- **Posts:**
  - `/posts` CRUD; each edit bumps `version`.
  - `PUT /posts/{id}/overrides/{account_id}`, `DELETE /posts/{id}/overrides/{account_id}`.
  - `POST /posts/{id}/validate` returns every violation for every target.
- **Publishing:**
  - `POST /posts/{id}/publish` with `{ targets[], at?, native_schedule?, dry_run?, confirm }`. `confirm: true` is required unless `dry_run` is true. Returns the job and its deliveries.
  - `GET /publish-jobs`, `GET /publish-jobs/{id}` (ETag), `POST /publish-jobs/{id}/cancel`, `PATCH /publish-jobs/{id}` with `{ at }` to reschedule.
  - `GET /calendar?from=…&to=…` returns jobs and deliveries in a range.
  - `POST /deliveries/{id}/retry`, `POST /deliveries/{id}/resolve` with `{ outcome: published, remote_url }` or `{ outcome: failed }`.
- **AI:**
  - `/ai/providers` CRUD, `POST /ai/providers/{id}/test`, `GET /ai/providers/{id}/models`.
  - `POST /ai/generate` with `{ topic, targets[], provider_id?, model? }` creates a draft.
- **Notifications:** `GET /notifications`, `POST /notifications/read` with `{ ids[] | all }`.
- **Preferences:** `GET /me/preferences`, `PUT /me/preferences`.
- **Admin:**
  - `GET /admin/platforms` (configured, compiled in, enabled, redirect URI), `PUT /admin/platforms/{id}` with `{ enabled }`.
  - `GET /admin/settings/publishing`, `PUT /admin/settings/publishing` with `{ live }`.
  - `GET /admin/doctor`.
  - `POST /admin/vault/rotate` starts re-sealing under the newest key version.

Stable error `code`s include `validation_failed`, `account_needs_reconnect`, `platform_disabled`, `platform_unavailable`, `live_publish_disabled`, `confirmation_required`, `quota_exceeded`, `rate_limited` (with `retry_after`), `outcome_unknown`, `not_reschedulable`, and `media_in_use`.

## Key flows

### Connecting a social account

1. Flutter calls `POST /social-accounts/connect/{platform}` with `return_to`: the web app origin, or the native scheme for the flavor (`postly-dev://oauth-done`, `postly-qa://oauth-done`, `postly://oauth-done`). `return_to` is checked against an allowlist from config.
2. The API creates an `oauth_states` row: a random 32-byte state stored as a hash, the PKCE verifier sealed, a 10-minute expiry. It returns the provider's `authorize_url`.
3. Flutter opens it: a new tab or popup on web, the system browser on native (`flutter_web_auth_2` or `url_launcher`).
4. The provider redirects to `/api/v1/platforms/{id}/oauth/callback?code&state`.
5. The server consumes the state row (single use, deleted in the same transaction), exchanges the code, runs the plugin's post-exchange hook (for example, Meta's long-lived token exchange and Page token derivation), discovers the accounts (YouTube channels, Facebook Pages, Instagram professional accounts), upserts `social_accounts`, seals the tokens, and redirects to `return_to?result=ok`.
6. Flutter refreshes the account list.

Expired or reused state, provider denial, and missing scopes redirect with `result=error&code=…` and create no rows.

### Token refresh

- A `refresh_social_token` cron job runs every 5 minutes and refreshes tokens that expire within 15 minutes. Plugins also refresh on demand after a 401.
- Both paths take `pg_advisory_xact_lock` keyed on the account ID, re-read the token, and skip the refresh if another process already did it. The rotated token is written in the same transaction. This makes X's refresh-token rotation safe across the API and worker processes.
- `invalid_grant` or a revoked token sets the account to `needs_reconnect`, sends a critical notification, and parks pending deliveries for that account with the reason `account_needs_reconnect`. Reconnecting resumes them.

### Publishing

1. `POST /posts/{id}/publish` runs full validation: common rules, then capability rules through the plugin's `TextMeasure` and limits, then the plugin's `validate`. Any violation returns 422 with every violation. A live publish without `confirm: true` returns 400 `confirmation_required`.
2. In one transaction, the API creates the job and one delivery per target account, then enqueues `publish_delivery` for each with `run_at` set to the schedule time or now.
3. The worker claims the delivery with `UPDATE deliveries SET state = 'claimed' … WHERE id = $1 AND state = 'pending' AND job not cancelled AND scheduled_at matches RETURNING …`. That row update is the lock; a duplicate or stale apalis job finds nothing to claim and exits.
4. The worker checks `app_settings.publishing.live` and `platforms.enabled`. If either blocks a live delivery, the delivery is parked with `live_publish_disabled` or `platform_disabled` and a notification is sent. It never silently degrades to a dry-run.
5. The worker calls `plugin.publish(resolved_post, mode)`:
   - Success: `Published`, or `Processing` followed by `poll_delivery_status` jobs.
   - Retryable failure: backoff with full jitter from `postly-http`, a new `run_at`, and a retry budget (5 attempts by default), ending in `DeadLetter`.
   - Ambiguous failure of a non-idempotent call: `OutcomeUnknown`, then `reconcile_delivery`. If the plugin returns `Unsupported`, the delivery is parked for the user to retry or resolve. It is never blindly retried.
6. Multi-step plugins (Instagram containers, TikTok `publish_id`, YouTube resumable sessions) persist `container_ref` before each next step, so a retry resumes rather than duplicating.
7. The job and post status are derived from the deliveries: `published`, `partial`, or `failed`. Notifications are sent on `DeadLetter`, `OutcomeUnknown`, `needs_reconnect`, and a `partial` job.

**Native scheduling.** When the plugin declares `supports_native_schedule` (YouTube `publishAt`, Facebook scheduled posts) and the user chooses it, the worker uploads immediately with the remote publish time and the delivery moves to `Processing` until the platform confirms.

**Due sweep.** The deliveries table is the source of truth, not the apalis queue. A cron job every minute re-enqueues any due `pending` delivery with no live job, so a lost queue entry delays a post by at most a minute.

**Dry-run.** A dry-run job validates, resolves overrides, and records the planned remote actions in `delivery_attempts` without calling any mutating endpoint.

### Rescheduling and cancelling

- `PATCH /publish-jobs/{id}` with a new time is allowed only while every delivery is `pending`. It updates `scheduled_at` and enqueues a new `publish_delivery`. The old apalis job wakes, sees that `scheduled_at` moved, and exits without claiming.
- A native-scheduled delivery that is already uploaded is rescheduled or deleted through the plugin where supported; otherwise the API returns 409 `not_reschedulable`.
- Cancelling sets pending deliveries to `Cancelled`. An in-flight delivery is cancelled at its next safe checkpoint.

### Media

- `POST /media` streams to `{storage_root}/{owner_id}/{yyyy}/{mm}/{uuid}`, computing SHA-256 while streaming. Size limits are enforced during the stream. The MIME type is sniffed from content, not trusted from the client.
- `MediaProbe` reads dimensions and duration without decoding (pure-Rust container parsing; an optional `ffprobe` implementation behind a feature).
- `MediaHost::public_url(asset, ttl)` signs `id|exp` with HMAC-SHA256 using `media.signing_key` (a `_FILE` secret). The default TTL is 1 hour. The public route verifies in constant time.
- The storage root is the only place media is read from. Paths are generated, never user-supplied, and are canonicalized and checked against the root.
- `media_gc` (daily cron) deletes assets that are unreferenced and older than 24 hours, and `failed` uploads.

## Group A — Domain foundation

### Phase A1 — Core domain models and the plugin contract

Needs P1. Create `postly-core` with:

- **Open platform identity.**
  - `PlatformId` is a validated lowercase string newtype such as `"x"` or `"youtube"`. There is no closed enum.
  - `PlatformDescriptor` holds the ID, display name, `Capabilities`, an optional `OAuthProviderSpec`, the plugin config schema version, and `supports_native_schedule`.
- **Accounts.** `AccountRef { platform: PlatformId, account: SocialAccountId }`. Publish targets are `AccountRef`s, not platforms.
- **Post models.** `Post` (text, media, link, tags, `disclose_ai_generated`), `PostOverrides` (per-`AccountRef` patch), and `PostVersion`.
- **Media.**
  - `MediaAsset`: kind, MIME type, byte size, optional duration and dimensions, content hash, and a `MediaSource`.
  - `MediaSource` is `Stored(MediaId)`, `PublicUrl(Url)`, or `RemoteRef`. There are no local paths.
  - Traits: `MediaStore` (open a stream by `MediaId`), `MediaProbe`, and `MediaHost` (public URL for a stored asset). Implementations live in `postly-media`.
- **Contracts.**
  - `PlatformPlugin`: `descriptor()`, `config_schema()`, `create_client(ctx) -> Box<dyn PlatformClient>`. The context carries the resolved plugin config, an HTTP handle, a token accessor, a media accessor, and the clock.
  - `PlatformClient`: `account_info` / health, `discover_accounts` (after OAuth), `validate`, `publish(resolved_post, mode)` with `DryRun` or `Live`, `status(receipt)`, `delete(receipt)`, `reschedule(receipt, at)` (optional), and `reconcile(delivery)` returning `Unsupported` where the platform cannot look posts up.
  - `PluginRegistry` maps `PlatformId` to `Arc<dyn PlatformPlugin>`, rejects duplicates, and is built explicitly by the composition root.
- **Receipts and statuses.** `PublishReceipt` (`Submitted`, `Processing`, `Published`, remote ID and URL), `AccountStatus`, and `DeliveryState`: `Pending → Claimed → InFlight → {Processing → Published | Failed(retryable) | OutcomeUnknown | DeadLetter | Cancelled | Parked(reason)}`.
- **Validation engine.** Common rules, then capability rules, then platform `validate`. Returns all violations.
- **Structured errors.** `PlatformError` covers authentication, authorization/scope, validation, rate limit (with retry-after), quota, transport, unsupported capability, remote API error, and outcome unknown, each with a retry classification.
- **Test seams.** `Clock` and `IdGenerator`.

Tests: serialization round trips, validation matrices, override resolution, registry duplicate rejection, and the trait-object compile test.

**Exit criteria:** all shared types are documented and tested. Core has no platform-specific, HTTP, or database code.

### Phase A2 — Vault, platforms table, and platform configuration

Needs A1 and P4.

- **`postly-vault`:**
  - Envelope encryption with XChaCha20-Poly1305. Key-encryption keys come from `vault.keys` (a list of versioned keys, `_FILE` secrets, at least 32 bytes each); the newest version seals, every listed version opens.
  - A `Sealed<T>` type for columns, with the key version and nonce stored alongside the ciphertext and the row ID bound as associated data so ciphertext cannot be moved between rows.
  - Development and QA may use a generated dev key with a startup warning. Production refuses to start without one.
  - `POST /admin/vault/rotate` enqueues a job that re-seals every sealed column under the newest key.
- **`platforms` table** and the startup upsert from the registry.
- **`[platforms.<id>]` configuration.** Each table is opaque to core and deserialized by the owning plugin (client ID, client secret as a `_FILE` secret, API version, …). Unknown platform tables and tables for plugins not compiled in are reported at startup. The redirect URI is derived from `server.public_url` and shown to admins.
- **`[publishing]`**: `live` default (`true` in every environment), retry budget, and sweep interval. **`[media]`**: storage root, size limits per kind, signing key, public URL TTL.

**Exit criteria:** sealed values round trip, rotation re-seals every row, a row's ciphertext cannot be opened under another row's ID, secrets never appear in `Debug`, errors, or logs, and platform config validation reports actionable errors.

## Group B — Shared infrastructure

B1 and B2 run in parallel after Group A. B3 and B4 follow; B5 needs B1 and B3.

### Phase B1 — HTTP, resilience, and observability

Needs A1. Create `postly-http`:

- A single `reqwest` client factory: rustls, connection pooling, per-request and connect timeouts, user agent, gzip. No global `Content-Type` and no cookie store.
- Request IDs, tracing spans, and redacted diagnostics for authorization headers, token-bearing query parameters, and configured sensitive URL patterns (including signed media URLs).
- Retry classification: transient errors retry; rate-limited responses honor `Retry-After` and plugin-supplied reset headers; non-idempotent mutations are never retried once the body may have been received and surface as `OutcomeUnknown`.
- Exponential backoff with full jitter (seeded in tests) and a retry budget.
- `governor` rate limiters keyed by plugin-defined buckets (per app, per account, per endpoint). Limits are per process; plugins that need a cross-process limit (for example, a daily quota) use `platform_quota_usage` instead.
- Streaming request bodies from `MediaStore` streams.
- Test helpers: a wiremock server builder and deterministic time and jitter.

**Exit criteria:** retry, timeout, rate-limit, redaction, and error mapping are verified without real API calls. No other crate constructs a `reqwest::Client`.

### Phase B2 — Domain schema and owner-scoped repositories

Needs A1, A2, and P4.

- Migrations for every table in [Data model](#data-model).
- Owner-scoped repositories taking `OwnerScope`. Admin repositories for users, platforms, and settings are separate types and cannot read owned content.
- Atomic claim queries for deliveries, the due-sweep query, and `FOR UPDATE SKIP LOCKED` where batch processing needs it.
- The idempotency constraint on deliveries.
- List methods return `emixdb::ResultSet<T>` with `emixdb::Pagination`.

Tests: cross-user isolation for every repository (user A never sees, updates, or deletes user B's rows), concurrent claim tests, the idempotency constraint, the sealed-column plaintext check, and migrations from empty and from each prior version.

**Exit criteria:** repositories can create posts, enqueue jobs, claim due deliveries safely under concurrency, record attempts, and reconcile success, failure, and unknown outcomes, with isolation proven by tests.

### Phase B3 — Social OAuth and token storage

Needs A2, B1, B2, P5, and P6. Create `postly-oauth`:

- OAuth 2.0 authorization-code flow with PKCE, driven by the plugin-provided `OAuthProviderSpec`: endpoints, scopes, PKCE support, client-auth method, extra parameters, token-response quirks, and an optional post-exchange hook. **No provider-specific configuration lives in this crate.**
- The server-side callback flow from [Connecting a social account](#connecting-a-social-account), including `oauth_states` and the `return_to` allowlist.
- A `TokenStore` trait with `PgTokenStore` (vault-sealed `social_tokens`) and an in-memory store for tests.
- Cross-process serialized refresh with advisory locks, the `refresh_social_token` cron, and the `needs_reconnect` transition.
- Revocation where the provider supports it, otherwise local deletion.
- Clear errors for missing platform config, denied authorization, invalid or expired state, expired or revoked refresh tokens, and missing scopes.
- **Phase-start check:** confirm each provider's redirect URI rules for development. Google web clients require a public top-level domain, and Meta and TikTok may reject `postly.local`. The documented fallback is a dev tunnel hostname (cloudflared or ngrok) configured as `server.public_url` for OAuth callbacks.

Tests: PKCE and state validation, single-use state, the `return_to` allowlist, refresh behavior, concurrent refresh across two pools, persistence round trips, redacted diagnostics, and mocked authorization endpoints.

**Exit criteria:** any plugin-provided spec can connect, refresh, retrieve, and revoke credentials through the server-side callback without depending on platform code or exposing secrets.

### Phase B4 — Media

Needs B2 and P5. Create `postly-media`:

- `FsMediaStore` over the configured storage root (a Docker volume in compose).
- Streamed intake with per-kind size limits, content sniffing, SHA-256 while streaming, and probing.
- `SignedUrlMediaHost` and the public route with range support.
- `media_gc` cron job.
- The media endpoints from [REST surface](#rest-surface).

Tests: streaming without full buffering (bounded memory test), limit enforcement mid-stream, MIME spoofing rejected, signature and expiry checks, range requests, GC behavior, and owner isolation.

**Exit criteria:** large uploads never buffer the whole file, signed URLs work for anonymous fetchers and fail closed, and no user-supplied path reaches the filesystem.

### Phase B5 — Platform kit and mock plugin

Needs B1 and B3. Create `postly-platform-kit`:

- A resumable/chunked upload driver: chunk size, resume-offset query, progress callback. Reused by YouTube, TikTok, X, and Meta.
- `poll_until` for remote processing status, with backoff and cancellation.
- Error-classification helpers from HTTP status and platform error codes to `PlatformError`.

- `testkit` feature: `run_conformance::<P: PlatformPlugin>(fixture)` plus shared wiremock fixtures.

Create `postly-platform-mock`: fully featured, scriptable failures (including `OutcomeUnknown` and `needs_reconnect`), a mock OAuth provider served by the testkit, and documented as the template for new platforms.

**Exit criteria:** the mock plugin passes the conformance suite. A new plugin needs only its protocol code, its capability declaration, and one registration line in `postly-server`.

Needs B1 and B2. Create `postly-content` (behind the `ai` feature in `postly-server`, enabled by default):

## Platform constraints and risks

Verify each at the start of the relevant phase, since platform policies change:

- **X:** write access and cost depend on the API access tier. Refresh tokens rotate. Media upload endpoints have moved from v1.1 to v2.
- **YouTube:** uploads from an unverified API project are locked to private until the project passes an audit. The daily quota is small, and uploads are expensive against it.
- **TikTok:** unaudited apps can only post with private visibility. `PULL_FROM_URL` needs domain verification of the API host.
- **Meta:** App Review is required for publishing permissions beyond test users. Instagram requires a professional account linked to a Page and is rate-limited per 24 hours. Most media must be at a public URL.
- **Redirect URIs in development:** Google, Meta, and TikTok may reject `https://postly.local`. The dev tunnel fallback is verified in B3 and documented in G2.
- **Public media in development:** platforms cannot fetch from `postly.local`. Instagram and TikTok `PULL_FROM_URL` need the tunnel in development, or the mock plugin.
- **Live publishing is on in development by decision.** A development worker connected to a real account posts for real. Mitigations: per-publish confirmation, the kill switch, `platforms.enabled`, the dry-run toggle, and the `test_account` label shown in the publish dialog.
- **Calendar package license:** checked in D5.
- **apalis 1.0 release status:** inherited from plan 02; re-checked at the start of D1.
- **Anthropic via its OpenAI-compatible endpoint** is feature-limited, which is why a native adapter exists.

## Definition of done

1. The Cargo workspace is pinned to Rust 1.98.1, and all crates pass the same quality gates, lints, and `cargo deny`.
2. The core plugin contract is stable, and all five platforms plus the mock are compile-time plugins that pass the shared conformance suite.
3. Adding a platform requires only a new crate, a Cargo feature, and one registration line. G1's extensibility test proves this, including the platform appearing in the API and the Flutter client without code changes there.
4. Each user's social accounts, tokens, media, posts, deliveries, AI providers, and notifications are private to them, proven by isolation tests at the repository and HTTP layers.
5. OAuth credentials are acquired through the server-side callback, refreshed with cross-process serialization, and stored only as vault-sealed ciphertext. No secret appears in logs, errors, or API responses.
6. Large media is streamed or chunked, served to platforms only through signed expiring URLs, with platform-appropriate resume and recovery.
7. Posts, schedules, deliveries, attempts, receipts, and partial successes are durable and idempotent. Unknown outcomes are reconciled, not duplicated.
8. The Flutter client covers accounts, media, composer with AI generation, dry-run, local and native scheduling, the calendar with drag-to-reschedule, queue, history, retry, resolve, cancel, notifications, AI providers, preferences, and the admin screens, on web, desktop, and mobile.
9. Content generation works with any OpenAI-compatible provider and with native Anthropic, configured per user in opencode's provider shape. AI disclosure is preserved through every applicable publish request.
10. Every live publish is explicitly confirmed and can be stopped by the kill switch or per-platform switch. Dry-run is safe everywhere.
11. CI verifies formatting, linting, type checking, tests, conformance suites, the SQLx offline cache, the OpenAPI and Dart client contract, dependency and security checks, and redaction.

## Revision notes

Changes relative to revision 2:

1. **Product shape.** The CLI is gone. postly is the plan 02 REST API and worker with a Flutter client. Every former CLI command is a REST endpoint and a Flutter screen. The emix `terminal` and `emixthreading` dependencies are dropped.
2. **Ownership model.** Added `owner_id` scoping on every domain table, with isolation tests. Admins manage the deployment, not user content.
3. **Workspace.** Crates move under `server/crates/` next to plan 02's crates. `crates/app` is replaced by `postly-server` and `postly-api`. A1 and A3 are replaced by plan 02 P1 and P2; the new A1 is revision 2's A2.
4. **Social OAuth.** Loopback and manual-paste callbacks are replaced by a server-side callback with `oauth_states`. The crate is renamed `postly-oauth` to avoid confusion with `postly-identity`.
5. **Token storage.** The OS keyring and encrypted-file stores are replaced by vault-sealed columns in Postgres (`postly-vault`, new). `{keyring:}` and `{file:}` secret references are replaced by plan 02's `_FILE` secrets.
6. **Cross-process refresh.** The in-process keyed mutex becomes a Postgres advisory lock.
7. **Persistence.** SQLite becomes PostgreSQL. A `platforms` table with a text natural key gives referential integrity and an admin enable switch.
8. **Scheduler.** `postly-scheduler` becomes `postly-publishing` on apalis through `postly-jobs`, with the deliveries table as the source of truth and a due sweep guarding against lost queue entries. `postly worker --once` is gone.
9. **Media.** Local file paths become streamed uploads into a storage volume (`postly-media`, new). `MediaHost` ships in v1 as signed URLs served by postly, instead of "user-supplied URL" only.
10. **LLM configuration.** Providers are per-user rows instead of an `[ai]` config section, with an outbound URL policy for custom base URLs.
11. **Live publishing.** The `POSTLY_LIVE_PUBLISH` gate is replaced by per-publish confirmation plus a runtime kill switch and per-platform switches, on in every environment.
12. **New capabilities.** In-app and email notifications (`postly-notify`, new), the calendar with drag-to-reschedule, rescheduling through `reschedule` on native-scheduling plugins, and per-user time zone preferences.
13. **Operations.** `postly doctor` becomes `GET /admin/doctor` and an admin screen. The threat model covers the web-facing surface.
