# Foundation

> Plan 02 (2026-09-25). Phases P1–P10. Read [01. Vision and architecture](01.%20vision%20and%20architecture.md) first: the decisions, engineering standards, crate dependencies, identity and access model, and data model live there and are not repeated here. [03. Publishing roadmap](03.%20publishing%20roadmap.md) builds on this plan.

## Objective

When this plan is done, postly is a working vertical slice:

- A Dockerized Rust API server and background worker run against PostgreSQL in `development`, `qa`, and `production`.
- Users sign in through OIDC. In development that is a bundled Zitadel; in CI, an in-process test issuer.
- The first admin is bootstrapped from config. New users land in `pending` until an admin approves them, and admins get an email about each one.
- A Flutter app for web, desktop, and mobile signs in through the IdP, shows a pending screen or the dashboard shell, and gives admins user management.
- apalis, behind our own seam, sends email and runs a recurring cleanup job. Admins watch and manage jobs from a Hangfire-style Jobs page in Flutter.

No social-platform, delegation, drafting, or publishing features are in this plan. Plan 03 adds them.

## Crates in this plan

`config`, `http`, `data`, `jobs`, `mail`, `identity`, `api`, and `server` (bin `postly`), plus `xtask`. Their order and ownership are defined in plan 01, [Crate dependencies](01.%20vision%20and%20architecture.md#crate-dependencies).

## Environments

### Environment selection

- `POSTLY_ENV` is `development`, `qa`, or `production`. Any other value fails startup.
- It defaults to `development` only when it is unset *and* the binary is a debug build. A release build without `POSTLY_ENV` refuses to start.

### Configuration layering

Configuration is loaded with `figment`, and later layers override earlier ones:

1. `config/default.toml`
2. `config/{env}.toml`
3. `config/local.toml` (development only, git-ignored)
4. `POSTLY__SECTION__KEY` environment variables (`__` separates nesting levels)
5. `POSTLY__…__KEY_FILE` variants, which read the value from a file (Docker and Kubernetes secrets)

Secrets deserialize into `SecretString`. At startup the server logs the effective config with secrets redacted. Invalid config exits non-zero with actionable messages.

### Per-environment behavior

| Setting | development | qa | production |
|---|---|---|---|
| Logs | pretty, `debug` | JSON, `info` | JSON, `info` |
| Swagger UI `/docs` | on | on | off (`/api/openapi.json` stays available) |
| CORS allowed origins | `https://postly.local:44310` | configured | configured |
| OIDC issuer | `https://postly.local:44330` (bundled Zitadel) | configured, required | configured, required |
| Bootstrap admin | `admin@postly.local` (Zitadel seed user) | configured | required at first boot when no admin exists |
| Mail transport | Mailpit (SMTP on 44325) | SMTP (use a test inbox) | SMTP |
| TLS | server or nginx terminates with the dev cert | reverse proxy | reverse proxy |

### Development hosting

- **Domain:** `postly.local` resolves to `127.0.0.1` and `::1` through `C:\Windows\System32\drivers\etc\hosts` (or `/etc/hosts`). A `localhost` request redirects to `postly.local`.
- **Certificates:** `cert.ps1` and `cert.sh` take `gen`, `trust`, `setup` (the default), and `help`, following the VigilixMambo scripts. They create a self-signed certificate with SAN `DNS:postly.local, IP:127.0.0.1, IP:::1` in `.crt`, `.key`, and `.pfx` form under `docker/shared/nginx/certs/`, and install it into the Windows Trusted Root store (`certutil -addstore Root`, which needs an elevated shell) or the Linux/macOS equivalent. Key material is git-ignored.
- **Port map.** All dev ports sit in 44300–44399. 44301–44304 are reserved as a gap after the API.

| Port | Service |
|---|---|
| 44300 | API: `/api/v1/*`, `/docs`, `/api/openapi.json`, `/health`, `/ready` |
| 44305 | Worker: `/health`, `/ready` |
| 44310 | Flutter web |
| 44320 | Mailpit web inbox |
| 44325 | Mailpit SMTP |
| 44330 | Zitadel (issuer, login UI, console) |
| 44340 | Postgres (published for SQLx tooling and `cargo sqlx prepare`) |

- **Docker dev** (`docker compose -f compose.yaml -f compose.dev.yaml up`):
  - nginx terminates TLS on 44300, 44305, 44310, 44320, and 44330 and proxies to plain-HTTP containers: `server` (role `all`), `web` (the static Flutter build), Mailpit, and Zitadel.
  - Zitadel uses its own database (`zitadel`) on the same Postgres server, created by an init script, and sends its email to Mailpit.
  - Postgres and Mailpit SMTP publish their ports as shown above.
  - Containers trust the dev cert through a mounted CA file. The server must trust it to fetch Zitadel's discovery document and JWKS.
- **Zitadel bootstrap.** `docker/zitadel/` holds the first-instance config: an organization, a human admin `admin@postly.local` (password in the README, change forced at first login), and a machine user whose key is written to a git-ignored path. `cargo xtask zitadel-bootstrap` then uses that key with the Zitadel management API to create, idempotently:
  - A project `postly` whose ID becomes the API audience.
  - A native/user-agent application for Flutter with PKCE, JWT access tokens, and the redirect URIs below.
  - A second human user `member@postly.local` for testing approvals and, later, delegation.
  - It writes the issuer, audience, and client ID into `server/config/local.toml` and the Flutter `config/development.json`.
- **Native dev** (`cargo run` and `flutter run`):
  - Only `postgres`, `mailpit`, `zitadel`, and nginx (for Zitadel's TLS) come from compose.
  - The server terminates TLS itself with rustls (`axum-server`) when `server.tls.cert_path` and `server.tls.key_path` are set. `development.toml` points them at the generated cert.
  - In role `all`, the API binds 44300 and the worker endpoints bind 44305.
  - Flutter web runs on 44310 with the same certificate.
- **CORS.** The API uses bearer tokens only and sets no cookies. CORS allows the web origin, the `Authorization` and `X-Postly-Act-As` headers, and no credentials. QA and production use the same shape, for example `api.example.com` and `app.example.com`.
- **Mobile dev.** Emulators and devices don't read the host's hosts file or trust store.
  - The Flutter `development` flavor includes a debug-only trust configuration for the dev certificate: Android `network_security_config` in the `development` source set only, and a documented profile install for the iOS simulator. It covers both the API and Zitadel.
  - The README documents name resolution: `adb reverse` or the emulator hosts file for Android, the Mac hosts file for the iOS simulator, and a LAN IP mapped to `postly.local` for physical devices.

### QA and production hosting

- The same image is promoted through dev, QA, and production. Only configuration changes.
- `compose.qa.yaml` and `compose.prod.yaml` run separate `api` and `worker` services with restart policies and Docker `secrets:`. They publish no database port and include no nginx and no IdP. The operator runs or subscribes to an OIDC provider; the docs cover Zitadel and list the generic requirements (JWT access tokens with postly's audience, PKCE public client, the redirect URIs).
- TLS is terminated by the operator's reverse proxy on 443 using configured hostnames. The 443xx convention applies to development only. The README gives a Caddy example; it isn't bundled.
- `server.trusted_proxies` (CIDRs) controls which hops may set `X-Forwarded-For`, which rate limiting and audit use.

## Server design

### Process roles

- `POSTLY_ROLE=all` (the development default) runs the API and the worker in one process. `api` runs only the HTTP API and enqueues jobs. `worker` runs only the job runner and its small HTTP surface on the worker port.
- Migrations run at startup under SQLx's Postgres advisory lock, so concurrent starts are safe. apalis keeps its tables in its own schema.
- The only flags are `postly --version` and `postly healthcheck`. The second calls the local `/health` and serves the Docker `HEALTHCHECK`.
- Shutdown is graceful on SIGTERM and Ctrl-C: stop accepting work, drain in-flight requests and jobs, then close the pool.

### `postly-config`

- Holds the typed settings tree:
  - `server`: bind addresses, TLS paths, trusted proxies, public URLs.
  - `database`.
  - `auth.oidc`: issuer, audiences, client ID and scopes for the Flutter client, accepted algorithms, leeway, JWKS refresh interval, claim names.
  - `auth.bootstrap`: `admin_email` or `admin_subject`.
  - `auth.pending_ttl`, `auth.principal_cache_ttl`.
  - `mail`: transport, from address, SMTP.
  - `jobs`: concurrency, cron schedules.
  - `http`: timeouts, user agent, extra trusted CA files (for the dev IdP).
  - `app.public_url`: the web app, used in email links.
  - `cors`.
- Owns the environment enum, the layering, the `_FILE` secret resolution, validation, and the redacted dump.
- Validation: the issuer must be `https` outside development; `audiences` must be non-empty; the bootstrap email and subject are mutually exclusive.

### `postly-http`

The foundation version of the only `reqwest` factory. Plan 03 phase B1 extends it.

- rustls, connection pooling, per-request and connect timeouts, user agent, gzip. No global `Content-Type` and no cookie store. Extra trusted CAs from config.
- Request IDs, tracing spans, and redaction of `Authorization` headers and token-bearing query parameters.
- An `HttpError` with retry classification (transient, rate-limited, permanent). Plugins map it to `PlatformError` in plan 03; `postly-http` does not know about platforms.
- Test helpers: a wiremock server builder.

### `postly-data`

- Owns the `PgPool` factory with its timeouts and pool size, the embedded migrations, and the repositories.
- Migrations in this plan: `users`, `audit_events`, and `user_preferences`, as defined in plan 01, [Data model](01.%20vision%20and%20architecture.md#data-model).
- **`OwnerScope`** is defined here now, with `actor`, `owner`, and `access`, even though only `Access::Owner` exists until plan 03 adds delegation. `OwnerScope::require(capability)` exists from the start, so no call site changes later.
- Admin repositories (users, audit) are separate types from owner-scoped repositories and cannot read owned content.
- Repository APIs return domain types. List endpoints use `emixdb::Pagination` and `ResultSet<T>`.
- Tests use `#[sqlx::test]` with a per-test database.

### `postly-jobs`

- **The seam:** a `JobQueue` trait (`enqueue`, `enqueue_at`) plus a typed job registration API. apalis types never leave this crate.
- **The worker runner** builds the apalis monitor from config: concurrency, retry policy with exponential backoff, and Postgres storage in its own schema with LISTEN/NOTIFY fetch.
- **Recurring jobs** go through `apalis-cron`, registered with the same API.
- **Job console API.** A `JobConsole` trait next to `JobQueue`, implemented over apalis-postgres's listing and metrics interfaces (the ones apalis-board uses), so apalis types stay inside this crate:
  - List jobs by state (`queued`, `scheduled`, `running`, `succeeded`, `failed`, `dead`, `killed`), job type, and time range, with pagination.
  - Job detail: type, state, attempts, timings, and each attempt's error.
  - Stats: counts per state and per job type, queue depth, and throughput over recent windows.
  - Actions: retry a failed or dead job, cancel a queued or scheduled job, delete a finished job.
  - Recurring jobs: name, cron expression, last run and outcome, next run, and trigger-now.
- **Safe summaries.** Every job type registers a `JobSummary` that exposes only its type and IDs (user, delivery, account, …). The console never returns raw job payloads, so admins never see post text, emails, or secrets. Errors shown in the console go through the same redaction as logs.
- **Retry is safe by design.** Every job handler must be idempotent against its own domain state. For example, a re-queued `publish_delivery` finds nothing to claim unless its delivery is still `pending`. Plan 03 phases test this for each job type they add.
- **No apalis-board.** It would need browser-cookie auth that postly does not have. The Flutter Jobs page (P8) replaces it.
- **Version risk:** apalis 1.0 was at a release candidate (`1.0.0-rc.10` on 2026-09-15; stable 0.7.4). Pin an exact version (`=`) and check the latest release at the start of P5. Upgrades touch only this crate.

### `postly-mail`

- The `Mailer` trait with `SmtpMailer` (`lettre`, TLS or STARTTLS, credentials as `SecretString`) and `MemoryMailer` for tests.
- Messages are rendered from embedded `askama` templates in plain text and HTML. Email links use `app.public_url`.
- The `send_email` job: retried with backoff, gives up after a configured budget, and records an audit event. Callers never send inline; they call `MailOutbox::send(message)`, which enqueues the job.
- Templates in this plan: `user_pending_approval` (to admins) and `user_approved` (to the user).

### `postly-identity`

Owns OIDC verification, claims transformation, users, roles, and bootstrap. It has no HTTP types.

- **Verifier:**
  - `OidcDiscovery` loads the discovery document and JWKS through `postly-http`. A `JwksSource` trait allows a static test source.
  - JWT validation with the `jsonwebtoken` crate (confirm at the start of P4; `openidconnect` is the alternative if it helps with discovery). Rules are in plan 01, [Authentication](01.%20vision%20and%20architecture.md#authentication-oidc).
  - Unknown `kid` triggers at most one refetch per minute.
- **Claims transformation** into a `Principal`, as in plan 01, [Claims transformation](01.%20vision%20and%20architecture.md#claims-transformation). Provisioning runs in one transaction with `INSERT … ON CONFLICT (oidc_issuer, oidc_subject) DO NOTHING`, so two concurrent first requests create one user.
- **Bootstrap:** a user matching `auth.bootstrap` becomes an active admin only while no active admin exists. `admin_email` requires `email_verified = true`. At startup, production fails with a clear message if no active admin exists and no bootstrap rule is set.
- **User administration service:** approve (`pending` to `active`, sends `user_approved`), disable, re-enable, change role, delete (the plan 01 deletion rules; plan 03 extends it for owned content). The last active admin cannot be disabled, demoted, or deleted.
- **Pending cleanup:** the `purge_pending_users` cron job (daily) deletes `pending` users older than `auth.pending_ttl`.
- **Audit events:** `user_provisioned`, `user_approved`, `user_disabled`, `user_enabled`, `role_changed`, `user_deleted`, `bootstrap_admin_granted`.

### `postly-api`

- An axum router under `/api/v1` with tower middleware:
  - Request ID propagated as `x-request-id`.
  - Tracing spans with redaction.
  - Timeout and body size limit.
  - CORS from config.
  - `tower_governor` rate limiting keyed by client IP after trusted-proxy resolution.
- **Errors:** RFC 9457 problem+json with a stable `code`. Codes in this plan: `unauthenticated` (401 with `WWW-Authenticate: Bearer error="invalid_token"`), `account_pending`, `account_disabled`, `forbidden`, `not_found`, `validation_failed`, `last_admin`, `rate_limited`.
- **Extractors:** `Auth` runs the verifier and claims transformation and yields the `Principal`. `ActiveUser` rejects `pending` and `disabled`. `RequireAdmin` checks the role. `Scope` builds the `OwnerScope` (self only in this plan; plan 03 adds the act-as header here and nowhere else).
- **Endpoints:**

| Method and path | Auth | Purpose |
|---|---|---|
| `GET /api/v1/auth/config` | none | Issuer, client ID, and scopes for the Flutter client. |
| `GET /api/v1/me` | any signed-in user, including `pending` | Profile, role, and status. |
| `GET /api/v1/users` | admin | Paginated list with search and a status filter. |
| `GET /api/v1/users/{id}` | admin | Detail view. |
| `PATCH /api/v1/users/{id}` | admin | Change role or status (approve, disable, re-enable). |
| `DELETE /api/v1/users/{id}` | admin | Delete a user. |
| `GET /api/v1/admin/jobs` | admin | Jobs filtered by state, type, and time range, paginated. |
| `GET /api/v1/admin/jobs/stats` | admin | Counts per state and type, queue depth, throughput. |
| `GET /api/v1/admin/jobs/{id}` | admin | Job detail with attempts and redacted errors. |
| `POST /api/v1/admin/jobs/{id}/retry` | admin | Re-queue a failed or dead job. |
| `POST /api/v1/admin/jobs/{id}/cancel` | admin | Cancel a queued or scheduled job. |
| `DELETE /api/v1/admin/jobs/{id}` | admin | Delete a finished job. |
| `GET /api/v1/admin/jobs/recurring` | admin | Recurring jobs with schedule, last run, and next run. |
| `POST /api/v1/admin/jobs/recurring/{name}/trigger` | admin | Run a recurring job now. |
| `GET /health`, `GET /ready` | none | Liveness, and readiness (database reachable, JWKS loaded). |

- Profile fields (name, email) come from the IdP and are read-only in postly. `GET /me` includes the IdP account-management URL when the discovery document or config provides one.
- **OpenAPI:** `utoipa` generates the spec with an OAuth2 authorization-code (PKCE) security scheme pointing at the configured issuer. It is served at `/api/openapi.json`, with Swagger UI at `/docs` outside production, configured to sign in with the same public client. `cargo xtask openapi` writes `api/openapi.json`.
- Tests drive the router with `tower::ServiceExt::oneshot`, using a real Postgres (`sqlx::test`), a `MemoryMailer`, a test job queue, and a test issuer that mints tokens with a generated key.

### `postly-server` (bin `postly`)

The composition root:

1. Load config and initialize tracing.
2. Build the pool and run migrations.
3. Load OIDC discovery and the JWKS (retrying in the background; `/ready` stays false until loaded).
4. Check the production bootstrap rule.
5. Build the services and the job queue, and register job handlers.
6. Start the roles selected by `POSTLY_ROLE`, with optional rustls TLS.
7. Shut down gracefully.

It also owns `postly healthcheck` and `postly --version`, and it is the only crate that uses `anyhow`.

### Docker image

- `server/Dockerfile` is multi-stage: `cargo-chef` for cached dependency layers, then a `SQLX_OFFLINE=true` release build (profile `dist`), then a `debian:bookworm-slim` runtime.
- The runtime has CA certificates, runs as a non-root user, and declares `HEALTHCHECK CMD postly healthcheck`.
- `EXPOSE 8080` (API) and `8081` (worker). Containers speak plain HTTP; nginx or the operator's proxy terminates TLS.
- Tags: `postly-server:<version>` and `postly-server:<git-sha>`.

## Flutter client (`app/`)

- **Toolchain:** latest Flutter stable at the start of P8, pinned in `pubspec.yaml` (`environment.flutter`) and in CI. Targets: web, Windows, macOS, Linux, Android, and iOS.
- **Stack:** `flutter_riverpod` for state, `go_router` with auth-aware redirects, and `dio` for HTTP.
- **Sign-in:** the `oidc` package (Bdaya) for authorization code with PKCE as a public client on every platform. The app reads issuer, client ID, and scopes from `GET /api/v1/auth/config`.
  - Redirect URIs: web `https://<web host>/auth/callback`; Android and iOS a custom scheme per flavor (`postly-dev://auth/callback`, `postly-qa://…`, `postly://…`); desktop a loopback redirect on `127.0.0.1` with a random port.
  - Sign-out calls the IdP's end-session endpoint and clears local state.
  - Token storage uses the package's secure store on native (Keychain, Keystore, DPAPI, libsecret). On web, tokens stay in memory and session storage, and refresh relies on the IdP's refresh-token rotation or a silent renew. The exact web behavior is confirmed at the start of P8.
- **HTTP:** a dio interceptor attaches the access token from the `oidc` user manager and, on 401, asks the manager for one refresh (single flight, shared by concurrent requests) before signing out.
- **Generated client:** built from `api/openapi.json` into `app/lib/api/` by `cargo xtask openapi`. The generator (`swagger_parser` or `openapi-generator` `dart-dio`) is confirmed at the start of P8 and never edited by hand.
- **Environments:**
  - `--dart-define-from-file=config/{development,qa,production}.json` supplies `API_BASE_URL` and `ENV`.
  - Android product flavors and iOS schemes named `development`, `qa`, and `production` use distinct app IDs (`io.github.asm2025.postly.dev`, `.qa`, and `io.github.asm2025.postly`), so all three can be installed side by side.
- **Screens:**
  - Sign in: one button that opens the IdP.
  - Pending approval: shown while `/me` reports `pending`, with a refresh button and sign-out.
  - Disabled: an explanation and sign-out.
  - Dashboard shell: responsive layout (navigation rail on wide screens, drawer on narrow), an empty Home, and a Profile page (IdP-owned name and email with a link to the IdP account page, and sign-out).
  - **Users** (admin only): list with search, status filter, and pagination; approve, disable, re-enable, change role, delete. A badge shows the pending count.
  - **Jobs** (admin only, added in P8): a Hangfire-style console.
    - Dashboard: counters per state, a throughput chart, and queue depth, refreshed by polling.
    - A list per state with filters by job type and time range.
    - Job detail: summary IDs, attempts, timings, and redacted errors, with retry, cancel, or delete as the state allows.
    - Recurring jobs: schedule, last run and outcome, next run, and trigger-now.
    - Destructive actions ask for confirmation. A failed-jobs badge appears in the admin navigation.
- **Theme and UI:** light, dark, and system theme. Errors are mapped from the problem+json `code` to user-facing messages.
- **Tests:**
  - Unit tests for the auth state machine and the interceptor, using a mocked HTTP adapter and a fake `oidc` manager.
  - Widget tests for the screens and redirects (signed out, pending, disabled, active, admin).
  - An `integration_test` smoke flow against the dev stack with Zitadel (opt-in, not in CI).

## Testing and CI

- **Rust:**
  - Unit tests per crate.
  - Integration tests against real Postgres (`#[sqlx::test]`). CI uses a `postgres:18` service container.
  - A test OIDC issuer in `postly-identity` (feature `testkit`) mints RS256 and ES256 tokens and serves discovery and JWKS through wiremock.
  - Verifier tests: wrong issuer, wrong audience, expired, not yet valid, bad signature, `alg: none`, HMAC with the public key, unknown `kid` refetch and its rate limit, key rotation.
  - Identity tests: concurrent first sign-in creates one user, the pending gate, the disabled gate, bootstrap only while no admin exists, `admin_email` ignored without `email_verified`, the last-admin guard, pending cleanup, and the production bootstrap refusal.
  - Redaction tests for config dumps, errors, and logs, covering bearer tokens and SMTP passwords.
- **GitHub Actions:**
  - **`server` job (Linux):** `cargo fmt --check`; `cargo clippy --workspace --all-targets --all-features -- -D warnings`; `cargo test --workspace` with a Postgres service; `cargo sqlx prepare --check --workspace`; `cargo deny check`.
  - **`server-windows` job:** `cargo check` and `clippy`, with no database.
  - **`contract` job:** runs `cargo xtask openapi` and fails if `api/openapi.json` or the generated Dart client differ from the committed files.
  - **`app` job:** `flutter analyze`, `flutter test`, and `flutter build web --dart-define-from-file=config/qa.json`.
  - **`docker` job:** builds the image (no push) and runs a container smoke test: compose with Postgres and a wiremock issuer, then check `/health` and `/ready`.
- CI never needs real SMTP, certificates, an IdP, or social credentials.

## Phases

### P1: Monorepo restructure and workspace foundation

- Move the Cargo workspace into `server/`: root `Cargo.toml`, `[workspace.package]`, `[workspace.dependencies]`, `[workspace.lints]`, and the existing `release`, `dist`, and `dev.package."*"` profiles.
- Add `rust-toolchain.toml` (1.98.1, rustfmt and clippy) and `deny.toml`.
- Create empty crates `config`, `http`, `data`, `jobs`, `mail`, `identity`, `api`, and `server` (bin `postly`), plus `xtask`.
- Add the async trait-object compile test and record the chosen approach.
- Remove starter dependencies that no crate uses: `dotenv`, `log`, the `blocking`, `cookies`, and `socks` reqwest features, `html-entities`, and `num_cpus`.
- Update `.gitignore` for certificates, `local.toml`, Zitadel machine keys, `.env` files, and Flutter build output.
- Add a CI skeleton with the `server` and `server-windows` jobs.

**Exit:** the quality gates pass in `server/`, `postly --version` runs, and CI is green.

### P2: Configuration, environments, and outbound HTTP

- Implement `postly-config` as described: the environment enum, layered TOML, env vars, `_FILE` secrets, validation, and the redacted dump.
- Add `config/*.toml` for all three environments and `deploy/env/*.env.example`.
- Implement the foundation `postly-http`.

**Exit:** precedence tests, unknown-key and invalid-value errors, a release build refusing to start without `POSTLY_ENV`, redaction tests, and `postly-http` timeout and redaction tests against wiremock all pass.

### P3: Dev infrastructure and the development IdP

- Add `cert.ps1` and `cert.sh`, and document the hosts entry.
- Add `compose.yaml` (postgres) and `compose.dev.yaml` (nginx with TLS server blocks for 44300, 44305, 44310, 44320, and 44330, Mailpit, Zitadel, and the published ports).
- Add `docker/shared/nginx/nginx.conf`, `docker/zitadel/`, `server/Dockerfile`, and `.dockerignore`.
- Add `cargo xtask zitadel-bootstrap`.
- Write the README quick start for Windows first, with Linux and macOS notes.

**Exit:** on a fresh Windows machine, following the README yields a trusted `https://postly.local:44330/.well-known/openid-configuration`, a Zitadel login for `admin@postly.local` and `member@postly.local`, Zitadel email arriving in Mailpit at `https://postly.local:44320`, and `local.toml` populated by the bootstrap task. Until P7, nginx serves a placeholder on 44300.

### P4: Data layer and identity

- Implement `postly-data`: the pool, migrations for `users`, `audit_events`, and `user_preferences`, `OwnerScope`, the repositories, and the committed `.sqlx` cache.
- Implement `postly-identity`: discovery and JWKS, the verifier, claims transformation, bootstrap, the user administration service, audit events, and the test issuer.

**Exit:** `#[sqlx::test]` suites cover every repository; migrations apply from empty; `cargo sqlx prepare --check` passes; the verifier and identity tests listed under Testing pass; no token appears in any `Debug` output, error, or audit row.

### P5: Jobs and mail

- Implement `postly-jobs`: the `JobQueue` seam, the apalis Postgres storage and worker runner, and cron registration.
- Implement `postly-mail`: `Mailer`, templates, `MailOutbox`, and `send_email`.
- Wire identity's approval emails and the `purge_pending_users` cron job.

**Exit:**
- A job enqueued through `JobQueue` runs in a worker.
- A new user's first sign-in emails every active admin: in Mailpit in development and in `MemoryMailer` in tests. Approval emails the user.
- The cron job fires on schedule (with an injected clock or a short test schedule).
- No apalis type appears in another crate's public API.

### P6: API and server binary

- Implement `postly-api`: the router, middleware, extractors, problem+json, the endpoints, and OpenAPI with Swagger UI sign-in.
- Implement `postly-server`: the roles, rustls TLS, graceful shutdown, and `healthcheck`.

## Risks and checks at phase start

- **apalis 1.0 is a release candidate.** Pin an exact version and re-check releases at the start of P5. The seam contains the fallout.
- **Zitadel setup (P3).** Confirm the current Zitadel version, whether its login UI runs as a separate container, its supported Postgres versions (use a separate Postgres container for Zitadel if 18 is unsupported), the first-instance config keys, and that JWT access tokens carry the project ID in `aud`. Native desktop loopback redirects may need Zitadel's development mode for `http://127.0.0.1`.
- **Flutter `oidc` package (P7).** Confirm web token storage, refresh behavior, and desktop loopback support. Confirm the Flutter web-dev-server TLS options and the Dart OpenAPI generator.
- **Mobile trust of the self-signed dev certificate** is the most fragile part of the dev setup, now for two hosts (API and IdP). The debug-only trust configuration must never ship in `qa` or `production`; P10 enforces it.
- **IdP outage.** If the IdP is down, nobody can sign in, but already-issued access tokens keep working until they expire because the JWKS is cached. Documented.
- **Cross-process principal cache.** A disabled user keeps access for up to `auth.principal_cache_ttl` on other processes. Default 60 seconds; documented.
