# Foundation

> Plan 02 (2026-09-25). Phases P1–P10. Read [01. Vision and architecture](01.%20vision%20and%20architecture.md) first: the decisions, engineering standards, crate dependencies, identity and access model, and data model live there and are not repeated here. [03. Publishing roadmap](03.%20publishing%20roadmap.md) builds on this plan.

## Objective

When this plan is done, postly is a working vertical slice:

- A Dockerized Rust API server and background worker run against PostgreSQL in `development`, `qa`, and `production`.
- Users sign in through OIDC. In development that is a bundled Zitadel; in CI, an in-process test issuer.
- The first admin is bootstrapped from config. New users land in `pending` until an admin approves them, and admins get an email about each one.
- A Flutter app for web, desktop, and mobile signs in through the IdP, shows a pending screen or the dashboard shell, and gives admins user management and an audit log.
- apalis, behind our own seam, sends email and runs a recurring cleanup job. Admins watch and manage jobs from a Hangfire-style Jobs page in Flutter.

No social-platform, delegation, drafting, or publishing features are in this plan. Plan 03 adds them.

## Crates in this plan

`config`, `http`, `data`, `jobs`, `mail`, `identity`, `api`, and `server` (bin `postly`), plus `xtask`. `core` is also created here, in P1, but only as a skeleton with the ID newtypes, `Clock`, and `IdGenerator`, because `data` and `identity` need them. Plan 03 phase A1 adds the domain models and the plugin contract. Their order and ownership are defined in plan 01, [Crate dependencies](01.%20vision%20and%20architecture.md#crate-dependencies).

## Environments

### Environment selection

- `POSTLY_ENV` is `development`, `qa`, or `production`. Any other value fails startup.
- It defaults to `development` only when it is unset *and* the binary is a debug build. A release build without `POSTLY_ENV` refuses to start.

### Configuration layering

Configuration is loaded with `figment`, and later layers override earlier ones:

1. `config/default.toml`
2. `config/{env}.toml`
3. `config/local.toml` (development only, git-ignored)
4. `POSTLY__SECTION__KEY` environment variables (`__` separates nesting levels)
5. `POSTLY__…__KEY_FILE` variants, which read the value from a file (Docker and Kubernetes secrets)

Secrets deserialize into `SecretString`. At startup the server logs the effective config with secrets redacted. Invalid config exits non-zero with actionable messages.

### Per-environment behavior

| Setting | development | qa | production |
|---|---|---|---|
| Logs | pretty, `debug` | JSON, `info` | JSON, `info` |
| Swagger UI `/docs` | on | on | off (`/api/openapi.json` stays available) |
| CORS allowed origins | `https://postly.local:44310` | configured | configured |
| OIDC issuer | `https://postly.local:44330` (bundled Zitadel) | configured, required | configured, required |
| Bootstrap admin | `admin@postly.local` (Zitadel seed user) | configured | required at first boot when no admin exists |
| Mail transport | Mailpit (SMTP on 44325) | SMTP (use a test inbox) | SMTP |
| TLS | server or nginx terminates with the dev cert | reverse proxy | reverse proxy |

### Development hosting

- **Domain:** `postly.local` resolves to `127.0.0.1` and `::1` through `C:\Windows\System32\drivers\etc\hosts` (or `/etc/hosts`). A `localhost` request redirects to `postly.local`.
- **Certificates:** `cert.ps1` and `cert.sh` take `gen`, `trust`, `setup` (the default), and `help`, following the VigilixMambo scripts. They create a self-signed certificate with SAN `DNS:postly.local, IP:127.0.0.1, IP:::1` in `.crt`, `.key`, and `.pfx` form under `docker/shared/nginx/certs/`, and install it into the Windows Trusted Root store (`certutil -addstore Root`, which needs an elevated shell) or the Linux/macOS equivalent. Key material is git-ignored.
- **Port map.** All dev ports sit in 44300–44399. 44301–44304 are reserved as a gap after the API.

| Port | Service |
|---|---|
| 44300 | API: `/api/v1/*`, `/docs`, `/api/openapi.json`, `/health`, `/ready` |
| 44305 | Worker: `/health`, `/ready` |
| 44310 | Flutter web |
| 44320 | Mailpit web inbox |
| 44325 | Mailpit SMTP |
| 44330 | Zitadel (issuer, login UI, console) |
| 44340 | Postgres (published for SQLx tooling and `cargo sqlx prepare`) |

- **Docker dev** (`docker compose -f compose.yaml -f compose.dev.yaml --profile app up`):
  - Two nginx services terminate TLS with the dev cert and proxy to plain-HTTP containers:
    - `nginx-infra` (always on) serves 44320 (Mailpit) and 44330 (Zitadel).
    - `nginx-app` (profile `app`) serves 44300 and 44305 (`server`, role `all`) and 44310 (the Flutter web build, served by the same `server` container on its web port; see [Web client hosting](#web-client-hosting)). It sets `client_max_body_size` to the media chunk limit and turns off request buffering for upload routes.
  - Zitadel uses its own database (`zitadel`) on the same Postgres server, created by an init script in `docker/postgres/init/`, and sends its email to Mailpit.
  - Postgres and Mailpit SMTP publish their ports as shown above.
  - Containers trust the dev cert through a mounted CA file. `nginx-infra` has the network alias `postly.local`, so the server reaches Zitadel's discovery document and JWKS at the same issuer URL the browser uses.
  - The `server` container runs `POSTLY_ENV=development` with compose environment overrides: plain HTTP on 8080 and 8081 (`POSTLY__SERVER__TLS__ENABLED=false`), Postgres and Mailpit (`mailpit:1025`) by service name, and the Docker network in `server.trusted_proxies` so `nginx-app` can forward client IPs.
- **Zitadel bootstrap.** `docker/zitadel/` holds the first-instance config: an organization, a human admin `admin@postly.local` with its email marked verified (so `auth.bootstrap.admin_email` matches; password in the README, change forced at first login), and a machine user whose key is written to a git-ignored path. `cargo xtask zitadel-bootstrap` then uses that key with the Zitadel management API to create, idempotently:
  - A project `postly` whose ID becomes the API audience.
  - A user-agent/native application with PKCE, JWT access tokens, the refresh-token grant, and development mode (needed for the `http://127.0.0.1` desktop loopback).
    - Redirect URIs: the Flutter ones listed under [Flutter client](#flutter-client-app) and Swagger UI's `https://postly.local:44300/docs/oauth2-redirect.html`.
    - Post-logout redirect URIs: the web origin and the native schemes.
  - A second human user `member@postly.local`, email verified, for testing approvals and, later, delegation.
  - It writes the issuer, audience, and client ID into `server/config/local.toml` and the Flutter `config/development.json`.
- **Native dev** (`cargo run` and `flutter run`):
  - Only `postgres`, `mailpit`, `zitadel`, and `nginx-infra` come from compose (no `app` profile), so ports 44300–44310 stay free for `cargo run` and `flutter run`.
  - The server terminates TLS itself with rustls (`axum-server`) when `server.tls.enabled` is true. `development.toml` enables it, points `server.tls.cert_path` and `server.tls.key_path` at the generated cert, and sends mail to Mailpit on `localhost:44325`.
  - In role `all`, the API binds 44300 and the worker endpoints bind 44305.
  - Flutter web runs on 44310 with the same certificate.
- **CORS.** The API uses bearer tokens only and sets no cookies. CORS allows the web origin and no credentials.
  - Allowed request headers: `Authorization`, `Content-Type`, `X-Postly-Act-As`, `If-Match`, `If-None-Match`, and `Idempotency-Key`.
  - Exposed response headers: `ETag`, `Location`, `Retry-After`, and `x-request-id`, so Flutter web can read them.
  - QA and production use the same shape, for example `api.example.com` and `app.example.com`.
- **Mobile dev.** Emulators and devices don't read the host's hosts file or trust store.
  - The Flutter `development` flavor includes a debug-only trust configuration for the dev certificate: Android `network_security_config` in the `development` source set only, and a documented profile install for the iOS simulator. It covers both the API and Zitadel.
  - The README documents name resolution: `adb reverse` or the emulator hosts file for Android, the Mac hosts file for the iOS simulator, and a LAN IP mapped to `postly.local` for physical devices.

### QA and production hosting

- The same image is promoted through dev, QA, and production. Only configuration changes.
- `compose.qa.yaml` and `compose.prod.yaml` run separate `api` and `worker` services with restart policies and Docker `secrets:`. They publish no database port and include no nginx and no IdP. The operator runs or subscribes to an OIDC provider; the docs cover Zitadel and list the generic requirements (JWT access tokens with postly's audience, PKCE public client, the redirect URIs).
- TLS is terminated by the operator's reverse proxy on 443 using configured hostnames. The 443xx convention applies to development only. The README gives a Caddy example; it isn't bundled.
- `server.trusted_proxies` (CIDRs) controls which hops may set `X-Forwarded-For`, which rate limiting and audit use.
- The proxy sets security headers for the web app (`Content-Security-Policy` allowing only the API and IdP origins, `frame-ancestors 'none'`, HSTS); the README's Caddy example includes them.

### Web client hosting

- The `postly-server` image contains the Flutter web build. Roles `all` and `api` serve it when `server.web.enabled` is true: on `server.web.bind` (a separate port; 44310 in development) or, when that is unset, at `/` on the API port (paths under `/api`, `/docs`, `/health`, and `/ready` excluded). Unknown paths fall back to `index.html`, so deep links such as `/auth/callback` load.
- `GET /config.json` on the web origin returns the runtime settings the web build needs (`API_BASE_URL`, `ENV`) from `server.web`. The web build reads it at startup instead of compile-time defines, so the same image serves every environment. Native builds keep `--dart-define-from-file`.
- Serving the web app from the API origin makes CORS unnecessary for it; a separate app host (`app.example.com` proxied to the web port) uses the configured CORS origins.
- In native development `development.toml` leaves `server.web.enabled` off, because `flutter run -d web-server` owns 44310 and serves a dev `web/config.json`. Docker development turns it on through compose overrides, on container port 8082 behind `nginx-app`.

## Server design

### Process roles

- `POSTLY_ROLE=all` (the development default) runs the API and the worker in one process. `api` runs only the HTTP API and enqueues jobs. `worker` runs only the job runner and its small HTTP surface on the worker port.
- Every role runs postly's migrations and then apalis's migrations at startup, each under a Postgres advisory lock. Concurrent starts are safe, and the `api` role can enqueue before any worker has started. apalis keeps its tables in its own schema.
- The only flags are `postly --version` and `postly healthcheck`. The second calls `/health` over plain HTTP on the local port of its role (the API port for `all` and `api`, the worker port for `worker`) and serves the Docker `HEALTHCHECK`.
- Readiness per role:
  - API `/ready`: the database is reachable and the JWKS is loaded.
  - Worker `/ready`: the database is reachable and the job storage is migrated. The worker does not need the JWKS.
- Shutdown is graceful on SIGTERM and Ctrl-C: stop accepting work, drain in-flight requests and jobs for up to `server.shutdown_timeout` (default 30 s), then close the pool. Compose sets `stop_grace_period` above that timeout. A job still running at the timeout is left to apalis's retry, which is safe because handlers are idempotent.

### `postly-config`

- Holds the typed settings tree:
  - `server`: bind addresses, TLS (`enabled`, cert and key paths), trusted proxies, public URLs, `shutdown_timeout`, and `web` (`enabled`, `root`, `bind`, `api_base_url`).
  - `database`.
  - `auth.oidc`: issuer, audiences, client ID and scopes for the Flutter client, accepted algorithms, leeway, JWKS refresh interval, claim names, `userinfo` (`fallback`, `always`, or `never`; default `fallback`), and an optional `account_url` for the IdP's account page (standard discovery has no such field).
  - `auth.bootstrap`: `admin_email` or `admin_subject`.
  - `auth.pending_ttl`, `auth.principal_cache_ttl`, `auth.approval_email_interval`.
  - `audit`: `retention`, `ip_retention`, and `pseudonym_key` (a `_FILE` secret). `qa` and `production` refuse to start without it. `development.toml` ships a fixed key that is clearly marked insecure and dev-only.
  - `retention`: the data retention periods from plan 01, [Data retention](01.%20vision%20and%20architecture.md#data-retention).
  - `ops`: `ops_health` thresholds (plan 01, [Rust practices](01.%20vision%20and%20architecture.md#rust-practices)).
  - `rate_limit`: per-IP rate and burst for unauthenticated requests, a stricter limit for requests that provision a user, and per-user rate and burst for authenticated requests (keyed by user ID, so a team behind one NAT address does not share a bucket).
  - `mail`: transport, from address, SMTP.
  - `jobs`: concurrency per queue, cron schedules, outbox relay poll interval, and job history retention (`retention.succeeded`, default 7 days; `retention.failed`, default 30 days).
  - `http`: timeouts, user agent, extra trusted CA files (for the dev IdP).
  - `app.public_url`: the web app, used in email links.
  - `cors`.
- Owns the environment enum, the layering, the `_FILE` secret resolution, validation, and the redacted dump.
- Validation: the issuer must be `https` outside development; `audiences` must be non-empty; the bootstrap email and subject are mutually exclusive; `audit.pseudonym_key` is required outside development.

### `postly-http`

The foundation version of the only `reqwest` factory. Plan 03 phase B1 extends it.

- rustls with the platform's native root store (`rustls-native-certs`) plus extra CA files from config, connection pooling, per-request and connect timeouts, user agent, gzip. No global `Content-Type` and no cookie store.
- Request IDs, tracing spans, and redaction of `Authorization` headers and token-bearing query parameters.
- An `HttpError` with retry classification (transient, rate-limited, permanent). Plugins map it to `PlatformError` in plan 03; `postly-http` does not know about platforms.
- Test helpers: a wiremock server builder.

### `postly-data`

- Owns the `PgPool` factory with its timeouts and pool size, the embedded migrations, and the repositories.
- Migrations in this plan: `users`, `audit_events`, `user_preferences`, and `idempotency_keys` (P4), and `job_recurring_runs` and `job_outbox` (P5), as defined in plan 01, [Data model](01.%20vision%20and%20architecture.md#data-model). Actor columns are nullable FKs with `ON DELETE SET NULL`. Plan 03's owned tables follow the `(owner_id, id)` composite-FK rule from plan 01.
- **Migrations stay compatible with the previous release.** During an upgrade the new `api` container migrates while the old `worker` still runs, so a release only adds (new tables, nullable or defaulted columns); dropping or renaming happens in a later release, once no running version reads the old shape (expand, then contract). The upgrade docs (P9) state this, and a migration review checklist enforces it.
- **Database privileges.** postly connects as the owner of its database and runs migrations with that role. `citext` is a trusted extension, so the first migration runs `CREATE EXTENSION IF NOT EXISTS citext` without superuser rights. The docs cover managed Postgres services that restrict extensions.
- **`AuditLog`**: the only writer of `audit_events`. It takes a typed event, puts other user references in `details` keys ending in `_user_id`, and rejects secret-typed values. The admin audit repository reads events for `GET /admin/audit`.
- **Data retention:** `postly-data` owns the purge queries that apply `[retention]`. In this plan they purge `idempotency_keys`; plan 03 phases add notifications, delivery attempts, and AI generations as they create those tables. `data` sits below `jobs`, so it cannot register a job itself: `postly-server` registers the daily `data_retention` cron job that calls these queries.
- **User-change notifications:** a `LISTEN postly_user_changed` task that evicts principal cache entries, clearing the whole cache on reconnect.
- **`OwnerScope`** is defined here now, with `actor`, `owner`, and `access`, even though only `Access::Owner` exists until plan 03 adds delegation. `OwnerScope::require(capability)` exists from the start, so no call site changes later.
- Admin repositories (users, audit) are separate types from owner-scoped repositories and cannot read owned content.
- Repository APIs return domain types. List endpoints use `emixdb::Pagination` and `ResultSet<T>`.
- Tests use `#[sqlx::test]` with a per-test database.

### `postly-jobs`

- **The seam:** a `JobQueue` trait (`enqueue`, `enqueue_at`, and `enqueue_in(&mut tx, …)`) plus a typed job registration API. apalis types never leave this crate.
- **Transactional enqueue (outbox).** `enqueue_in` inserts a `job_outbox` row in the caller's transaction, so the job exists if and only if the change committed. A relay in every process that runs a worker, woken by `NOTIFY` on commit and by a short poll, moves outbox rows into the apalis storage and deletes them in the same transaction. Duplicates after a relay crash are harmless because handlers are idempotent. `enqueue` and `enqueue_at` remain for work not tied to a transaction.
- **Queues.** Job types are assigned to named queues (`mail`, `publishing`, `maintenance`, `default`), each with its own concurrency from `jobs`, so long uploads cannot starve email or cleanup.
- **Retry policy per job type.** Each registration sets its apalis retry policy. Jobs whose domain state machine does its own retrying (plan 03's `publish_delivery`, `poll_delivery_status`, `reconcile_delivery`) run with no apalis retry; a handler crash is recovered by the domain's sweep instead.
- **The worker runner** builds the apalis monitor from config: queues and their concurrency, the per-type retry policies with exponential backoff, and Postgres storage in its own schema with LISTEN/NOTIFY fetch.
- **Recurring jobs** go through `apalis-cron`, registered with the same API, and each tick becomes an enqueue into the Postgres storage:
  - The tick first inserts a `job_recurring_runs` row keyed on (name, scheduled tick) with `ON CONFLICT DO NOTHING`. Only the process whose insert succeeded enqueues, so with several worker processes each tick still runs once.
  - The row records the run's job ID and outcome, which the console shows as last run and outcome.
  - Trigger-now inserts a manual row and enqueues through the storage. The `api` role never runs a job in-process.
- **Job history retention:** the `job_history_purge` cron job (daily) deletes succeeded jobs after `jobs.retention.succeeded` and failed, dead, or killed jobs after `jobs.retention.failed`, along with `job_recurring_runs` rows older than both.
- **Job console API.** A `JobConsole` trait next to `JobQueue`, implemented over apalis-postgres's listing and metrics interfaces (the ones apalis-board uses), so apalis types stay inside this crate:
  - List jobs by state (`queued`, `scheduled`, `running`, `succeeded`, `failed`, `dead`, `killed`), job type, and time range, with pagination.
  - Job detail: type, state, attempts, timings, and each attempt's error.
  - Stats: counts per state and per job type, queue depth, and throughput over recent windows.
  - Actions: retry a failed or dead job, cancel a queued or scheduled job, delete a finished job.
  - Recurring jobs: name, cron expression, last run and outcome, next run, and trigger-now.
  - Every action takes the acting admin and records an audit event (`job_retried`, `job_cancelled`, `job_deleted`, `job_triggered`) with the job ID and type.
- **Safe summaries.** Every job type registers a `JobSummary` that exposes only its type and IDs (user, delivery, account, …). The console never returns raw job payloads, so admins never see post text, emails, or secrets.
- **Safe errors.** Redaction removes secrets but not user content, and a platform error body can echo a caption. So the console shows a job's error as its classified error kind and code only. A job type may opt in to showing the redacted message when its errors cannot contain user content (for example, `job_history_purge`).
- **Console actions per job type.** Each registration declares which console actions apply. Jobs driven by domain state (plan 03's publishing jobs) disable console retry and cancel and explain why: the delivery's state decides whether work happens, so the user acts on the delivery instead.
- **Retry is safe by design.** Every job handler must be idempotent against its own domain state. For example, a re-queued `publish_delivery` finds nothing to claim unless its delivery is still `pending`. Plan 03 phases test this for each job type they add.
- **No apalis-board.** It would need browser-cookie auth that postly does not have. The Flutter Jobs page (P8) replaces it.
- **Version risk:** apalis 1.0 was at a release candidate (`1.0.0-rc.10` on 2026-09-15; stable 0.7.4). Pin an exact version (`=`) and check the latest release at the start of P5. Upgrades touch only this crate.

### `postly-mail`

- The `Mailer` trait with `SmtpMailer` (`lettre`, TLS or STARTTLS, credentials as `SecretString`) and `MemoryMailer` for tests.
- Messages are rendered from embedded `askama` templates in plain text and HTML. Email links use `app.public_url`.
- **Payloads carry IDs, not content.** Callers never send inline. They call `MailOutbox::send` with a mail kind, a recipient user ID, and typed ID parameters (for example, the IDs of the newly pending users). The call enqueues the `send_email` job.
- **Rendering happens when the job runs.** The job reads the recipient through `postly-data`. Each mail kind registers a context loader, implemented by the crate that owns the data (`identity` in this plan, `notify` in plan 03), which loads the current data by ID. No address, name, or body is ever stored in the job tables.
- **Dropped mail.** A recipient who was deleted, is not `active`, or has no verified email is dropped instead of sent. Referenced users who no longer exist are left out of the message.
- **Opt-out.** The `email_notifications` preference applies to workspace notification emails (plan 03, `postly-notify`). Account emails (`user_approved`) and admin emails (approval requests, `ops_health` alerts) are always sent, so no admin can silence the only alert channel by accident.
- **Sent markers.** Each mail kind's context loader also reports and records its sent marker (`notifications.emailed_at`, `user_preferences.last_approval_email_at`, …). The handler skips mail already marked and writes the marker after the SMTP accept. Delivery is at-least-once: a crash between the accept and the marker write can send twice.
- The `send_email` job is retried with backoff and gives up after a configured budget. It records `email_sent`, `email_dropped`, or `email_failed` audit events with the recipient ID and mail kind.
- Templates in this plan: `user_pending_approval` (to admins) and `user_approved` (to the user).

### `postly-identity`

Owns OIDC verification, claims transformation, users, roles, and bootstrap. It has no HTTP types.

- **Verifier:**
  - `OidcDiscovery` loads the discovery document and JWKS through `postly-http`. A `JwksSource` trait allows a static test source.
  - JWT validation with the `jsonwebtoken` crate (confirm at the start of P4; `openidconnect` is the alternative if it helps with discovery). Rules are in plan 01, [Authentication](01.%20vision%20and%20architecture.md#authentication-oidc).
  - Unknown `kid` triggers at most one refetch per minute.
- **Claims transformation** into a `Principal`, as in plan 01, [Claims transformation](01.%20vision%20and%20architecture.md#claims-transformation), including the userinfo fallback for profile claims missing from the access token and `pg_notify` on admin changes.
  - A userinfo response is used only when its `sub` equals the token's `sub`.
  - `display_name` comes from `name`, then `preferred_username`, then `email`, then the subject, so it is never empty. `DELETE /me` confirms against it.
  - `last_seen_at` is written only on a principal cache miss, so at most once per `auth.principal_cache_ttl` per process.
  - Provisioning runs in one transaction with `INSERT … ON CONFLICT (oidc_issuer, oidc_subject) DO NOTHING`, so two concurrent first requests create one user.
- **Bootstrap:** a user matching `auth.bootstrap` becomes an active admin only while no active admin exists. The check and the insert run under a transaction-scoped advisory lock, so two concurrent bootstrap-eligible sign-ins produce one admin. `admin_email` requires `email_verified = true`.
- **Approval-request emails** are coalesced per admin by `auth.approval_email_interval`, as described in plan 01, [Roles and statuses](01.%20vision%20and%20architecture.md#roles-and-statuses). At startup, production fails with a clear message if no active admin exists and no bootstrap rule is set.
- **User administration service.**
  - Status changes through `PATCH`: `pending` to `active` (approve, sends `user_approved`), `active` to `disabled`, and `disabled` to `active`. Any other transition returns 422 `validation_failed`. Role changes apply to `active` and `disabled` users.
  - Rejecting a pending user is a delete.
  - An admin cannot delete themselves through `DELETE /users/{id}` (403 `forbidden`). They use `DELETE /me`.
  - Both deletion paths set the user to the terminal `deleting` status and run the resumable `delete_user` job from plan 01, [User deletion](01.%20vision%20and%20architecture.md#user-deletion), including the HMAC pseudonymization of every audit column and `_user_id` details key; plan 03 extends the job for owned content. Status changes on a `deleting` user return 409 `user_deleting`. The last active admin cannot be disabled, demoted, or deleted.
- **Pending cleanup:** the `purge_pending_users` cron job (daily) sets each `pending` user older than `auth.pending_ttl` to `deleting` and enqueues `delete_user` for them, so their audit events are pseudonymized like any other deletion.
- **Audit retention:** the `audit_retention` cron job (daily) applies `audit.ip_retention` and `audit.retention`.
- **Audit events:** `user_provisioned`, `user_approved`, `user_disabled`, `user_enabled`, `role_changed`, `user_deleted`, `bootstrap_admin_granted`.

### `postly-api`

- An axum router under `/api/v1` with tower middleware:
  - Request ID propagated as `x-request-id`.
  - Tracing spans with redaction.
  - Timeout and body size limit. A route can declare its own timeout and body limit (plan 03 uses this for media uploads, the public media route, and AI generation); every other route gets the global values.
  - CORS from config.
  - `tower_governor` rate limiting from `[rate_limit]`: unauthenticated requests keyed by client IP after trusted-proxy resolution, authenticated requests keyed by user ID.
- **Errors:** RFC 9457 problem+json with a stable `code`. Codes in this plan: `unauthenticated` (401 with `WWW-Authenticate: Bearer error="invalid_token"`), `account_pending`, `account_disabled`, `forbidden`, `not_found`, `validation_failed`, `last_admin`, `user_deleting`, `rate_limited`, `version_conflict` (412), `precondition_required` (428), `idempotency_key_reused`, `idempotency_in_progress` (409).
- **API compatibility.** Within `/api/v1`, changes are additive: new routes, new optional fields, and new enum values that clients must tolerate. The `contract` CI job diffs `api/openapi.json` against the previous release and fails on removed or changed operations, so older mobile and desktop builds keep working.
- **Idempotency and preconditions:** middleware for the optional `Idempotency-Key` header on create endpoints and a helper that checks `If-Match` against a resource version, both per plan 01. Plan 03 applies them to its routes. Plan 02 has no create endpoint, so tests exercise both through a test-only route compiled under `cfg(test)`.
- **Extractors:** `Auth` runs the verifier and claims transformation and yields the `Principal`. `ActiveUser` rejects `pending`, `disabled`, and `deleting`. `RequireAdmin` checks the caller's own role. `Scope` builds the `OwnerScope` (self only in this plan; plan 03 adds the act-as header here and nowhere else, and admin routes reject it).
- **Endpoints:**

| Method and path | Auth | Purpose |
|---|---|---|
| `GET /api/v1/auth/config` | none | Issuer, client ID, and scopes for the Flutter client. |
| `GET /api/v1/me` | any signed-in user, including `pending` | Profile, role, and status. |
| `DELETE /api/v1/me` | active user, own workspace only (never act-as) | Delete own account; the body must repeat the display name. 202 once `deleting` is set and the job is enqueued. 409 `last_admin` for the last active admin. |
| `GET /api/v1/users` | admin | Paginated list with search and a status filter. |
| `GET /api/v1/users/{id}` | admin | Detail view. |
| `PATCH /api/v1/users/{id}` | admin | Change role or status (approve, disable, re-enable), per the allowed transitions above. |
| `DELETE /api/v1/users/{id}` | admin | Delete another user, or reject a pending one. 202 once `deleting` is set and the job is enqueued. |
| `GET /api/v1/admin/audit` | admin | Audit events filtered by kind, time range, and actor or subject user ID, paginated. Pseudonymized IDs are marked as deleted users. |
| `GET /api/v1/admin/jobs` | admin | Jobs filtered by state, type, and time range, paginated. |
| `GET /api/v1/admin/jobs/stats` | admin | Counts per state and type, queue depth, throughput. |
| `GET /api/v1/admin/jobs/{id}` | admin | Job detail with attempts and redacted errors. |
| `POST /api/v1/admin/jobs/{id}/retry` | admin | Re-queue a failed or dead job. |
| `POST /api/v1/admin/jobs/{id}/cancel` | admin | Cancel a queued or scheduled job. |
| `DELETE /api/v1/admin/jobs/{id}` | admin | Delete a finished job. |
| `GET /api/v1/admin/jobs/recurring` | admin | Recurring jobs with schedule, last run, and next run. |
| `POST /api/v1/admin/jobs/recurring/{name}/trigger` | admin | Run a recurring job now. |
| `GET /health`, `GET /ready` | none | Liveness and readiness, per role (see [Process roles](#process-roles)). |
| `GET /config.json` (web origin) | none | Runtime settings for the web build (see [Web client hosting](#web-client-hosting)). |

- Profile fields (name, email) come from the IdP and are read-only in postly. `GET /me` includes `auth.oidc.account_url` when it is configured.
- **OpenAPI:** `utoipa` generates the spec with an OAuth2 authorization-code (PKCE) security scheme pointing at the configured issuer. It is served at `/api/openapi.json`, with Swagger UI at `/docs` outside production, configured to sign in with the same public client. `cargo xtask openapi` writes `api/openapi.json`.
- Tests drive the router with `tower::ServiceExt::oneshot`, using a real Postgres (`sqlx::test`), a `MemoryMailer`, a test job queue, and a test issuer that mints tokens with a generated key.

### `postly-server` (bin `postly`)

The composition root:

1. Load config and initialize tracing.
2. Build the pool and run migrations.
3. Load OIDC discovery and the JWKS (retrying in the background; `/ready` stays false until loaded).
4. Check the production bootstrap rule.
5. Build the services and the job queue, and register job handlers.
6. Start the roles selected by `POSTLY_ROLE`, with optional rustls TLS, the web client when `server.web.enabled`, and the outbox relay in every process that runs a worker.
7. Shut down gracefully.

It also owns `postly healthcheck` and `postly --version`, and it is the only crate that uses `anyhow`.

### Docker image

- `server/Dockerfile` is multi-stage: `cargo-chef` for cached dependency layers, then a `SQLX_OFFLINE=true` release build (profile `dist`), a Flutter stage that runs `flutter build web` for `app/` (from P7; a placeholder page before that), then a `debian:trixie-slim` runtime. The Docker build context is the repository root.
- The runtime has CA certificates and the web build under `/srv/web`, runs as a non-root user, and declares `HEALTHCHECK CMD postly healthcheck`.
- `EXPOSE 8080` (API), `8081` (worker), and `8082` (web). Containers speak plain HTTP; nginx or the operator's proxy terminates TLS.
- Tags: `postly-server:<version>` and `postly-server:<git-sha>`.

## Flutter client (`app/`)

- **Toolchain:** latest Flutter stable at the start of P7, pinned in `pubspec.yaml` (`environment.flutter`) and in CI. Targets: web, Windows, macOS, Linux, Android, and iOS.
- **Stack:** `flutter_riverpod` for state, `go_router` with auth-aware redirects, and `dio` for HTTP.
- **Sign-in:** the `oidc` package (Bdaya) for authorization code with PKCE as a public client on every platform. The app reads issuer, client ID, and scopes from `GET /api/v1/auth/config`.
  - Redirect URIs: web `https://<web host>/auth/callback` (the web build ships the `oidc` package's callback page, and the web server falls back to `index.html`); Android and iOS a custom scheme per flavor (`postly-dev://auth/callback`, `postly-qa://…`, `postly://…`); desktop a loopback redirect on `127.0.0.1` with a random port.
  - Sign-out calls the IdP's end-session endpoint and clears local state.
  - Token storage uses the package's secure store on native (Keychain, Keystore, DPAPI, libsecret). On web, tokens stay in memory and session storage, and refresh relies on the IdP's refresh-token rotation or a silent renew. The exact web behavior is confirmed at the start of P7.
- **HTTP:** a dio interceptor attaches the access token from the `oidc` user manager and, on 401, asks the manager for one refresh (single flight, shared by concurrent requests) before signing out.
- **Generated client:** built from `api/openapi.json` into `app/lib/api/` by `cargo xtask openapi`. The generator (`swagger_parser` or `openapi-generator` `dart-dio`) is confirmed at the start of P7, and its output is never edited by hand. `cargo xtask openapi` writes only `api/openapi.json` in P6 and also generates the Dart client from P7.
- **Environments:**
  - Native builds: `--dart-define-from-file=config/{development,qa,production}.json` supplies `API_BASE_URL` and `ENV`.
  - Web: one build for every environment; it reads `API_BASE_URL` and `ENV` from `/config.json` at startup (see [Web client hosting](#web-client-hosting)).
  - Distribution: store releases and signed installers are a non-goal (plan 01). The README documents building each flavor from source and internal distribution.
  - Android product flavors and iOS schemes named `development`, `qa`, and `production` use distinct app IDs (`io.github.asm2025.postly.dev`, `.qa`, and `io.github.asm2025.postly`), so all three can be installed side by side.
- **Screens:**
  - Sign in: one button that opens the IdP.
  - Pending approval: shown while `/me` reports `pending`, with a refresh button and sign-out.
  - Disabled: an explanation and sign-out.
  - Dashboard shell: responsive layout (navigation rail on wide screens, drawer on narrow), an empty Home, and a Profile page (IdP-owned name and email with a link to the IdP account page, sign-out, and "Delete my postly account" with a type-your-name confirmation).
  - **Users** (admin only): list with search, status filter, and pagination; approve, disable, re-enable, change role, delete. A badge shows the pending count.
  - **Audit** (admin only): a paginated event list with filters by kind, time range, and user. Pseudonymized IDs show as "deleted user".
  - **Jobs** (admin only, added in P8): a Hangfire-style console.
    - Dashboard: counters per state, a throughput chart, and queue depth, refreshed by polling.
    - A list per state with filters by job type and time range.
    - Job detail: summary IDs, attempts, timings, and redacted errors, with retry, cancel, or delete as the state allows.
    - Recurring jobs: schedule, last run and outcome, next run, and trigger-now.
    - Destructive actions ask for confirmation. A failed-jobs badge appears in the admin navigation.
- **Theme and UI:** light, dark, and system theme. Errors are mapped from the problem+json `code` to user-facing messages.
- **Tests:**
  - Unit tests for the auth state machine and the interceptor, using a mocked HTTP adapter and a fake `oidc` manager.
  - Widget tests for the screens and redirects (signed out, pending, disabled, active, admin).
  - An `integration_test` smoke flow against the dev stack with Zitadel (opt-in, not in CI).

## Risks and checks at phase start

- **apalis 1.0 is a release candidate.** Pin an exact version and re-check releases at the start of P5. The seam contains the fallout.
- **Zitadel setup (P3).** Confirm the current Zitadel version, whether its login UI runs as a separate container, its supported Postgres versions (use a separate Postgres container for Zitadel if 18 is unsupported), the first-instance config keys, and that JWT access tokens carry the project ID in `aud`. Native desktop loopback redirects may need Zitadel's development mode for `http://127.0.0.1`.
- **Flutter `oidc` package (P7).** Confirm web token storage, refresh behavior, and desktop loopback support. Confirm the Flutter web-dev-server TLS options and the Dart OpenAPI generator.
- **Mobile trust of the self-signed dev certificate** is the most fragile part of the dev setup, now for two hosts (API and IdP). The debug-only trust configuration must never ship in `qa` or `production`; P10 enforces it.
- **IdP outage.** If the IdP is down, nobody can sign in, but already-issued access tokens keep working until they expire because the JWKS is cached. Documented.
- **Cross-process principal cache.** A disabled user keeps access for up to `auth.principal_cache_ttl` on other processes. Default 60 seconds; documented.
