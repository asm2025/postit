## Objective

postly is a self-hosted social publishing service for a small team. Each user signs in through the deployment's OpenID Connect provider, connects their own social accounts, creates posts by hand or with an LLM, publishes them immediately or on a schedule (postly-scheduled or platform-native), and tracks delivery history. A user can let another postly user work on their behalf through a scoped delegation.

The product has two parts:

- A Rust REST API and background worker on PostgreSQL, shipped as one Docker image.
- A Flutter client for web, desktop, and mobile.

There is no end-user CLI.

The initial platforms are X, YouTube, Facebook, Instagram, and TikTok. They are **compile-time plugins** to a platform-agnostic core: each platform is its own crate implementing the `PlatformPlugin` contract. New platforms (Threads, LinkedIn, Bluesky, Mastodon, …) are added without changing the core, the publishing engine, the schema, the REST API, or the Flutter client. Platform-specific OAuth details, validation, rate limits, upload protocols, and API types stay inside each platform crate.

## Decisions

### Product and deployment

| Topic | Decision |
|---|---|
| Product shape | Rust REST API with background jobs, plus a Flutter client (web, desktop, mobile). No end-user CLI. |
| Tenancy | One deployment per team. No multi-tenancy and no teams inside a deployment. |
| Repo layout | Monorepo: `server/` (Cargo workspace), `app/` (Flutter), `api/openapi.json` (generated contract), `docker/`, `deploy/`. |
| Processes | One binary `postly`, one image. `POSTLY_ROLE=all|api|worker`. |
| Environments | `POSTLY_ENV=development|qa|production`, with layered config per environment and matching Flutter flavors. |
| Dev hosting | `https://postly.local` with a self-signed cert trusted in the OS root store and a hosts-file entry. Ports in 44300–44399. |
| Database | PostgreSQL 18 via SQLx, with compile-checked queries and a committed offline `.sqlx` cache. |
| Background jobs | apalis (`apalis`, `apalis-postgres`, `apalis-cron`) with an exact version pin, wrapped by our own `JobQueue` and `JobConsole` seams in one crate. Admins get a Hangfire-style Jobs page in Flutter (list, stats, detail, retry, cancel, delete, recurring jobs, trigger-now). apalis-board is not used. |

### Identity and access

| Topic | Decision |
|---|---|
| User authentication | **Generic OpenID Connect only.** postly stores no passwords and issues no tokens. The API verifies bearer JWTs from one configured issuer. Code is provider-agnostic. |
| Identity provider | Deployment choice. Development compose and the docs bundle **Zitadel**. CI uses an in-process test issuer (wiremock JWKS). Kanidm, Authentik, Keycloak, and Firebase-style issuers work if they issue JWTs with the configured audience. |
| User key | `(issuer, sub)`. Never email. |
| Authorization | Owned by the postly database: role (`admin` or `member`) and status (`pending`, `active`, `disabled`, `deleting`). IdP role or group claims are ignored, so claim shapes do not matter. |
| Provisioning | First sign-in creates the user as `pending`. An admin approves before the user can do anything except read `/me`. |
| First admin | Bootstrapped from config (`auth.bootstrap.admin_email` with a verified email claim, or `auth.bootstrap.admin_subject`). Production refuses to start when no admin exists and neither is set. `admin_subject` is recommended for QA and production: `admin_email` trusts the IdP's `email_verified`, which federated or misconfigured IdPs may set for addresses the user does not control, and the first such sign-in wins. |
| Account email | Sign-up, passwords, MFA, and account recovery belong to the IdP. postly sends email only for its own events (approval requests, approvals, publishing notifications). |
| Ownership | **Private per user.** Social accounts, tokens, media, posts, jobs, deliveries, AI providers, and notifications belong to one user (`owner_id`). |
| Delegation | An owner can grant another active user scoped access to their workspace (levels `view`, `edit`, `publish`, optionally limited to chosen social accounts). No re-delegation. The delegate acts as the owner through a per-request act-as header. See [Delegation](#delegation). |
| Admin role | Admins approve and disable users, change roles, manage background jobs, and manage deployment settings: platform developer apps, the live-publishing kill switch, per-platform enablement, and diagnostics. Admins **cannot** read other users' content or secrets and cannot create delegations for others. This is an application-level boundary (see [Trust boundary](#trust-boundary)). |

### Publishing

| Topic | Decision |
|---|---|
| Platform developer apps | Deployment-level. One client ID/secret per platform in config (`[platforms.<id>]` plus `_FILE` secrets). Each user connects their own accounts through them. |
| LLM provider keys | Per user. Each user configures providers (opencode-shaped) with their own keys. No deployment-level AI config. |
| Stored secrets | Social tokens, PKCE verifiers, and LLM keys are sealed in Postgres with envelope encryption (`postly-vault`). |
| Social OAuth callback | Server-side: `https://<api host>/api/v1/platforms/{id}/oauth/callback`. The Flutter client opens the authorize URL and receives the result redirect. |
| Media hosting | Filesystem storage volume. Platforms fetch media through short-lived HMAC-signed public URLs. `MediaStore` and `MediaHost` are traits, so an S3 backend can be added later. |
| Live publishing | On in every environment. Every live publish requires explicit confirmation by the acting user. A runtime kill switch (`publishing.live`) and per-platform `enabled` flags stop postly-driven publishing. A per-publish dry-run toggle is always available. CI never publishes live. |
| Kill switch limit | The switches cannot stop deliveries already uploaded with native scheduling: the platform publishes them at their scheduled time. Turning a switch off does not unschedule them. The switch dialog and `GET /admin/doctor` show how many such deliveries exist (counts per platform, no content), and owners (or `publish` delegates) cancel them individually, which deletes them on the platform where the plugin supports it. |
| Scheduling UI | Composer, queue, history, and a calendar (month, week, agenda) with drag-to-reschedule. |
| Platform order | X and YouTube first. Meta (Facebook, Instagram) and TikTok follow in parallel. |
| Notifications | In-app notifications plus email for critical events, with a per-user email opt-out. No mobile push. |
| Live progress | Polling with ETags. No SSE or WebSocket. |

## Engineering standards

These apply to every phase in plans 02 and 03 and are part of every phase's exit criteria.

### DRY and ownership

**One owner per concern.** Each cross-cutting concern has exactly one implementation that everything else reuses:

| Concern | Owner |
|---|---|
| Config, environments, `_FILE` secrets, redacted dump | `postly-config` |
| Outbound HTTP: the only `reqwest` factory, retry, rate limiting, redaction | `postly-http` |
| Postgres pool, migrations, repositories, owner scoping, the audit writer (`AuditLog`), `app_settings` reads and writes, data retention purges | `postly-data` |
| The job runner (the only crate that depends on apalis) | `postly-jobs` |
| Mail transport, templates, and the `send_email` job | `postly-mail` |
| OIDC token verification, claims transformation, users, roles, delegation resolution | `postly-identity` |
| HTTP surface, extractors, problem+json, OpenAPI, inbound rate limiting, CORS, `If-Match` and `Idempotency-Key` handling | `postly-api` |
| Domain models, plugin contract, registry, validation engine, `Clock` and `IdGenerator` | `postly-core` |
| Encryption of stored secrets | `postly-vault` |
| Social OAuth flows and token storage | `postly-oauth` |
| Media storage, intake, probing, public hosting | `postly-media` |
| Shared plugin machinery and the conformance suite | `postly-platform-kit` |
| Meta Graph API client | `postly-platform-meta` |
| LLM providers and generation | `postly-content` |
| Delivery state machine and publishing orchestration | `postly-publishing` |
| Notifications | `postly-notify` |

Further DRY rules:

- **Platforms declare, the engine executes.** Validation runs in one core engine that reads plugin-supplied capability data: limits, media rules, and a text-measure function (for example, X's weighted character count). No validation logic is duplicated per endpoint or per platform.
- **One conformance suite.** Every plugin passes the same generic suite from `postly-platform-kit` (feature `testkit`): the dry-run contract, error mapping, idempotency, cancellation, and redaction. Platform crates add only protocol-specific tests. Shared wiremock fixtures (mocked OAuth, token refresh, rate-limit responses, malformed payloads) also come from the testkit.
- **Access checks live in one place.** Every repository method in `postly-data` that touches owned rows takes an `OwnerScope`, filters on `owner_id`, and applies the delegation's account limit. Services call `OwnerScope::require(capability)` before acting. Handlers and services never write their own ownership filters.
- **Audit goes through one writer.** Every audit event is recorded through `postly-data`'s `AuditLog`, which enforces the event shape: user references only in the ID columns or in `details` keys ending in `_user_id`, and never secrets or user content. Services never insert into `audit_events` directly.
- **Jobs are console-safe.** Every job type registers an ID-only `JobSummary`, so the admin Jobs console never shows payloads. Payloads themselves carry IDs, not content: `send_email` renders from current data when it runs, so the job tables never hold addresses or message bodies. Every handler is idempotent against its domain state, so a console retry cannot duplicate a post or an email.
- **Thin handlers.** axum handlers parse input, call a service, and map the result. Business rules live in service crates, so jobs and tests reuse them without HTTP.
- **The API contract is generated, never hand-written.** `utoipa` annotations produce `api/openapi.json`, and the Dart client is generated from that file. CI fails if either is stale.
- **Workspace-level dependencies.** Every dependency version is declared once in `[workspace.dependencies]`; crates use `dep.workspace = true` and enable only the features they need.

### Rust practices

- Toolchain pinned to Rust 1.98.1 (`rust-toolchain.toml`, rustfmt and clippy), edition 2024.
- `[workspace.lints]` inherited by all crates:
  - `unsafe_code = "forbid"`.
  - `clippy::all` and `clippy::pedantic` at warn. Allowances are justified in `Cargo.toml` comments.
  - `clippy::unwrap_used`, `clippy::expect_used`, and `clippy::panic` denied outside tests.
  - `missing_docs` warn on library crates.
- **Errors.** Library crates use `thiserror` enums. Only `postly-server` uses `anyhow`. Errors carry structured context and never include secret values. The API maps them to RFC 9457 problem+json with a stable `code` extension and the request ID. Internal errors never expose details.
- **Secrets are typed.** Tokens, auth codes, API keys, client secrets, SMTP passwords, and encryption keys use `secrecy::SecretString` (or newtypes over it), so `Debug` and `Display` redact by construction. Log redaction is a backstop.
- **No secret reaches a log, an error, an API response, or the OpenAPI examples.** This covers bearer tokens, social tokens, auth codes, API keys, signed media URLs, sealed values, and SMTP or vault keys. Tests assert it.
- **Newtypes** for identifiers: `UserId`, `DelegationId`, `PlatformId`, `SocialAccountId`, `PostId`, `MediaId`, `PublishJobId`, `DeliveryId`, `DeliveryAttemptId`, `RemotePostId`, `AiProviderId`, `AiGenerationId`, `ModelId`, `NotificationId`, `AuditEventId`. Internal IDs are UUID v7, generated in Rust.
- **Deterministic tests.** Injected `Clock` and `IdGenerator` traits, a seeded jitter RNG, and no real network in non-ignored tests.
- **Async trait objects.** `PlatformClient`, `PlatformPlugin`, `LlmProvider`, `TokenStore`, `MediaStore`, `MediaHost`, `Mailer`, and `JwksSource` are used as `dyn` objects. Phase P1 adds a trait-object compile test and picks one approach: native dyn-compatible async traits if the pinned toolchain supports them, otherwise `async-trait`.
- **Tracing** with `tracing` and `tracing-subscriber` everywhere. `#[instrument(skip(...))]` on any function that receives a secret.
- **Operational alerts.** There is no metrics exporter (see [Non-goals](#non-goals)). Instead, an `ops_health` cron job (every 5 minutes) checks thresholds from `[ops]` config: due deliveries overdue by more than 5 minutes, new `DeadLetter` or `OutcomeUnknown` deliveries, failing token refreshes, failed jobs in the queue, and the JWKS or mail transport being unhealthy. When a check first crosses its threshold, active admins get an in-app notification and a critical email; they are not sent again until the check recovers. The notification contains counts and IDs only, never user content. `GET /admin/doctor` shows the same checks.
- **Dependency hygiene.** reqwest uses rustls, streaming, JSON, and multipart only; no `blocking`, `cookies`, or `socks`. `cargo-deny` covers licenses, advisories, and duplicate crates.

### Reuse of essentialMix-rs (`emix*` crates)

Crates come from crates.io with a loose `"0"` spec, declared once in `[workspace.dependencies]`, with `default-features = false` where a crate enables heavy defaults. `Cargo.lock` keeps builds reproducible. Because a `0.x` minor bump is semver-breaking, run the full quality gates after each `cargo update`.

| Crate | Use in postly | Where |
|---|---|---|
| `emixdb` | `Pagination` and `ResultSet<T>` for every list endpoint | `data`, `api` |
| `emixcrypto` (`default-features = false`) | `Sha256Hash` for media content hashes, OAuth state hashes, and idempotency keys | `core`, `data`, `media`, `oauth` |
| `emixcore` | Only as a conversion source: `impl From<emixcore::Error>` where emix APIs are called | where used |

Evaluated and **not** used:

- `emixai`: built on kalosm with heavy local-inference dependencies, a hard-coded OpenAI model enum, and no custom base URL. postly's `LlmProvider` layer could later be upstreamed.
- `emixnet`: `pool_max_idle_per_host(0)` disables connection reuse, a forced JSON `Content-Type` breaks multipart and binary uploads, and it enables a cookie store. Worth fixing upstream with an options struct.
- `emixlog`: log4rs/slog-based; postly standardizes on `tracing`.
- `emixseaorm`, `emixdiesel`: postly uses SQLx.
- `emixcollections`: no current need.
- `emix` (`terminal`) and `emixthreading`: they served the old CLI, which is gone.
- `emix::datetime::parse_date_any`: interprets input as UTC and ignores the time zone. Schedule input is time-zone-aware.

## Crate dependencies

Dependencies point strictly downward. A crate may depend only on crates on earlier levels. Crates on the same level never depend on each other; the one exception is that `facebook` and `instagram` depend on `meta`.

1. `config`, `core` (no internal dependencies).
2. `http` (config), `vault` (config).
3. `data` (config, core, vault for the `Sealed<T>` column type).
4. `jobs` (config, data). The only crate that sees apalis.
5. `mail` (config, data, jobs). Owns `send_email`; reads recipients and writes audit events through `data`.
6. `notify` (config, core, data, jobs, mail). Every other service crate records notifications through it.
7. `identity` (config, http, data, jobs, mail, notify).
8. `oauth`, `media`, `platform-kit`, `content` (core, http, data, vault, jobs, notify as needed).
9. Platform crates (core, http, platform-kit; `facebook` and `instagram` also `meta`). They get tokens and media only through the `core` traits in their plugin context, never by depending on `oauth` or `media`.
10. `publishing` (core, data, jobs, notify, identity, oauth, media, platform-kit).
11. `api` (every service crate). `server` (everything).

The levels set allowed dependencies, not build order: `core` starts in plan 02 phase P1 as a skeleton (ID newtypes, `Clock`, `IdGenerator`) and gets the domain and plugin contract in plan 03 phase A1; `data` gains `vault` in plan 03 phase A2; `notify` is created in plan 03 phase D1, and `identity` gains its dependency on it then.

Rules:

- `core` has no platform-specific, HTTP, or database code.
- Job handlers live in the domain crate that owns the work and register through the `postly-jobs` registration API. Everything enqueues through the `JobQueue` seam. The one exception is `data_retention`: `data` sits below `jobs`, so `data` owns the purge queries and `server` registers the job.
- `server` registers each platform plugin behind a Cargo feature (`x`, `youtube`, `facebook`, `instagram`, `tiktok`, `mock-platform`). All are on by default except `mock-platform`, which development and CI builds enable.
- Platform API types never leave their platform crate.

## Identity and access

### Authentication (OIDC)

- `[auth.oidc]` holds the issuer URL, the accepted `audiences`, the Flutter `client_id` and `scopes` (served to the client by `GET /api/v1/auth/config`), accepted algorithms (default `RS256`, `ES256`, `EdDSA`), and clock-skew leeway (default 60 s).
- At startup, the server reads `{issuer}/.well-known/openid-configuration` and the JWKS through `postly-http`. `/ready` fails until the JWKS is loaded.
- The JWKS is cached, refreshed on an interval (default 1 hour), and refetched on an unknown `kid` at most once per minute, so random `kid` values cannot be used to flood the IdP.
- Every request's bearer token must be a JWT with a valid signature, the configured `iss`, an accepted `aud`, and valid `exp` and `nbf`. `alg: none` and HMAC algorithms are always rejected. Opaque tokens and token introspection are not supported; the IdP must issue JWT access tokens for postly's audience.
- postly has no sessions. Signing out ends the IdP session from the client through the IdP's `end_session_endpoint`. Access token lifetime is IdP configuration; the docs recommend 15 minutes or less.

### Claims transformation

One axum extractor layer turns a verified token into a `Principal`:

1. Look up `(iss, sub)` in a short `moka` cache (default TTL 60 s). On a miss, load the `users` row.
2. If no row exists, create it with status `pending`, or `active` with role `admin` when it matches the bootstrap rule and no active admin exists yet. The bootstrap check and insert run in one transaction under a Postgres advisory lock, so concurrent first sign-ins cannot create two bootstrap admins. Record an audit event. Notify admins of the pending user (see [Pending-user flood control](#roles-and-statuses)).
3. Refresh profile fields from configurable claims (`email`, `email_verified`, `name`, `preferred_username`) when they changed. Many IdPs (Zitadel by default) put these claims only in the ID token, not the access token. When a configured claim is missing from the access token, postly calls the discovery document's `userinfo_endpoint` with the same bearer token, through `postly-http`. It does this only on provisioning and on a cache miss, caches the result with the principal, and ignores a userinfo response whose `sub` differs from the token's. `display_name` falls back from `name` to `preferred_username`, `email`, and the subject, so it is never empty. `auth.oidc.userinfo = "fallback" | "always" | "never"` (default `fallback`) controls this. `GET /admin/doctor` warns when no profile claims were found in recent sign-ins, because bootstrap by `admin_email` and delegate lookup by email depend on them.
4. Build the `Principal { user_id, role, status }`. `pending` users may call only `GET /me` (403 `account_pending` elsewhere). `disabled` and `deleting` users get 403 `account_disabled` everywhere.

**Cache invalidation across processes.** Admin changes to a user (status, role, deletion) invalidate the local cache entry and send `pg_notify('postly_user_changed', <user id>)`. Every process `LISTEN`s on that channel and evicts the entry, so a disable takes effect everywhere within about a second. If the listener connection drops, the process clears the whole principal cache on reconnect; the TTL bounds staleness while it is down. IdP-side role or group claims are never read.

### Roles and statuses

- `admin`: everything a member can do in their own workspace, plus user administration and deployment settings. Never other users' content.
- `member`: their own workspace and any workspace delegated to them.
- The last active admin cannot be disabled, demoted, or deleted.
- `deleting` is terminal: it is set when a `delete_user` job is enqueued (see [User deletion](#user-deletion)) and can never be changed back to `active`, `pending`, or `disabled`. Admin status changes on a `deleting` user return 409 `user_deleting`.
- `pending` users older than `auth.pending_ttl` (default 30 days) are deleted by a cron job.
- **Pending-user flood control.** An IdP with open self-registration can create many `pending` users. Provisioning is covered by the per-IP rate limit, and approval-request emails are coalesced: at most one email per admin per `auth.approval_email_interval` (default 15 minutes), listing every user that became pending since the last one. The admin Users page always shows the full pending list.
- **Disabled owners.** Disabling a user blocks API access and their delegations in both directions. Their scheduled work is kept, not cancelled: when a delivery comes due, the worker parks it with `owner_disabled`. Re-enabling the user makes parked `owner_disabled` deliveries eligible again, but a delivery whose scheduled time has passed stays parked until the owner (or a `publish` delegate) retries or cancels it. Deliveries already uploaded with native scheduling are left on the platform.

### Delegation

An owner grants another active postly user access to their workspace. The grant has a level and an optional account limit:

| Level | Allows |
|---|---|
| `view` | Read social accounts, media, posts, overrides, publish jobs, deliveries, and the calendar. |
| `edit` | `view`, plus create, edit, and delete posts and overrides, upload and delete media, validate, dry-run, and generate drafts with the owner's AI providers (keys are never revealed). |
| `publish` | `edit`, plus live publish, schedule, reschedule, cancel, retry, and resolve. |

- **Account limit.** A grant covers either all of the owner's social accounts or a chosen set (`delegation_accounts`). A limited delegate sees only those social accounts, can target and override only them, and sees only their deliveries. Posts and media stay visible as a whole.
- **Empty account limit.** When disconnecting accounts removes the last entry from a limited grant, the grant stays valid with no accounts: the delegate keeps access to posts and media at their level, but sees no social accounts or deliveries and cannot publish anywhere. The owner and the delegate get an in-app notification, and the owner's Delegations screen marks the grant as having no accounts.
- **Whole-object rule for limited delegates.** A limited delegate may edit or delete a post, or cancel or reschedule a publish job, only when every override on the post and every non-terminal delivery of its jobs belongs to an account in their limit. Otherwise the request fails with 403 `account_not_in_scope`, so a limited delegate can never change what is published to an account they cannot see. Retry and resolve act on a single delivery and need only that delivery's account to be in the limit.
- **Owner-only, never delegable:** connecting, reconnecting, and disconnecting social accounts; AI provider configuration and keys; delegations; preferences; notifications; deleting the account.
- **No re-delegation.** A delegate cannot grant access to a workspace they do not own.
- **Acting as the owner.** The client sends `X-Postly-Act-As: <owner user id>`. On every request, `postly-identity` resolves it against an active delegation where both users are `active` and the grant is not revoked or expired. An invalid header returns 403 `delegation_invalid`. Without the header, the scope is the caller's own workspace. Delegation lookups are not cached, and the lookup query reads both users' status from `users` directly (not from the principal cache), so revocation and a disabled owner take effect on the next request.
- **`OwnerScope`** = `{ actor, owner, access }`, where `access` is `Owner` or `Delegated { level, accounts }`. Repositories filter by `owner`; services call `scope.require(capability)`; every write records `created_by` or `updated_by` as the `actor`.
- **Work outlives the grant.** Jobs and posts belong to the owner. Revoking a delegation does not cancel jobs the delegate scheduled; the owner sees who created them.
- **Notifications** about the owner's work go to the owner, and also to the actor when a delegate triggered the event and the grant is still active.
- **Finding a delegate.** `GET /users/lookup?email=…` returns the ID and display name of the active user with that exact verified email. It is rate-limited and returns nothing for partial matches. Email is not unique, so when more than one active user has that verified email, it also returns nothing (with the same response shape as no match), and the owner has to sort it out with the delegate outside postly.
- Granting, changing, revoking, and leaving a delegation are audited, and the other party gets an in-app notification.
- **Concurrent edits.** An owner and delegates can edit the same post at once. Post and override responses carry an `ETag` derived from `posts.version`. Updates and deletes require `If-Match`: a mismatch returns 412 `version_conflict`, and a missing header returns 428 `precondition_required`. The Flutter client shows the conflict and reloads. No edit silently overwrites another.

### Trust boundary

"Admins cannot read other users' content or secrets" is enforced by the application: no API route, job console view, doctor check, or notification exposes it. It is not a guarantee against anyone with host, database, or backup access. The vault keys live on the same host as the database, so whoever operates the deployment can decrypt stored tokens. The docs state this so users know that the operator is trusted.

## Data model

All tables are owned by postly, use UUID v7 IDs generated in Rust, and use `timestamptz`. Every **owned** table carries `owner_id` (FK to `users`), `created_at`, `updated_at`, `created_by`, and `updated_by`. `created_by` and `updated_by` hold the actor, which can be a delegate.

- **Owned tables:** `delegations`, `social_accounts`, `social_tokens`, `media_assets`, `posts`, `post_media`, `post_overrides`, `publish_jobs`, `deliveries`, `delivery_attempts`, `ai_providers`, `ai_generations`, `platform_quota_usage`, `notifications`, and `idempotency_keys`. Child tables (`social_tokens`, `post_media`, `post_overrides`, `deliveries`, `delivery_attempts`) repeat `owner_id` instead of relying on a join, so every repository filter is a plain column check. `delegation_accounts` is a pure link table; its owner is the delegation's.
- **Same-owner references are enforced by the database.** Each owned table has a unique `(owner_id, id)`, and every reference between owned rows is a composite FK on `(owner_id, <ref>_id)`. So `post_media` cannot link another owner's media, an override or delivery cannot target another owner's account, and `delegation_accounts` cannot list an account the grantor does not own, whatever the repository code does.
- **Actor columns do not block deletion.** `created_by`, `updated_by`, `users.approved_by`, `delegations.revoked_by`, and similar actor columns are nullable FKs to `users` with `ON DELETE SET NULL`. When a delegate or admin is deleted, the owner's rows stay and the client shows "deleted user". `owner_id` FKs cascade, because owned rows are deleted with their owner.

Token and key values exist in the database only as vault-sealed ciphertext. A test asserts that no column contains a plaintext value from the test fixtures.

### Identity (plan 02, except delegations in plan 03)

- **`users`**: `id`, `oidc_issuer`, `oidc_subject` (unique together), `email citext` (informational, not unique), `email_verified bool`, `display_name`, `role` (`admin`, `member`), `status` (`pending`, `active`, `disabled`, `deleting`), `approved_at`, `approved_by`, `last_seen_at`, `created_at`, `updated_at`.
- **`audit_events`**: `id`, `at`, `actor_user_id`, `owner_id` (null for deployment events), `subject_user_id`, `kind`, `ip`, `request_id`, `details jsonb`. Records provisioning, approval, role and status changes, delegation changes, settings changes, and publishing milestones. Never stores secrets or tokens. Written only through `AuditLog`; any other user reference goes in a `details` key ending in `_user_id`, so pseudonymization can find it.
  - Retention: an `audit_retention` cron job (daily) clears `ip` after `audit.ip_retention` (default 90 days) and deletes events older than `audit.retention` (default 2 years).
  - User IDs are not foreign keys, so audit rows survive user deletion (see [User deletion](#user-deletion)).
- **`delegations`**: `id`, `owner_id`, `delegate_id` (check `owner_id <> delegate_id`), `level` (`view`, `edit`, `publish`), `all_accounts bool`, `expires_at` (optional), `revoked_at`, `revoked_by`, plus the owned-table columns. A partial unique index allows one live grant per (`owner_id`, `delegate_id`).
- **`delegation_accounts`**: `delegation_id`, `account_id` (FK to `social_accounts`, cascade on delete). Used when `all_accounts` is false.
- **`user_preferences`**: `user_id` (1:1), `email_notifications bool`, `timezone` (IANA), `store_ai_prompts bool`.

### Deployment

- **`platforms`**: `id text PRIMARY KEY` (checked against `^[a-z][a-z0-9_-]{0,31}$`), `display_name`, `enabled bool`, `first_seen_at`.
  - `id` is the plugin identifier from `PlatformDescriptor` (`x`, `youtube`, …). It is a natural text key, so adding a platform needs no migration and IDs are identical across environments.
  - The server upserts one row per registered plugin at startup, after migrations. Code stays the source of truth; the table gives referential integrity and the admin `enabled` switch.
  - A row whose plugin is compiled out stays, and the API reports the platform as unavailable in this build.
- **`app_settings`**: deployment-level runtime settings edited by admins. Initially `publishing.live`, seeded from config.
- **`job_recurring_runs`** (plan 02): `name`, `scheduled_for`, `manual bool`, `job_id`, `outcome`, `finished_at`, unique on (`name`, `scheduled_for`) for scheduled runs. The unique insert makes each cron tick run once across worker processes, and the rows feed the Jobs console's last run and outcome. Purged by `job_history_purge`.

### Owned content (plan 03)

- **`social_accounts`**: `platform_id text REFERENCES platforms(id)`, `remote_account_id`, `display_name`, `avatar_url`, `scopes text[]`, `status` (`active`, `needs_reconnect`, `revoked`), `test_account bool` (informational label). Unique on (`platform_id`, `remote_account_id`) across the deployment: a remote account belongs to one postly owner, and sharing goes through delegation. When another owner has already connected an account that the OAuth callback discovers, that account is skipped, the other discovered accounts are still connected, and the redirect carries `code=account_connected_elsewhere` without saying who owns it. Reconnecting by the same owner updates the row.
- **`social_tokens`**: `account_id` (1:1), `access_token` sealed, `refresh_token` sealed, `expires_at`, `key_version`.
- **`oauth_states`**: `state_hash bytea unique`, `user_id`, `platform_id text REFERENCES platforms(id)`, `pkce_verifier` sealed, `return_to`, `created_at`, `expires_at` (10 minutes). An `oauth_state_purge` cron job (hourly) deletes expired rows.
- **`media_assets`**: `storage_key`, `original_filename`, `mime`, `bytes`, `sha256`, `width`, `height`, `duration_ms`, `status` (`uploading`, `ready`, `failed`). There is no content deduplication: identical uploads are separate assets, and `sha256` is used only for integrity checks and platform upload checksums.
- **`posts`**: `text`, `link`, `tags text[]`, `disclose_ai_generated bool`, `version int`, `status` (`draft`, `scheduled`, `publishing`, `published`, `partial`, `failed`, `cancelled`).
  - A post can have several publish jobs over its lifetime but **at most one non-terminal job** at a time (enforced by a partial unique index on `publish_jobs`).
  - `posts.status` describes the **current version**. It mirrors the latest job when that job's `post_version` equals `posts.version`, and is `draft` otherwise: no job yet, or the post was edited after its last job ended. Earlier jobs stay as history, and the client shows "last published vN" from them.
  - **Locked while publishing.** Editing or deleting a post, or changing its media or overrides, returns 409 `post_locked` while it has a non-terminal job. The user cancels the job, or waits for it to finish, and then edits. So a job always publishes exactly the `post_version` it was created with, and native-scheduled uploads never drift from the post.
  - **`post_media`**: `post_id`, `media_id`, `position`.
  - **`post_overrides`**: `post_id`, `account_id`, `patch jsonb`. Overrides never mutate the canonical post; the engine resolves a per-target view.
- **`publish_jobs`**: `post_id`, `post_version`, `scheduled_at` (UTC, null for "now"), `native_schedule bool`, `dry_run bool`, `status` (derived from deliveries), `cancelled_at`.
- **`deliveries`**: `job_id`, `account_id`, `state`, `idempotency_key bytea UNIQUE`, `attempt_count`, `next_attempt_at`, `remote_id`, `remote_url`, `container_ref` (Instagram container ID, TikTok `publish_id`, YouTube upload session), `last_error jsonb`, `parked_reason`.
  - `idempotency_key = sha256(job_id, account_id)` via `emixcrypto`. This prevents duplicate deliveries within one job and still lets a new job publish the same post version to the same account again (for example, after a cancel or after the remote post was deleted). The publish dialog warns when the same version has already been published to a target account.
- **`delivery_attempts`**: `delivery_id`, `started_at`, `finished_at`, `outcome`, classified error, redacted request summary. The request summary and the error are covered by the plaintext-secret test, like sealed columns.
- **`ai_providers`**: `provider_key`, `config jsonb` (opencode-shaped, without the key), `api_key` sealed, `is_default bool`.
- **`ai_generations`**: `provider_id`, `model`, `prompt_hash`, `prompt` (only when the owner enables storing prompts), token usage, `post_id`.
- **`platform_quota_usage`**: `account_id`, `platform_id text REFERENCES platforms(id)`, `day date`, `units_used`, unique on (`account_id`, `platform_id`, `day`). `day` is the quota day in the time zone the plugin declares for its reset (for example, YouTube resets at midnight `America/Los_Angeles`), not UTC.
- **`notifications`**: `user_id` (recipient; the owner or a delegate actor), `owner_id` (the workspace), `kind`, `severity`, `payload jsonb`, `read_at`, `emailed_at`.
- **`idempotency_keys`**: `actor_id`, `key`, `route`, `request_hash`, `response_status`, `response_body jsonb`, `expires_at` (24 hours), unique on (`actor_id`, `key`). Create endpoints (`POST /posts`, `POST /media`, publish, schedule) accept an optional `Idempotency-Key` header. A repeat with the same key and body returns the stored response; with a different body it returns 422 `idempotency_key_reused`. This stops a mobile retry from creating a duplicate post or upload.

### Data retention

A daily `data_retention` cron job (purge queries in `postly-data`, registered by `postly-server`) applies these defaults, each configurable under `[retention]`:

| Data | Default |
|---|---|
| Read notifications | Deleted 90 days after `read_at`. Unread notifications are kept. |
| `delivery_attempts` | Deleted after 180 days. The delivery row keeps its final state, `remote_id`, and `last_error`. |
| `ai_generations.prompt` | Cleared after 30 days. The row (model, token usage, `prompt_hash`) is deleted after 1 year. |
| Terminal `publish_jobs` and `deliveries` | Kept for the life of the post. They are the publishing history. |
| `idempotency_keys` | Deleted after `expires_at`. |
| `audit_events`, `oauth_states` | As described above. |

### User deletion

A user can be deleted in two ways:

- An admin deletes the user with `DELETE /users/{id}`.
- The owner deletes their own account with `DELETE /me`, confirming by sending their display name. This is owner-only and never available through act-as.

The last active admin can never be deleted. Both paths run the same `delete_user` job:

1. The user is set to `deleting` right away, in the same transaction that enqueues the job. This blocks access, deactivates delegations in both directions, and cannot be reversed, so an admin cannot re-enable a half-deleted user.
2. Non-terminal publish jobs are cancelled. In-flight deliveries finish or are cancelled at their next safe checkpoint first, and the job waits for them.
3. Deliveries uploaded with native scheduling but not yet live are deleted on the platform through the plugin where supported. The ones that cannot be deleted are listed in the audit event and in the admin's confirmation, because they will still go live.
4. Social tokens are revoked at each provider where supported.
5. Owned rows, stored media, delegations in both directions, and preferences are deleted. Actor columns in other owners' rows that point at this user become null (`ON DELETE SET NULL`); those rows are kept.
6. In `audit_events`, the user's ID is replaced by `HMAC-SHA256(audit.pseudonym_key, user_id)` everywhere it appears: `actor_user_id`, `owner_id`, `subject_user_id`, and every `details` key ending in `_user_id`. The key is a deployment `_FILE` secret, so the value cannot be reversed by hashing known user IDs, while events for the same deleted user stay linked. The HMAC is stored as the UUID built from its first 16 bytes, so the column types do not change.
7. The `users` row is deleted last.

The job is idempotent and can be resumed after a crash. The IdP account is untouched, and signing in again creates a new `pending` user. There is no data export (see [Non-goals](#non-goals)).

### Secrets that must be backed up

A Postgres backup is useless without the `vault.keys` versions that sealed it: losing a key version means every user has to reconnect the affected social accounts and re-enter their AI keys. Backups must include every live `vault.keys` version, `media.signing_key`, and `audit.pseudonym_key`, stored separately from the database backup.

## Non-goals

- Passwords, password reset, invites, MFA, or account recovery inside postly (the IdP owns them).
- Opaque access tokens, token introspection, several issuers at once, SCIM, or IdP-driven roles.
- Migrating users to a different IdP or issuer. Users are keyed on `(issuer, sub)`, so changing the issuer makes every existing user a new `pending` user. A future relink tool would map old keys to new ones; until then, the issuer is fixed for the life of a deployment.
- User data export.
- Metrics exporters (Prometheus, OpenTelemetry). Admin alerting is the built-in `ops_health` check.
- Multi-tenancy, teams, shared workspaces beyond delegation, and approval workflows.
- Out-of-process or dynamic-library plugins.
- Threads, replies, comments (including an automatic first comment), DMs, analytics, and insights. Editing already-published posts.
- Recurring or evergreen posts and posting queues with time slots. (The admin Jobs console's "recurring jobs" are internal cron jobs, not user posts.)
- Bulk import of posts (CSV or similar), link shortening, and UTM tagging.
- Video generation. Deployment-level AI providers.
- S3-compatible media storage (the traits leave room for it).
- Mobile push notifications, SSE or WebSocket, universal links, and localization.
- Horizontal-scale tuning, Kubernetes manifests, and a bundled TLS proxy for QA and production.

## Definition of done (all plans)

1. The Cargo workspace is pinned to Rust 1.98.1, and all crates pass the same quality gates, lints, and `cargo deny`.
2. Users sign in only through the configured OIDC provider on web, desktop, and mobile. New users wait for admin approval. No password or postly-issued token exists anywhere.
3. The core plugin contract is stable, and all five platforms plus the mock are compile-time plugins that pass the shared conformance suite.
4. Adding a platform requires only a new crate, a Cargo feature, and one registration line, proven by a test, including the platform appearing in the API and the Flutter client without code changes there.
5. Each user's workspace is private, and delegation grants exactly the documented level and account limit, proven by isolation tests at the repository and HTTP layers and by composite-FK tests showing the database rejects cross-owner references.
6. OAuth credentials are acquired through the server-side callback, refreshed with cross-process serialization, and stored only as vault-sealed ciphertext. No secret appears in logs, errors, or API responses.
7. Large media is streamed or chunked, served to platforms only through signed expiring URLs, with platform-appropriate resume and recovery.
8. Posts, schedules, deliveries, attempts, receipts, and partial successes are durable and idempotent. Unknown outcomes are reconciled, not duplicated.
9. The Flutter client covers sign-in, user administration, delegation, accounts, media, the composer with AI generation, dry-run, local and native scheduling, the calendar, queue, history, retry, resolve, cancel, notifications, AI providers, preferences, and the admin screens.
10. Every live publish is explicitly confirmed and can be stopped by the kill switch or a per-platform switch, except native-scheduled uploads already on the platform, which are reported and cancelled individually. Dry-run is safe everywhere.
11. User deletion completes and resumes after a crash at every step, leaves other owners' rows intact, and pseudonymizes every audit reference. Audit events are written for every event kind listed in the data model.
12. `ops_health` raises and clears each alert, and data retention purges run as configured.
13. A documented backup and restore drill (Postgres, the media volume, and the separately stored secrets) has been performed against QA.
14. CI verifies formatting, linting, type checking, tests, conformance suites, the SQLx offline cache, the OpenAPI and Dart client contract, dependency and security checks, and redaction.
