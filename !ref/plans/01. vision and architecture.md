## Objective

postit is a marketing tool for people with little technical experience and a small budget: one place to publish to their own social accounts and email their own contact lists. Each user signs in through the deployment's OpenID Connect provider, connects their own accounts, writes posts by hand or has the AI drafter write them, publishes them now, on a schedule, or on a repeating schedule, replies to comments, and sees how their posts did. A user can let another postit user work on their behalf through a scoped delegation. The UI ships in English and Arabic.

postit runs either self-hosted by one team or as one hosted deployment that an operator runs for many independent users. Both are the same image. The product guidelines in plan 03 (real accounts only, official APIs only, AI drafts and people approve, email only to people who agreed) bind every phase.

The product has two parts:

- A Rust REST API and background worker on PostgreSQL, shipped as one Docker image.
- A React web client (the full product, including the admin screens) and a Flutter mobile client (Android first; iOS builds from the same code). There is no native desktop client.

There is no end-user CLI.

Each platform is an **agent**: a compile-time crate implementing the `Agent` contract of a platform-agnostic core. Plan 03 builds Email, Telegram, Slack, Discord, Bluesky, Mastodon, TikTok, X, YouTube, LinkedIn, Facebook, Instagram, and Threads, in that order. New platforms are added without changing the core, the publishing engine, the schema, the REST API, or the web and mobile clients. Platform-specific connection details, formats, validation, rate limits, upload protocols, and API types stay inside each agent crate.

## Decisions

### Product and deployment

| Topic | Decision |
|---|---|
| Product shape | Rust REST API with background jobs, plus a React web client and a Flutter mobile client (Android, iOS). No end-user CLI. |
| Tenancy | One deployment serves its users, each with a private workspace: either one team self-hosting, or a hosted deployment the operator runs for many independent users. No tenant hierarchy, no teams inside a deployment, and no billing. Per-user limits (`user_limits`) keep a hosted deployment safe. |
| Hosting | Host-neutral image. The first deployment (plan 03 G1) is a Linux VPS with Docker, Caddy for HTTPS, and Terraform for the chosen provider. PaaS hosts without an always-on worker and a persistent disk are out. |
| Repo layout | Monorepo: `server/` (Cargo workspace), `web/` (React, Vite, TypeScript), `app/` (Flutter, mobile only), `api/openapi.json` (generated contract), `docker/`, `deploy/`. |
| Processes | One binary `postit`, one image. `POSTIT_ROLE=all|api|worker`. |
| Environments | `POSTIT_ENV=development|qa|production`, with layered config per environment and matching mobile app flavors. |
| Dev hosting | `https://postit.local` with a self-signed cert trusted in the OS root store and a hosts-file entry. Ports in 44300–44399. |
| Database | PostgreSQL 18 via SQLx, with compile-checked queries and a committed offline `.sqlx` cache. |
| Background jobs | apalis (`apalis`, `apalis-postgres`, `apalis-cron`) with an exact version pin, wrapped by our own `JobQueue` and `JobConsole` seams in one crate. Admins get a Hangfire-style Jobs page in the web app (list, stats, detail, retry, cancel, delete, recurring jobs, trigger-now). apalis-board is not used. |

### Identity and access

| Topic | Decision |
|---|---|
| User authentication | **Generic OpenID Connect only.** postit stores no passwords and issues no tokens. The API verifies bearer JWTs from one configured issuer. Code is provider-agnostic. |
| Identity provider | Deployment choice. Development compose and the docs bundle **Zitadel**. CI uses an in-process test issuer (wiremock JWKS). Kanidm, Authentik, Keycloak, and Firebase-style issuers work if they issue JWTs with the configured audience. |
| User key | `(issuer, sub)`. Never email. |
| Authorization | Owned by the postit database: role (`admin` or `member`) and status (`pending`, `active`, `disabled`, `deleting`). IdP role or group claims are ignored, so claim shapes do not matter. |
| Provisioning | First sign-in creates the user as `pending`. An admin approves before the user can do anything except read `/me`. |
| First admin | Bootstrapped from config (`auth.bootstrap.admin_email` with a verified email claim, or `auth.bootstrap.admin_subject`). Production refuses to start when no admin exists and neither is set. `admin_subject` is recommended for QA and production: `admin_email` trusts the IdP's `email_verified`, which federated or misconfigured IdPs may set for addresses the user does not control, and the first such sign-in wins. |
| Account email | Sign-up, passwords, MFA, and account recovery belong to the IdP. postit's own mail transport sends only postit's own events (approval requests, approvals, notifications, digests). Campaign email goes through each user's own sending method, never the deployment's. |
| Ownership | **Private per user.** Connected accounts, credentials, media, posts, campaigns, recurrences, contacts, inbox items, metrics, jobs, deliveries, AI providers, push endpoints, and notifications belong to one user (`owner_id`). |
| Delegation | An owner can grant another active user scoped access to their workspace (levels `view`, `edit`, `publish`, optionally limited to chosen accounts). No re-delegation. The delegate acts as the owner through a per-request act-as header. See [Delegation](#delegation). |
| Admin role | Admins approve and disable users, change roles, manage background jobs, and manage deployment settings: platform developer apps, the live-publishing kill switch, per-platform enablement, and diagnostics. Admins **cannot** read other users' content or secrets and cannot create delegations for others. This is an application-level boundary (see [Trust boundary](#trust-boundary)). |

### Publishing

| Topic | Decision |
|---|---|
| Agents | One compile-time agent per platform. Each declares its kind (`broadcast` or `direct`), connect method (OAuth or pasted credentials), formats, capabilities (comments, inbox, metrics, direct sending, native scheduling), and options schema as data (plan 03, [Agents](03.%20publishing%20roadmap.md#agents)). |
| Account connection | Official APIs only: OAuth, or a scoped, revocable credential the platform issues (bot token, webhook URL, app password, access token, SMTP login). No platform passwords, no browser automation, no account creation. Credential platforms also support CSV import; OAuth platforms cannot be imported. |
| Platform developer apps | Deployment-level for OAuth platforms. One client ID/secret per platform in config (`[platforms.<id>]` plus `_FILE` secrets). Each user connects their own accounts through them. Credential platforms need no deployment config. |
| LLM provider keys | Per user, bring your own key. Each user configures providers (opencode-shaped; presets for Gemini, OpenAI, Anthropic, OpenRouter, Abacus RouteLLM, MiniMax, Moonshot, and any OpenAI-compatible endpoint; local servers only when the deployment allows private endpoints). No deployment-level AI provider. Without one, everything but drafting works. |
| AI and approval | The drafter writes text only. Every live post, comment, and reply is confirmed by a person; a recurrence with "rewrite each time" is confirmed once for its occurrences. |
| Stored secrets | OAuth tokens, pasted credentials, PKCE verifiers, LLM keys, and push endpoints are sealed in Postgres with envelope encryption (`postit-vault`). |
| OAuth callback | Server-side: `https://<api host>/api/v1/platforms/{id}/oauth/callback`. The client (web or mobile) opens the authorize URL and receives the result redirect, then confirms the connection with its bearer token, so a callback can never attach accounts to a user who did not complete it (plan 03, [Connecting an account with OAuth](03.%20publishing%20roadmap.md#connecting-an-account-with-oauth)). |
| Grants | One OAuth authorization or one pasted credential is a **grant**. A grant can yield several accounts (YouTube channels, Facebook Pages, Telegram channels), which share its credential. Refresh is serialized per grant, and the grant is revoked at the provider only when its last account is disconnected. |
| Email campaigns | The email agent is a direct agent: each user has one sending method (SMTP first; SendGrid, Amazon SES, Mailgun, Postmark, Brevo, Resend later), contacts with recorded consent, suppression of unsubscribes and bounces, one-click unsubscribe, click tracking, opt-in open tracking, and an operator-set daily cap. |
| Media hosting | Filesystem storage volume. Platforms fetch media through short-lived HMAC-signed public URLs, and the web client displays media through short-lived signed view URLs (web video and image elements cannot send a bearer header). `MediaStore` and `MediaHost` are traits, so an S3 backend can be added later. Platforms that pull media (Instagram, Facebook photos by URL, Slack image blocks) need `media.public_base_url` reachable from the internet; the rest of the API may stay private. |
| Media fitting | Basic fitting with a preview: the composer overlays each target's frame and safe zones; the user picks crop or pad and trim; the worker produces a derived asset with ffmpeg or the `image` crate. Cheap fixes (remux, downscale, cover frame, orientation, PNG to JPEG) are offered, never applied silently. |
| Web client hosting | The `postit-server` image carries the React web build and serves it (`server.web`). The web build reads its runtime settings from `GET /config.json`, so one image is promoted unchanged across environments. |
| Live publishing | On in every environment. Every live publish requires explicit confirmation by the acting user. A runtime kill switch (`publishing.live`) and per-platform `enabled` flags stop postit-driven publishing. A per-publish dry-run toggle is always available. CI never publishes live. |
| Kill switch limit | The switches cannot stop deliveries already uploaded with native scheduling: the platform publishes them at their scheduled time. Turning a switch off does not unschedule them. The switch dialog and `GET /admin/doctor` show how many such deliveries exist (counts per platform, no content), and owners (or `publish` delegates) cancel them individually, which deletes them on the platform where the agent supports it. |
| Scheduling UI | Composer, queue, history, and a calendar (month, week, agenda) with drag-to-reschedule. |
| Platform order | Email, Telegram, Slack, Discord, Bluesky, Mastodon (no platform review needed), then TikTok (the product's main target), X, YouTube, LinkedIn, Facebook, Instagram, Threads. WhatsApp and Kick are later plans. |
| Engagement | Comment replies and comments on posts (as `comment` posts through the publishing engine), an inbox for agents that can read comments, recurring posts, campaigns, target groups, a brand profile, per-account writing styles, and analytics with charts. |
| Notifications | In-app notifications, email for critical events and an optional daily comment digest (per-kind switches), and Android push through UnifiedPush (RFC 8291 Web Push) with a polling fallback. No FCM; iOS uses the polling fallback. |
| Localization | UI in English (US, default) and Arabic with right-to-left layout; French and German later. The server returns codes, the clients translate; server-rendered text uses the recipient's locale. |
| Mobile distribution | A signed APK installed by hand, with an in-app update check, first; a self-hosted F-Droid repository, the main F-Droid repository, and Google Play later if usage grows. No App Store distribution. |
| Live progress | Polling with ETags. No SSE or WebSocket. |

## Engineering standards

These apply to every phase in plans 02 and 03 and are part of every phase's exit criteria.

### DRY and ownership

**One owner per concern.** Each cross-cutting concern has exactly one implementation that everything else reuses:

| Concern | Owner |
|---|---|
| Config, environments, `_FILE` secrets, redacted dump | `postit-config` |
| Outbound HTTP: the only `reqwest` factory, retry, rate limiting, redaction | `postit-http` |
| Postgres pool, migrations, repositories, owner scoping, the audit writer (`AuditLog`), `app_settings` reads and writes, data retention purges | `postit-data` |
| The job runner (the only crate that depends on apalis) | `postit-jobs` |
| Mail transport, templates, and the `send_email` job | `postit-mail` |
| OIDC token verification, claims transformation, users, roles, delegation resolution | `postit-identity` |
| HTTP surface, extractors, problem+json, OpenAPI, inbound rate limiting, CORS, `If-Match` and `Idempotency-Key` handling | `postit-api` |
| Domain models, agent contract, registry, formats and validation engine, `Clock` and `IdGenerator` | `postit-core` |
| Encryption of stored secrets | `postit-vault` |
| Account connection (OAuth and pasted credentials), credential storage and refresh | `postit-oauth` |
| Media storage, intake, probing, fitting, public hosting | `postit-media` |
| Shared agent machinery and the conformance suite | `postit-agent-kit` |
| Meta Graph API client | `postit-agent-meta` |
| Contacts, lists, consent, suppression, imports | `postit-contacts` |
| LLM providers and drafting | `postit-drafter` |
| Delivery state machine, publishing orchestration, direct sends, recurrences | `postit-publishing` |
| Inbox polling and items | `postit-inbox` |
| Metrics collection and aggregation | `postit-analytics` |
| Notifications and push | `postit-notify` |
| Server-side message catalogs (English, Arabic) | `postit-i18n` |

Further DRY rules:

- **Agents declare, the engine executes.** Validation runs in one core engine that reads agent-supplied format data: limits, media rules, safe zones, and a text-measure function (for example, X's weighted character count). No validation logic is duplicated per endpoint or per platform.
- **One conformance suite.** Every agent passes the same generic suite from `postit-agent-kit` (feature `testkit`): the dry-run contract, error mapping, idempotency, cancellation, redaction, the schema subset, and declared capabilities matching exposed traits. Agent crates add only protocol-specific tests. Shared wiremock fixtures (mocked OAuth, token refresh, rate-limit responses, malformed payloads) also come from the testkit.
- **Access checks live in one place.** Every repository method in `postit-data` that touches owned rows takes an `OwnerScope`, filters on `owner_id`, and applies the delegation's account limit. Services call `OwnerScope::require(capability)` before acting. Handlers and services never write their own ownership filters.
- **Audit goes through one writer.** Every audit event is recorded through `postit-data`'s `AuditLog`, which enforces the event shape: user references only in the ID columns or in `details` keys ending in `_user_id`, and never secrets or user content. Services never insert into `audit_events` directly.
- **Jobs are console-safe.** Every job type registers an ID-only `JobSummary`, so the admin Jobs console never shows payloads. Payloads themselves carry IDs, not content: `send_email` renders from current data when it runs, so the job tables never hold addresses or message bodies. Every handler is idempotent against its domain state, so a console retry cannot duplicate a post. Email is at-least-once: a handler checks its sent marker before sending, but a crash between the SMTP accept and the marker write can send twice.
- **Enqueue with the change.** Work that must follow a state change is enqueued with `JobQueue::enqueue_in(tx, …)` in the same transaction as the change, through the `postit-jobs` outbox (plan 02, `postit-jobs`). A crash can never commit the change and lose the job.
- **Thin handlers.** axum handlers parse input, call a service, and map the result. Business rules live in service crates, so jobs and tests reuse them without HTTP.
- **The API contract is generated, never hand-written.** `utoipa` annotations produce `api/openapi.json`, and the TypeScript types (`web/`) and the Dart client (`app/`) are generated from that file. CI fails if any is stale.
- **Workspace-level dependencies.** Every dependency version is declared once in `[workspace.dependencies]`; crates use `dep.workspace = true` and enable only the features they need.

### Rust practices

- Toolchain floats on Rust stable (`rust-toolchain.toml` channel `stable`, rustfmt and clippy) with `rust-version = "1.98"` as the workspace floor, edition 2024. New stable lints are fixed as they land.
- `[workspace.lints]` inherited by all crates:
  - `unsafe_code = "forbid"`.
  - `clippy::all` and `clippy::pedantic` at warn. Allowances are justified in `Cargo.toml` comments.
  - `clippy::unwrap_used`, `clippy::expect_used`, and `clippy::panic` denied outside tests.
  - `missing_docs` warn on library crates.
- **Errors.** Library crates use `thiserror` enums. Only `postit-server` uses `anyhow`. Errors carry structured context and never include secret values. The API maps them to RFC 9457 problem+json with a stable `code` extension and the request ID. Internal errors never expose details.
- **Secrets are typed.** Tokens, auth codes, API keys, client secrets, SMTP passwords, and encryption keys use `secrecy::SecretString` (or newtypes over it), so `Debug` and `Display` redact by construction. Log redaction is a backstop.
- **No secret reaches a log, an error, an API response, or the OpenAPI examples.** This covers bearer tokens, OAuth tokens, pasted credentials, auth codes, API keys, signed media URLs, webhook URLs, push endpoints, unsubscribe tokens, sealed values, and SMTP or vault keys. Tests assert it.
- **Newtypes** for identifiers: `UserId`, `DelegationId`, `PlatformId`, `GrantId`, `AccountId`, `PostId`, `MediaId`, `PublishJobId`, `DeliveryId`, `DeliveryAttemptId`, `RemotePostId`, `CampaignId`, `TargetGroupId`, `RecurrenceId`, `ContactId`, `ContactListId`, `DirectSendId`, `InboxItemId`, `AiProviderId`, `AiGenerationId`, `ModelId`, `NotificationId`, `PushEndpointId`, `AuditEventId`. Internal IDs are UUID v7, generated in Rust.
- **Deterministic tests.** Injected `Clock` and `IdGenerator` traits, a seeded jitter RNG, and no real network in non-ignored tests.
- **Async trait objects.** `Agent`, `AgentClient`, the capability traits (`Commenter`, `InboxReader`, `MetricsReader`, `DirectSender`, `NativeScheduler`), `LlmProvider`, `CredentialStore`, `MediaStore`, `MediaHost`, `Mailer`, and `JwksSource` are used as `dyn` objects. Phase P1 adds a trait-object compile test and picks one approach: native dyn-compatible async traits if the stable toolchain supports them (revisit when stable gains them), otherwise `async-trait`.
- **Tracing** with `tracing` and `tracing-subscriber` everywhere. `#[instrument(skip(...))]` on any function that receives a secret.
- **Operational alerts.** There is no metrics exporter (see [Non-goals](#non-goals)). Instead, an `ops_health` cron job (every 5 minutes) checks thresholds from `[ops]` config: due deliveries overdue by more than 5 minutes, new `DeadLetter` or `OutcomeUnknown` deliveries, failing token refreshes, failed jobs in the queue, and the JWKS or mail transport being unhealthy. When a check first crosses its threshold, active admins get an in-app notification and a critical email; they are not sent again until the check recovers. Alert state is stored in `ops_alerts`, so it survives restarts and is shared by every worker process. The notification contains counts and IDs only, never user content. `GET /admin/doctor` shows the same checks.
- **Dependency hygiene.** reqwest uses rustls, streaming, JSON, and multipart only; no `blocking`, `cookies`, or `socks`. `cargo-deny` covers licenses, advisories, and duplicate crates.

### Reuse of essentialMix-rs (`emix*` crates)

Crates come from crates.io with a loose `"0"` spec, declared once in `[workspace.dependencies]`, with `default-features = false` where a crate enables heavy defaults. `Cargo.lock` keeps builds reproducible. Because a `0.x` minor bump is semver-breaking, run the full quality gates after each `cargo update`.

| Crate | Use in postit | Where |
|---|---|---|
| `emixdb` | `Pagination` and `ResultSet<T>` for every list endpoint | `data`, `api` |
| `emixcrypto` (`default-features = false`) | `Sha256Hash` for media content hashes, OAuth state hashes, and idempotency keys | `core`, `data`, `media`, `oauth` |
| `emixcore` | Only as a conversion source: `impl From<emixcore::Error>` where emix APIs are called | where used |

Evaluated and **not** used:

- `emixai`: built on kalosm with heavy local-inference dependencies, a hard-coded OpenAI model enum, and no custom base URL. postit's `LlmProvider` layer could later be upstreamed.
- `emixnet`: `pool_max_idle_per_host(0)` disables connection reuse, a forced JSON `Content-Type` breaks multipart and binary uploads, and it enables a cookie store. Worth fixing upstream with an options struct.
- `emixlog`: log4rs/slog-based; postit standardizes on `tracing`.
- `emixseaorm`, `emixdiesel`: postit uses SQLx.
- `emixcollections`: no current need.
- `emix` (`terminal`) and `emixthreading`: they served the old CLI, which is gone.
- `emix::datetime::parse_date_any`: interprets input as UTC and ignores the time zone. Schedule input is time-zone-aware.

## Crate dependencies

Dependencies point strictly downward. A crate may depend only on crates on earlier levels. Crates on the same level never depend on each other; the one exception is that the Meta agents (`facebook`, `instagram`, `threads`) depend on `meta`.

1. `config`, `core`, `i18n` (no internal dependencies).
2. `http` (config, core), `vault` (config).
3. `data` (config, core, vault for the `Sealed<T>` column type).
4. `jobs` (config, data). The only crate that sees apalis.
5. `mail` (config, data, jobs, i18n). Owns `send_email`; reads recipients and writes audit events through `data`.
6. `notify` (config, core, http, data, jobs, mail, i18n, vault). Every other service crate records notifications through it; push goes out through `http`.
7. `identity` (config, http, data, jobs, mail, notify, i18n).
8. `oauth`, `media`, `agent-kit`, `contacts`, `drafter` (config, core, http, data, vault, jobs, notify as needed). `oauth` takes `config` for the platform catalog's `[platforms.<id>]` tables.
9. Agent crates (core, http, agent-kit; the Meta agents also `meta`). They get credentials and media only through the `core` traits in their agent context, never by depending on `oauth` or `media`. The email agent receives recipients only through the `DirectSender` arguments, never by depending on `contacts`.
10. `publishing` (core, data, jobs, notify, identity, oauth, media, agent-kit, contacts, drafter).
11. `inbox`, `analytics` (core, data, jobs, notify, agent-kit, oauth).
12. `api` (every service crate). `server` (everything).

The levels set allowed dependencies, not build order: `core` starts in plan 02 phase P1 as a skeleton (ID newtypes, `Clock`, `IdGenerator`) and gets the domain and agent contract in plan 03 phase A1; `data` gains `vault` in plan 03 phase A2; `notify` is created in plan 03 phase D1, and `identity` gains its dependency on it then.

Rules:

- `core` has no platform-specific, HTTP, or database code.
- Job handlers live in the domain crate that owns the work and register through the `postit-jobs` registration API. Everything enqueues through the `JobQueue` seam. The one exception is `data_retention`: `data` sits below `jobs`, so `data` owns the purge queries and `server` registers the job.
- `server` registers each agent behind a Cargo feature named after its platform ID (`email`, `telegram`, …, `threads`, and `mock-agent`). All are on by default except `mock-agent`, which development and CI builds enable.
- Platform API types never leave their platform crate.

## Identity and access

### Authentication (OIDC)

- `[auth.oidc]` holds the issuer URL, the accepted `audiences`, the web and mobile `client_id` and `scopes` (served to the client by `GET /api/v1/auth/config`), accepted algorithms (default `RS256`, `ES256`, `EdDSA`), and clock-skew leeway (default 60 s).
- At startup, the server reads `{issuer}/.well-known/openid-configuration` and the JWKS through `postit-http`. `/ready` fails until the JWKS is loaded.
- The JWKS is cached, refreshed on an interval (default 1 hour), and refetched on an unknown `kid` at most once per minute, so random `kid` values cannot be used to flood the IdP.
- Every request's bearer token must be a JWT with a valid signature, the configured `iss`, an accepted `aud`, and valid `exp` and `nbf`. `alg: none` and HMAC algorithms are always rejected. Opaque tokens and token introspection are not supported; the IdP must issue JWT access tokens for postit's audience.
- postit has no sessions. Signing out ends the IdP session from the client through the IdP's `end_session_endpoint`. Access token lifetime is IdP configuration; the docs recommend 15 minutes or less.

### Claims transformation

One axum extractor layer turns a verified token into a `Principal`:

1. Look up `(iss, sub)` in a short `moka` cache (default TTL 60 s). On a miss, load the `users` row.
2. If no row exists, create it with status `pending`, or `active` with role `admin` when it matches the bootstrap rule and no active admin exists yet. The bootstrap check and insert run in one transaction under a Postgres advisory lock, so concurrent first sign-ins cannot create two bootstrap admins. Record an audit event. Notify admins of the pending user by email (see [Pending-user flood control](#roles-and-statuses)); from plan 03 phase D1, admins also get an in-app notification.
3. Refresh profile fields from configurable claims (`email`, `email_verified`, `name`, `preferred_username`) when they changed. Many IdPs (Zitadel by default) put these claims only in the ID token, not the access token. When a configured claim is missing from the access token, postit calls the discovery document's `userinfo_endpoint` with the same bearer token, through `postit-http`. It does this only on provisioning and on a cache miss, caches the result with the principal, and ignores a userinfo response whose `sub` differs from the token's. `display_name` falls back from `name` to `preferred_username`, `email`, and the subject, so it is never empty. `auth.oidc.userinfo = "fallback" | "always" | "never"` (default `fallback`) controls this. `GET /admin/doctor` warns when no profile claims were found in recent sign-ins, because bootstrap by `admin_email` and delegate lookup by email depend on them.
4. Build the `Principal { user_id, role, status }`. `pending` users may call only `GET /me` (403 `account_pending` elsewhere). `disabled` and `deleting` users get 403 `account_disabled` everywhere.

**Cache invalidation across processes.** Admin changes to a user (status, role, deletion) invalidate the local cache entry and send `pg_notify('postit_user_changed', <user id>)`. Every process `LISTEN`s on that channel and evicts the entry, so a disable takes effect everywhere within about a second. If the listener connection drops, the process clears the whole principal cache on reconnect; the TTL bounds staleness while it is down. IdP-side role or group claims are never read.

### Roles and statuses

- `admin`: everything a member can do in their own workspace, plus user administration and deployment settings. Never other users' content.
- `member`: their own workspace and any workspace delegated to them.
- The last active admin cannot be disabled, demoted, or deleted.
- `deleting` is terminal: it is set when a `delete_user` job is enqueued (see [User deletion](#user-deletion)) and can never be changed back to `active`, `pending`, or `disabled`. Admin status changes on a `deleting` user return 409 `user_deleting`.
- `pending` users older than `auth.pending_ttl` (default 30 days) are deleted by a cron job.
- **Pending-user flood control.** An IdP with open self-registration can create many `pending` users. Provisioning is covered by the per-IP rate limit, and approval-request emails are coalesced: at most one email per admin per `auth.approval_email_interval` (default 15 minutes), listing every user that became pending since the last one. The time of each admin's last approval email is stored in `user_preferences.last_approval_email_at`. The admin Users page always shows the full pending list.
- **Disabled owners.** Disabling a user blocks API access and their delegations in both directions. Their scheduled work is kept, not cancelled: when a delivery comes due, the worker parks it with `owner_disabled`. Re-enabling the user makes parked `owner_disabled` deliveries eligible again, but a delivery whose scheduled time is more than `publishing.park_grace` (default 15 minutes) in the past stays parked until the owner (or a `publish` delegate) retries or cancels it. The same parking rule applies to every parking reason (plan 03, [Delivery states](03.%20publishing%20roadmap.md#delivery-states)). Deliveries already uploaded with native scheduling are left on the platform.

### Delegation

An owner grants another active postit user access to their workspace. The grant has a level and an optional account limit:

| Level | Allows |
|---|---|
| `view` | Read accounts, writing styles, target groups, the brand profile, campaigns, media, posts, overrides, recurrences, contacts and lists, the inbox, analytics, publish jobs, deliveries, and the calendar. |
| `edit` | `view`, plus create, edit, and delete posts, overrides, campaigns, target groups, writing styles, the brand profile, contacts, and lists; upload, fit, and delete media; validate, dry-run, and generate drafts with the owner's AI providers (keys are never revealed); and mark inbox items. A post that has live publish history can be deleted only at `publish`, because deleting it deletes that history. |
| `publish` | `edit`, plus live publish, schedule, reschedule, cancel, retry, resolve, recurrences, replies and comments, and deleting posts that have live publish history. |

- **Account limit.** A grant covers either all of the owner's accounts or a chosen set (`delegation_accounts`). A limited delegate sees only those accounts, can target and override only them, and sees only their deliveries, inbox items, writing styles, and metrics. Posts, media, campaigns, and contacts stay visible as a whole.
- **Empty account limit.** When disconnecting accounts removes the last entry from a limited grant, the grant stays valid with no accounts: the delegate keeps access to posts and media at their level, but sees no accounts or deliveries and cannot publish anywhere. The owner and the delegate get an in-app notification, and the owner's Delegations screen marks the grant as having no accounts.
- **Whole-object rule for limited delegates.** A limited delegate may edit or delete a post, or cancel or reschedule a publish job, only when every override on the post and every non-terminal delivery of its jobs belongs to an account in their limit. Otherwise the request fails with 403 `account_not_in_scope`, so a limited delegate can never change what is published to an account they cannot see. Retry, resolve, and single-delivery cancel act on one delivery and need only that delivery's account to be in the limit.
- **Owner-only, never delegable:** connecting, reconnecting, importing, and disconnecting accounts (and so every credential, including the email sending method); AI provider configuration and keys; contact import and export; removing suppressions; delegations; preferences; notifications; push endpoints; deleting the account.
- **No re-delegation.** A delegate cannot grant access to a workspace they do not own.
- **Acting as the owner.** The client sends `X-Postit-Act-As: <owner user id>`. On every request, `postit-identity` resolves it against an active delegation where both users are `active` and the grant is not revoked or expired. An invalid header returns 403 `delegation_invalid`. Without the header, the scope is the caller's own workspace. Delegation lookups are not cached, and the lookup query reads both users' status from `users` directly (not from the principal cache), so revocation and a disabled owner take effect on the next request.
- **Admin routes act on the admin's own authority.** They reject `X-Postit-Act-As` with 403 `owner_only`, and `RequireAdmin` checks the caller's role, never a delegated owner's.
- **`OwnerScope`** = `{ actor, owner, access }`, where `access` is `Owner` or `Delegated { level, accounts }`. Repositories filter by `owner`; services call `scope.require(capability)`; every write records `created_by` or `updated_by` as the `actor`.
- **Work outlives the grant.** Jobs and posts belong to the owner. Revoking a delegation does not cancel jobs the delegate scheduled; the owner sees who created them.
- **Notifications** about the owner's work go to the owner, and also to the actor when a delegate triggered the event and the grant is still active.
- **Finding a delegate.** `GET /users/lookup?email=…` returns the ID and display name of the active user with that exact verified email. It is rate-limited and returns nothing for partial matches. Email is not unique, so when more than one active user has that verified email, it also returns nothing (with the same response shape as no match), and the owner has to sort it out with the delegate outside postit.
- Granting, changing, revoking, and leaving a delegation are audited, and the other party gets an in-app notification.
- **Concurrent edits.** An owner and delegates can edit the same post at once. Post and override responses carry an `ETag` derived from `posts.version`. Every change to what the post would publish bumps `posts.version`: text and fields, media and alt text, draft targets, and override writes and deletes. Updates and deletes require `If-Match`: a mismatch returns 412 `version_conflict`, and a missing header returns 428 `precondition_required`. Publishing requires `If-Match` too, so a live confirmation always applies to the version the confirming user reviewed. The clients show the conflict and reload. No edit silently overwrites another.

### Trust boundary

"Admins cannot read other users' content or secrets" is enforced by the application: no API route, job console view, doctor check, or notification exposes it. It is not a guarantee against anyone with host, database, or backup access. The vault keys live on the same host as the database, so whoever operates the deployment can decrypt stored tokens. The docs state this so users know that the operator is trusted.

## Data model

All tables are owned by postit, use UUID v7 IDs generated in Rust, and use `timestamptz`. Every **owned** table carries `owner_id` (FK to `users`), `created_at`, `updated_at`, `created_by`, and `updated_by`. `created_by` and `updated_by` hold the actor, which can be a delegate.

- **Owned tables:** `delegations`, `account_grants`, `connected_accounts`, `account_tokens`, `pending_connections`, `writing_styles`, `brand_profiles`, `target_groups`, `campaigns`, `media_assets`, `posts`, `post_media`, `post_targets`, `post_overrides`, `recurrences`, `publish_jobs`, `deliveries`, `delivery_attempts`, `contacts`, `contact_lists`, `contact_list_members`, `suppressions`, `contact_imports`, `direct_sends`, `email_events`, `inbox_items`, `post_metric_snapshots`, `account_metrics_daily`, `ai_providers`, `ai_generations`, `platform_quota_usage`, `push_endpoints`, `notifications`, and `idempotency_keys`. Child tables repeat `owner_id` instead of relying on a join, so every repository filter is a plain column check. `delegation_accounts`, `target_group_accounts`, and `contact_list_members` are link tables whose owner is their parent's (`contact_list_members` repeats `owner_id` for the audience query).
- **Same-owner references are enforced by the database.** Each owned table has a unique `(owner_id, id)`, and every reference between owned rows is a composite FK on `(owner_id, <ref>_id)`. So `post_media` cannot link another owner's media, an override, target, or delivery cannot target another owner's account, an account cannot use another owner's grant, a list cannot hold another owner's contact, and `delegation_accounts` cannot list an account the grantor does not own, whatever the repository code does.
- **Actor columns do not block deletion.** `created_by`, `updated_by`, `users.approved_by`, `delegations.revoked_by`, and similar actor columns are nullable FKs to `users` with `ON DELETE SET NULL`. When a delegate or admin is deleted, the owner's rows stay and the client shows "deleted user". `owner_id` FKs cascade, because owned rows are deleted with their owner.
- **System writes.** Changes made by jobs and cron (delivery transitions, token refresh, expiry) leave `updated_by` null, and the client shows them as "postit". The actor of the request that caused the work is recorded where it happened (`created_by`, audit events).
- **Recipient columns cascade.** A user reference that is not an actor and not the owner (`notifications.user_id`, `idempotency_keys.actor_id`, `oauth_states.user_id`, `push_endpoints.user_id`) is a FK with `ON DELETE CASCADE`: those rows exist only for that user.
- **Third-party personal data.** Contacts and inbox items describe people who are not postit users. They are owned rows, deleted with their owner, never shown to admins, and covered by the retention defaults below.

Token and key values exist in the database only as vault-sealed ciphertext. A test asserts that no column contains a plaintext value from the test fixtures.

### Identity (plan 02, except delegations in plan 03)

- **`users`**: `id`, `oidc_issuer`, `oidc_subject` (unique together), `email citext` (informational, not unique), `email_verified bool`, `display_name`, `role` (`admin`, `member`), `status` (`pending`, `active`, `disabled`, `deleting`), `approved_at`, `approved_by`, `last_seen_at`, `created_at`, `updated_at`.
- **`audit_events`**: `id`, `at`, `actor_user_id`, `owner_id` (null for deployment events), `subject_user_id`, `kind`, `ip`, `request_id`, `details jsonb`. Records provisioning, approval, role and status changes, delegation changes, settings changes, and publishing milestones. Never stores secrets or tokens. Written only through `AuditLog`; any other user reference goes in a `details` key ending in `_user_id`, so pseudonymization can find it.
  - Retention: an `audit_retention` cron job (daily) clears `ip` after `audit.ip_retention` (default 90 days) and deletes events older than `audit.retention` (default 2 years).
  - User IDs are not foreign keys, so audit rows survive user deletion (see [User deletion](#user-deletion)).
- **`delegations`**: `id`, `owner_id`, `delegate_id` (check `owner_id <> delegate_id`), `level` (`view`, `edit`, `publish`), `all_accounts bool`, `expires_at` (optional), `ended_at`, `ended_reason` (`revoked`, `left`, `expired`), `revoked_by`, plus the owned-table columns. Revoking, leaving, and the `delegation_expiry` job set `ended_at`. A partial unique index on (`owner_id`, `delegate_id`) `WHERE ended_at IS NULL` allows one live grant per pair (an index predicate cannot use `now()`, so an expired grant counts as live until the expiry job ends it; granting again first ends an already-expired grant in the same transaction). Act-as resolution checks both `ended_at` and `expires_at`.
- **`delegation_accounts`**: `delegation_id`, `account_id` (FK to `connected_accounts`, cascade on delete). Used when `all_accounts` is false.
- **`user_preferences`**: `user_id` (1:1, created with the user), `email_notifications bool`, `notification_channels jsonb` (per-kind push and email switches, and the daily comment digest), `locale` (`en-US` or `ar`; defaults to the locale the client reports at first sign-in, else `en-US`), `timezone` (IANA; defaults to the zone the client reports at first sign-in, else `UTC`), `onboarding jsonb` (which first-run steps are done or skipped), `store_ai_prompts bool`, `last_approval_email_at` (admins only; approval-email coalescing).

### Deployment

- **`platforms`**: `id text PRIMARY KEY` (checked against `^[a-z][a-z0-9_]{0,31}$`), `display_name`, `enabled bool`, `first_seen_at`.
  - `id` is the agent identifier from `AgentDescriptor` (`x`, `youtube`, …). It is a natural text key, so adding a platform needs no migration and IDs are identical across environments.
  - The server upserts one row per registered agent at startup, after migrations. Code stays the source of truth; the table gives referential integrity and the admin `enabled` switch.
  - A row whose agent is compiled out stays, and the API reports the platform as unavailable in this build.
- **`app_settings`**: deployment-level runtime settings edited by admins. Initially `publishing.live`, seeded from config.
- **`user_limits`** (plan 03): `user_id` (1:1, created with the user from `[limits]`), `email_daily_cap`, `contacts_cap`, `storage_quota_bytes`, `updated_by`. Admin-edited per user; not owned content, so admins may read and change it. A later billing plan would set these.
- **`platform_app_quota_usage`** (plan 03): `platform_id text REFERENCES platforms(id)`, `bucket`, `period_start date`, `units_used`, unique on (`platform_id`, `bucket`, `period_start`). Deployment-wide quota such as YouTube's per-project daily quota or an X app's monthly post cap, shared by every user. Not owned; it holds no user reference. `period_start` is the first day of the bucket's period (`day` or `month`) in the agent's reset time zone, as in `platform_quota_usage`.
- **`job_recurring_runs`** (plan 02): `name`, `scheduled_for`, `manual bool`, `job_id`, `outcome`, `finished_at`, unique on (`name`, `scheduled_for`) for scheduled runs. The unique insert makes each cron tick run once across worker processes, and the rows feed the Jobs console's last run and outcome. Purged by `job_history_purge`.
- **`job_outbox`** (plan 02): `id`, `job_type`, `payload jsonb` (IDs only), `run_at`, `created_at`. Written by `JobQueue::enqueue_in` inside the caller's transaction and drained into the apalis storage by the `postit-jobs` relay, which deletes each row once its job is stored.
- **`ops_alerts`** (plan 03, G4): `check` (primary key), `firing bool`, `since`, `notified_at`, `recovered_at`. Holds `ops_health` alert state; counts and IDs only.

### Owned content (plan 03)

- **`account_grants`**: `platform_id text REFERENCES platforms(id)`, `kind` (`oauth`, `credentials`), `remote_user_id` (the authorizing identity at the provider, when known), `credential` sealed (OAuth access and refresh tokens, or the pasted credential fields marked secret), `connection_config jsonb` (non-secret fields such as a Mastodon instance URL or an SMTP host), `expires_at`, `reconnect_by`, `reconnect_warned` (`none`, `7d`, `1d`, `expired`), `scopes text[]`, `status` (`active`, `needs_reconnect`, `revoked`). One row per authorization or pasted credential. Refresh, `needs_reconnect`, and revocation act on the grant and so on every account that uses it. A grant with no remaining accounts is revoked at the provider where supported and deleted.

Unique on (`platform_id`, `remote_account_id`) across the deployment among rows that are not `disconnected`: a remote account belongs to one postit owner, and sharing goes through delegation. A partial unique index allows one non-disconnected `email` account per owner (one sending method).
  - **Disconnecting keeps the row** with status `disconnected`, no grant, and no credential, so delivery history keeps its account (plan 03, [Disconnecting an account](03.%20publishing%20roadmap.md#disconnecting-an-account)). The row is deleted only with its owner.

After the callback, the same row holds the pending result until the client confirms it: `connect_id_hash bytea unique`, the sealed grant tokens, and the discovered accounts. An `oauth_state_purge` cron job (hourly) deletes expired rows.
- **`pending_connections`**: `connect_id_hash bytea unique`, `platform_id`, `credential` sealed, `connection_config jsonb`, `discovered jsonb`, `expires_at` (10 minutes). The credentials-flow counterpart of a confirmed-pending `oauth_states` row; purged by `oauth_state_purge`.
- **`writing_styles`**: `account_id` (1:1), `tone`, `emoji` (`none`, `light`, `heavy`), `hashtags` (`none`, `few`, `many`), `language` (optional override), `notes`.
- **`brand_profiles`**: one per owner: `description`, `audience`, `offerings`, `avoid_words text[]`, `default_language`, `examples text[]` (up to five).
- **`target_groups`** and **`target_group_accounts`**: a named set of accounts.
- **`campaigns`**: `name`, `starts_on`, `ends_on`, `color`, `archived bool`.
- **`media_assets`**: `storage_key`, `thumbnail_key`, `original_filename`, `mime`, `bytes`, `sha256`, `width`, `height`, `duration_ms`, `status` (`uploading`, `processing`, `ready`, `failed`), `derived_from` (composite FK to `media_assets`, for fitted and converted assets), `fit_spec jsonb`, and for resumable upload sessions `declared_bytes`, `upload_offset`, and `upload_expires_at`. No content deduplication; `sha256` is for integrity checks and platform checksums. Stored bytes of `ready` assets (derived ones included) plus the `declared_bytes` of open sessions count against `user_limits.storage_quota_bytes`.

  - `posts.status` describes the **current version**: it mirrors the latest live job when that job's `post_version` equals `posts.version`, and is `draft` otherwise.

  - **`post_media`**: `post_id`, `media_id`, `position`, `alt_text`.
  - **`post_targets`**: `post_id`, `account_id`. The draft's chosen targets; a limited delegate sees and changes only the targets in their limit.

Overrides never mutate the canonical post.

| Data | Default |
|---|---|
| Read notifications | Deleted 90 days after `read_at`. Unread notifications are kept. |
| `delivery_attempts` | Deleted after 180 days. The delivery row keeps its final state, `remote_id`, and `last_error`. |
| `ai_generations.prompt` | Cleared after 30 days. The row (model, token usage, `prompt_hash`) is deleted after 1 year. |
| `inbox_items` | Deleted after 180 days, and when their account is disconnected. |
| `direct_sends`, `email_events` | Deleted after 180 days. The delivery keeps its counts. |
| `post_metric_snapshots`, `account_metrics_daily` | Kept for the life of the post or account. |
| `contact_imports` | Deleted after 30 days. |
| Terminal `publish_jobs` and `deliveries` | Kept for the life of the post. They are the publishing history. |
| `idempotency_keys` | Deleted after `expires_at`. |
| `audit_events`, `oauth_states` | As described above. |

### User deletion

A user can be deleted in two ways:

- An admin deletes the user with `DELETE /users/{id}`.
- The owner deletes their own account with `DELETE /me`, confirming by sending their display name. This is owner-only and never available through act-as.

The last active admin can never be deleted. Both paths, and the `purge_pending_users` cleanup of stale pending users, run the same `delete_user` job:

1. The user is set to `deleting` right away, in the same transaction that enqueues the job (`enqueue_in`, so the job cannot be lost). This blocks access, deactivates delegations in both directions, and cannot be reversed, so an admin cannot re-enable a half-deleted user.
2. Non-terminal publish jobs are cancelled. In-flight deliveries finish or are cancelled at their next safe checkpoint first, and the job waits for them.
3. Deliveries uploaded with native scheduling but not yet live are deleted on the platform through the agent where supported. The ones that cannot be deleted are listed in the audit event and in the admin's confirmation, because they will still go live.
4. OAuth grants are revoked at each provider where supported.
5. Owned rows (contacts, suppressions, inbox items, and metrics included), stored media, push endpoints, delegations in both directions, preferences, and limits are deleted. Actor columns in other owners' rows that point at this user become null (`ON DELETE SET NULL`); those rows are kept.
6. In `audit_events`, the user's ID is replaced by `HMAC-SHA256(audit.pseudonym_key, user_id)` everywhere it appears: `actor_user_id`, `owner_id`, `subject_user_id`, and every `details` key ending in `_user_id`. The key is a deployment `_FILE` secret, so the value cannot be reversed by hashing known user IDs, while events for the same deleted user stay linked. The HMAC is stored as the UUID built from its first 16 bytes with the version nibble set to 8 (UUIDv8, which postit never generates otherwise), so the column types do not change and `GET /admin/audit` can mark pseudonyms as deleted users. The `ip` of every event this user performed is cleared at the same time.
7. The `users` row is deleted last.

The job is idempotent and can be resumed after a crash. The IdP account is untouched, and signing in again creates a new `pending` user. There is no data export (see [Non-goals](#non-goals)).

### Secrets that must be backed up

A Postgres backup is useless without the `vault.keys` versions that sealed it: losing a key version means every user has to reconnect the affected accounts and re-enter their AI keys. Backups must include every live `vault.keys` version, `media.signing_key`, `email.signing_key` (unsubscribe links in sent mail stop working without it), `push.vapid_private_key`, and `audit.pseudonym_key`, stored separately from the database backup.

## Non-goals

- Creating accounts on any platform, generating identities, running several accounts as different "people", and any bot-detection evasion (captcha solving, proxy or user-agent rotation). Storing platform passwords or driving platform websites with browser automation.
- Passwords, password reset, invites, MFA, or account recovery inside postit (the IdP owns them).
- Native desktop clients, and the admin screens on mobile. Desktop users use the web app; mobile covers the signed-in user's own features except the email block editor and contact CSV import and export.
- Opaque access tokens, token introspection, several issuers at once, SCIM, or IdP-driven roles.
- Migrating users to a different IdP or issuer. Users are keyed on `(issuer, sub)`, so changing the issuer makes every existing user a new `pending` user.
- User data export beyond contacts CSV.
- Metrics exporters (Prometheus, OpenTelemetry). Admin alerting is the built-in `ops_health` check.
- Billing, plans, tenant hierarchies, teams, shared workspaces beyond delegation, and approval workflows between users.
- Out-of-process or dynamic-library agents.
- DMs and messaging inboxes, threads of several posts, and an automatic first comment. (Replies and comments on posts are in plan 03.)
- Editing or deleting already-published posts (agents delete remote posts only to cancel native-scheduled uploads and during user deletion).
- Professional video editing: codec conversion beyond the cheap fixes, frame-rate conversion, filters, captions, and audio work. Plan 03 provides basic fitting only.
- Sending TikTok posts to the creator's inbox as drafts. TikTok uses Direct Post only.
- Posting queues with per-account time slots, and evergreen rotation. (Recurring posts are in plan 03.)
- Bulk import of posts (CSV or similar), link shortening, and UTM tagging.
- Image, video, and audio generation. Deployment-level AI providers.
- S3-compatible media storage (the traits leave room for it).
- SSE or WebSocket, universal links, FCM, and APNs.
- Localization beyond English and Arabic in plan 03 (French and German later), and non-Gregorian calendars.
- App Store distribution and signed desktop installers. Android starts with a sideloaded APK; F-Droid and Google Play come later.
- WhatsApp, Kick, Reddit, Pinterest, and Tumblr agents in plan 03.
- Horizontal-scale tuning and Kubernetes manifests. The only bundled reverse proxy is the Caddy recipe of plan 03's first deployment.

## Definition of done (all plans)

1. The Cargo workspace builds on current Rust stable with a `rust-version = "1.98"` floor, and all crates pass the same quality gates, lints, and `cargo deny`.
2. Users sign in only through the configured OIDC provider on web and mobile. New users wait for admin approval. No password or postit-issued token exists anywhere.
3. The core agent contract is stable, and every agent in plan 03 plus the mock is a compile-time agent that passes the shared conformance suite.
4. Adding a platform requires only a new crate, a Cargo feature, and one registration line, proven by a test, including the platform appearing in the API and the web and mobile clients without code changes there.
5. Each user's workspace is private, and delegation grants exactly the documented level and account limit, proven by isolation tests at the repository and HTTP layers and by composite-FK tests showing the database rejects cross-owner references.
6. Credentials are acquired only through OAuth's server-side callback or a verified credential form, refreshed with cross-process serialization where they refresh, and stored only as vault-sealed ciphertext. No secret appears in logs, errors, or API responses.
7. Large media is streamed or chunked, served to platforms only through signed expiring URLs, with platform-appropriate resume and recovery, and fitting never alters media without the user's choice.
8. Posts, comments, schedules, recurrences, deliveries, direct sends, attempts, receipts, and partial successes are durable and idempotent. Unknown outcomes are reconciled, not duplicated.
9. The web client covers sign-in, first-run setup, user administration and limits, delegation, accounts (OAuth, credentials, CSV import), writing styles, target groups, the brand profile, media with fitting, the composer with the drafter, campaigns, email campaigns and contacts, dry-run, local, native, and recurring scheduling, the calendar, queue, history, retry, resolve, cancel, the inbox with replies, analytics, notifications, AI providers, preferences, and the admin screens. The mobile client covers the same user features except the email block editor, contact CSV import and export, and the admin screens.
10. Every live post, comment, and reply is explicitly confirmed by a person (a recurrence once for its occurrences) and can be stopped by the kill switch or a per-platform switch, except native-scheduled uploads already on the platform, which are reported and cancelled individually. Dry-run is safe everywhere.
11. Every campaign email carries a working one-click unsubscribe and the sender's postal address, goes only to consented, unsuppressed contacts, and respects the sender's daily cap.
12. The web and mobile UIs are complete in English and Arabic, with correct right-to-left layout, and server-rendered text follows the recipient's locale.
13. User deletion completes and resumes after a crash at every step, leaves other owners' rows intact, and pseudonymizes every audit reference. Audit events are written for every event kind listed in the plans.
14. `ops_health` raises and clears each alert, and data retention purges run as configured.
15. A documented backup and restore drill (Postgres, the media volume, and the separately stored secrets) has been performed against QA and the first deployment.
16. CI verifies formatting, linting, type checking, tests, conformance suites, the SQLx offline cache, the OpenAPI, TypeScript types, and Dart client contract, message catalog completeness, dependency and security checks, and redaction. CI never publishes live or sends real email.
