## Objective

postit is a self-hosted social publishing service for a small team. Each user signs in through the deployment's OpenID Connect provider, connects their own social accounts, creates posts by hand or with an LLM, publishes them immediately or on a schedule (postit-scheduled or platform-native), and tracks delivery history. A user can let another postit user work on their behalf through a scoped delegation.

The product has two parts:

- A Rust REST API and background worker on PostgreSQL, shipped as one Docker image.
- A Flutter client for web, desktop, and mobile.

There is no end-user CLI.

The initial platforms are X, YouTube, Facebook, Instagram, and TikTok. They are **compile-time plugins** to a platform-agnostic core: each platform is its own crate implementing the `PlatformPlugin` contract. New platforms (Threads, LinkedIn, Bluesky, Mastodon, …) are added without changing the core, the publishing engine, the schema, the REST API, or the Flutter client. Platform-specific OAuth details, validation, rate limits, upload protocols, and API types stay inside each platform crate.

## Decisions

### Product and deployment

| Topic | Decision |
|---|---|
| Product shape | Rust REST API with background jobs, plus a Flutter client (web, desktop, mobile). No end-user CLI. |
| Tenancy | One deployment per team. No multi-tenancy and no teams inside a deployment. |
| Repo layout | Monorepo: `server/` (Cargo workspace), `app/` (Flutter), `api/openapi.json` (generated contract), `docker/`, `deploy/`. |
| Processes | One binary `postit`, one image. `POSTIT_ROLE=all|api|worker`. |
| Environments | `POSTIT_ENV=development|qa|production`, with layered config per environment and matching Flutter flavors. |
| Dev hosting | `https://postit.local` with a self-signed cert trusted in the OS root store and a hosts-file entry. Ports in 44300–44399. |
| Database | PostgreSQL 18 via SQLx, with compile-checked queries and a committed offline `.sqlx` cache. |
| Background jobs | apalis (`apalis`, `apalis-postgres`, `apalis-cron`) with an exact version pin, wrapped by our own `JobQueue` and `JobConsole` seams in one crate. Admins get a Hangfire-style Jobs page in Flutter (list, stats, detail, retry, cancel, delete, recurring jobs, trigger-now). apalis-board is not used. |

### Identity and access

| Topic | Decision |
|---|---|
| User authentication | **Generic OpenID Connect only.** postit stores no passwords and issues no tokens. The API verifies bearer JWTs from one configured issuer. Code is provider-agnostic. |
| Identity provider | Deployment choice. Development compose and the docs bundle **Zitadel**. CI uses an in-process test issuer (wiremock JWKS). Kanidm, Authentik, Keycloak, and Firebase-style issuers work if they issue JWTs with the configured audience. |
| User key | `(issuer, sub)`. Never email. |
| Authorization | Owned by the postit database: role (`admin` or `member`) and status (`pending`, `active`, `disabled`, `deleting`). IdP role or group claims are ignored, so claim shapes do not matter. |
| Provisioning | First sign-in creates the user as `pending`. An admin approves before the user can do anything except read `/me`. |
| First admin | Bootstrapped from config (`auth.bootstrap.admin_email` with a verified email claim, or `auth.bootstrap.admin_subject`). Production refuses to start when no admin exists and neither is set. `admin_subject` is recommended for QA and production: `admin_email` trusts the IdP's `email_verified`, which federated or misconfigured IdPs may set for addresses the user does not control, and the first such sign-in wins. |
| Account email | Sign-up, passwords, MFA, and account recovery belong to the IdP. postit sends email only for its own events (approval requests, approvals, publishing notifications). |
| Ownership | **Private per user.** Social accounts, tokens, media, posts, jobs, deliveries, AI providers, and notifications belong to one user (`owner_id`). |
| Delegation | An owner can grant another active user scoped access to their workspace (levels `view`, `edit`, `publish`, optionally limited to chosen social accounts). No re-delegation. The delegate acts as the owner through a per-request act-as header. See [Delegation](#delegation). |
| Admin role | Admins approve and disable users, change roles, manage background jobs, and manage deployment settings: platform developer apps, the live-publishing kill switch, per-platform enablement, and diagnostics. Admins **cannot** read other users' content or secrets and cannot create delegations for others. This is an application-level boundary (see [Trust boundary](#trust-boundary)). |

### Publishing

| Topic | Decision |
|---|---|
| Platform developer apps | Deployment-level. One client ID/secret per platform in config (`[platforms.<id>]` plus `_FILE` secrets). Each user connects their own accounts through them. |
| LLM provider keys | Per user. Each user configures providers (opencode-shaped) with their own keys. No deployment-level AI config. |
| Stored secrets | Social tokens, PKCE verifiers, and LLM keys are sealed in Postgres with envelope encryption (`postit-vault`). |
| Social OAuth callback | Server-side: `https://<api host>/api/v1/platforms/{id}/oauth/callback`. The Flutter client opens the authorize URL and receives the result redirect, then confirms the connection with its bearer token, so a callback can never attach accounts to a user who did not complete it (plan 03, [Connecting a social account](03.%20publishing%20roadmap.md#connecting-a-social-account)). |
| Social grants | One OAuth authorization is a **grant**. A grant can yield several social accounts (YouTube channels, Facebook Pages), which share its tokens. Refresh is serialized per grant, and the grant is revoked at the provider only when its last account is disconnected. |
| Media hosting | Filesystem storage volume. Platforms fetch media through short-lived HMAC-signed public URLs, and the Flutter client displays media through short-lived signed view URLs (web video and image elements cannot send a bearer header). `MediaStore` and `MediaHost` are traits, so an S3 backend can be added later. Platforms that pull media (Instagram, TikTok `PULL_FROM_URL`, Facebook photos by URL) need `media.public_base_url` reachable from the internet; the rest of the API may stay private. |
| Web client hosting | The `postit-server` image carries the Flutter web build and serves it (`server.web`). The web build reads its runtime settings from `GET /config.json`, so one image is promoted unchanged across environments. |
| Live publishing | On in every environment. Every live publish requires explicit confirmation by the acting user. A runtime kill switch (`publishing.live`) and per-platform `enabled` flags stop postit-driven publishing. A per-publish dry-run toggle is always available. CI never publishes live. |
| Kill switch limit | The switches cannot stop deliveries already uploaded with native scheduling: the platform publishes them at their scheduled time. Turning a switch off does not unschedule them. The switch dialog and `GET /admin/doctor` show how many such deliveries exist (counts per platform, no content), and owners (or `publish` delegates) cancel them individually, which deletes them on the platform where the plugin supports it. |
| Scheduling UI | Composer, queue, history, and a calendar (month, week, agenda) with drag-to-reschedule. |
| Platform order | X and YouTube first. Meta (Facebook, Instagram) and TikTok follow in parallel. |
| Notifications | In-app notifications plus email for critical events, with a per-user email opt-out. No mobile push. |
| Live progress | Polling with ETags. No SSE or WebSocket. |

## Engineering standards

These apply to every phase in plans 02 and 03 and are part of every phase's exit criteria.

### DRY and ownership

**One owner per concern.** Each cross-cutting concern has exactly one implementation that everything else reuses:

| Concern | Owner |
|---|---|
| Config, environments, `_FILE` secrets, redacted dump | `postit-config` |
| Outbound HTTP: the only `reqwest` factory, retry, rate limiting, redaction | `postit-http` |
| Postgres pool, migrations, repositories, owner scoping, the audit writer (`AuditLog`), `app_settings` reads and writes, data retention purges | `postit-data` |
| The job runner (the only crate that depends on apalis) | `postit-jobs` |
| Mail transport, templates, and the `send_email` job | `postit-mail` |
| OIDC token verification, claims transformation, users, roles, delegation resolution | `postit-identity` |
| HTTP surface, extractors, problem+json, OpenAPI, inbound rate limiting, CORS, `If-Match` and `Idempotency-Key` handling | `postit-api` |
| Domain models, plugin contract, registry, validation engine, `Clock` and `IdGenerator` | `postit-core` |
| Encryption of stored secrets | `postit-vault` |
| Social OAuth flows and token storage | `postit-oauth` |
| Media storage, intake, probing, public hosting | `postit-media` |
| Shared plugin machinery and the conformance suite | `postit-platform-kit` |
| Meta Graph API client | `postit-platform-meta` |
| LLM providers and generation | `postit-content` |
| Delivery state machine and publishing orchestration | `postit-publishing` |
| Notifications | `postit-notify` |

Further DRY rules:

- **Platforms declare, the engine executes.** Validation runs in one core engine that reads plugin-supplied capability data: limits, media rules, and a text-measure function (for example, X's weighted character count). No validation logic is duplicated per endpoint or per platform.
- **One conformance suite.** Every plugin passes the same generic suite from `postit-platform-kit` (feature `testkit`): the dry-run contract, error mapping, idempotency, cancellation, and redaction. Platform crates add only protocol-specific tests. Shared wiremock fixtures (mocked OAuth, token refresh, rate-limit responses, malformed payloads) also come from the testkit.
- **Access checks live in one place.** Every repository method in `postit-data` that touches owned rows takes an `OwnerScope`, filters on `owner_id`, and applies the delegation's account limit. Services call `OwnerScope::require(capability)` before acting. Handlers and services never write their own ownership filters.
- **Audit goes through one writer.** Every audit event is recorded through `postit-data`'s `AuditLog`, which enforces the event shape: user references only in the ID columns or in `details` keys ending in `_user_id`, and never secrets or user content. Services never insert into `audit_events` directly.
- **Jobs are console-safe.** Every job type registers an ID-only `JobSummary`, so the admin Jobs console never shows payloads. Payloads themselves carry IDs, not content: `send_email` renders from current data when it runs, so the job tables never hold addresses or message bodies. Every handler is idempotent against its domain state, so a console retry cannot duplicate a post. Email is at-least-once: a handler checks its sent marker before sending, but a crash between the SMTP accept and the marker write can send twice.
- **Enqueue with the change.** Work that must follow a state change is enqueued with `JobQueue::enqueue_in(tx, …)` in the same transaction as the change, through the `postit-jobs` outbox (plan 02, `postit-jobs`). A crash can never commit the change and lose the job.
- **Thin handlers.** axum handlers parse input, call a service, and map the result. Business rules live in service crates, so jobs and tests reuse them without HTTP.
- **The API contract is generated, never hand-written.** `utoipa` annotations produce `api/openapi.json`, and the Dart client is generated from that file. CI fails if either is stale.
- **Workspace-level dependencies.** Every dependency version is declared once in `[workspace.dependencies]`; crates use `dep.workspace = true` and enable only the features they need.

### Rust practices

- Toolchain pinned to Rust 1.98.1 (`rust-toolchain.toml`, rustfmt and clippy), edition 2024.
- `[workspace.lints]` inherited by all crates:
  - `unsafe_code = "forbid"`.
  - `clippy::all` and `clippy::pedantic` at warn. Allowances are justified in `Cargo.toml` comments.
  - `clippy::unwrap_used`, `clippy::expect_used`, and `clippy::panic` denied outside tests.
  - `missing_docs` warn on library crates.
- **Errors.** Library crates use `thiserror` enums. Only `postit-server` uses `anyhow`. Errors carry structured context and never include secret values. The API maps them to RFC 9457 problem+json with a stable `code` extension and the request ID. Internal errors never expose details.
- **Secrets are typed.** Tokens, auth codes, API keys, client secrets, SMTP passwords, and encryption keys use `secrecy::SecretString` (or newtypes over it), so `Debug` and `Display` redact by construction. Log redaction is a backstop.
- **No secret reaches a log, an error, an API response, or the OpenAPI examples.** This covers bearer tokens, social tokens, auth codes, API keys, signed media URLs, sealed values, and SMTP or vault keys. Tests assert it.
- **Newtypes** for identifiers: `UserId`, `DelegationId`, `PlatformId`, `SocialAccountId`, `PostId`, `MediaId`, `PublishJobId`, `DeliveryId`, `DeliveryAttemptId`, `RemotePostId`, `AiProviderId`, `AiGenerationId`, `ModelId`, `NotificationId`, `AuditEventId`. Internal IDs are UUID v7, generated in Rust.
- **Deterministic tests.** Injected `Clock` and `IdGenerator` traits, a seeded jitter RNG, and no real network in non-ignored tests.
- **Async trait objects.** `PlatformClient`, `PlatformPlugin`, `LlmProvider`, `TokenStore`, `MediaStore`, `MediaHost`, `Mailer`, and `JwksSource` are used as `dyn` objects. Phase P1 adds a trait-object compile test and picks one approach: native dyn-compatible async traits if the pinned toolchain supports them, otherwise `async-trait`.
- **Tracing** with `tracing` and `tracing-subscriber` everywhere. `#[instrument(skip(...))]` on any function that receives a secret.
- **Operational alerts.** There is no metrics exporter (see [Non-goals](#non-goals)). Instead, an `ops_health` cron job (every 5 minutes) checks thresholds from `[ops]` config: due deliveries overdue by more than 5 minutes, new `DeadLetter` or `OutcomeUnknown` deliveries, failing token refreshes, failed jobs in the queue, and the JWKS or mail transport being unhealthy. When a check first crosses its threshold, active admins get an in-app notification and a critical email; they are not sent again until the check recovers. Alert state is stored in `ops_alerts`, so it survives restarts and is shared by every worker process. The notification contains counts and IDs only, never user content. `GET /admin/doctor` shows the same checks.
- **Dependency hygiene.** reqwest uses rustls, streaming, JSON, and multipart only; no `blocking`, `cookies`, or `socks`. `cargo-deny` covers licenses, advisories, and duplicate crates.

### Reuse of essentialMix-rs (`emix*` crates)

Crates come from crates.io with a loose `"0"` spec, declared once in `[workspace.dependencies]`, with `default-features = false` where a crate enables heavy defaults. `Cargo.lock` keeps builds reproducible. Because a `0.x` minor bump is semver-breaking, run the full quality gates after each `cargo update`.

| Crate | Use in postit | Where |
|---|---|---|
| `emixdb` | `Pagination` and `ResultSet<T>` for every list endpoint | `data`, `api` |
| `emixcrypto` (`default-features = false`) | `Sha256Hash` for media content hashes, OAuth state hashes, and idempotency keys | `core`, `data`, `media`, `oauth` |
| `emixcore` | Only as a conversion source: `impl From<emixcore::Error>` where emix APIs are called | where used |

Evaluated and **not** used:

- `emixai`: built on kalosm with heavy local-inference dependencies, a hard-coded OpenAI model enum, and no custom base URL. postit's `LlmProvider` layer could later be upstreamed.
- `emixnet`: `pool_max_idle_per_host(0)` disables connection reuse, a forced JSON `Content-Type` breaks multipart and binary uploads, and it enables a cookie store. Worth fixing upstream with an options struct.
- `emixlog`: log4rs/slog-based; postit standardizes on `tracing`.
- `emixseaorm`, `emixdiesel`: postit uses SQLx.
- `emixcollections`: no current need.
- `emix` (`terminal`) and `emixthreading`: they served the old CLI, which is gone.
- `emix::datetime::parse_date_any`: interprets input as UTC and ignores the time zone. Schedule input is time-zone-aware.

## Crate dependencies

Dependencies point strictly downward. A crate may depend only on crates on earlier levels. Crates on the same level never depend on each other; the one exception is that `facebook` and `instagram` depend on `meta`.

1. `config`, `core` (no internal dependencies).
2. `http` (config), `vault` (config).
3. `data` (config, core, vault for the `Sealed<T>` column type).
4. `jobs` (config, data). The only crate that sees apalis.
5. `mail` (config, data, jobs). Owns `send_email`; reads recipients and writes audit events through `data`.
6. `notify` (config, core, data, jobs, mail). Every other service crate records notifications through it.
7. `identity` (config, http, data, jobs, mail, notify).
8. `oauth`, `media`, `platform-kit`, `content` (core, http, data, vault, jobs, notify as needed).
9. Platform crates (core, http, platform-kit; `facebook` and `instagram` also `meta`). They get tokens and media only through the `core` traits in their plugin context, never by depending on `oauth` or `media`.
10. `publishing` (core, data, jobs, notify, identity, oauth, media, platform-kit).
11. `api` (every service crate). `server` (everything).

The levels set allowed dependencies, not build order: `core` starts in plan 02 phase P1 as a skeleton (ID newtypes, `Clock`, `IdGenerator`) and gets the domain and plugin contract in plan 03 phase A1; `data` gains `vault` in plan 03 phase A2; `notify` is created in plan 03 phase D1, and `identity` gains its dependency on it then.

Rules:

- `core` has no platform-specific, HTTP, or database code.
- Job handlers live in the domain crate that owns the work and register through the `postit-jobs` registration API. Everything enqueues through the `JobQueue` seam. The one exception is `data_retention`: `data` sits below `jobs`, so `data` owns the purge queries and `server` registers the job.
- `server` registers each platform plugin behind a Cargo feature (`x`, `youtube`, `facebook`, `instagram`, `tiktok`, `mock-platform`). All are on by default except `mock-platform`, which development and CI builds enable.
- Platform API types never leave their platform crate.

## Identity and access

### Authentication (OIDC)

- `[auth.oidc]` holds the issuer URL, the accepted `audiences`, the Flutter `client_id` and `scopes` (served to the client by `GET /api/v1/auth/config`), accepted algorithms (default `RS256`, `ES256`, `EdDSA`), and clock-skew leeway (default 60 s).
- At startup, the server reads `{issuer}/.well-known/openid-configuration` and the JWKS through `postit-http`. `/ready` fails until the JWKS is loaded.
- The JWKS is cached, refreshed on an interval (default 1 hour), and refetched on an unknown `kid` at most once per minute, so random `kid` values cannot be used to flood the IdP.
- Every request's bearer token must be a JWT with a valid signature, the configured `iss`, an accepted `aud`, and valid `exp` and `nbf`. `alg: none` and HMAC algorithms are always rejected. Opaque tokens and token introspection are not supported; the IdP must issue JWT access tokens for postit's audience.
- postit has no sessions. Signing out ends the IdP session from the client through the IdP's `end_session_endpoint`. Access token lifetime is IdP configuration; the docs recommend 15 minutes or less.

### Claims transformation

One axum extractor layer turns a verified token into a `Principal`:

1. Look up `(iss, sub)` in a short `moka` cache (default TTL 60 s). On a miss, load the `users` row.
2. If no row exists, create it with status `pending`, or `active` with role `admin` when it matches the bootstrap rule and no active admin exists yet. The bootstrap check and insert run in one transaction under a Postgres advisory lock, so concurrent first sign-ins cannot create two bootstrap admins. Record an audit event. Notify admins of the pending user by email (see [Pending-user flood control](#roles-and-statuses)); from plan 03 phase D1, admins also get an in-app notification.
3. Refresh profile fields from configurable claims (`email`, `email_verified`, `name`, `preferred_username`) when they changed. Many IdPs (Zitadel by default) put these claims only in the ID token, not the access token. When a configured claim is missing from the access token, postit calls the discovery document's `userinfo_endpoint` with the same bearer token, through `postit-http`. It does this only on provisioning and on a cache miss, caches the result with the principal, and ignores a userinfo response whose `sub` differs from the token's. `display_name` falls back from `name` to `preferred_username`, `email`, and the subject, so it is never empty. `auth.oidc.userinfo = "fallback" | "always" | "never"` (default `fallback`) controls this. `GET /admin/doctor` warns when no profile claims were found in recent sign-ins, because bootstrap by `admin_email` and delegate lookup by email depend on them.
4. Build the `Principal { user_id, role, status }`. `pending` users may call only `GET /me` (403 `account_pending` elsewhere). `disabled` and `deleting` users get 403 `account_disabled` everywhere.

**Cache invalidation across processes.** Admin changes to a user (status, role, deletion) invalidate the local cache entry and send `pg_notify('postit_user_changed', <user id>)`. Every process `LISTEN`s on that channel and evicts the entry, so a disable takes effect everywhere within about a second. If the listener connection drops, the process clears the whole principal cache on reconnect; the TTL bounds staleness while it is down. IdP-side role or group claims are never read.

### Roles and statuses

- `admin`: everything a member can do in their own workspace, plus user administration and deployment settings. Never other users' content.
- `member`: their own workspace and any workspace delegated to them.
- The last active admin cannot be disabled, demoted, or deleted.
- `deleting` is terminal: it is set when a `delete_user` job is enqueued (see [User deletion](#user-deletion)) and can never be changed back to `active`, `pending`, or `disabled`. Admin status changes on a `deleting` user return 409 `user_deleting`.
- `pending` users older than `auth.pending_ttl` (default 30 days) are deleted by a cron job.
- **Pending-user flood control.** An IdP with open self-registration can create many `pending` users. Provisioning is covered by the per-IP rate limit, and approval-request emails are coalesced: at most one email per admin per `auth.approval_email_interval` (default 15 minutes), listing every user that became pending since the last one. The time of each admin's last approval email is stored in `user_preferences.last_approval_email_at`. The admin Users page always shows the full pending list.
- **Disabled owners.** Disabling a user blocks API access and their delegations in both directions. Their scheduled work is kept, not cancelled: when a delivery comes due, the worker parks it with `owner_disabled`. Re-enabling the user makes parked `owner_disabled` deliveries eligible again, but a delivery whose scheduled time is more than `publishing.park_grace` (default 15 minutes) in the past stays parked until the owner (or a `publish` delegate) retries or cancels it. The same parking rule applies to every parking reason (plan 03, [Delivery states](03.%20publishing%20roadmap.md#delivery-states)). Deliveries already uploaded with native scheduling are left on the platform.

### Delegation

An owner grants another active postit user access to their workspace. The grant has a level and an optional account limit:

| Level | Allows |
|---|---|
| `view` | Read social accounts, media, posts, overrides, publish jobs, deliveries, and the calendar. |
| `edit` | `view`, plus create, edit, and delete posts and overrides, upload and delete media, validate, dry-run, and generate drafts with the owner's AI providers (keys are never revealed). A post that has live publish history can be deleted only at `publish`, because deleting it deletes that history. |
| `publish` | `edit`, plus live publish, schedule, reschedule, cancel, retry, resolve, and deleting posts that have live publish history. |

- **Account limit.** A grant covers either all of the owner's social accounts or a chosen set (`delegation_accounts`). A limited delegate sees only those social accounts, can target and override only them, and sees only their deliveries. Posts and media stay visible as a whole.
- **Empty account limit.** When disconnecting accounts removes the last entry from a limited grant, the grant stays valid with no accounts: the delegate keeps access to posts and media at their level, but sees no social accounts or deliveries and cannot publish anywhere. The owner and the delegate get an in-app notification, and the owner's Delegations screen marks the grant as having no accounts.
- **Whole-object rule for limited delegates.** A limited delegate may edit or delete a post, or cancel or reschedule a publish job, only when every override on the post and every non-terminal delivery of its jobs belongs to an account in their limit. Otherwise the request fails with 403 `account_not_in_scope`, so a limited delegate can never change what is published to an account they cannot see. Retry, resolve, and single-delivery cancel act on one delivery and need only that delivery's account to be in the limit.
- **Owner-only, never delegable:** connecting, reconnecting, and disconnecting social accounts; AI provider configuration and keys; delegations; preferences; notifications; deleting the account.
- **No re-delegation.** A delegate cannot grant access to a workspace they do not own.
- **Acting as the owner.** The client sends `X-Postit-Act-As: <owner user id>`. On every request, `postit-identity` resolves it against an active delegation where both users are `active` and the grant is not revoked or expired. An invalid header returns 403 `delegation_invalid`. Without the header, the scope is the caller's own workspace. Delegation lookups are not cached, and the lookup query reads both users' status from `users` directly (not from the principal cache), so revocation and a disabled owner take effect on the next request.
- **Admin routes act on the admin's own authority.** They reject `X-Postit-Act-As` with 403 `owner_only`, and `RequireAdmin` checks the caller's role, never a delegated owner's.
- **`OwnerScope`** = `{ actor, owner, access }`, where `access` is `Owner` or `Delegated { level, accounts }`. Repositories filter by `owner`; services call `scope.require(capability)`; every write records `created_by` or `updated_by` as the `actor`.
- **Work outlives the grant.** Jobs and posts belong to the owner. Revoking a delegation does not cancel jobs the delegate scheduled; the owner sees who created them.
- **Notifications** about the owner's work go to the owner, and also to the actor when a delegate triggered the event and the grant is still active.
- **Finding a delegate.** `GET /users/lookup?email=…` returns the ID and display name of the active user with that exact verified email. It is rate-limited and returns nothing for partial matches. Email is not unique, so when more than one active user has that verified email, it also returns nothing (with the same response shape as no match), and the owner has to sort it out with the delegate outside postit.
- Granting, changing, revoking, and leaving a delegation are audited, and the other party gets an in-app notification.
- **Concurrent edits.** An owner and delegates can edit the same post at once. Post and override responses carry an `ETag` derived from `posts.version`. Every change to what the post would publish bumps `posts.version`: text and fields, media and alt text, draft targets, and override writes and deletes. Updates and deletes require `If-Match`: a mismatch returns 412 `version_conflict`, and a missing header returns 428 `precondition_required`. Publishing requires `If-Match` too, so a live confirmation always applies to the version the confirming user reviewed. The Flutter client shows the conflict and reloads. No edit silently overwrites another.

### Trust boundary

"Admins cannot read other users' content or secrets" is enforced by the application: no API route, job console view, doctor check, or notification exposes it. It is not a guarantee against anyone with host, database, or backup access. The vault keys live on the same host as the database, so whoever operates the deployment can decrypt stored tokens. The docs state this so users know that the operator is trusted.

## Data model

All tables are owned by postit, use UUID v7 IDs generated in Rust, and use `timestamptz`. Every **owned** table carries `owner_id` (FK to `users`), `created_at`, `updated_at`, `created_by`, and `updated_by`. `created_by` and `updated_by` hold the actor, which can be a delegate.

- **Owned tables:** `delegations`, `social_grants`, `social_accounts`, `social_account_tokens`, `media_assets`, `posts`, `post_media`, `post_targets`, `post_overrides`, `publish_jobs`, `deliveries`, `delivery_attempts`, `ai_providers`, `ai_generations`, `platform_quota_usage`, `notifications`, and `idempotency_keys`. Child tables (`social_account_tokens`, `post_media`, `post_targets`, `post_overrides`, `deliveries`, `delivery_attempts`) repeat `owner_id` instead of relying on a join, so every repository filter is a plain column check. `delegation_accounts` is a pure link table; its owner is the delegation's.
- **Same-owner references are enforced by the database.** Each owned table has a unique `(owner_id, id)`, and every reference between owned rows is a composite FK on `(owner_id, <ref>_id)`. So `post_media` cannot link another owner's media, an override, target, or delivery cannot target another owner's account, an account cannot use another owner's grant, and `delegation_accounts` cannot list an account the grantor does not own, whatever the repository code does.
- **Actor columns do not block deletion.** `created_by`, `updated_by`, `users.approved_by`, `delegations.revoked_by`, and similar actor columns are nullable FKs to `users` with `ON DELETE SET NULL`. When a delegate or admin is deleted, the owner's rows stay and the client shows "deleted user". `owner_id` FKs cascade, because owned rows are deleted with their owner.
- **System writes.** Changes made by jobs and cron (delivery transitions, token refresh, expiry) leave `updated_by` null, and the client shows them as "postit". The actor of the request that caused the work is recorded where it happened (`created_by`, audit events).
- **Recipient columns cascade.** A user reference that is not an actor and not the owner (`notifications.user_id`, `idempotency_keys.actor_id`, `oauth_states.user_id`) is a FK with `ON DELETE CASCADE`: those rows exist only for that user.

Token and key values exist in the database only as vault-sealed ciphertext. A test asserts that no column contains a plaintext value from the test fixtures.

### Identity (plan 02, except delegations in plan 03)

- **`users`**: `id`, `oidc_issuer`, `oidc_subject` (unique together), `email citext` (informational, not unique), `email_verified bool`, `display_name`, `role` (`admin`, `member`), `status` (`pending`, `active`, `disabled`, `deleting`), `approved_at`, `approved_by`, `last_seen_at`, `created_at`, `updated_at`.
- **`audit_events`**: `id`, `at`, `actor_user_id`, `owner_id` (null for deployment events), `subject_user_id`, `kind`, `ip`, `request_id`, `details jsonb`. Records provisioning, approval, role and status changes, delegation changes, settings changes, and publishing milestones. Never stores secrets or tokens. Written only through `AuditLog`; any other user reference goes in a `details` key ending in `_user_id`, so pseudonymization can find it.
  - Retention: an `audit_retention` cron job (daily) clears `ip` after `audit.ip_retention` (default 90 days) and deletes events older than `audit.retention` (default 2 years).
  - User IDs are not foreign keys, so audit rows survive user deletion (see [User deletion](#user-deletion)).
- **`delegations`**: `id`, `owner_id`, `delegate_id` (check `owner_id <> delegate_id`), `level` (`view`, `edit`, `publish`), `all_accounts bool`, `expires_at` (optional), `ended_at`, `ended_reason` (`revoked`, `left`, `expired`), `revoked_by`, plus the owned-table columns. Revoking, leaving, and the `delegation_expiry` job set `ended_at`. A partial unique index on (`owner_id`, `delegate_id`) `WHERE ended_at IS NULL` allows one live grant per pair (an index predicate cannot use `now()`, so an expired grant counts as live until the expiry job ends it; granting again first ends an already-expired grant in the same transaction). Act-as resolution checks both `ended_at` and `expires_at`.
- **`delegation_accounts`**: `delegation_id`, `account_id` (FK to `social_accounts`, cascade on delete). Used when `all_accounts` is false.
- **`user_preferences`**: `user_id` (1:1, created with the user), `email_notifications bool`, `timezone` (IANA; defaults to the zone the client reports at first sign-in, else `UTC`), `store_ai_prompts bool`, `last_approval_email_at` (admins only; approval-email coalescing).

### Deployment

- **`platforms`**: `id text PRIMARY KEY` (checked against `^[a-z][a-z0-9_-]{0,31}$`), `display_name`, `enabled bool`, `first_seen_at`.
  - `id` is the plugin identifier from `PlatformDescriptor` (`x`, `youtube`, …). It is a natural text key, so adding a platform needs no migration and IDs are identical across environments.
  - The server upserts one row per registered plugin at startup, after migrations. Code stays the source of truth; the table gives referential integrity and the admin `enabled` switch.
  - A row whose plugin is compiled out stays, and the API reports the platform as unavailable in this build.
- **`app_settings`**: deployment-level runtime settings edited by admins. Initially `publishing.live`, seeded from config.
- **`platform_app_quota_usage`** (plan 03): `platform_id text REFERENCES platforms(id)`, `bucket`, `period_start date`, `units_used`, unique on (`platform_id`, `bucket`, `period_start`). Deployment-wide quota such as YouTube's per-project daily quota or an X app's monthly post cap, shared by every user. Not owned; it holds no user reference. `period_start` is the first day of the bucket's period (`day` or `month`) in the plugin's reset time zone, as in `platform_quota_usage`.
- **`job_recurring_runs`** (plan 02): `name`, `scheduled_for`, `manual bool`, `job_id`, `outcome`, `finished_at`, unique on (`name`, `scheduled_for`) for scheduled runs. The unique insert makes each cron tick run once across worker processes, and the rows feed the Jobs console's last run and outcome. Purged by `job_history_purge`.
- **`job_outbox`** (plan 02): `id`, `job_type`, `payload jsonb` (IDs only), `run_at`, `created_at`. Written by `JobQueue::enqueue_in` inside the caller's transaction and drained into the apalis storage by the `postit-jobs` relay, which deletes each row once its job is stored.
- **`ops_alerts`** (plan 03, G2): `check` (primary key), `firing bool`, `since`, `notified_at`, `recovered_at`. Holds `ops_health` alert state; counts and IDs only.

### Owned content (plan 03)

- **`social_grants`**: `platform_id text REFERENCES platforms(id)`, `remote_user_id` (the authorizing identity at the provider), `access_token` sealed, `refresh_token` sealed, `expires_at`, `reconnect_by` (when the grant ends regardless of refresh, if the provider says so), `reconnect_warned` (`none`, `7d`, `1d`, `expired`; so each reminder is sent once), `scopes text[]`, `status` (`active`, `needs_reconnect`, `revoked`). One row per OAuth authorization. Refresh, `needs_reconnect`, and revocation act on the grant and so on every account that uses it. A grant with no remaining accounts is revoked at the provider where supported and deleted.
- **`social_accounts`**: `grant_id` (composite FK to `social_grants`; null once `disconnected`), `platform_id text REFERENCES platforms(id)`, `remote_account_id`, `display_name`, `avatar_url`, `scopes text[]`, `status` (`active`, `needs_reconnect`, `revoked`, `disconnected`), `test_account bool` (informational label, set by the owner), `last_checked_at`. Unique on (`platform_id`, `remote_account_id`) across the deployment among rows that are not `disconnected` (a partial unique index): a remote account belongs to one postit owner, and sharing goes through delegation. When another owner has already connected an account that the OAuth callback discovers, that account is skipped, the other discovered accounts are still connected, and the redirect carries `code=account_connected_elsewhere` without saying who owns it. Reconnecting by the same owner updates the row, including a `disconnected` one.
  - **Disconnecting keeps the row** with status `disconnected`, no grant, and no token, so delivery history keeps its account (plan 03, [Disconnecting a social account](03.%20publishing%20roadmap.md#disconnecting-a-social-account)). The row is deleted only with its owner.
- **`social_account_tokens`**: `account_id` (1:1, optional), `access_token` sealed, `expires_at`. Only for platforms that derive a token per account from the grant (Facebook Page tokens). Other accounts use their grant's token.
- **`oauth_states`**: `state_hash bytea unique`, `user_id`, `platform_id text REFERENCES platforms(id)`, `pkce_verifier` sealed, `return_to`, `created_at`, `expires_at` (10 minutes). After the callback, the same row holds the pending result until the client confirms it: `connect_id_hash bytea unique`, the sealed grant tokens, and the discovered accounts. An `oauth_state_purge` cron job (hourly) deletes expired rows, confirmed or not.
- **`media_assets`**: `storage_key`, `thumbnail_key`, `original_filename`, `mime`, `bytes`, `sha256`, `width`, `height`, `duration_ms`, `status` (`uploading`, `ready`, `failed`), and for resumable upload sessions `declared_bytes`, `upload_offset`, and `upload_expires_at`. There is no content deduplication: identical uploads are separate assets, and `sha256` is used only for integrity checks and platform upload checksums. `ready` assets form the owner's media library and are kept until the owner deletes them. Stored bytes of `ready` assets plus the `declared_bytes` of open upload sessions count against `media.user_quota_bytes`, so concurrent sessions cannot overshoot it.
- **`posts`**: `text`, `link`, `tags text[]`, `disclose_ai_generated bool`, `version int`, `status` (`draft`, `scheduled`, `publishing`, `published`, `partial`, `failed`, `cancelled`).
  - A post can have several publish jobs over its lifetime but **at most one non-terminal live job** at a time (enforced by a partial unique index on `publish_jobs` that excludes dry-run jobs).
  - `posts.status` describes the **current version**. It mirrors the latest live (non-dry-run) job when that job's `post_version` equals `posts.version`, and is `draft` otherwise: no live job yet, or the post was edited after its last job ended. Earlier jobs stay as history, and the client shows "last published vN" from them.
  - **Locked while publishing.** Editing or deleting a post, or changing its media, targets, or overrides, returns 409 `post_locked` while it has a non-terminal job. The user cancels the job, or waits for it to finish, and then edits. Every edit and every job creation first takes `SELECT … FOR UPDATE` on the `posts` row, so an edit and a publish can never interleave.
  - **Deleting a post** deletes its jobs, deliveries, and attempts. When it has any live (non-dry-run) job, it needs the `publish` level (plan 01, [Delegation](#delegation)).
  - **`post_media`**: `post_id`, `media_id`, `position`, `alt_text`.
  - **`post_targets`**: `post_id`, `account_id`. The draft's chosen target accounts, so a reopened draft keeps its selection. The publish request still names its targets explicitly. A limited delegate sees and changes only the targets in their limit; the others are kept as they are.
  - **`post_overrides`**: `post_id`, `account_id`, `patch jsonb`, `options jsonb` (the platform's per-target publish options, validated against the plugin's options schema). `patch` may set `text`, `link`, `tags`, and `media` (an ordered subset of the post's media, with per-target alt text); nothing else. Overrides never mutate the canonical post; the engine resolves a per-target view.
- **`publish_jobs`**: `post_id`, `post_version`, `content_snapshot jsonb`, `scheduled_at` (UTC, null for "now"), `native_schedule bool`, `dry_run bool`, `status` (derived from deliveries), `version int`, `cancelled_at`.
  - `content_snapshot` is the resolved per-target content (text, link, tags, media IDs with alt text, and options) at creation. Workers, retries, and reconcile publish from the snapshot, never from the current post, so a retry after the post was edited publishes exactly what was confirmed. A retry revalidates the snapshot; a referenced media asset that was deleted since makes the retry fail with a violation.
  - `version` is bumped by every change to the job or any of its deliveries; the job ETag is derived from it.
- **`deliveries`**: `job_id`, `account_id`, `state` (plan 03, [Delivery states](03.%20publishing%20roadmap.md#delivery-states)), `idempotency_key bytea UNIQUE`, `dispatch_gen int` (incremented on every re-enqueue, so stale queue entries cannot claim), `lease_expires_at`, `cancel_requested_at` (set by the API for an `InFlight` delivery; the worker honors it at its next safe checkpoint), `attempt_count`, `next_attempt_at`, `remote_id`, `remote_url`, `container_ref` (Instagram container ID, TikTok `publish_id`, YouTube upload session), `remote_publish_at` (native scheduling), `last_error jsonb`, `parked_reason`.
  - `idempotency_key = sha256(job_id, account_id)` via `emixcrypto`. This prevents duplicate deliveries within one job and still lets a new job publish the same post version to the same account again (for example, after a cancel or after the remote post was deleted). The publish dialog warns when the same version has already been published to a target account.
- **`delivery_attempts`**: `delivery_id`, `started_at`, `finished_at`, `outcome`, classified error, redacted request summary. The request summary and the error are covered by the plaintext-secret test, like sealed columns.
- **`ai_providers`**: `provider_key`, `config jsonb` (opencode-shaped, without the key), `api_key` sealed, `is_default bool`.
- **`ai_generations`**: `provider_id`, `model`, `prompt_hash`, `prompt` (only when the owner enables storing prompts), token usage, `post_id` (null until the client saves the draft as a post).
- **`platform_quota_usage`**: `account_id`, `platform_id text REFERENCES platforms(id)`, `bucket`, `period_start date`, `units_used`, unique on (`account_id`, `platform_id`, `bucket`, `period_start`). `period_start` is the first day of the bucket's period (`day` or `month`) in the time zone the plugin declares for its reset (for example, YouTube resets at midnight `America/Los_Angeles`), not UTC. Rolling windows (Instagram's 24 hours) are not counted here; the plugin checks them against the platform before publishing.
- **`notifications`**: `user_id` (recipient; the owner, a delegate actor, or an admin), `owner_id` (the workspace; null for deployment notifications to admins, such as pending users and `ops_health` alerts), `kind`, `severity`, `payload jsonb` (IDs and counts), `read_at`, `emailed_at`. The notifications repository filters on `user_id` (the recipient), not on the workspace owner: a delegate reads their own notifications about an owner's work.
- **`idempotency_keys`**: `actor_id`, `owner_id` (the workspace the request acted in), `key`, `route`, `request_hash`, `state` (`in_progress`, `completed`), `response_status`, `response_body jsonb`, `expires_at` (24 hours), unique on (`owner_id`, `actor_id`, `key`). Create endpoints (`POST /posts`, `POST /media`, `POST /media/uploads`, publish, schedule) accept an optional `Idempotency-Key` header. The first request inserts the row as `in_progress` before doing any work; a concurrent request with the same key gets 409 `idempotency_in_progress`. A repeat after completion with the same key and body returns the stored response; with a different body it returns 422 `idempotency_key_reused`. An `in_progress` row whose request failed without a response is deleted, so the client can retry. This stops a mobile retry from creating a duplicate post or upload.

### Data retention

A daily `data_retention` cron job (purge queries in `postit-data`, registered by `postit-server`) applies these defaults, each configurable under `[retention]`:

| Data | Default |
|---|---|
| Read notifications | Deleted 90 days after `read_at`. Unread notifications are kept. |
| `delivery_attempts` | Deleted after 180 days. The delivery row keeps its final state, `remote_id`, and `last_error`. |
| `ai_generations.prompt` | Cleared after 30 days. The row (model, token usage, `prompt_hash`) is deleted after 1 year. |
| Terminal `publish_jobs` and `deliveries` | Kept for the life of the post. They are the publishing history. |
| `idempotency_keys` | Deleted after `expires_at`. |
| `audit_events`, `oauth_states` | As described above. |

### User deletion

A user can be deleted in two ways:

- An admin deletes the user with `DELETE /users/{id}`.
- The owner deletes their own account with `DELETE /me`, confirming by sending their display name. This is owner-only and never available through act-as.

The last active admin can never be deleted. Both paths, and the `purge_pending_users` cleanup of stale pending users, run the same `delete_user` job:

1. The user is set to `deleting` right away, in the same transaction that enqueues the job (`enqueue_in`, so the job cannot be lost). This blocks access, deactivates delegations in both directions, and cannot be reversed, so an admin cannot re-enable a half-deleted user.
2. Non-terminal publish jobs are cancelled. In-flight deliveries finish or are cancelled at their next safe checkpoint first, and the job waits for them.
3. Deliveries uploaded with native scheduling but not yet live are deleted on the platform through the plugin where supported. The ones that cannot be deleted are listed in the audit event and in the admin's confirmation, because they will still go live.
4. Social tokens are revoked at each provider where supported.
5. Owned rows, stored media, delegations in both directions, and preferences are deleted. Actor columns in other owners' rows that point at this user become null (`ON DELETE SET NULL`); those rows are kept.
6. In `audit_events`, the user's ID is replaced by `HMAC-SHA256(audit.pseudonym_key, user_id)` everywhere it appears: `actor_user_id`, `owner_id`, `subject_user_id`, and every `details` key ending in `_user_id`. The key is a deployment `_FILE` secret, so the value cannot be reversed by hashing known user IDs, while events for the same deleted user stay linked. The HMAC is stored as the UUID built from its first 16 bytes with the version nibble set to 8 (UUIDv8, which postit never generates otherwise), so the column types do not change and `GET /admin/audit` can mark pseudonyms as deleted users. The `ip` of every event this user performed is cleared at the same time.
7. The `users` row is deleted last.

The job is idempotent and can be resumed after a crash. The IdP account is untouched, and signing in again creates a new `pending` user. There is no data export (see [Non-goals](#non-goals)).

### Secrets that must be backed up

A Postgres backup is useless without the `vault.keys` versions that sealed it: losing a key version means every user has to reconnect the affected social accounts and re-enter their AI keys. Backups must include every live `vault.keys` version, `media.signing_key`, and `audit.pseudonym_key`, stored separately from the database backup.

## Non-goals

- Passwords, password reset, invites, MFA, or account recovery inside postit (the IdP owns them).
- Opaque access tokens, token introspection, several issuers at once, SCIM, or IdP-driven roles.
- Migrating users to a different IdP or issuer. Users are keyed on `(issuer, sub)`, so changing the issuer makes every existing user a new `pending` user. A future relink tool would map old keys to new ones; until then, the issuer is fixed for the life of a deployment.
- User data export.
- Metrics exporters (Prometheus, OpenTelemetry). Admin alerting is the built-in `ops_health` check.
- Multi-tenancy, teams, shared workspaces beyond delegation, and approval workflows.
- Out-of-process or dynamic-library plugins.
- Threads, replies, comments (including an automatic first comment), DMs, analytics, and insights. Editing or deleting already-published posts (plugins delete remote posts only to cancel native-scheduled uploads and during user deletion).
- Media transcoding, resizing, or cropping for a platform's format rules. Uploads are published as they are, and a platform's constraints surface as validation violations.
- Sending TikTok posts to the creator's inbox as drafts. TikTok uses Direct Post only.
- Recurring or evergreen posts and posting queues with time slots. (The admin Jobs console's "recurring jobs" are internal cron jobs, not user posts.)
- Bulk import of posts (CSV or similar), link shortening, and UTM tagging.
- Image and video generation. Deployment-level AI providers.
- S3-compatible media storage (the traits leave room for it).
- Mobile push notifications, SSE or WebSocket, universal links, and localization.
- App store distribution and signed installers (Play Store, App Store, MSIX, notarized macOS builds). The docs cover building each flavor from source and internal distribution (APK sideloading, optional TestFlight).
- Horizontal-scale tuning, Kubernetes manifests, and a bundled TLS proxy for QA and production.

## Definition of done (all plans)

1. The Cargo workspace is pinned to Rust 1.98.1, and all crates pass the same quality gates, lints, and `cargo deny`.
2. Users sign in only through the configured OIDC provider on web, desktop, and mobile. New users wait for admin approval. No password or postit-issued token exists anywhere.
3. The core plugin contract is stable, and all five platforms plus the mock are compile-time plugins that pass the shared conformance suite.
4. Adding a platform requires only a new crate, a Cargo feature, and one registration line, proven by a test, including the platform appearing in the API and the Flutter client without code changes there.
5. Each user's workspace is private, and delegation grants exactly the documented level and account limit, proven by isolation tests at the repository and HTTP layers and by composite-FK tests showing the database rejects cross-owner references.
6. OAuth credentials are acquired through the server-side callback, refreshed with cross-process serialization, and stored only as vault-sealed ciphertext. No secret appears in logs, errors, or API responses.
7. Large media is streamed or chunked, served to platforms only through signed expiring URLs, with platform-appropriate resume and recovery.
8. Posts, schedules, deliveries, attempts, receipts, and partial successes are durable and idempotent. Unknown outcomes are reconciled, not duplicated.
9. The Flutter client covers sign-in, user administration, delegation, accounts, media, the composer with AI generation, dry-run, local and native scheduling, the calendar, queue, history, retry, resolve, cancel, notifications, AI providers, preferences, and the admin screens.
10. Every live publish is explicitly confirmed and can be stopped by the kill switch or a per-platform switch, except native-scheduled uploads already on the platform, which are reported and cancelled individually. Dry-run is safe everywhere.
11. User deletion completes and resumes after a crash at every step, leaves other owners' rows intact, and pseudonymizes every audit reference. Audit events are written for every event kind listed in the data model.
12. `ops_health` raises and clears each alert, and data retention purges run as configured.
13. A documented backup and restore drill (Postgres, the media volume, and the separately stored secrets) has been performed against QA.
14. CI verifies formatting, linting, type checking, tests, conformance suites, the SQLx offline cache, the OpenAPI and Dart client contract, dependency and security checks, and redaction.
