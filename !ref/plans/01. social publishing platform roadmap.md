# Social Publishing Platform Roadmap

## Objective

Build `postly` as a Rust 1.98.1 stable Cargo workspace that lets users authenticate social accounts, create and validate posts, publish immediately or on a schedule, generate content with LLM-backed providers, and track publishing history across TikTok, Facebook, Instagram, YouTube, and X.

The architecture must keep platform-specific OAuth, validation, rate limits, upload protocols, and API behavior inside each platform crate. Shared application behavior consumes the `PlatformClient` abstraction and domain models rather than platform SDK details.

## Delivery model

Work is organized into dependency-aware phases. Phases in the same group may run in parallel when their prerequisites are complete. Each phase is independently testable and should leave the workspace compiling and usable.

- **Sequential:** Group A establishes the workspace and shared contracts.
- **Parallel:** Groups B and C can proceed independently after Group A; platform implementation tracks can proceed in parallel once their shared prerequisites are complete.
- **Integration:** Later groups combine the completed platform clients with persistence, scheduling, content generation, and the CLI.
- **Release safety:** Real publishing remains behind an explicit dry-run/publish boundary until validation, observability, and platform integration tests are in place.

## Target workspace

```text
Cargo.toml
rust-toolchain.toml
.env.example
crates/
  core/
  auth/
  platforms/
    tiktok/
    facebook/
    instagram/
    youtube/
    x/
  content/
  scheduler/
  data/

```

The root workspace owns shared dependency versions and lint configuration. Crates should expose narrow interfaces, avoid circular dependencies, and use feature flags for optional provider/platform behavior where appropriate.

## Group A — Foundation and contracts

### Phase A1 — Convert the repository into a workspace

- Replace the starter binary layout with a workspace root and `crates/app` binary crate.
- Add the Rust toolchain pin for stable 1.98.1.
- Establish workspace package metadata, shared dependency versions, resolver settings, formatting, linting, and test conventions.
- Add `.env.example` and ensure local secrets and token stores are ignored.
- Preserve a minimal `postly --help` executable while the remaining crates are introduced.
- Add CI-ready commands for formatting, linting, type checking/building, unit tests, and integration tests.

**Exit criteria:** `cargo fmt --check`, `cargo clippy --workspace --all-targets --all-features -- -D warnings`, `cargo check --workspace --all-targets`, and `cargo test --workspace` pass on a clean checkout.

### Phase A2 — Define core domain models and platform contract

Create `crates/core` with:

- `Platform` enum for TikTok, Facebook, Instagram, YouTube, and X.
- `Post`, `PostOverrides`, `MediaAsset`, media kind/MIME metadata, scheduling metadata, and `disclose_ai_generated`.
- Streaming-oriented media input abstractions so large videos are not loaded into memory unnecessarily.
- `PublishReceipt`, `AccountStatus`, capability metadata, and shared identifiers.
- `PlatformClient` async trait with authentication, publish, delete, and health-check operations.
- Structured platform-independent errors for authentication, validation, rate limits, transport failures, unsupported capabilities, and remote API errors.
- Validation rules that can run before any network call, including media size/type constraints supplied by platform capabilities.

Add serialization tests, validation tests, trait-object compilation tests, and compatibility tests for platform overrides.

**Exit criteria:** all shared types are documented by usage through tests/examples, are serializable where persistence requires it, and contain no platform-specific API client logic.

## Group B — Shared infrastructure

Group B1, B2, and B3 can run in parallel after A2, provided they depend only on `core` contracts.

### Phase B1 — Authentication and secure token storage

Create `crates/auth` with:

- OAuth 2.0 authorization-code flow primitives and PKCE support.
- Local callback/state handling suitable for a CLI login flow.
- Token expiry tracking and refresh-token handling.
- A provider-neutral token store interface with a secure OS keyring implementation and a test in-memory implementation.
- Secret-safe configuration loading using environment variables/configuration files without logging credentials.
- Provider-specific OAuth configuration models for Google, Meta, TikTok, and X without coupling the shared flow to any one platform.
- Clear errors for missing credentials, denied authorization, invalid state, expired refresh tokens, and unavailable secure storage.

Test PKCE/state validation, refresh behavior, persistence round trips, redacted diagnostics, and mocked authorization endpoints.

**Exit criteria:** an app-level authentication service can obtain, refresh, retrieve, and revoke credentials without exposing secrets or depending on platform publishing code.

### Phase B2 — HTTP, resilience, and observability foundation

Create shared infrastructure used by platform crates:

- `reqwest` with rustls and common JSON/error handling.
- Timeouts, request IDs, tracing spans, and redacted request diagnostics.
- Rate-limit metadata and retry classification.
- Exponential backoff with jitter for transient failures, while avoiding retries for authentication, validation, and non-idempotent operations unless explicitly safe.
- Governor-based client-side rate limiting where platform policies require it.
- Test helpers for mocked HTTP servers and deterministic retry behavior.

**Exit criteria:** platform crates can share reliable transport behavior and tests can verify retry, timeout, rate-limit, and error mapping without real API calls.

### Phase B3 — Persistence schema and repository boundaries

Create `crates/data` using SQLite and SQLx:

- Database initialization and migrations.
- Tables for connected accounts/tokens metadata, drafts, media metadata, scheduled posts, per-platform delivery attempts, publish receipts, and audit/history records.
- Repository traits and SQLite implementations for operations needed by the scheduler and CLI.
- Idempotency keys and unique constraints preventing duplicate delivery after retries.
- Migration tests and transactional state-transition tests.
- Token values remain in secure storage; the database stores references and non-secret metadata only.

**Exit criteria:** repositories can create drafts, enqueue jobs, claim due work safely, record attempts, and reconcile success/failure states.

## Group C — Initial platform clients

C1 and C2 can run in parallel after A2 and B1/B2. They should use mocked API tests and never require live credentials in CI.

### Phase C1 — X platform client

Create `crates/platforms/x` implementing `PlatformClient`:

- OAuth 2.0 PKCE account authentication.
- X API v2 text post creation and deletion.
- Media upload integration using the required X media upload API path, isolated behind a media-upload adapter.
- Capability reporting and validation for text, images, and supported video constraints.
- Mapping of X responses, rate limits, and API errors into shared types.
- Dry-run support at the client boundary so validation can execute without the final mutation call.
- Wiremock tests for OAuth, token refresh, post creation, deletion, rate-limit responses, malformed responses, and retries.

**Exit criteria:** a configured X client can authenticate, validate, publish supported posts, delete them, report account health, and provide deterministic mocked tests.

### Phase C2 — YouTube platform client

Create `crates/platforms/youtube` implementing `PlatformClient`:

- Google OAuth authorization and refresh-token integration.
- Channel/account health checks.
- Resumable video upload sessions with streaming media, chunking, progress, retry, and resumable recovery.
- Title, description, tags, privacy, scheduled publish metadata, and AI disclosure mapping where supported.
- Thumbnail upload as a separate optional operation if required by the domain model.
- Upload-session and remote-processing status handling.
- Capability reporting and validation for file size, MIME type, duration, metadata, and scheduling limitations.
- Wiremock tests for OAuth, resumable session negotiation, chunk responses, recovery after interruption, processing states, and API errors.

**Exit criteria:** large video uploads do not require whole-file buffering, interrupted uploads can resume, and publish receipts distinguish upload completion from remote processing completion.

## Group D — Application workflows and CLI

D1 and D2 can begin after B3; D3 requires at least one platform client.

### Phase D1 — Scheduler and queue

Create `crates/scheduler`:

- Queue model backed by `data` repositories.
- Immediate and scheduled job creation.
- Cron-style or interval-based polling with graceful shutdown.
- Claim leases, retry budgets, exponential backoff, and dead-letter/final-failure states.
- Per-platform delivery state so one platform failure does not incorrectly mark the whole post successful.
- Idempotent execution keyed by post/platform/version.
- Dry-run execution mode that performs validation and records what would happen without remote mutation.

Test due-job selection, concurrent workers, lease expiry, retries, cancellation, partial multi-platform success, and restart recovery.

**Exit criteria:** queued work is durable, safely claimed, observable, retryable, and idempotent.

### Phase D2 — Content generation service

Create `crates/content`:

- Provider-neutral LLM interface for text, image, and video generation requests.
- Initial provider adapter behind an optional feature/configuration boundary.
- Prompt/input models, output validation, generation metadata, and draft persistence integration.
- Platform-aware length, tone, hashtag, and media constraints through `PostOverrides` and capability data.
- Explicit AI-generated disclosure propagation into `Post`.
- No provider keys in logs or persisted drafts.
- Mock provider tests and deterministic validation tests.

**Exit criteria:** `generate --topic ... --save-draft` can create a validated draft without requiring publishing credentials.

### Phase D3 — CLI application

Expand `crates/app` with commands:

- `auth login <platform>` and account/status management.
- Draft creation and editing from text/media inputs.
- `generate --topic ... --save-draft`.
- `post` for immediate or scheduled queueing.
- `publish` with explicit `--dry-run` and a separate real-publish path.
- `status`, history, retry, and cancellation commands.
- Platform selection and per-platform overrides.
- Human-readable output plus a machine-readable JSON mode.
- Exit codes for validation, authentication, remote, and scheduling failures.

Wire clients through dependency injection/factories rather than allowing command handlers to construct platform-specific HTTP details directly.

**Exit criteria:** a user can authenticate, create or generate a draft, validate it, dry-run delivery, schedule it, inspect status, and publish to X or YouTube end to end with mocked services.

## Group E — Meta platform clients

E1 and E2 can run in parallel after the shared auth, core, transport, and data contracts are stable. Instagram depends on Meta authentication infrastructure but can be developed independently from Facebook client code.

### Phase E1 — Facebook client

Create `crates/platforms/facebook` implementing `PlatformClient`:

- Meta OAuth and long-lived token exchange/refresh handling.
- Page/account discovery and health checks.
- Text, link, image, and video publishing flows supported by the selected Graph API version.
- Upload/publish polling where asynchronous processing is required.
- Page permissions, capability validation, error mapping, rate-limit handling, and AI disclosure fields supported by the API.
- Mocked Graph API contract tests and opt-in live smoke tests.

**Exit criteria:** Facebook publishing works through the same queue/CLI workflow without leaking Graph API types outside the crate.

### Phase E2 — Instagram client

Create `crates/platforms/instagram` implementing `PlatformClient`:

- Meta account/page discovery and Instagram professional-account validation.
- Media container creation, processing polling, and publish steps.
- Image, carousel, reel/video, caption, hashtag, and scheduling capability validation.
- Media URL/accessibility requirements and clear preflight errors.
- Rate-limit and Graph API error mapping.
- Mocked multi-step publishing tests and opt-in live smoke tests.

**Exit criteria:** Instagram publishing is modeled as an explicit multi-step workflow and can be retried without duplicating a successfully created/published container.

## Group F — TikTok platform client

### Phase F1 — TikTok Content Posting API

Create `crates/platforms/tiktok` implementing `PlatformClient`:

- TikTok OAuth and required scope checks.
- Creator/account health and posting eligibility checks.
- Video posting with both `FILE_UPLOAD` chunked transfer and `PULL_FROM_URL` where supported.
- Upload initialization, chunk sizing, progress, retry, status polling, and resumable behavior.
- Caption, privacy, interaction, disclosure, and content-policy metadata mapping.
- Capability validation for file types, sizes, durations, and approval-dependent features.
- Clear errors for unapproved scopes or developer-app review limitations.
- Mocked API tests for both upload modes, polling, chunk recovery, and rejected scopes.

**Exit criteria:** TikTok’s approval-sensitive and chunked upload behavior is isolated and exposed through the same publish contract as the other platforms.

## Group G — Cross-platform integration and quality

### Phase G1 — Cross-platform orchestration

- Register platform clients through a factory/registry keyed by `Platform`.
- Implement fan-out publishing with independent per-platform results.
- Apply common post validation first, then platform-specific validation.
- Persist one delivery record per platform and preserve partial successes.
- Support platform-specific overrides without mutating the canonical draft.
- Add end-to-end tests covering X, YouTube, Facebook, Instagram, and TikTok through mocked clients.

### Phase G2 — Operations and observability

- Structured tracing for authentication, validation, queue transitions, uploads, retries, and remote IDs.
- Redaction tests for tokens, authorization codes, API keys, and sensitive URLs.
- Useful CLI diagnostics and JSON event output.
- Configuration validation at startup.
- Health/status checks for database, token storage, configured providers, and platform accounts.
- Document operational limits, required developer approvals, scopes, and environment variables in the repository’s user documentation.

### Phase G3 — Security and reliability hardening

- Threat-model OAuth callbacks, local token storage, media paths, and command-line inputs.
- Validate local media paths and avoid arbitrary unintended file access.
- Enforce upload size limits before opening or streaming files where possible.
- Verify secure token storage availability and fail safely when unavailable.
- Test cancellation and process restart during uploads and scheduled jobs.
- Run dependency audits, formatting, clippy, tests, and platform contract tests in CI.
- Keep live publishing disabled by default in development and CI.

**Exit criteria:** the complete workspace has reproducible builds, no secret leakage in tested logs, durable queue recovery, platform-isolated failures, and documented release checks.

## Parallel execution map

```text
A1 -> A2
A2 -> B1, B2, B3
A2 + B1 + B2 -> C1, C2
B3 -> D1, D2
C1 or C2 + D1 + D2 -> D3
B1 + B2 + A2 -> E1, E2
A2 + B1 + B2 -> F1
C1 + C2 + D3 + E1 + E2 + F1 -> G1
G1 -> G2 -> G3
```

Recommended parallel workstreams after Group A:

- **Infrastructure:** B1, B2, B3
- **Initial platforms:** C1, C2
- **Application:** D1, D2
- **Meta:** E1, E2
- **TikTok:** F1

Platform work may start with mocked contracts before the corresponding developer-app approvals are available. Live smoke tests should remain opt-in and use dedicated test accounts.

## Definition of done

The roadmap is complete when:

1. The repository is a Cargo workspace pinned to Rust 1.98.1 with all crates compiling under the same quality gates.
2. Core models and `PlatformClient` provide a stable boundary for all five platforms.
3. OAuth credentials are acquired, refreshed, and stored securely without token values in SQLite or logs.
4. X, YouTube, Facebook, Instagram, and TikTok clients pass mocked contract and failure-path tests.
5. Large media is streamed or chunked and supports retry/recovery appropriate to each platform.
6. Drafts, scheduled posts, delivery attempts, receipts, retries, and partial successes are durable and idempotent.
7. CLI workflows cover authentication, generation, drafting, dry-run validation, scheduling, publishing, status, history, retry, and cancellation.
8. AI disclosure is preserved from generated content through every applicable platform publish request.
9. Real mutation calls require an explicit publish path; dry-run is safe and useful throughout development.
10. CI verifies formatting, linting, type checking, tests, dependency/security checks, and secret-redaction behavior.
