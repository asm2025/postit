# Social Publishing Platform Roadmap

> Revision 2 (2026-09-25). **Superseded** by [03. social publishing roadmap, revision 3](03.%20social%20publishing%20roadmap%2C%20revision%203.md). Kept for history. Changes from revision 1 are summarized in [Revision notes](#revision-notes) at the end.

## Objective

Build `postly` as a Rust 1.98.1 stable Cargo workspace that lets users authenticate social accounts, create and validate posts, publish immediately or on a schedule, generate content with any OpenAI-compatible or Anthropic LLM provider, and track publishing history.

The initial platforms are TikTok, Facebook, Instagram, YouTube, and X. They are **compile-time plugins** to a platform-agnostic core engine: each platform is its own crate implementing the `PlatformPlugin` contract, and new platforms (Threads, LinkedIn, Bluesky, Mastodon, …) can be added later without changing the core, the scheduler, the data schema, or the CLI.

Platform-specific OAuth details, validation, rate limits, upload protocols, and API types stay inside each platform crate. Shared behavior consumes only the plugin contract and core domain models.

## Engineering standards

These apply to every phase and are part of every phase's exit criteria.

### DRY and ownership

- **One owner per concern.** Each cross-cutting concern has exactly one implementation that everything else reuses:
  - HTTP transport, retry, and redaction: `postly-http`.
  - OAuth flows: `postly-auth`.
  - Shared plugin machinery (chunked uploads, status polling, error classification, OAuth wiring, and the conformance test suite): `postly-platform-kit`.
  - Meta Graph API client: `postly-platform-meta`.
  - Configuration loading and secret resolution: `postly-config`.
- **Platforms declare, the engine executes.** Validation runs in one core engine. The engine reads plugin-supplied capability data: limits, media rules, and a text-measure function (for example, X's weighted character count). No validation logic is duplicated per command or per platform.
- **One conformance suite.** Every plugin must pass the same generic test suite from `postly-platform-kit` (feature `testkit`). The suite covers the dry-run contract, error mapping, idempotency, cancellation, and redaction. Platform crates add only protocol-specific tests.
- **Shared wiremock fixtures.** Plugins get helpers for mocked OAuth, token refresh, rate-limit responses, and malformed payloads from the testkit instead of each writing their own.
- **Workspace-level dependencies.** Every dependency version is declared once in `[workspace.dependencies]`. Crates reference it with `dep.workspace = true`, and each crate enables only the features it needs.

### Rust best practices

- `[workspace.lints]` inherited by all crates:
  - `unsafe_code = "forbid"`.
  - `clippy::all` and `clippy::pedantic` at warn. Allowances must be justified in `Cargo.toml` comments.
  - `clippy::unwrap_used`, `clippy::expect_used`, and `clippy::panic` denied outside tests.
  - `missing_docs` warn on library crates.
- **Errors.** Library crates use `thiserror` enums. Only `crates/app` uses `anyhow` for top-level reporting. Errors carry structured context and must never include secret values.
- **Secrets are typed.** Tokens, auth codes, API keys, and client secrets use `secrecy::SecretString` (or a newtype over it), so `Debug`/`Display` redact by construction. Log redaction is a backstop, not the primary control.
- **Newtypes** for identifiers: `PlatformId`, `AccountId`, `PostId`, `DeliveryId`, `RemotePostId`, `ProviderId`, `ModelId`. Internal IDs use UUID v7 (time-ordered).
- **Deterministic tests.** Injected `Clock` and `IdGenerator` traits, a seeded jitter RNG, and no real network in non-ignored tests.
- **Async trait objects.** `PlatformClient`, `PlatformPlugin`, `LlmProvider`, and `TokenStore` are used as `dyn` objects. Phase A2 adds a trait-object compile test and picks a single approach: native dyn-compatible async traits if the pinned toolchain supports them, otherwise `async-trait`.
- **Tracing.** Use `tracing` and `tracing-subscriber` everywhere, not `log`/`log4rs`. Use `#[instrument(skip(...))]` on any function that receives a secret.
- **Dependency hygiene.**
  - `dotenv` is replaced by `dotenvy`, since `dotenv` is unmaintained.
  - reqwest uses rustls, streaming, JSON, and multipart. The `blocking`, `cookies`, and `socks` features are dropped unless a phase proves it needs them.
  - `cargo-deny` covers licenses, advisories, and duplicate crates.

### Reuse of essentialMix-rs (`emix*` crates)

Use crates from crates.io with a loose `"0"` spec (for example `emixdb = "0"`), declared once in `[workspace.dependencies]`, with `default-features = false` wherever a crate enables heavy defaults. `Cargo.lock` keeps builds reproducible. `cargo update` picks up new `0.x` releases without editing manifests. Because a `0.x` minor bump is semver-breaking by Cargo convention, run the full quality gates after each update.

| Crate | Use in postly | Where |
|---|---|---|
| `emixdb` | `Pagination` and `ResultSet<T>` for history, status, and draft listings | `data`, `app` |
| `emixcrypto` (`default-features = false`) | `Sha256Hash` for media content hashes and idempotency-key derivation | `core`, `data` |
| `emix` (`terminal` feature) | Interactive prompts: publish confirmation (`confirm`) and API-key entry (`get_password`) | `app` |
| `emixthreading` | `Spinner` for status polling and processing waits (upload progress bars use `indicatif` directly) | `app` |
| `emixcore` | Only as a conversion source: `impl From<emixcore::Error>` in the crates that call emix APIs | where used |

Evaluated and **not** used, each with a reason and a suggested upstream fix:

- `emixai`:
  - It is built on kalosm and pulls in heavy local-inference dependencies.
  - The OpenAI source is a hard-coded model enum with an unfinished `ModelSource` implementation.
  - It has no custom base-URL or OpenAI-compatible provider support.
  - Postly's `LlmProvider` layer could later be upstreamed into `emixai`.
- `emixnet`:
  - `build_client*` sets `pool_max_idle_per_host(0)`, which disables connection reuse.
  - It forces a JSON `Content-Type` default header, which breaks multipart and binary uploads.
  - It enables a cookie store, which API clients should not use.
  - Worth fixing upstream with an options struct. Postly builds clients in `postly-http`.
- `emixlog`: it is log4rs/slog-based, and postly standardizes on `tracing`.
- `emixseaorm` and `emixdiesel`: postly uses SQLx (see B3).
- `emixcollections`: no current need.
- `emix::datetime::parse_date_any`: not used for schedule input, because it interprets input as UTC and ignores the local time zone. Schedule parsing is time-zone-aware (see D3).

## Delivery model

Work is organized into dependency-aware phases. Phases in the same group may run in parallel once their prerequisites are complete. Each phase is independently testable and leaves the workspace compiling and usable.

- **Sequential:** Group A establishes the workspace, the plugin contract, and configuration.
- **Parallel:** Group B infrastructure runs in parallel after Group A. Platform tracks (C, E, F) run in parallel once the platform kit (B4) exists.
- **Mock-first:** a `mock` platform plugin (B4) lets the scheduler, CLI, and orchestration be built and tested before any real platform is complete.
- **Release safety:** real publishing stays behind an explicit publish path. Dry-run works everywhere. Live publishing is disabled by default in dev and CI.

```text

deny.toml
.env.example
crates/
  core/                     # postly-core: domain models, plugin contract, registry, validation engine
  config/                   # postly-config: config file + env overlay + secret references
  http/                     # postly-http: shared transport, retry, rate limiting, redaction
  auth/                     # postly-auth: OAuth 2.0 + PKCE flows, token stores, refresh coordination
  data/                     # postly-data: SQLite/SQLx repositories and migrations
  platform-kit/             # postly-platform-kit: shared plugin helpers + `testkit` conformance suite
  platforms/
    mock/                   # postly-platform-mock: reference plugin used by tests and as a template
    x/
    youtube/
    meta/                   # postly-platform-meta: shared Graph API client + Meta OAuth (library, not a plugin)
    facebook/
    instagram/
    tiktok/
  content/                  # postly-content: provider-neutral LLM layer
  scheduler/                # postly-scheduler: durable queue and worker
  app/                      # postly (binary): CLI, composition root, plugin registration
```

Package names use the `postly-` prefix. Dependency direction is strictly downward: `core` depends on nothing internal, platform crates never depend on each other except `facebook`/`instagram` → `meta`, and only `app` depends on every platform.

## Group A — Foundation and contracts

### Phase A1 — Convert the repository into a workspace

- Replace the starter layout with the workspace root and a `crates/app` binary crate (binary name `postly`).
- Add `rust-toolchain.toml` pinned to 1.98.1 with the `rustfmt` and `clippy` components.
- Move shared metadata and dependency versions into `[workspace.package]` and `[workspace.dependencies]`, and add `[workspace.lints]`. Keep the existing `release`, `dist`, and `dev.package."*"` profiles.
- Clean up dependencies: `dotenv` becomes `dotenvy`, `log` becomes `tracing`, and unused reqwest features are removed.
- Add `.env.example`. Ignore `.env`, local databases, and any file-based token store.
- Keep a minimal `postly --help` (clap derive) working.
- Add CI (GitHub Actions) covering fmt, clippy, check, test, and `cargo deny check`, on Linux and Windows.

**Exit criteria:** `cargo fmt --check`, `cargo clippy --workspace --all-targets --all-features -- -D warnings`, `cargo check --workspace --all-targets`, and `cargo test --workspace` pass on a clean checkout. CI is green.

### Phase A2 — Core domain models and the plugin contract

Create `crates/core` with:

- **Open platform identity.**
  - `PlatformId` is a validated lowercase string newtype such as `"x"` or `"youtube"`. There is no closed enum, so adding a platform never touches core, persisted data, or CLI parsing.
  - `PlatformDescriptor` holds the ID, display name, `Capabilities`, an optional `OAuthProviderSpec`, and the plugin config schema version.
- **Accounts.** `AccountRef { platform: PlatformId, account: AccountId }` supports multiple accounts per platform, such as several Facebook Pages or YouTube channels. Publish targets are `AccountRef`s, not platforms.
- **Post models.**
  - `Post` fields: text, media list, link, tags, `disclose_ai_generated`, and schedule.
  - `PostOverrides` is a per-`AccountRef` patch. It never mutates the canonical post; the engine produces a resolved view per target.
  - `PostVersion` is a monotonically increasing version, bumped on every edit and used in idempotency keys.
- **Media.**
  - `MediaAsset` has kind, MIME type, byte size, optional duration and dimensions, content hash, and a `MediaSource`.
  - `MediaSource` is one of: a local file path, streamed on demand and never fully buffered; a public URL; or an already uploaded remote reference.
  - The `MediaProbe` trait reads duration and dimensions without decoding. The default implementation uses pure-Rust container parsing; an optional `ffprobe` implementation is behind a feature.
  - The `MediaHost` trait turns a local asset into a public URL for platforms that require one (Instagram containers, TikTok `PULL_FROM_URL`). v1 ships only the "user supplies URL" host (see A2 decisions).
- **Contracts.**
  - `PlatformPlugin` provides `descriptor()`, `config_schema()`, and `create_client(ctx) -> Box<dyn PlatformClient>`. The context carries the resolved plugin config, an HTTP handle, a token accessor, and the clock.
  - `PlatformClient` provides:
    - `account_info` / health.
    - `validate(resolved_post)`: platform-specific checks that the engine cannot express declaratively.
    - `publish(resolved_post, mode)`, where the mode is `DryRun` or `Live`.
    - `status(receipt)`: remote processing state.
    - `delete(receipt)`.
    - `reconcile(delivery)`: find a remote post created by an attempt whose outcome is unknown. It returns `Unsupported` where the platform cannot look posts up.
  - `PluginRegistry` maps `PlatformId` to `Arc<dyn PlatformPlugin>` and rejects duplicate IDs. It is built explicitly by the composition root, with no link-time magic such as `inventory`.
- **Receipts and statuses.**
  - `PublishReceipt` separates `Submitted`, `Processing`, and `Published`, and records the remote ID and URL.
  - `AccountStatus`.
  - `DeliveryState`, the state machine shared with the scheduler: `Pending → Claimed → InFlight → {Processing → Published | Failed(retryable) | OutcomeUnknown | DeadLetter | Cancelled}`.
- **Validation engine.** Common rules run first: required fields, media existence, and size checks before opening files. Capability-driven rules run next: length via the plugin's `TextMeasure`, media count, MIME type, size, duration, aspect ratio, and scheduling window. Platform `validate` runs last. The engine returns all violations, not just the first.
- **Structured errors.** `PostlyError` / `PlatformError` cover authentication, authorization/scope, validation (with a list of violations), rate limit (with retry-after), quota, transport, unsupported capability, remote API error, and outcome unknown. Each carries a retry classification.
- **Test seams.** `Clock` and `IdGenerator` traits.

Tests: serialization round trips, validation matrices, override resolution, registry duplicate rejection, and a trait-object compile test.

**Exit criteria:** all shared types are documented and exercised through tests or examples. Types are serializable where persistence requires it. Core has no platform-specific or HTTP-client code.

**A2 decisions made:**

- The v1 `MediaHost` is "user-supplied public URL" only. Preflight fails clearly when a platform needs a URL and none is given. An S3-compatible host is listed under future work.
- Plugins are compile-time only. External or out-of-process plugins are a non-goal for v1, but nothing in the contract prevents adding them later.

### Phase A3 — Configuration and secret references

Create `crates/config`:

- Config file `postly.toml` in the platform config directory (via `directories`), overridable with `--config` and `POSTLY_*` env vars, with `.env` loaded through `dotenvy` in development only.
- Top-level sections: `[database]`, `[scheduler]`, `[http]`, `[platforms.<id>]`, and `[ai]`.
- **Platform sections are opaque to core.** Each `[platforms.<id>]` table is deserialized by the owning plugin into its own typed config: client ID, redirect port, API version, and so on. Unknown platform tables are reported, not silently ignored.
- **Secret references**, following opencode's substitution syntax:
  - `{env:VAR}` reads an environment variable.
  - `{file:path}` reads a file, subject to the path policy in G3.
  - `{keyring:name}` reads from the OS keyring via `postly-auth`.
  - Resolved values are `SecretString` and are never written back or logged.
- `postly config validate` and `postly config show --redacted`.

**Exit criteria:** config loads from file, env, and defaults with documented precedence. Invalid or unknown keys produce actionable errors. Secret values never appear in `Debug`, errors, or logs, and a test proves this.

## Group B — Shared infrastructure

B1, B2, and B3 run in parallel after Group A. B4 needs B1 and B2.

### Phase B1 — Authentication and secure token storage

Create `crates/auth`:

- OAuth 2.0 authorization-code flow with PKCE, driven by the plugin-provided `OAuthProviderSpec`: endpoints, scopes, PKCE support, client-auth method, extra parameters, and token-response quirks. **No provider-specific configuration lives in this crate.** Google, Meta, TikTok, and X specs live in their plugin crates.
- **Callback strategies** (a plugin declares which ones it supports):
  - A loopback HTTP listener on `127.0.0.1` with a random or fixed port and state validation.
  - Manual code paste for providers that forbid loopback redirects.
  - A hook for plugin-specific flows, such as Meta's long-lived token exchange.
- Token expiry tracking and refresh. **Refreshes are serialized per account** with a keyed async mutex, and rotated refresh tokens are persisted atomically. X rotates refresh tokens, so concurrent refreshes would otherwise invalidate the account.
- A `TokenStore` trait with three implementations:
  - The OS keyring (`keyring` crate).
  - An in-memory store for tests.
  - An opt-in encrypted file store for headless or WSL hosts with no Secret Service. It uses authenticated encryption: `age` or ChaCha20-Poly1305 with an Argon2-derived key, not unauthenticated AES-CBC.
- Keyring entries are namespaced as `postly/<platform>/<account>` and `postly/ai/<provider>`. The database stores only these references.
- Revocation where the provider supports it; otherwise local deletion.
- Clear errors for missing credentials, denied authorization, invalid state, expired or revoked refresh tokens, and an unavailable secure store.

Tests: PKCE and state validation, refresh behavior, concurrent-refresh serialization, persistence round trips, redacted diagnostics, and mocked authorization endpoints.

**Exit criteria:** an auth service can obtain, refresh, retrieve, and revoke credentials for any plugin-provided spec without depending on platform code or exposing secrets.

### Phase B2 — HTTP, resilience, and observability foundation

Create `crates/http`:

- A single `reqwest` client factory with rustls, connection pooling, per-request and connect timeouts, user agent, and gzip. It has no global `Content-Type` and no cookie store.
- Request IDs, tracing spans, and redacted request/response diagnostics. Authorization headers, token-bearing query parameters, and configured sensitive URL patterns are redacted.
- Retry classification:
  - Transient errors are retried.
  - Rate-limited responses honor `Retry-After` and the platform reset headers supplied by the plugin.
  - Non-idempotent mutations are never retried after the request body may have been received. They surface as `OutcomeUnknown` instead.
- Exponential backoff with full jitter (seeded in tests), and a retry budget.
- `governor` rate limiters keyed by plugin-defined buckets (per app, per account, per endpoint).
- Streaming request bodies from `MediaSource` for uploads.
- Test helpers: a wiremock server builder and deterministic time/jitter.

**Exit criteria:** retry, timeout, rate-limit, redaction, and error mapping are verified without real API calls. No other crate constructs a `reqwest::Client`.

### Phase B3 — Persistence schema and repository boundaries

Create `crates/data` with SQLite and SQLx:

- WAL mode, a busy timeout, and embedded migrations (`sqlx::migrate!`). Use compile-checked queries with an offline `.sqlx` cache committed so CI needs no database, and a `cargo sqlx prepare --check` step in CI.
- Tables:
  - `accounts`: platform ID, account ID, display name, token-store reference, scopes, status.
  - `drafts` / `posts`, including version.
  - `post_overrides`.
  - `media_assets`: path or URL, hash, probed metadata.
  - `jobs`: schedule and state.
  - `deliveries`: one per target per job, with state, lease, attempt count, and next attempt time.
  - `delivery_attempts`.
  - `receipts`.
  - `audit_events`.
  - `ai_generations`: provider, model, prompt hash, and token usage. No keys.
- Platform IDs are stored as text. Adding a platform never requires a migration.
- Idempotency keys are derived as `hash(post_id, post_version, account_ref)` with `emixcrypto` SHA-256. A unique constraint on the key prevents duplicate deliveries.
- Atomic claim-with-lease queries (`UPDATE … RETURNING`) and lease expiry and recovery.
- Listing APIs return `emixdb::ResultSet<T>` with `emixdb::Pagination`.
- Token values never touch the database. A test asserts that no column contains values from the test token store.

**Exit criteria:** repositories can create drafts, enqueue jobs, claim due work safely under concurrency, record attempts, and reconcile success, failure, and unknown-outcome states. Migrations are tested from empty and from each prior version.

### Phase B4 — Platform kit and mock plugin

Create `crates/platform-kit`, the shared machinery for all plugins:

- An `OAuthProviderSpec` builder and wiring into `postly-auth`.
- A generic resumable/chunked upload driver. It takes chunk size, a resume-offset query, and a progress callback, and is reused by YouTube, TikTok, X, and Meta.
- A generic `poll_until` helper for remote processing status, with backoff and cancellation.
- Error-classification helpers that map HTTP status and platform error codes to `PlatformError`.
- Capability-declaration helpers and common `TextMeasure` implementations (grapheme count and X-weighted count).
- `testkit` feature: the **plugin conformance suite**, a generic `run_conformance::<P: PlatformPlugin>(fixture)` that every plugin calls, plus shared wiremock fixtures.

Create `crates/platforms/mock`, the reference plugin. It is fully featured, configurable to fail in scripted ways, used by the scheduler, CLI, and end-to-end tests, and documented as the template for new platforms.

**Exit criteria:** the mock plugin passes the conformance suite. A new plugin needs only its protocol code, its capability declaration, and one `registry.register(...)` line in `app`.

## Group C — Initial platform clients

C1 and C2 run in parallel after B4. All tests use mocks; CI never needs live credentials.

### Phase C1 — X plugin

Create `crates/platforms/x`:

- OAuth 2.0 PKCE with scopes `tweet.read`, `tweet.write`, `users.read`, `offline.access`, and `media.write`. Refresh-token rotation is handled via B1.
- X API v2 post creation and deletion.
- Media upload through the v2 media upload endpoints (chunked INIT/APPEND/FINALIZE/STATUS) using the kit's chunked driver.
- Capabilities: X-weighted text length (URLs count as a fixed length), image, GIF, and video limits, and media count.
- Mapping of X errors, rate-limit headers, and access-tier errors (for example, an app tier without write access) to clear `PlatformError`s.
- Dry-run executes everything except the final create/upload calls.
- Conformance suite plus X-specific wiremock tests.

**Exit criteria:** a configured X client can authenticate, validate, publish supported posts, delete them, and report account health, all with deterministic mocked tests.

### Phase C2 — YouTube plugin

Create `crates/platforms/youtube`:

- Google OAuth spec: offline access and consent prompt for a refresh token, and the `youtube.upload` and `youtube.readonly` scopes.
- Channel discovery. Each channel is an `AccountRef`.
- Resumable upload through the kit driver: streaming, chunk alignment, resuming after interruption by querying the offset, and progress.
- Mapping of title, description, tags, category, privacy, `publishAt` native scheduling, made-for-kids, and the altered/synthetic content disclosure.
- Optional thumbnail upload. Processing status is polled via `status`.
- **Quota awareness.** Per-call quota cost is declared, and daily usage is tracked in `data`. A publish is refused preflight if the remaining quota is insufficient.
- Capabilities: file size, MIME type, duration, metadata lengths, and scheduling window.

**Exit criteria:** large uploads never buffer the whole file, interrupted uploads resume, and receipts distinguish upload completion from processing completion.

## Group D — Application workflows and CLI

D1 and D2 start after B3 and B4 (using the mock plugin). D3 starts after D1.

### Phase D1 — Scheduler and queue

Create `crates/scheduler`:

- Jobs expand into one delivery per `AccountRef`. Each delivery has independent state, so partial success is preserved.
- **Run model:**
  - `postly worker` is a long-running worker with graceful shutdown on Ctrl-C or SIGTERM.
  - `postly worker --once` is intended for OS schedulers (cron, systemd timers, Windows Task Scheduler).
  - G2 documents the OS-service setup.
- **Native scheduling (opt-in).** When a plugin declares `supports_native_schedule`, for example YouTube `publishAt` or Facebook scheduled posts, the user can choose `--native-schedule`. The upload then happens immediately with a remote publish time, and no local worker is needed at the scheduled time.
- Lease-based claiming, lease expiry recovery, and retry budgets with backoff from `postly-http`, ending in dead-letter.
- **Unknown-outcome handling.** A delivery in `OutcomeUnknown` is never blindly retried. The scheduler calls `reconcile()`. If the platform cannot reconcile, the delivery is parked for the user to resolve with `postly retry --force` or `postly resolve`.
- Idempotent execution keyed by post, version, and account.
- Cancellation of pending deliveries. For in-flight deliveries, cancellation takes effect at the next safe checkpoint.
- A dry-run mode that validates and records the planned actions without remote mutation.

Tests: due-job selection, concurrent workers, lease expiry, retries, cancellation, partial multi-account success, restart recovery, and unknown-outcome reconciliation.

**Exit criteria:** queued work is durable, safely claimed, observable, retryable, and idempotent, and a crash after a remote success cannot cause a duplicate post.

### Phase D2 — Content generation (LLM layer)

Create `crates/content` (behind the `ai` feature in `app`, enabled by default):

- **Provider-neutral trait.** `LlmProvider` provides `chat(request) -> response` and an optional `chat_stream`. Messages, system prompt, temperature, max tokens, JSON-schema structured output where supported, and token usage are all modeled provider-neutrally. `ImageProvider` is a separate optional trait.
- **Two wire-protocol adapters**, both built on `postly-http` so redaction, retry, and tracing are shared:
  - `openai-compatible`: the Chat Completions API with configurable base URL, headers, and query parameters. This one adapter serves:
    - OpenAI.
    - Abacus AI RouteLLM (`https://routellm.abacus.ai/v1`).
    - Google Gemini through its OpenAI endpoint (`https://generativelanguage.googleapis.com/v1beta/openai/`).
    - OpenRouter, Groq, DeepSeek, Mistral, xAI, Together, Ollama, LM Studio, vLLM, and any other compatible server.
    - It tolerates provider extensions such as extra fields and missing `usage`.
  - `anthropic`: the native Messages API (`x-api-key`, `anthropic-version`, system as a top-level field, content blocks). It is native because Anthropic's OpenAI-compatible endpoint is limited.
- **opencode-shaped provider configuration.** The `[ai.provider.<id>]` tables mirror opencode's `provider` block, so entries can be copied field for field:

  ```toml
  [ai]
  model = "abacus/gpt-5"            # "<provider>/<model>", as in opencode

  [ai.provider.abacus]
  npm = "@ai-sdk/openai-compatible" # opencode package name, mapped to a protocol
  name = "Abacus AI"
  options = { baseURL = "https://routellm.abacus.ai/v1", apiKey = "{keyring:abacus}" }
  models = { "gpt-5" = {}, "claude-sonnet-4" = {} }

  [ai.provider.anthropic]
  protocol = "anthropic"            # explicit alternative to `npm`
  options = { apiKey = "{env:ANTHROPIC_API_KEY}" }
  ```

  - `npm` values are mapped to protocols:
    - `@ai-sdk/openai-compatible` and `@ai-sdk/openai` map to `openai-compatible`.
    - `@ai-sdk/anthropic` maps to `anthropic`.
    - `@ai-sdk/google` maps to `openai-compatible` with the Gemini base URL.
    - An explicit `protocol` key overrides the mapping.
  - Built-in presets for `openai`, `anthropic`, `gemini`, `abacus`, `openrouter`, and `ollama` mean users only supply a key. Preset base URLs are verified at phase start.
  - postly never reads opencode's files or its `auth.json`.
- `postly ai login <provider>` stores the key in the keyring. `postly ai models <provider>` lists models via `/models` where the provider supports it.
- **Generation pipeline.** A prompt template is combined with platform capability data: length, hashtag conventions, and media constraints per target `AccountRef`. The pipeline then parses structured output, runs the core validation engine, and makes one repair attempt if validation fails. The result is a draft with `disclose_ai_generated = true` and a generation record.
- No provider keys appear in logs, drafts, or generation records. Prompts are stored only if `ai.store_prompts = true`.
- Tests: wiremock contract tests for both protocols (including Gemini-style and Abacus-style responses), a mock provider, and deterministic validation and repair tests.

**Exit criteria:** the library can produce a validated, disclosure-flagged draft for any configured provider without publishing credentials. The CLI command is delivered in D3.

**Deferred:** video generation. `ImageProvider` covers OpenAI-compatible `/images/generations`. A `VideoProvider` trait is reserved but not implemented in v1.

### Phase D3 — CLI application

Expand `crates/app` (clap derive; also serves as the composition root):

- `auth login|logout|list <platform> [--account]` and `accounts` management.
- `draft new|edit|show|list|delete` from text and media inputs, with per-target overrides.
- `generate --topic … [--targets …] [--model provider/model] --save-draft`.
- `post <draft> --targets … [--at <time>] [--native-schedule]`, where `--at` accepts RFC 3339, local times with an IANA zone (`chrono-tz`), or relative forms such as `+2h`. Times are stored in UTC and displayed in local time, and schedules crossing a DST transition are validated.
- `publish <draft> --dry-run` and `publish <draft> --live`. The live path asks for interactive confirmation unless `--yes` is given, and is refused when `POSTLY_LIVE_PUBLISH` is not enabled.
- `status`, `history` (paginated), `retry`, `resolve`, `cancel`, `worker`, `config`, `ai`, and `completions <shell>`.
- Human-readable output, `--json` for machine-readable output, and `--json-events` for streaming progress.
- Documented exit codes for validation, authentication, remote, scheduling, config, and internal failures.
- `PluginRegistry` is built in one place, with each plugin behind a Cargo feature (`x`, `youtube`, `facebook`, `instagram`, `tiktok`, `mock-platform`), all enabled by default except `mock-platform`.

**Exit criteria:** with the mock plugin and wiremock, a user can authenticate, create or generate a draft, validate it, dry-run delivery, schedule it, inspect status, and publish end to end. The same flow works for X and YouTube against mocked APIs.

## Group E — Meta platforms

E0 comes first. E1 and E2 then run in parallel.

### Phase E0 — Meta shared library

Create `crates/platforms/meta`, a library and not a plugin:

- Meta OAuth spec, short-to-long-lived token exchange, and Page token derivation.
- A Graph API client with a pinned, configurable API version, error-code mapping, and parsing of the app and business usage headers for rate limiting.
- Page and Instagram professional-account discovery.

### Phase E1 — Facebook plugin

- Each Page is an `AccountRef`.
- Text, link, photo, and video posts. Videos use resumable upload through the kit driver.
- Native scheduled posts via the scheduled publish time. Processing is polled.
- Permission and capability validation, and AI disclosure where the API supports it.
- Conformance suite, mocked Graph contract tests, and opt-in live smoke tests.

**Exit criteria:** Facebook publishing works through the same queue and CLI without leaking Graph types.

### Phase E2 — Instagram plugin

- Professional-account validation.
- An explicit container workflow: create container, poll status, publish. Container IDs are persisted so a retry resumes rather than duplicating.
- Image, carousel, and reel posts, with caption, hashtag, and mention limits.
- Media must be reachable by URL. Preflight uses `MediaHost` and fails clearly without a public URL. Direct resumable upload for reels is used if the pinned Graph version supports it; this is verified at phase start.
- Rate limits: the per-account 24-hour publishing limit is checked preflight.

**Exit criteria:** Instagram publishing is an explicit multi-step workflow that can be retried without duplicating a created or published container.

## Group F — TikTok

### Phase F1 — TikTok Content Posting API plugin

- TikTok OAuth spec, with checks for the required scopes (`video.publish` / `video.upload`).
- Creator info query, which returns allowed privacy levels, interaction toggles, and maximum duration, and is required before posting.
- `FILE_UPLOAD` chunked transfer through the kit driver. `PULL_FROM_URL` requires a verified domain and uses `MediaHost`.
- Status polling, and mapping of caption, privacy, interaction, commercial-content, and AI-generated disclosure fields.
- Clear errors for unaudited apps (posts restricted to private visibility) and missing scopes.
- Conformance suite, plus mocked tests for both upload modes, polling, chunk recovery, and rejected scopes.

**Exit criteria:** TikTok's approval-sensitive and chunked behavior is isolated behind the standard contract.

## Group G — Integration and quality

### Phase G1 — Cross-platform orchestration

- Fan-out publishing across mixed targets with independent per-target results. Common validation runs first, then capability rules, then plugin validation, and all violations are reported together.
- Overrides are resolved per target without mutating the canonical draft.
- End-to-end tests covering all five platforms and the mock plugin through wiremock, including partial success and one platform failing while the others succeed.
- **Extensibility proof.** A test-only second mock plugin is registered from the `tests/` crate without modifying core, data, scheduler, or CLI code.

### Phase G2 — Operations and observability

- Structured tracing for authentication, validation, queue transitions, uploads, retries, reconciliation, and remote IDs.
- Redaction tests for tokens, auth codes, API keys, and sensitive URLs, run across every crate's error and log paths.
- `postly doctor`: health checks for the database, token store, config, AI providers, platform accounts, scopes, and quota.
- User documentation:
  - Per-platform developer app setup, required approvals, scopes, redirect URIs, and known limits.
  - Environment variables.
  - Worker and OS-service setup.
  - A **plugin authoring guide** based on the mock plugin.

### Phase G3 — Security and reliability hardening

- Threat-model OAuth callbacks (bind to loopback only, state and PKCE, single-use listener), token storage, media paths, `{file:}` references, and CLI input.
- A media path policy: canonicalize paths, reject device files, check size limits before opening, and allow optional root directories. Never follow symlinks outside allowed roots.
- Verify secure-store availability and fail safely. The encrypted-file fallback is opt-in only.
- Test cancellation and process restarts during uploads, container workflows, and scheduled jobs.
- CI: `cargo deny`, fmt, clippy, tests, the conformance suites, and the `sqlx prepare --check` step. Live publishing stays disabled in development and CI.

**Exit criteria:** reproducible builds, no secret leakage in any tested output, durable queue recovery, platform-isolated failures, and documented release checks.

## Platform constraints and risks

Verify each of these at the start of the relevant phase, since platform policies change:

- **X:** write access and cost depend on the API access tier. Refresh tokens rotate. Media upload endpoints have moved from v1.1 to v2.
- **YouTube:** uploads from an unverified API project are locked to private until the project passes an audit. The daily quota is small, and uploads are expensive against it.
- **TikTok:** unaudited apps can only post with private visibility. `PULL_FROM_URL` needs domain verification. Redirect URI rules for desktop and loopback use must be confirmed. The manual code-paste strategy is the fallback.
- **Meta:** App Review is required for publishing permissions beyond test users. Instagram requires a professional account linked to a Page, and publishing is rate-limited per 24 hours. Most media must be at a public URL.
- **Anthropic via OpenAI-compatible endpoint:** feature-limited, which is why a native adapter exists.
- **Local-only scheduling:** requires the worker to run at the scheduled time. Native scheduling mitigates this where supported.

## Non-goals for v1

Out-of-process or dynamic-library plugins; threads, replies, and comments; analytics and insights; DMs; editing already-published posts; a GUI or web server; multi-user or server deployment; video generation; S3-compatible media hosting. The contracts leave room for each of these.

## Definition of done

1. The Cargo workspace is pinned to Rust 1.98.1, and all crates pass the same quality gates, lints, and `cargo deny`.
2. The core plugin contract is stable, and all five platforms plus the mock are compile-time plugins that pass the shared conformance suite.
3. Adding a platform requires only a new crate, a Cargo feature, and one registration line. G1's extensibility test proves this.
4. OAuth credentials are acquired, refreshed (serialized per account), and stored securely. No token values appear in SQLite, logs, or errors.
5. Large media is streamed or chunked, with platform-appropriate resume and recovery.
6. Drafts, schedules, deliveries, attempts, receipts, and partial successes are durable and idempotent. Unknown outcomes are reconciled, not duplicated.
7. The CLI covers auth, accounts, generation, drafting, dry-run, scheduling (local and native), publishing, status, history, retry, resolve, cancel, worker, doctor, and config.
8. Content generation works with any OpenAI-compatible provider and with native Anthropic, configured in opencode's provider schema. AI disclosure is preserved through every applicable publish request.
9. Real mutations require the explicit live path. Dry-run is safe everywhere.
10. CI verifies formatting, linting, type checking, tests, conformance suites, the SQLx offline cache, dependency and security checks, and redaction.

## Revision notes

Gaps fixed relative to revision 1:

1. **Closed `Platform` enum replaced** by `PlatformId` plus `PlatformPlugin` and `PluginRegistry`, so platforms are real plugins. Platform IDs are stored as text, so adding a platform needs no migration.
2. **Provider-specific OAuth configuration moved out of `auth`** into each plugin, as `OAuthProviderSpec`.
3. **Multi-account support added** through `AccountRef`. Revision 1 targeted platforms, not accounts.
4. **Unknown outcomes.** Non-idempotent remote creates that fail mid-flight used to risk duplicate posts on retry. Added the `OutcomeUnknown` state and `reconcile()`.
5. **Refresh-token rotation race.** Added per-account serialized refresh.
6. **Unnamed HTTP layer** now has its own crate (`postly-http`), and no other crate may build clients.
7. **New crates:** `config` (A3), `platform-kit` with the conformance testkit and mock plugin (B4), and the shared `meta` library (E0), all for DRY reasons.
8. **Registry moved earlier.** It was in G1 while D3 needed it. It now lives in A2, with the mock plugin in B4 unblocking D1–D3.
9. **Circular exit criterion fixed.** D2's exit criterion depended on a D3 CLI command; it is now library-level.
10. **Scheduling run model defined:** a worker, `--once` for OS schedulers, and opt-in native platform scheduling.
11. **Media hosting and probing:** added the `MediaHost` and `MediaProbe` abstractions, since Instagram and TikTok pull-from-URL need public URLs and duration validation needs probing.
12. **Additional gaps:** time-zone-aware schedule input, YouTube quota tracking, X weighted text length, the SQLx offline cache for CI, headless keyring fallback, `secrecy` typed secrets, workspace lints, `dotenv` replaced by `dotenvy`, reqwest feature cleanup, and a platform constraints and risks section.
13. **LLM layer made provider-agnostic.** It uses an OpenAI-compatible adapter plus a native Anthropic adapter, with opencode-shaped configuration. Video generation is deferred.
14. **Reuse of essentialMix-rs crates** is documented, including which are used and why others are not.
