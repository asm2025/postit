## Objective

When this plan is done:

- Per-environment secrets are packed into a single encrypted `!ref/vault.7z` archive, committed, and extracted in place to `!ref/vault/<environment>/`, matching the VigilixMambo pattern.
- The two root-level compose files move under `docker/`, renamed to `docker-compose.yml` / `docker-compose.development.yml` (one file per environment, named after it), with a pinned Compose project name and a `docker/.env.example`.
- `db drop` (`db.ps1` / `db.sh`) gives a scripted, confirmed way to reset an environment's Postgres database to empty.
- `db prepare` refreshes the sqlx offline query caches; `db migrate` wraps `sqlx-cli` (add/run/revert/info) once the single-migration policy ends at plan 03 G1.
- `CLAUDE.md` and `README.md` describe all of the above, so a fresh clone follows the same setup story VigilixMambo does.

None of this changes application behavior. It is tooling and repository layout only.

## Why not a straight copy of VigilixMambo's scripts

VigilixMambo's database-drop and `migrate` scripts carry two things postit does not have and should not invent here:

- **ECS scaling and an SSM bastion tunnel.** postit has no AWS account, and its only Terraform is the per-provider first-deployment module of plan 03 G1 (server, IP, DNS), not ECS — plan 02's [QA and production hosting](02.%20foundation.md#qa-and-production-hosting) is "the same image, promoted, run by the operator's own Compose/Kubernetes/whatever," reached directly. So `db drop` here has nothing to scale down and nothing to tunnel through; it connects to whatever host the operator gives it.
- **EF Core.** postit's migrations are `sqlx` migrations embedded in `postit-data` (plan 02 P4, [Data layer](02.%20foundation.md#data-layer)) and applied automatically by the server at every boot under a Postgres advisory lock (plan 02, [Process roles](02.%20foundation.md#process-roles)). `migrate.ps1`/`.sh` are a thin `sqlx-cli` wrapper for authoring migrations and refreshing the offline query cache, not a `dotnet ef`-style scaffolding tool.

What carries over: the vault-as-a-packed-archive convention, retyping the database name before an irreversible drop, compose files living under `docker/` instead of at the root, and treating "the process that auto-migrates on boot must not be running while you drop" as a hard rule — enforced by stopping the app services with `docker compose stop <services>` instead of ECS desired-count juggling.

## V1: Vault packaging

- `!ref/vault/<environment>/` folders (`development`, `qa`, `production`, already created locally) hold the files an operator needs and must not commit in the clear:
  - One `KEY=value` file per project, secrets only (usernames, passwords, keys, client secrets); URLs and other settings stay in the project's config. `postgres.env` (`POSTGRES_USER=postgres`, a random `POSTGRES_PASSWORD`) and `postit.env` (`POSTIT__DATABASE__USERNAME` / `__PASSWORD`, `POSTIT__AUDIT__PSEUDONYM_KEY`, and in qa/production `POSTIT__MAIL__SMTP__USERNAME` / `__PASSWORD`) in every environment; `zitadel.env` (`ZITADEL_MASTERKEY`, the Zitadel database logins) in development only. Every environment uses the default `postgres` superuser. Future secrets, such as plan 03's per-platform developer app credentials, go into the owning project's file.
  - *(Superseded layout: one `.txt` file per value — `postit-database-url.txt`, `postit-pseudonym-key.txt`, …. Replaced because a URL is config, not a secret.)*
  - **No `local.toml`.** The file `cargo xtask zitadel-bootstrap` writes holds the client and project IDs of one specific Zitadel instance; a fresh clone's Zitadel generates different IDs, so a shared copy would break sign-in. Every clone runs the bootstrap.
- **Encryption is mandatory**, because the archive holds `production` secrets and lives in git history forever:

  ```bash
  ./vault.sh pack      # .\vault.ps1 pack; 7-Zip prompts for the password
  ```

  It runs `7z a -p -mhe=on` on `!ref/vault/` (every environment, production included, `.gitkeep` left out) into a temporary archive and replaces `!ref/vault.7z` only when 7-Zip succeeds. `-mhe=on` encrypts file names too. The password is shared out of band (password manager), never committed, never put in CI. Consequences to accept knowingly: every committed archive version stays decryptable with the password it was made with, so **rotating a leaked secret means rotating the secret itself**, not just re-packing; and changing the archive password does not protect old commits.
- Extraction, documented in the README the same way Mambo's is:

  ```bash
  ./vault.sh unpack    # prompts for the password, produces !ref/vault/<environment>/...
  ```

  plus the fallback without a 7-Zip command line (7-Zip GUI: extract `vault.7z` into `!ref/`). `vault check` compares the archive with the extracted files by SHA-256 and names the files that differ.
- Git-ignore the extracted folder while keeping its layout. A leading `!` is gitignore's negation operator, so the literal `!ref` must be escaped:

  ```gitignore
  # Extracted vault (the encrypted !ref/vault.7z is committed instead)
  \!ref/vault/**
  !\!ref/vault/*/
  !\!ref/vault/*/.gitkeep
  ```

  with a `.gitkeep` in each of `development/`, `qa/`, `production/`.
- Re-packing is the maintainer's `vault pack` after editing files in place (first a manual `7z a`; a script since 2026-11-07, so the temporary-archive rule and the exclusions are never typed by hand).
- `CLAUDE.md` gets a short "Vault" note under Commands; `README.md` gets the full "Extract configuration files (vault)" section (V5).

**Exit:** `!ref/vault.7z` exists, is encrypted (listing it without the password shows no file names), and extracts to the layout above; `git status` shows nothing under `!ref/vault/` except the three `.gitkeep` files; README documents extraction.

## V2: Docker directory restructure

- `git mv compose.yaml docker/docker-compose.yml` and `git mv compose.dev.yaml docker/docker-compose.development.yml`. (First landed as `.yaml` / `dev.yaml`; renamed to the VigilixKC convention — `.yml`, full environment name, `postit-` prefixed services — together with a compose launcher script, since split into the operator scripts.)
- **Pin the project name.** Compose derives the default project name from the directory of the first compose file, so after the move it would change from `postit` to `docker`, creating a fresh `docker_postgres-data` volume and orphaning the existing Postgres and Zitadel state (and with it the IDs in every developer's `local.toml`). Add a top-level `name: postit` to `docker/docker-compose.yml` so volumes, networks, and container names do not follow the directory name. (The later `postit-` rename of services and of the volume, to `postit_postit-pgdata`, did start every developer on a fresh database: delete `docker/zitadel/machinekey/` and re-run `cargo xtask zitadel-bootstrap` after the first `compose up`.)
- **Rewrite the bind-mount paths.** Relative paths in compose files resolve against the project directory, which is the directory of the first `-f` file — `docker/` after the move, regardless of where the command runs. The mounts are currently written relative to the repo root (`./docker/postgres/init`, `./docker/zitadel/steps.yaml`, `./docker/shared/nginx/...`) and become `./postgres/init`, `./zitadel/steps.yaml`, `./shared/nginx/...`. The contents of `docker/postgres/`, `docker/shared/`, and `docker/zitadel/` do not change. The xtask's `../docker/zitadel/machinekey/...` path is relative to `backend/`, not to compose, and is unaffected.
- The qa and production compose files (plan 02 P10, not yet created) are named after the environment they serve so scripts can derive them from `POSTIT_ENV`: `docker/docker-compose.qa.yml` and `docker/docker-compose.production.yml`.
- Add `docker/.env.example`, committed, and a git-ignored `docker/.env` for local overrides — Mambo's pair. Compose loads `.env` from the project directory, which is why it lives in `docker/`. It lists only variables compose actually reads today:

  ```sh
  # Copy to docker/.env for local overrides. Development needs none of this.
  # COMPOSE_PROFILES=app   # always include the app profile
  ```

  The dev stack keeps its fixed, clearly insecure `postit`/`postit` credentials (they must match `backend/config/development.toml`); a `DB_PASSWORD` variable belongs to the qa/production compose files when P10 builds them. The current `.gitignore` rule `.env.*` also matches `.env.example`, so add `!.env.example` after it.
- Commands keep working from any directory, but the documented convention is Mambo's "run compose from `docker/`":

  ```sh
  ./compose.sh up --app      # or ./compose.ps1 up -App; builds the same -f chain from anywhere
  ```

- Update every reference to `compose.yaml` / `compose.dev.yaml` / `compose.qa.yaml` / `compose.prod.yaml` in `CLAUDE.md`, `README.md`, the header comment of `docker-compose.development.yml`, and plan 02 ([Development hosting](02.%20foundation.md#development-hosting), [QA and production hosting](02.%20foundation.md#qa-and-production-hosting), phases P3 and P10) to the new names and the `cd docker` convention. Plan 02 is the authoritative spec for environments, so it is edited in place rather than left disagreeing — the plans are one consistent set, not layered revisions. The CI workflow and plan 02's CI `docker` job build the image directly and do not reference compose files; nothing to change there.
- `cert.ps1`/`cert.sh` already write into `docker/shared/nginx/certs/`; no change needed there.

**Exit:** `docker/docker-compose.yml` and `docker/docker-compose.development.yml` exist, no root-level `compose*.yaml` remains, `docker compose config` resolves cleanly from `docker/` and reports project `postit`, an existing dev stack comes back up on its old volumes with Zitadel sign-in still working, and every doc reference matches.

## V3: `db drop` (first built as a separate script)

Resets an environment's postit database to empty. Postgres only — no ECS, no bastion. The server recreates the schema on its next boot.

- `db.ps1 drop <environment> [-Force] [-NoStop]` / `db.sh drop <environment> [--force] [--no-stop]`, from any directory.
- **Connection.** Runs `psql` inside `postit-postgres` (`docker exec`) as the container's own `POSTGRES_USER` over the local socket, which the postgres image trusts — no password handled, no host `psql`, and it works in qa/production where no database port is published. `ADMIN_DATABASE_URL` (`postgres://user:password@host:port/db`) reaches a database elsewhere with a host `psql`, the password passed via `PGPASSWORD`, never on the command line.
- **Stop the migrating processes first.** Unless `--no-stop`:
  - For `development`, stop only the running app services, never the whole stack — a bare `docker compose stop` would stop `postgres` too, and then there is nothing to drop against: `docker compose -f docker/docker-compose.yml -f docker/docker-compose.development.yml --profile '*' stop <app services>`. The app services are the ones that connect to Postgres (`postit-server`, `postit-api`, `postit-worker`) and are running; every profile is listed, so the `app` profile's `postit-server` is seen.
  - The script cannot see a natively run server (`cargo run`), so for `development` it also prints a reminder to stop any `cargo run` process, next to the confirmation.
  - For `qa`/`production`, which the operator runs on their own host, print the equivalent instruction (`docker stop postit-api postit-worker`) and refuse to proceed without `--no-stop`, which asserts the operator has done it.
- **Drop and recreate** against the `postgres` maintenance database via `psql`, as two separate `-c` invocations (`DROP DATABASE` cannot run inside a transaction block):

  ```sql
  DROP DATABASE IF EXISTS "<db>" WITH (FORCE);
  CREATE DATABASE "<db>";   -- owned by the connecting role, as the dropped one was
  ```

  `WITH (FORCE)` (Postgres 13+) terminates remaining sessions itself, replacing Mambo's separate `pg_terminate_backend` step. The recreate is required: the server's migrations need the database to exist, and the postgres image's init scripts (`docker/postgres/init/`) run only on an empty volume. The `zitadel` database is never touched.
- **Privileges.** The role must be allowed to connect to `postgres`, drop the database (owner or superuser), and create databases (`CREATEDB` or superuser); `WITH (FORCE)` additionally needs rights to terminate the other sessions (same role, `pg_signal_backend`, or superuser). The dev `postit` role is a superuser. For qa/production, where plan 02 has postit connect as the database owner without superuser rights, the README documents the grants or says to run the script with an admin URL (an `ADMIN_DATABASE_URL` environment variable overrides the vault file).
- **Restart.** After the drop, when the script stopped dev app services, it starts the same ones again and polls `docker compose ps` until they are running — the Compose counterpart of Mambo's "scale back up and wait for stable".
- **Confirmation.** Retype the database name, asked before anything is stopped, so a "no" (or no input at all) leaves everything as it was. `--force` skips it for `development` and `qa`; `production` always prompts and refuses `--force`, matching Mambo.
- No region flag, no AWS credential check, no SSM tunnel cleanup — none of that machinery has an equivalent here, so it's absent rather than stubbed.

**Exit:** `./db.sh drop development --force` against the dev stack leaves an empty `postit` database and an untouched `zitadel` database; once plan 02 P4 exists the server rebuilds the schema on its next start; `production` cannot be forced; `qa`/`production` refuse without `--no-stop`.

## V4: `db prepare` now, `db migrate` at plan 03 G1

**`prepare` is built** (2026-11-07) as `db prepare`: every crate keeps its own offline cache (`backend/crates/<crate>/.sqlx/`, today only `postit-data`), so it creates a scratch database `postit_prepare` on the development server, applies `backend/crates/data/migrations` with `sqlx migrate run`, runs `SQLX_OFFLINE=false cargo sqlx prepare -- --all-targets --all-features` from each crate that has a `.sqlx/` with `DATABASE_URL` pointing at it (through the environment only), and drops the scratch database on every exit path. CI checks each crate with `cargo sqlx prepare --check -- --all-targets`.

**The rest waits for plan 03 G1.** Until the first production deployment the schema is one migration file, `0001_init.sql`, edited in place, so there is nothing to add or revert. When G1 ends that policy, the operations below become `db migrate <add|run|revert|info>`:

- `db migrate {add|run|revert|info} [Name]`, a thin wrapper around `sqlx-cli` that resolves paths from the script's own location, so it works from any directory the way Mambo's script always passes the right `--project`/`--startup-project`:
  - `add <Name>` → `sqlx migrate add -r <Name> --source backend/crates/data/migrations` (reversible: `.up.sql` + `.down.sql`, matching plan 01's "expand, then contract" compatibility rule).
  - `run` → `sqlx migrate run --source backend/crates/data/migrations`. Only useful ahead of a server start (the server migrates on boot anyway), mainly before `prepare`.
  - `revert` → `sqlx migrate revert --source backend/crates/data/migrations`.
  - `info` → `sqlx migrate info --source backend/crates/data/migrations`.
- `DATABASE_URL` resolution: an explicit `DATABASE_URL` in the environment always wins; otherwise it is assembled from `database.url` in `backend/config/<env>.toml` (`POSTIT_ENV`, default `development`) and the credentials in `!ref/vault/<env>/postit.env`, reachable from the host only in development (5432).
- **Guard outside development.** `run` and `revert` against `qa`/`production` require retyping the environment name; `revert` against `production` is refused outright (production rolls forward with a new migration). `add`, `info`, and `prepare` need no guard.
- `sqlx-cli` must be installed at the version matching the workspace's `sqlx` dependency (`cargo install sqlx-cli --version <x> --no-default-features --features rustls,postgres --locked`); the README gives the exact command and the script fails with that hint when `sqlx` is missing.
- No `clear` operation: `sqlx` records each applied migration's version and checksum in `_sqlx_migrations`, so deleting migration files the way Mambo's EF `clear` does makes `migrate run` and the server's boot fail with "previously applied but missing" on every already-migrated environment. If a clean slate is genuinely needed, that's a manual `db drop` + delete-and-`add` again, done deliberately.

**Exit:** `db prepare` leaves every `.sqlx/` cache current and no `postit_prepare` database behind, also when `cargo sqlx prepare` fails; at G1, `db migrate add <name>` scaffolds a reversible migration under `backend/crates/data/migrations` and `db migrate revert production` is refused.
