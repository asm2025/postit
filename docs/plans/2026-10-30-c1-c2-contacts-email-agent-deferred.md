# C1 contacts and C2 email agent: deferred items

Agent work found while executing the C1 and C2 plan that cannot be done inside it. Human-only checks are in `2026-10-30-c1-c2-contacts-email-agent-verification.md`.

## Client catalog entries for the new violation codes and the DNS finding codes

- **Issue:** the plan's global constraints and Task 15 ask for web and mobile catalog entries, in English, for the three `ViolationCode`s C2 added and for the DNS check's finding codes. None were written:
  - Violation codes (in `backend/crates/core`, raised by the email agent's `validate`): `email_too_large` (parameters `max_bytes`, `actual_bytes`), `email_postal_address_required`, and `email_merge_tag_invalid` (with the block path, such as `email.blocks[2].url`). The agent's two agent-rule violations, `link_scheme_not_allowed` and `compile_failed`, carry message keys with English defaults and need the same treatment.
  - Finding codes (`DomainFinding.code` in `GET /api/v1/accounts/{id}/dns-check`, already in `backend/openapi.json` with `DomainRecord` and `DomainStatus`): `spf_ok`, `spf_missing`, `spf_weak`, `spf_unknown`, `dkim_ok`, `dkim_missing`, `dkim_unknown`, `dmarc_ok`, `dmarc_missing`, `dmarc_weak`, and `dmarc_unknown`. Each needs plain-language guidance (what the record does and what to add), and `dkim_unknown` needs two texts, because it covers both "no selector given" and "the lookup failed" (the client knows whether it sent a selector).
- **Why it cannot be fixed now:** neither client has a violation catalog or a finding catalog yet. The error maps (`web/src/i18n/*/common.json`, `mobile/lib/l10n/app_*.arb`) cover problem `code`s only, and `ViolationCode` is not in the API contract until D3's validate and publish routes return violations. Building the catalogs means deciding how violations render with their parameters, paths, and suggested fixes, which is the D3/D4/D6 client design work; entries added now would have no structure to live in and no screen to show them. The test-email route already returns violations in its 422, but no client calls it yet.
- **Trigger:** plan 03 D3 (when `ViolationCode` joins the contract, add the catalog structure and these three codes with the existing ones), then D4 (the web composer and the account's email setup screen, which shows the DNS findings) and D6 (the mobile equivalents). Add catalog completeness tests in both clients so a new code fails CI without an entry.

## Click and open recording shares the per-IP unauthenticated bucket

- **Issue:** `may_record` in `backend/crates/api/src/routes/public_email.rs` charges `state.limits.ip`, the shared per-IP bucket of `rate_limit.unauthenticated` (60 per minute, burst 20), for every click and open on a valid token, as the plan's Task 10 specified. An office or mail proxy that puts many recipients behind one address can drain that bucket with ordinary clicks. The links keep working (a valid token is never refused), but while the bucket is empty that IP's other unauthenticated requests answer 429, and a failed bearer request from it can put the IP into `blocked()`, which then refuses its unauthenticated traffic for a while.
- **Why it cannot be fixed now:** the fix is a separate event-recording bucket keyed by IP, with its own `rate_limit` setting, and its numbers should come from real click traffic, which does not exist before a public deployment. The plan fixed the shared bucket as the design for this phase; changing the limiter design is a hardening decision, not a C2 task.
- **Trigger:** plan 03 G1 (first deployment) hardening, or the first report of 429s from a shared office address, whichever comes first. Add `rate_limit.email_events` (per IP), use it in `may_record` only, document it in `docs/configuration.md`, and test that many clicks from one IP leave `rate_limit.unauthenticated` untouched.

## NUL characters reach Postgres on routes outside contacts

- **Issue:** Postgres stores no NUL in `text` or `jsonb`, and its error can quote the value. This branch refuses NUL in everything the contact routes and the CSV import store (`refuse_nul` and `has_nul` in `backend/crates/contacts/src`), but no other route does. A `\u0000` in a JSON body on an older route that stores text, such as an account rename, still fails in the database and answers 500.
- **Why it cannot be fixed now:** the C1 and C2 routes that write text are all covered, and test-email and dns-check store none. The other routes predate this branch, and the fix belongs to the shared input layer: a check in `ApiJson` and `ApiQuery` that answers `validation_failed`, across every route. That is a cross-cutting hardening change, not contact or email work.
- **Trigger:** plan 03 G1 hardening. Refuse NUL once in `ApiJson` and `ApiQuery` (a fast byte scan for the escape, then a walk of the parsed value only on a hit), test it with an older route, and keep the contact checks, because the CSV import and multipart options do not pass through `ApiJson`.

## Clicks record no link index

- **Issue:** `email_events.link_index` is never written. A click token (`backend/crates/api/src/email_links.rs`, `Click`) carries only the send and the destination URL, so `record` in `backend/crates/api/src/routes/public_email.rs` passes `None` for every `clicked` event, and per-link click counts cannot be derived from the events.
- **Why it cannot be fixed now:** adding the index changes the signed click token format, which every rendered email embeds. Nothing reads the index before analytics exists, so changing the format now would only add a second token shape to keep accepting for links already sent. The ruling for this branch is to keep the token format; plan 01's `email_events` note says E3 adds the index.
- **Trigger:** plan 03 E3 (analytics), when email click metrics are built: add the link's position in the document to the click token (with the old shape still accepted for links already sent, or a cutover note if none were sent live yet), pass it to `DirectRepo::record_event`, and test that a click records its `link_index`.
