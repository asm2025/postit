# B4: Media Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a user upload images and videos (in one request or through resumable sessions), see them, get signed URLs for them, and delete them, with the bytes streamed and never buffered whole, the storage quota enforced under concurrency, and no user-supplied path reaching the filesystem.

**Architecture:**
- New crate `postit-media` (`backend/crates/media/`) owns content sniffing, generated storage keys, `FsMediaStore` (implements core `MediaStore`), probing (`NativeProbe`, and `FfprobeProbe` behind the `ffprobe` feature), thumbnails, URL signing and `SignedUrlMediaHost` (implements core `MediaHost`), `MediaService` (the one entry point the API calls), and the `media_gc` job.
- `postit-data` extends `MediaRepo` with the atomic quota reservation, session offset writes, state changes, system lookups, and the GC queries.
- `postit-api` adds the B4 `/api/v1/media*` routes and `GET /public/media/{id}` (plus its thumbnail), with streaming limits (idle timeouts, no overall timeout). `postit-server` builds the service, replaces the `UnavailableMedia` stand-in, registers `media_gc`, and the Docker image gains `ffmpeg` and the `ffprobe` feature.

**Tech Stack:** Rust 2024, axum 0.8, tower-http 0.6 (`ServeFile` for range and conditional requests, `RequestBodyTimeoutLayer`, `ResponseBodyTimeoutLayer`), sqlx (Postgres), `sha2` (streaming SHA-256), `hmac`, `infer` (new, sniffing), `imagesize` (new, image dimensions), `mp4` (new, MP4/QuickTime probing), `image` (new, thumbnails), `mime` (new, for `ServeFile`), `peak_alloc` (new, dev-only, the bounded-memory test).

**Spec:** `docs/plans/03. publishing roadmap.md`: phase B4 and the [Media](#media) section under Key flows, plus the Media rows of the REST surface, the `media_gc` row of "Jobs added by this plan", and the error codes list. Plan 01's `media_assets` data model and "Engineering standards" apply. There is no separate design doc: the **Decisions** below are this plan's calls and are not reopened during execution.

## Decisions

1. **SHA-256 uses `sha2::Sha256` incrementally**, not `emixcrypto`: `emixcrypto` 0.7 hashes only whole buffers, and streaming is required. `sha2` is already a workspace dependency. Edit plan 01's `emixcrypto` row to say media hashes use `sha2` for streaming.
2. **Sniffing uses `infer`** on the first 8 KiB. Allowed results map to `(mime, kind)`: `image/jpeg`, `image/png`, `image/gif`, `image/webp` to `Image`; `video/mp4`, `video/quicktime` to `Video`. `infer` reporting nothing or anything else is unsupported. The stored MIME is the sniffed one, never the client's `Content-Type`.
3. **Kind comes from the filename extension at declare time** (`jpg`, `jpeg`, `png`, `gif`, `webp` to image; `mp4`, `m4v`, `mov` to video; case-insensitive; anything else is 415 up front). The sniffed kind must equal it at completion, else 415 and the asset is failed and its file removed. This lets `POST /media/uploads` apply the per-kind size limit before any byte arrives.
4. **Per-kind limits are new config:** `media.image_max_bytes` (default `52428800`, 50 MiB) and `media.video_max_bytes` (default `4294967296`, 4 GiB). `POST /media` accepts at most `min(single_request_max, kind max)`.
5. **Probing.** `NativeProbe`: `imagesize` for images (from the file header), `mp4::Mp4Reader` for MP4 and QuickTime (first video track's width and height, movie duration), run in `spawn_blocking`. `FfprobeProbe` (feature `ffprobe`): `ffprobe -v error -print_format json -show_streams -show_format <path>` through `tokio::process`, used for video; images still use `NativeProbe`. A probe failure on a sniffed-valid file is 415 (the file is not usable media). New config `media.ffprobe_path` (default `ffprobe`).
6. **Thumbnails** are JPEG, longest side 480 px, quality 80. Images: the `image` crate with `Limits` (`max_alloc` 512 MiB) and a pixel-count check against new config `media.thumbnail_max_pixels` (default `40000000`) read from the probed dimensions before decoding; over the limit means no thumbnail, and the asset is still `ready`. GIF uses its first frame. Videos: only with the `ffprobe` feature, `ffmpeg -ss 0 -i <path> -frames:v 1 -vf scale=480:480:force_original_aspect_ratio=decrease <out>.jpg` through `media.ffmpeg_path`; without it, no video thumbnail. A thumbnail failure never fails the upload.
7. **Storage keys** are `{owner_uuid}/{yyyy}/{mm}/{asset_uuid}` (UTC creation month); the thumbnail key is `{storage_key}.thumb.jpg`. `StorageKey::parse` accepts only that grammar (lowercase hyphenated UUIDs, 4-digit year, 2-digit month, optional `.thumb.jpg`), and `FsMediaStore::resolve` joins it to the canonical root and checks the result's parent stays under it.
8. **Chunk appends serialize on the asset row.** `PUT /media/uploads/{id}` opens a transaction, takes `SELECT … FOR UPDATE` on the uploading row, checks `Content-Range` start equals `upload_offset`, truncates the file to `upload_offset` (dropping bytes a dropped connection left behind), appends the chunk while counting bytes, then writes the new offset and commits. A second concurrent PUT waits on the lock and then sees a moved offset (409).
9. **The quota reservation is atomic.** `MediaRepo::reserve` locks the owner's `user_limits` row `FOR UPDATE`, sums stored bytes (ready and processing `bytes`, plus `declared_bytes` of uploading rows), refuses when `used + declared > quota` (quota `0` = unlimited), and inserts the row, all in one transaction. `stored_bytes` counts `processing` rows (today it counts them as 0, which lets a completing upload escape the quota).
10. **`POST /media`** takes the raw file as the body, `?filename=` (required, 1–255 characters after trimming, control characters refused), and requires `Content-Length` (missing is 422 `validation_failed`, field `content_length`). `Content-Length` is the declared size for the reservation; a body that ends short or runs long fails the upload (422, asset failed, file removed).
11. **Idempotency.** `POST /media/uploads` uses the existing `idempotency::run` with the JSON body hash. `POST /media` hashes method, route, filename, `Content-Length`, and `Content-Type` (the body is streamed and not hashed); this is documented on the route.
12. **Signed URLs.** Message `"{target}|{exp}"`, where `target` is `{id}` for content and `{id}/thumbnail` for the thumbnail; signature = HMAC-SHA256 with `media.signing_key`, base64url without padding; `exp` = Unix seconds. URL = `{media.public_base_url or server.public_url}/public/media/{target}?exp=…&sig=…`. Verification is constant time (`Mac::verify_slice`). Bad, missing, or expired signature: 403 `forbidden`. Valid signature, asset gone or not ready: 404. View URLs use `media.view_url_ttl`; `MediaHost::public_url` uses the TTL passed in (callers pass `media.public_url_ttl`). The server refuses to start without `media.signing_key` (development.toml already sets one).
13. **Serving** goes through `tower_http::services::ServeFile::new_with_mime(path, sniffed_mime)` for range (`206`, `416`) and conditional requests, then adds `X-Content-Type-Options: nosniff` and `Content-Security-Policy: sandbox`. Bearer routes keep the API's `Cache-Control: no-store`; the public route sends `Cache-Control: private, max-age=<seconds until exp>`.
14. **Route limits.** Upload, chunk, content, thumbnail, and public routes have no overall timeout: request bodies get `RequestBodyTimeoutLayer(media.idle_timeout)`, responses `ResponseBodyTimeoutLayer(media.idle_timeout)` (new config, default `60s`). Body limits: `POST /media` `single_request_max`, `PUT` chunk `chunk_max`, downloads 0. `complete` gets `TimeoutLayer(media.complete_timeout)` (new config, default `10min`), since it hashes and probes the whole file. Each group goes through one new helper next to `with_limits`.
15. **Upload-session headers.** `HEAD /media/uploads/{id}` answers 200 with `Upload-Offset` and `Upload-Length` headers and no body; CORS exposes both.
16. **`media_gc`** (new schedule `jobs.schedules.media_gc`, default `0 50 3 * * *`, queue `maintenance`): in batches of 500, delete rows that are `failed`, `uploading` past `upload_expires_at`, or `processing` with `updated_at` older than `media.upload_session_ttl` (a crash during completion), removing their files; then walk the storage root and delete every regular file whose key parses, whose mtime is older than `upload_session_ttl`, and that no row names as `storage_key` or `thumbnail_key`; then remove empty month and year directories. Files whose names do not parse are logged (key only) and left alone. A user's files after `delete_user` cascades their rows are reclaimed by this sweep; the explicit deletion step is D1's.
17. **Asset resolution for agents.** `MediaService::assets(scope, ids) -> Vec<MediaAsset>` maps rows to core `MediaAsset` (`processing` maps to `MediaAssetState::Uploading`; `sha256` as lowercase hex). `FsMediaStore::open(asset)` looks up the ready row by `(asset.owner_id, asset.id)` to get its storage key, so the core type needs no storage field. This settles B4's half of the B5 deferred item; the request assembly and conformance fixture stay D1's.

## Review Focus

1. **The runtime user cannot write the media volume.** The image runs as uid 10001; a named volume mounted on a directory that does not exist in the image is root-owned, so every upload fails with 500 in qa and production. The Dockerfile creates `/var/lib/postit/media` owned by `postit` before `USER`, and Task 11 checks a write into a fresh named volume as that user.
2. **The web CSP blocks media.** When `media.public_base_url` is another origin than the app, the web CSP's `img-src`/`media-src` must list it, or every thumbnail and video in the web app breaks. Task 10 tests the CSP with a different media origin.
3. **A dropped connection in the middle of a chunk.** Bytes past the stored offset are on disk; the resumed PUT from `HEAD`'s offset must truncate them, and the completed SHA-256 must equal the original file's. Task 6 tests it with a stream that errors halfway.
4. **Hostile or unusual filenames:** `../../etc/passwd`, `a/b\c.jpg`, a 300-character name, an Arabic name, a name with a NUL. None reaches a path; the Arabic name round-trips; over-long or control-character names are 422. Task 6 tests them.
5. **Size edge cases:** a declared size of 0, a declared size over the kind limit (413 `payload_too_large` before any byte), a `Content-Range` past the declared total, `complete` before the last byte (409 `upload_offset_mismatch` with `offset`), and a range request past the end (416). Tasks 6 and 9 test them.
