# D4d Email and onboarding Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The last D4 slice: a web user manages contacts, lists, and suppressions, imports contacts from CSV with column mapping and consent, exports them, checks their sending domain, writes an email campaign in a block editor with raw HTML and a live preview, sends a test, and sends the campaign to a list; a new user is walked through first-run setup and sees what is left on the dashboard. The D4 exit criteria hold.

**Architecture:** Five small backend changes: a preview route rendered by the email agent's own renderer (a new `DirectSender::preview` method, so the preview is what recipients get); a raw-HTML email block, sanitized with `ammonia` and rendered through `mj-raw`; a typed DNS finding code so the clients' catalogs can be checked for completeness; two setup fields on the preferences; and a route listing the lists one contact is in. Then web screens: a contacts area, an email document editor that plugs into the D4b composer's `TargetTab.directContent` slot, the DNS check on the email account's page, and a setup wizard with a derived checklist.

**Tech Stack:** Rust (axum, sqlx, `mrml`, `ammonia`, `html2text`), React 19, React Router 8, TanStack Query 5, `openapi-fetch`, i18next, Radix/shadcn, Tailwind 4, Vitest + MSW, Playwright.

**Spec:** `docs/specs/2026-11-27-d4-web-publishing-ui-design.md` (sections "Shared decisions", "Backend changes D4 needs: D4d", "Slice details: D4d Email and onboarding"). Also read plan 03 Phases C1, C2, and D4, "Sending an email campaign", and the REST surface in `docs/contracts/03. publishing roadmap.md`; the C1/C2 plan `docs/plans/2026-10-30-c1-c2-contacts-email-agent.md`; and the as-built D4b and D4c plans (`docs/plans/2026-11-28-d4b-compose-publish.md`, `docs/plans/2026-11-28-d4c-ai.md`). **D4b and D4c must be merged before Task 7** (when this plan was written only their plans existed, so every D4b and D4c name below is a planned name). **Before Task 7, check the D4b and D4c names this plan consumes (`TargetTab`'s `directContent`, `ComposerState.overrides`, `ComposerAction.setOverride`, `isDirty`, `MediaPicker`, `ViolationList`, `useValidation`'s `429` handling, the clock seam `web/src/lib/clock.tsx` with `useNow` and the test clock, `useBrandProfile`, `useAiProviders`) against the merged code** and use the built names where an "As built" note renamed one. Tasks 1 to 6 need nothing from D4b or D4c.

## Review Focus

1. **Hostile or broken raw HTML:** a pasted block with `<script>`, an `onclick`, a `javascript:` link, a `<form>`, an `<iframe>`, a `<style>` with `@import`, a `style` attribute with `url(http:…)`, a merge tag inside `style`, an unclosed tag, a 200 KB table, or a 2 MB paste. Scripts, handlers, forms, frames, and unsafe URLs are removed; a merge tag in a URL or in `style` is refused; the rest renders; raw input over 100 KiB is refused before sanitizing, and the rendered size check refuses what is over 100 KiB with `email_too_large`; the footer and unsubscribe still come from the renderer; links in both the HTML and the plain-text part are click-tracked. Tests in Task 2.
2. **A preview that differs from the sent mail:** the preview, a test send, and a real send of the same document go through the same `Skeleton` with the same blocks, images, and footer. The preview is a test send's rendering (no tracking, the test unsubscribe token) with sample merge values in place of the empty ones; a real send differs from both only in tracking and its own unsubscribe link. Test in Task 1 (`preview_matches_a_test_send_but_for_merge_values`). One known difference is outside the renderer: images from other sites in a raw HTML block are blocked in the preview by the web CSP, and the preview says so (Task 8).
3. **A contact file that is not what it seems:** a semicolon-separated file (the server sniffs it), a UTF-8 BOM, a header row with duplicate or empty names, a formula-escaped header (`'=x`, which the server reads as `=x`, so `'=x` and `=x` together are a duplicate), a 50 MB file, a file with no consent column, the attestation left unchecked, or Start clicked twice. The mapping screen previews the first rows in the browser and refuses to start without the email and consent columns mapped and the attestation ticked; the upload carries an `Idempotency-Key`, so a second click answers the first import; the server's `csv_invalid`, `csv_too_large`, `payload_too_large`, `request_timeout`, `consent_attestation_required`, and the idempotency answers show plainly, and `contact_limit_exceeded` shows as a row rejection in the report. Tests in Task 5.
4. **A suppression the owner tries to undo:** only `bounced` entries offer Remove; `unsubscribed`, `complained`, and `manual` explain why they stay (the contact must opt in again, or the owner sets the contact `subscribed`); `409 suppression_not_removable` shows its message. Test in Task 4.
5. **First-run setup interrupted or done elsewhere:** a reload on `/setup` stays in the wizard at the first undone step; leaving the wizard by choice (a nav link) is respected for the rest of that tab session; a new tab session redirects to it again until it is finished or skipped; it never reopens once `setup_completed_at` is set (also from the mobile app later); the connect step comes back to `/setup` after a credential or OAuth connection; and a delegate never sees it for the owner's workspace. Tests in Task 9.

## Decisions taken in this plan

- **Preview through the agent (spec, shape is a call):** `DirectSender` gains `async fn preview(&self, account: &AccountRef, variant: &Variant, assets: &[MediaAsset]) -> Result<DirectPreview, AgentError>` with `pub struct DirectPreview { pub subject: String, pub html: String, pub text: String }` in core. A required method (no default), so a future direct agent must decide what its preview is. The email agent compiles the `Skeleton` and renders it for a sample recipient under `TEST_SEND_ID` (no tracking, the test unsubscribe token) with merge fields `first_name` "Alex", `last_name` "Rivera", and every other tag's fallback. The mock direct agent and the agent-kit echo client return a plain HTML page of the document's text.
- **Route:** `POST /api/v1/accounts/{id}/email-preview` `{ email: EmailDocument }` → `200 EmailPreviewDto { subject, html, text }`; `edit`, account in limit; charged to `state.limits.publish` (the bucket D4b's validation also draws from, so the web client handles its `429` the same way, Task 8); a document that does not compile answers `422 validation_failed` with its violations, as the test-email route does; an account without `DirectSender` answers `409 capability_unsupported`; a disconnected account answers `422 validation_failed` (as `AccountError::AccountDisconnected` maps today); a disabled platform `409 platform_disabled`. Not stopped by the live switch (it sends nothing).
- **The preview checks the account in scope first:** `AccountService::bound_client(owner, id)` is system-side and checks no delegation limit (the test-email route gets away with it because it is owner-only). The preview handler first loads the account through the scoped accounts repository (`scope.require(Capability::Edit)`, then the owner- and limit-filtered lookup the other `edit` account routes use), so a limited delegate naming an account outside the limit gets `404 not_found` like every other account route, and only then calls `bound_client`. The 403s documented are `account_disabled`, `account_pending`, `delegation_invalid`, and `capability_required`; `account_not_in_scope` is not used here.
- **Raw HTML block (spec):** `EmailBlock::Html { html: String }` (`"type": "html"`).
  - **Input cap:** a block whose raw `html` is over 100 KiB (`HTML_BLOCK_MAX_BYTES = 102_400`) is refused with `email_too_large` (`max_bytes`, `actual_bytes` of the raw input, path `email.blocks[i].html`) before `ammonia` runs, so a large paste costs nothing on each validate and preview. The rendered measure (`worst_case_html_bytes`) still applies to the whole mail afterwards.
  - **Sanitizer:** an `ammonia::Builder` that keeps the email-safe tags (tables, `p`, `div`, `span`, headings, lists, `a`, `img`, `br`, `hr`, `strong`, `em`, `b`, `i`, `u`, `center`, `font`) and the attributes `style`, `align`, `valign`, `width`, `height`, `bgcolor`, `border`, `cellpadding`, `cellspacing`, `colspan`, `rowspan`, `href`, `src`, `alt`, `title`, `dir`; URL schemes `http`, `https`, `mailto`, `tel`; everything else stripped, including `script`, `style`, `form`, `input`, `iframe`, `object`, `embed`, and every `on*` attribute. `img src` must be `https` (a `data:` or `http:` image is dropped, since mail clients block them). A `style` attribute holding `url(`, `expression(`, `@import`, or `behavior:` (case-insensitive, after CSS-unescaping) is dropped whole, so a background image cannot get around the `https` image rule or load from an `http` host.
  - **Unsafe links are dropped, not refused (call):** the other blocks refuse a `javascript:` link with `link_scheme_not_allowed`, because their URL is one field the user typed. A raw HTML block is usually pasted from another tool, and refusing the whole paste for one bad link would push the user to edit HTML by hand; so the sanitizer removes the `href` (the text stays) and says nothing. The editor's warning (Task 7) says scripts, forms, frames, and unsafe links are removed, and the preview shows the result.
  - **Merge tags:** allowed in text and in `alt` and `title`; refused (`email_merge_tag_invalid`, path `email.blocks[i].html`) inside `href`, `src`, and `style`, raw or percent-encoded, since a contact's own field values must not become a URL or CSS. A merge tag's fallback is HTML-decoded once after sanitizing (`ammonia` writes `&` as `&amp;`), so the renderer's `Escape::Html` does not escape it twice; test `{{first_name|Tom & Jerry}}` renders `Tom &amp; Jerry`, not `Tom &amp;amp; Jerry`.
  - **How it fits the renderer:** the renderer's sentinel prefix is chosen per compile attempt inside `mjml::compile_with`, after `Parsed::new`, so the sanitizer cannot write sentinels. Instead `Parsed::new` sanitizes each `Html` block into `Block::Html { html: Vec<HtmlPart>, text: Vec<HtmlPart> }` with `enum HtmlPart { Markup(String), Link(Url), Field { name, fallback } }`: `Markup` is sanitized markup written as is, `Link` is an `href` checked by `checked_url` (and so click-tracked through `Slot::Link` on a campaign send, untracked on a test send or preview), `Field` a merge tag. `ammonia`'s `attribute_filter` cannot return an error, so it records each `href` and each refused merge tag in a `RefCell` side list and replaces the `href` with an index marker that the second pass splits on; the first refusal becomes the block's `RenderError::MergeTagInUrl`. `mjml.rs` writes `Markup` with `raw` and the others with `slot`; `text.rs` writes the `text` parts with `literal` and `slot`. The `text` parts come from `html2text` of the sanitized markup with each link marker still in place, at a width large enough not to wrap (the existing text part is not wrapped; use `usize::MAX / 2` or the crate's no-wrap option) so a marker or a merge tag is never split across lines; html2text's link footnotes then hold `Slot::Link`s, so the plain-text links are tracked too.
  - **Placement:** it renders inside `mj-raw` in its own `mj-section` and `mj-column` (white background, same 600 px body), between the sections before and after it; `mrml` 6's `mj-raw` accepts void elements, and the tests include `<br>`, `<img>`, and `&nbsp;`.
  - **Later link index:** clicks record no link index until E3 (`2026-10-30-c1-c2-contacts-email-agent-deferred.md`, "Clicks record no link index"). Links in an `Html` block count in document order with the others, so E3 needs nothing special for them.
- **Preview and the web CSP (call):** the app's CSP has `frame-src 'none'`, which governs URLs loaded in frames; an `about:srcdoc` frame is not fetched and is not blocked by it, and that stays so (Task 11 confirms in a real browser, since jsdom applies no CSP). A `srcdoc` document inherits the app's policy, so its images load only from the app and the media origin, and a link clicked inside it is blocked by `frame-src 'none'`. The policy is not widened for this: an `img-src https:` would apply to the whole app. Instead the preview says, when the document has a raw HTML block with an `img` from another host, "Images from other sites show in the sent email but not in this preview", and links in the preview do not open (the hint says to send a test to try them). `default_csp`'s doc comment changes from "no framing in either direction" to "no framing of other documents in either direction; the email preview frames only `srcdoc` content, sandboxed".
- **A contact's lists (spec gap, call):** `ContactDto` carries no lists and no route lists a contact's lists, so the contact page could not show them. `GET /api/v1/contacts/{id}/lists` → `200 Vec<ContactListDto>` (`view`, owner scope; `operation_id = "list_contact_lists"`; 404 for an unknown contact), from a new `ContactListRepo::for_contact(scope, contact_id)`, ordered by name. Not a field on `ContactDto`, which would cost a join on every contacts page.
- **Typed finding codes (call):** `DomainFinding.code` becomes `DomainFindingCode` (an enum with the eleven snake_case values the email agent already returns), so `backend/openapi.json` lists them and both clients' catalogs can be checked like violations. The wire is unchanged.
- **Setup state (spec):** `user_preferences.setup_completed_at TIMESTAMPTZ` and `checklist_dismissed BOOLEAN NOT NULL DEFAULT FALSE`; `PreferencesDto` gains `setup_completed_at: Option<DateTime<Utc>>` and `checklist_dismissed: bool`; `UpdatePreferences` gains `setup_completed: Option<bool>` (`true` sets `now()` when unset and is idempotent; `false` is `422 validation_failed`, since setup is never reopened) and `checklist_dismissed: Option<bool>`. Self preferences, so they follow the signed-in user, not the workspace; `UserPreferencesRepo` reads and writes them.
- **The language item (call):** the stored locale and zone cannot tell "saved" from "default" (`en-US` and `UTC` are the column defaults, and English is the only language), so a zone test would never tick for a user who really is in UTC. The wizard's first step instead saves the zone the user confirms (the browser's zone preselected) with `PUT /me/preferences`, and the `language` item is done when `setup_completed_at` is set or the zone differs from `UTC`; a user in UTC who confirms it is past that step because Next moves on (a reload mid-setup shows them that step once more, one click), and finishing or skipping setup ticks it.
- **No AI on this server:** a server built without the `ai` feature has no AI routes, so `GET /ai/providers` answers `404`. The checklist and the wizard drop the `ai` item and step on that `404` (checked once per session through `useAiProviders`' error, no retry), never by a build flag in the web app. Verify at Task 9 that the routes are not registered without the feature; if they answer something else, key on that.
- **Routes (call):** `/contacts`, `/contacts/:id`, `/contacts/lists`, `/contacts/suppressions`, `/contacts/import`, `/setup`. The DNS check sits on the email account's detail page (`/accounts/:id`), shown when the descriptor has the `sender_domain_check` capability.
- **Email editor placement:** the D4b `TargetTab` for a direct account renders `EmailEditor` through `directContent`; the document lives in `overrides[account].patch.email`, and the target's direct-send options (lists, tag filter, open tracking) stay the agent's options schema through `SchemaForm`, as every other option.
- **A new email is not a change:** when the override holds no document, the editor shows `emptyDocument(language)` as a display default and dispatches nothing; the first edit writes the whole document with `setOverride`. So opening a post with an email target never makes the composer dirty and never trips D4b's leave guard. The default language is the brand profile's default language when it is an `EmailLanguage`, else `en-US`.
- **A forced workspace switch:** D4b keeps only `base` in `sessionStorage` after a forced switch, so an unsaved email document is lost then, as every unsaved override is. That is D4b's rule for all overrides and stays; the email editor adds nothing to `sessionStorage` (documents may hold merge-tag text but never contact data, and the rule is one rule).
- **Block reordering (call):** "Move up" and "Move down" buttons on each block (keyboard reachable, no drag library).
